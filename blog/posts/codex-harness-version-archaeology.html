Codex Harness 0.95 → 0.149：半年真正新增了什么

一句话结论：不是“没有新东西”，而是没有新的 agent loop，也没有 8 月 19 日突然开源的新仓库。真正的半年增量，是把 2 月已经可嵌入的 loop，长成一套更接近产品级的 Agent control plane：Permission Profiles、typed World State、SQLite 分页历史、Multi-Agent V2、Plugin / Extension 平台、Python App Server SDK，以及 remote environment / executor 路由。

0. 先给判断

问题 判断 解释
8 月 19 日是否新开源了 Harness？ 否 仍是既有 openai/codex；这次是平台化定位与集成叙事
2 月后是否重写了 agent loop？ 基本没有 sampling → tool → tool output 回填 → 继续 sampling 的主循环早已有之
半年是否有实质工程增量？ 有，而且很大 新增主要发生在状态、安全、多 Agent、扩展、协议与远程执行控制面
是否已经是冻结的 production public API？ 还不是 0.149 的 145 个显式 v2 client RPC 中，52 个整方法仍标为 experimental
最值得学习什么？ 控制面，不是聊天循环 Permission、World State、ThreadStore、Multi-Agent tree、协议序列化最有含金量

如果只挑三个最硬的新东西：

  1. Permission control plane：从 command / file approval，升级为 filesystem + network + additional grants + profile intersection + runtime request_permissions + Guardian / auto-review。
  2. Durable Thread platform：从 JSONL 记录与 SQLite metadata，升级为 ThreadStore、分页 Turn / Item、SQLite materialization、single-writer、搜索、revert、queue / goal 等可驱动产品 UI 的状态服务。
  3. Multi-Agent V2 + Extension platform：从已有的 spawn/send/interrupt，升级为 Agent tree/path、mailbox、follow-up、wait、residency、budget，并把 Skills、MCP、Apps、Hooks 组合成 Plugin / Extension 能力包。

1. 比较口径：为什么基线是 0.95，不是 0.94 或 0.96

OpenAI 的 Unlocking the Codex harness 发布于 2026-02-04 13:00 UTC。同日稳定版的时间顺序是：

Artifact 时间（UTC） 是否进入基线
rust-v0.95.0 2026-02-04 04:54 是
OpenAI App Server 文章 2026-02-04 13:00 —
rust-v0.96.0 2026-02-04 18:23 否，属于发布后的 look-ahead
rust-v0.149.0 2026-08-20 21:04 终点

文章示例中的 codex_vscode/0.94.0-alpha.7 只是 client user-agent，不足以把整篇文章绑定到 0.94。因此最公平的 stable-to-stable 对比是：

rust-v0.95.0@12dbb76  →  rust-v0.149.0@758ef40

两端 release commit 从共同父节点各自切出，GitHub Compare 显示 target side ahead_by=6,248、baseline side behind_by=1。所以准确说法是“目标侧新增 6,248 commits”，不是假设两 tag 线性相承。完整对比见 GitHub Compare。

2. 2 月 4 日已经有什么：这些不能再算 8 月新增

2.1 最小可嵌入 Harness 已经完整

0.95 App Server README 已明确提供：

  • stdio 上的双向 JSONL / JSON-RPC-lite；
  • initialize handshake 与版本化 schema；
  • Thread / Turn / Item 三层对象；
  • thread/start|resume|fork|list|read|archive|unarchive|name/set|rollback；
  • turn/start|interrupt、Item delta、plan、reasoning、command、file-change 等事件流；
  • review/start 与 sandboxed command/exec；
  • model、Skills、Apps、MCP OAuth / status、account auth、config read/write；
  • command / file 的 server-initiated approval request；
  • stable / experimental capability gate。

也就是说，Thread / Turn / Item、持久会话、事件流、审批、Skills / MCP、App Server 本身都不是这半年的新发明。0.95 已有 35 个显式 v2 client RPC。

2.2 Agent loop、工具并发与 subagent 也已经存在

基线 core/src/codex.rs 已实现：history → Responses sampling → function call → tool output 回填 → 再次 sampling → assistant message 结束，并包含 auto-compaction。

基线 tools/parallel.rs 已按工具 capability 使用 RwLock：可并行工具共享 read lock，有写入 / 副作用风险的工具形成独占屏障。

基线 agent/control.rs 已有 multi-agent v1 的 spawn、send、interrupt、status；基线也已有 Skills loader、MCP、AGENTS / project instructions、JSONL rollout 和 SQLite metadata。

2.3 TypeScript SDK 早已有，但不是完整 App Server SDK

TypeScript SDK 在 0.95 已存在，且到 0.149 的基本架构仍是启动 codex exec --json 子进程的 wrapper。它适合一次性或流式程序调用，但不能把它误算成半年后新增的 typed App Server client。

3. 真正新增一：Permission / Safety 变成独立控制面

这是半年里最重要的架构增量之一。

3.1 Before → After

0.95
command / file 是否需要 approval
        ↓
允许或拒绝本次动作

0.149
Permission Profile
  ├─ filesystem read / write / deny precedence
  ├─ network policy
  ├─ additional requested permissions
  ├─ session / turn / environment grant scope
  └─ user review 或 Guardian auto-review
        ↓
统一 ApprovalAction
  Shell · ExecCommand · ApplyPatch · MCP · Network · RequestPermissions
        ↓
executor / sandbox enforcement

当前 approvals.rs 已把 shell、exec、patch、MCP、network、request-permissions 归入统一审批链；permissions.rs 明确 filesystem read / write / deny 的优先级；request_permissions handler 允许 Agent 在运行中申请额外能力。

Hooks 也从早期 AfterToolUse 扩展为 11 类生命周期事件，包括 Pre/PostToolUse、Permission、Compact、Session、Subagent 与 Stop，见 hooks/src/lib.rs。

这不是多几个 approval 弹窗，而是把“允许谁、在什么范围、持续多久、由谁复核、在哪层强制”建模成 control plane。

边界：Permission Profiles 和 granular approval 的部分 App Server surface 仍需 experimental opt-in；Guardian 依赖 managed reviewer，不等于开源本地代码独立完成全部安全判断；PostToolUse 仍不能撤销已发生的副作用。

4. 真正新增二：Context / Thread 从日志升级为可恢复状态平台

这部分由两个互补机制组成。

4.1 Typed World State：每个 model step 有一致的运行时视图

基础 agent loop 没变，但当前 run_turn 会在 step 边界捕获 StepContext，并把 environment、permissions、model、plugins、tools、multi-agent、realtime 等状态投影为 typed World State。

context/world_state 提供 section / diff / extension contract，使状态可以持久化、比较、replay，并在 compaction / resume 后重建一致上下文。后来新增的 remote compaction、context-window lineage 与整棵 Agent tree 的 rollout token budget，都建立在这类显式状态边界上。

这是真正的 Harness 增量：不是给 prompt 多塞一段文字，而是让“模型这一步看到的世界”成为可记录、可比较、可恢复的对象。

4.2 ThreadStore：从 recorder 变成 product state service

0.95 已有 JSONL canonical rollout 与 SQLite metadata recorder；当前 ThreadStore trait 则统一 create / resume / append / flush / history / model-context / fork / revert / list。

半年新增包括：

  • 分页 Thread / Turn / Item history；
  • SQLite materialization 与 legacy rollout migration；
  • single-writer 与 durable revert；
  • thread search、status、section、project、goal、queue；
  • bounded model-context suffix，不必为 UI 或模型每次重放整段历史；
  • 跨进程可查询的 Thread 生命周期。

ThreadStore README 仍明确：本地 canonical history 是 JSONL，SQLite 负责 queryable metadata / projection。

关键边界：仓库曾加入 remote ThreadStore，后来又移除；0.149 开源实现主要是 local / in-memory seam。它证明 storage-neutral abstraction，不等于附送一个可自托管的远程 Codex cloud store。

5. 真正新增三：Multi-Agent V2，而不是“首次支持 subagent”

0.95 已能 spawn / send / interrupt / status；后续的实质增量是把 subagent 从几个子任务句柄变成一棵可治理的 Thread tree：

  • canonical agent path，例如 /root/researcher；
  • nickname、role 与 structured message；
  • mailbox、follow-up、list、wait、automatic final-result delivery；
  • full-history fork 与 fork sanitation；
  • active-execution concurrency limit；
  • LRU residency / reload；
  • parent-child rollout budget；
  • per-turn multi-agent mode 与 App Server / TUI control surface。

当前 AgentControl 是 root-tree scoped 的 registry + residency + execution limiter + budget 控制面；AgentRegistry 维护 tree / path / nickname / limits。

这让 multi-agent 从“Agent 能开子 Agent”，升级为“宿主能观察、寻址、约束和恢复一棵 Agent execution graph”。

边界：源码与配置仍长期称为 V2，半年内经历 assign-task → follow-up、close → interrupt、fork / residency 语义变化；它已很实用，但不是冻结协议。

6. 真正新增四：Skills + MCP + Apps + Hooks 组合成 Plugin / Extension 平台

0.95 已有 local Skills、MCP 和 Apps。新东西不是“支持工具”，而是把扩展能力做成可发现、安装、组合与投影的包：

  • structured plugin manifest；
  • curated marketplace、install / uninstall、@plugin mention；
  • 一个 plugin 聚合 Skills、MCP、Apps 与 Hooks；
  • typed Extension API；
  • host / executor / orchestrator 等不同 Skills 来源；
  • token-budgeted catalog 与 progressive disclosure；
  • tool_search / deferred MCP tools，避免全量 schema 常驻上下文。

当前 plugin/src/lib.rs 的 capability summary 已把 Skills、MCP、Apps、Hooks 放进同一个模型；ext/extension-api 提供 typed contributor surface。

这意味着 Codex 从“带几个 extension 点的 agent”走向“可装配 capability package 的 runtime”。但 curated catalog、认证和 remote executor 仍依赖 managed services；Extension API 半年内变化很快，不能视为长期稳定 ABI。

7. 真正新增五：App Server 从 loop API 变成产品 control plane

7.1 协议面积变化

对 app-server-protocol 的显式 v2 macro 计数：

Surface 0.95 0.149 变化
client → server RPC（排除 initialize） 35 145 112 新增、2 删除
server → client requests 5 9 +4
notifications 27 76 +49

删除的两个 RPC 是早期 skills/remote/read|write；相应能力后来被 marketplace / plugin surface 取代。当前 145 个方法中，52 个整方法仍标 #[experimental]，所以“RPC 多了四倍”说明 control plane 变大，不等于全部 production-ready。

新增的高价值 surface 包括：

  • turn/steer、connection-aware resume、unsubscribe 与 thread status；
  • 分页 turns / items、search、metadata、sections、projects；
  • goals、durable queue、memory mode；
  • filesystem RPC、watch、PTY / TTY streaming process lifecycle；
  • permission profile、network request、MCP elicitation；
  • subagent descendant / fork / status 投影；
  • realtime / audio 与 remote-control；
  • plugin / marketplace / environment APIs。

当前 0.149 App Server README 已更像“Agent product backend contract”，而不只是启动一个 Turn 的 API。

7.2 Keyed request serialization 是低调但关键的成熟化

新增的 request_serialization.rs 会按 thread / global resource 对 RPC 排队，部分全局读取可共享执行。这样同一 Thread 的 lifecycle / state mutation 不再由多个裸 handler 任意并发，避免 resume、archive、turn-start、metadata 更新之间的 race。

这类并发正确性没有新 UI 那么显眼，却是“能否当产品控制面”的核心差别。

7.3 Transport 扩展了，但不能过度宣传

0.95 只有 stdio。后续加入 WebSocket、Unix socket、health probe 与独立 app-server-transport。WebSocket 曾加入、回退、再恢复；0.149 README 仍把它标为 experimental / unsupported。

所以它证明 transport abstraction 在成熟，不代表开源仓库已经提供可直接暴露公网的 production Agent server。

8. 真正新增六：Python typed App Server SDK

这是最容易被明确称为“新组件”的增量。

sdk/python 从 generated protocol foundation 演进为 openai-codex：

  • 启动匹配的 Codex binary；
  • typed stdio JSON-RPC；
  • sync / async client；
  • Thread lifecycle、stream / steer / interrupt；
  • auth、approval 与 sandbox preset；
  • runtime-generated protocol types。

它和旧 TypeScript SDK 的关键差别是：Python 版直接面向 App Server typed protocol，而不是仅包装 codex exec --json。

边界：高层 wrapper 只覆盖精选 RPC，不等于暴露全部 145 个方法；0.149 源码快照仍绑定 0.147 runtime，说明 SDK 与 CLI binary 版本耦合且可能短暂滞后。

9. 真正新增七：Environment / Remote execution plane

半年后，Harness 不再假定所有 shell / file / patch 都必须发生在本机 CLI 进程旁：

  • multi-environment per turn 与 sticky environment selection；
  • exec-server protocol 与 executor registry；
  • remote executor auth / registration；
  • remote filesystem、AGENTS、sandbox intent 与 network policy callback；
  • remote-control、daemon、Noise-encrypted relay；
  • remote Code Mode host 与 executor-provided Skills。

这使同一个 Turn 可以把动作路由到选定 executor / environment，而 UI 与 Harness control plane 留在另一侧。

边界同样重要：开源仓库提供 client、protocol、local pieces 和 seams；managed registration、relay、身份与 OpenAI remote runtime 并没有因此全部变成可离线自托管服务。

11. 所以 8 月 19 日“新增了什么”应该分三层回答

11.1 公告当天的代码增量：接近零

没有新建 codex-harness repo，没有重写 agent loop，也没有在当天突然开放此前私有的整套产品代码。8 月 20 日的 0.149 是正常连续 release。

11.2 半年累计的产品增量：很大

从 0.95 到 0.149，Codex 从“有完整会话协议的本地 coding agent”变成：

Agent Loop
  + Permission / Approval control plane
  + Typed World State
  + Durable ThreadStore / pagination / queue / goal
  + Multi-Agent execution tree
  + Plugin / Extension marketplace model
  + App Server product protocol
  + Python typed SDK
  + Local / remote environment abstraction

这不是 foundation-model 算法创新，但属于非常实质的 runtime / distributed-systems / product-platform 工程。

11.3 8 月公告真正新增的公共承诺：中等

OpenAI 在 Codex as a platform 中第一次把积累起来的 CLI、SDK、App Server 明确包装成“open agent harness”的正式建设路径，并告诉开发者：脚本用 exec、程序调用用 SDK、深度产品嵌入用 App Server。

因此这次的增量是 定位、文档、组件清单与平台承诺，而不是 source availability 本身。

12. 最终评分

维度 评分 理由
Core agent-loop 新意 2 / 5 主循环没变；World State、step consistency、remote compaction lineage 是真实增强
Runtime / control-plane 新增 5 / 5 Permission、ThreadStore、MAv2、Plugin、App Server、remote env 都是实质系统工程
Stable public API 成熟度 2.5 / 5 面积大、已有产品使用，但 experimental / v2 / managed seams 仍多
8 月 19 日单日“开源事件” 0.5 / 5 主要是叙事与官方承诺，不是新 repo 或首次放出源码

最准确的总结是：

“Agent loop 没有新东西”是对的；“整个项目半年没有新东西”是错的。Codex 的创新重心已经从 loop 移到 control plane。

13. 建议的源码学习顺序

  1. 用 0.95 core/src/codex.rs 对照 0.149 core/src/session/turn.rs，看不变的 loop 与新增的 step / world-state lifecycle。
  2. 读 protocol/src/permissions.rs、core/src/tools/approvals.rs、sandboxing/，理解 declaration、approval 与 enforcement 的分层。
  3. 读 thread-store/，追一条 append → materialize → paginate → resume / fork / revert 链路。
  4. 读 core/src/agent/control.rs 与 registry.rs，画出 Agent tree、mailbox、residency 与 budget。
  5. 最后读 App Server method registry 与 request serialization，理解 UI / SDK 如何安全驱动上述控制面。
