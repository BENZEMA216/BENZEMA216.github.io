2026-08-21 产品拆解

OpenAI Codex 开源 Agent Harness：协议、审批与可审计 runtime

一句话结论：OpenAI 这次真正做的，不是新开一个 codex-harness 仓库，而是把早已开源的 openai/codex 正式定义为一套可嵌入产品的 agent runtime / harness：模型之外的 Thread、Turn、上下文、工具、事件流、审批、沙箱、持久化和多 Agent 控制面，都可以通过 CLI、SDK 或 App Server 被宿主应用复用。

0. 先校正时间线：“刚开源”不等于代码第一次公开

时间 发生了什么 准确含义
2025-04-16 OpenAI 在 o3 / o4-mini 发布文中宣布 Codex CLI fully open-source openai/codex 的开源起点，不是 2026-08-19
2026-02-04 OpenAI 发布 Unlocking the Codex harness 开始把 App Server 和底层 loop 作为可复用能力解释
2026-08-19 发布 Codex as a platform: build on the open agent harness 本次触发点：正式的平台化定位、开放组件清单与嵌入路径
2026-08-20 GitHub 发布稳定版 rust-v0.149.0 本报告查询时的最新稳定版本
2026-08-21 本地只读 checkout main@9ab176f 本报告的源码证据快照；不是稳定 tag

因此，更准确的表述是：

Codex 代码不是今天才开源；OpenAI 今天把已有开源实现正式产品化为 “open agent harness platform”。

这也解释了为什么 vault 在 2026-04 收录的二手访谈中已经出现“Rust 核心 Codex Harness 开源”的说法。那条材料可证明这个叙事早已存在，但本次范围以 OpenAI 官方公告、官方组件清单和固定 SHA 源码为准。

1. 到底开放了什么，没开放什么

OpenAI 官方组件清单给出的边界很清楚：

组件 是否开源 作用
Codex CLI 是 终端产品，也是 harness 的主要开源宿主
Codex SDK（TypeScript / Python） 是 在程序中 start / resume / stream 本地 Codex Thread
Codex App Server 是 把 Thread / Turn / Item / Event / Approval 暴露为双向 JSON-RPC 协议
Skills / Plugins 是 可复用的模型指令、工具与扩展包
Universal cloud environment 部分基础环境开源 Codex cloud 使用的基础环境，不等于 cloud 服务本身
IDE extension 否 VS Code / IDE 产品表面不在开源清单中
Codex cloud 否 托管执行、调度、身份与服务端能力不在仓库中
模型权重 / 模型服务 否 Harness 通过 Responses API 等模型入口工作；模型访问仍是独立服务

许可证是 Apache-2.0，允许使用、修改和分发。但治理上有一个很重要的反直觉边界：官方 CONTRIBUTING.md 明确写着 不接受外部代码贡献或 Pull Request，社区参与入口是 issue、复现、root-cause analysis 和设计讨论。

所以它是：

  • 真正可读、可改、可 fork 的开源代码；
  • 但不是共同维护、外部 PR 可合入的开放治理项目；
  • 更不是“整个 Codex 产品栈”和“OpenAI 模型”一起开源。

2. 这个项目真正是什么产品

最容易误读的方式，是把 Codex 看成一个 CLI，或者把 App Server 看成“给 Codex 套 API”。更准确的三层模型是：

Agent Product = Host Application + Codex Harness + Model / Managed Services
  • Host Application 拥有用户界面、业务对象、system of record、身份、业务规则、产品级 consent，以及 application-owned MCP actions。
  • Codex Harness 拥有 Thread / Turn 生命周期、上下文装配、agent loop、工具路由、事件流、审批协商、shell 沙箱、持久化、steering 和 subagent 控制。
  • Model / Managed Services 提供推理与托管能力；不属于开源 harness。

最后一条 Tools → Host 很关键：业务工具修改记录后，宿主应用必须刷新自己的业务视图。Harness 负责 agent loop，不自动成为业务数据库的事实源。

3. 源码地图：134 个 Rust workspace member，但先只抓六条主干

本报告固定在 main@9ab176f。该快照有 6,443 个 tracked files、3,257 个 Rust 文件、134 个 Cargo workspace members。规模很大，但核心认知可以压成六层：

层 源码入口 回答的问题

两个横切面：

  • Context / instructions：core/src/agents_md.rs 与 ext/skills/src/catalog_prompt.rs。
  • Multi-agent：agent/control.rs 与 agent/registry.rs。

4. 一次 Turn 到底怎样运行

4.1 Thread 是双向消息通道，不只是聊天记录

CodexThread 的注释直接把它定义为组成一个 Thread 的双向消息流 conduit：

  • client 向 Thread submit(Op)；
  • core 向 client 暴露 next_event()；
  • Thread 还持有 session、rollout path、状态订阅、设置快照等运行时信息。

这是一条很强的架构分界：UI 不直接调用 loop 内部函数，而是提交操作、订阅事件。CLI、App Server、IDE / App surface 因此可以共享核心但拥有不同 UX。

更底层的 Session 是一个持续运行的 actor：它持有 submission / event channels，处理 user input、interrupt、approval response、MCP refresh、compact、rollback、review，直到显式 shutdown。也就是说，thread.run() 只是 SDK 给出的方便表面，内核不是一个同步函数调用。

4.2 run_turn 是最小 agent loop

源码注释给出的终止规则非常干净：

  1. 模型返回 function call → Harness 执行工具；
  2. 把 tool output 放回下一次 sampling request；
  3. 模型只返回 assistant message → 记录消息，Turn 完成。

真实实现比这个三步多出的部分，恰好就是 Harness 的价值：

  1. Turn 开始前检查并执行 compaction；
  2. 从用户输入解析 required MCP servers / mentioned plugins；
  3. 捕获本 Turn 的 step context 与 world state；
  4. 构建 Skills / Plugins 注入项；
  5. 运行 session-start / pre-turn hooks 并持久化输入；
  6. 组装完整 prompt 和 model-visible tool specs；
  7. 流式消费模型事件，同时调度 tool futures；
  8. 把结果写回历史，必要时中途 compaction，再继续 sampling；
  9. 接受 steering / cancellation，直到 assistant message 或错误终止。

build_prompt() 不是“拼一个字符串”：它把 history items、base instructions、该 step 可见的 tool schema、并行调用开关和最终输出 schema 组装成结构化 Prompt。因此 context engineering 在这里是一套运行时装配过程，而不是一段 system prompt 文案。

模型层也有边界：provider 可以换 base URL、认证和 transport，仓库内有 OpenAI、Amazon Bedrock、Ollama、LM Studio 等入口；但当前通用 seam 是 Responses-compatible API，不是“接任意 chat completion API 就能跑”。ModelClientSession 还是 turn-scoped，用来复用该 Turn 内的 WebSocket / routing 状态，不能把它当跨 Turn 的业务 Session。

4.3 Tool 并发不是简单 join_all

Codex 为每个工具判断 supports_parallel：

  • 可并行工具取得共享 read lock；
  • 不可并行工具取得独占 write lock；
  • 因而多个 read-safe tool 可以并发，write / unsafe tool 形成屏障；
  • cancellation 会终止仍在执行的 dispatch task。

随后 registry 负责完整生命周期：payload kind 校验 → PreToolUse hook → handler → telemetry → PostToolUse hook → model-visible result。

一个非常值得记住的细节：PostToolUse block 只能拒绝已经产生的结果，不能撤销已经发生的副作用。源码对此有明确注释。因此有副作用的业务动作必须把 auth、idempotency、transaction / compensation 和 approval 放在执行前或业务服务本身，不能把 post-hook 当 rollback。

5. 安全控制面：Approval、Sandbox、MCP Trust 是三件不同的事

Codex 把 ExecCommand、ApplyPatch、McpToolCall、NetworkAccess、RequestPermissions 都纳入统一 ApprovalAction，但这不意味着它们共享同一种隔离：

控制 解决什么 不解决什么
Approval 这次动作是否经过用户 / policy 授权 不能物理阻止已获准进程越界
Permission profile 本 Turn / Environment 应拥有哪些声明式能力 仍需 executor / tool 真正 enforcement
OS sandbox 限制本地 shell / process 的文件和网络能力 不自动包住远端 MCP 服务的内部执行
PreToolUse hook 执行前 block 或改写输入 不是 OS 隔离层
PostToolUse hook 过滤、替换模型能看到的结果 不能撤销已发生的 side effect
MCP / application auth 限定业务 principal、scope、record-level permission 由 MCP 服务和宿主应用自己实现

本地 executor 按平台选择 macOS Seatbelt、Linux seccomp 路径或 Windows Restricted Token，并可叠加 managed network proxy。与此同时，OpenAI 对 agent loop 的官方解释也明确提醒：Codex shell 的 sandbox 不等于 MCP tool 被同一个 sandbox 包裹。

Codex 对 MCP 还做了一层很实在的 TOCTOU 防护：每个 step 冻结模型看到的 tool catalog / client / config binding，真正调用前校验 catalog revision；若“模型看到的工具 A”在执行时已经换成 B，则拒绝调用。但这只能保证 binding 一致，不能替 MCP server 实现业务鉴权和 side-effect 安全。

这对产品集成的直接结论是：

“用户点了批准”不是完整安全模型；必须同时回答谁批准、批准什么 capability、在哪个执行环境强制、业务 API 如何鉴权、失败后怎样恢复。

6. 状态模型：Thread / Turn / Item + JSONL canonical history

App Server 以三层对象组织生命周期：

  • Thread：一个持续会话，可 start / resume / fork / archive；
  • Turn：一次用户输入到 agent 完成 / 中断的运行；
  • Item：user message、assistant message、reasoning、command、file change、MCP call 等流式活动单元。

本地存储也不是一个模糊的“memory”：

  • ThreadStore::append_items 是 canonical history append API；
  • LocalThreadStore 用 rollout JSONL 保存 history；
  • SQLite 保存可查询 metadata，并从 JSONL rollout 抽取 / mirror 状态；
  • core 通过 storage-neutral ThreadStore 边界工作，也允许仓库外实现其他 store。

这比“内存里放一个 messages 数组”强得多，因为 resume、列表、metadata 查询、迁移和未来远端 store 都有明确边界。但它也不同于 DSH 更强的 model-visible ⟺ logged 运行时不变量；不能因为 Codex 有 JSONL 就自动推导每一份模型输入都能字节级重建。

7. Context 是 Harness 的程序，而不是 Prompt 的附件

Codex 的 context stack 至少包括：

  • model/base instructions；
  • sandbox / permission 的 developer context；
  • host-provided user instructions；
  • 从 project root 到 cwd 的 AGENTS.md 层级；
  • selected Skills 的 metadata 与按需读取的 SKILL.md；
  • MCP / plugin / connector 的 tool schemas；
  • Thread history、tool outputs、world-state changes；
  • compaction 后的摘要或 opaque compacted items。

源码中的几个确定性约束很值得学习：

  • AGENTS.md 从 project root 向 cwd 收集，绝不越过 project root；
  • AGENTS.override.md 是优先本地覆盖名；
  • project docs 有总字节预算；
  • untrusted project 不加载项目指令，只保留 host-provided user instructions；
  • Skills 采用 progressive disclosure：先给 metadata catalog，选择后主 Agent 必须完整读取 SKILL.md。

官方公开的 ARC-AGI-3 数字称：retained reasoning + context compaction 让 GPT-5.6 Sol 从 13.3% 提升到 38.3%，同时 output token 降低六倍。它说明 Harness 设计可能显著影响同一模型的结果；但这是 OpenAI 自己在特定模型 / benchmark / harness 配置上的证据，不应外推成“任何任务都提升三倍”。

8. Multi-agent 的本体：一棵共享控制面的 Thread 树

Codex 的 subagent 不是简单开几个匿名异步函数：

  • 每个 subagent 是独立 Thread；
  • root 和 descendants 共享一个 session-scoped AgentControl；
  • registry 保存 agent tree、Thread ID、path、nickname、role；
  • spawn 有最大 Thread 数和深度限制；
  • control plane 提供 spawn、message、follow-up、interrupt、list、wait；
  • child thread 可继承或裁剪父历史，父子关系可以持久化。

这个设计使 delegation、独立 context、并发预算和生命周期管理落到同一个 Thread 抽象上。它比“Tool 里递归再调一次 LLM”更重，但也更适合 UI 可视化、resume、治理和长任务。

9. App Server 为什么是这次平台化的关键

如果 core 是 engine，App Server 就是可被其他产品消费的 ABI：

  • 双向 JSON-RPC 2.0（wire 上省略 jsonrpc: "2.0"）；
  • 默认 stdio transport 是 newline-delimited JSON / JSONL；
  • client 发送 initialize、thread/start、turn/start；
  • server 流式发送 turn/started、item/*、turn/completed；
  • server 可以反向请求 command / file change approval；
  • schema 可由当前 Codex binary 生成 TypeScript 或 JSON Schema，而且 schema 与该版本精确绑定。

WebSocket transport 截至本报告仍标为 experimental / unsupported for production。官方文档还提醒非 loopback listener 在 rollout 期间可能默认无认证；远端暴露前必须配置 WebSocket auth。产品化时应优先从本地 stdio + pinned runtime 开始，而不是直接把 experimental WebSocket 当公网 Agent server。

10. 四种接入方式怎么选

方式 适合 你获得什么 主要代价
codex exec CI、脚本、一次性后台任务 最小集成、结构化输出 对中途事件和 UX 控制少
TypeScript / Python SDK 服务端 start / resume / stream Agent task 稳定的程序接口；Python SDK pin 对应 CLI runtime 仍要管理进程、权限、事件与业务状态
App Server Agent 是产品本身的一部分 直接控制 Thread 生命周期、流式 Item、interrupt、approval 和 UI 协议面大、版本耦合、实验功能多
Fork Rust core 必须改变 loop / executor / persistence 的底层语义 最大控制权 维护 134-crate 快速演进代码库；上游又不收外部 PR

默认学习和产品 PoC 路线应是：

codex exec → SDK → app-server → 最后才考虑 fork core

11. 真正厉害的地方，以及哪些并不新

真正厉害

  1. 把成熟 coding agent 的运行时拆成可复用平台：不是另写一个 demo SDK，而是 App / CLI / IDE 共用的生产核心。
  2. Thread / Turn / Item / Event 形成产品协议：UI、后台任务和 core 不必共享控制流，只共享 typed lifecycle。
  3. 安全成为运行时 control plane：approval、permission、OS sandbox、hooks、network policy 分层，而不是一个 --dangerously-skip 布尔值。
  4. Context assembly 被工程化：AGENTS、Skills、MCP、world state、compaction、history 都有确定的发现、预算和注入路径。
  5. 持久化和多 Agent 复用同一个 Thread 原语：resume / fork / subagent / queue / steering 可以落在统一对象模型上。
  6. 宿主应用边界说得很清楚：产品拥有业务 context、规则、工具、consent 与 system of record；Harness 不抢业务真相。

并不新，但组合价值很高

  • model → tool → model 的 loop 本身是标准 agent pattern；
  • JSON-RPC、event streaming、JSONL、SQLite、read/write lock 都是成熟工程原语；
  • Skills progressive disclosure、AGENTS.md、MCP、hooks 也不是 Codex 独有。

Codex 的护城河不在发明某一个原语，而在把这些机制与模型 prompt、产品 surfaces、平台安全和长期兼容一起磨成了同一个可运行系统。

12. Anti-thesis：不要被“Open Agent Harness”叙事带走

  1. 不是刚刚第一次开源：2026-08-19 是定位升级，不是源码诞生。
  2. 不是完整 Codex：IDE extension、Codex cloud、模型和 managed services 不开源。
  3. 开源不等于开放治理：Apache-2.0 可以 fork，但官方不接 external code PR。
  4. App Server 仍有 maturity 风险：协议面很大，许多方法标 experimental；generated schema 与 binary 版本绑定。
  5. 本地沙箱不覆盖所有工具：MCP / business service 是另一条 trust boundary。
  6. Approval 不等于事务：尤其 PostToolUse 无法撤销副作用。
  7. 平台文章里的 benchmark 是 vendor evidence：ARC-AGI-3 数字很强，但不是独立、跨任务的通用因果证明。
  8. 复杂度非常真实：固定快照已有 134 个 Rust workspace members；若产品只需要一次性 task，fork core 很可能是过度工程。

13. 与 DSH 的对照：产品化 runtime vs 可组合 microkernel

维度 Codex Harness DeepSeek Harness（DSH）
第一目标 给 Codex App / CLI / IDE 和第三方产品提供统一 runtime 让 harness 每一层都能被插件组合、替换和发行
Agent loop 强 opinionated 的 Rust core loop loop 本身也可作为 Cordis plugin 替换
扩展模型 tools、hooks、skills、plugins、MCP、extension APIs typed events + capability seam + profile / bundle / patch
状态 ThreadStore canonical append；本地 JSONL history + SQLite metadata append-only session log 是唯一事实源，并强制 model-visible ⟺ logged
协议 App Server 的 Thread / Turn / Item JSON-RPC Headless / Web / SDK / ACP，多 profile 组合
安全强项 跨 macOS / Linux / Windows 的真实 OS sandbox + approvals provider 可替换、fail-closed capability / sandbox / credential 设计
产品成熟度 已驱动真实 Codex 多 surface，规模和集成深 developer preview，但开放组合权更彻底
社区治理 Apache-2.0，但不接外部代码 PR 更像开放框架生态路线

两者不是谁“更先进”，而是在优化不同变量：

  • Codex 优先解决 同一套强 runtime 如何驱动多个真实产品；
  • DSH 优先解决 不同 runtime / capability / product shape 如何被第三方重新组合。

14. 对 Agent 产品的直接启示

最值得迁移的不是复制 Codex UI，而是以下边界：

  1. 用 Thread → Turn → Item → Event 做稳定协议，不让 UI 直接耦合 loop 内部控制流。
  2. 宿主产品拥有业务 record、auth、规则、consent 和最终 read-back；Harness 拥有推理 loop、工具交互和运行态。
  3. 把 approval、permission、sandbox、credential、business authorization 分成五个可独立审计的层。
  4. 所有 consequential writes 都要执行前授权、幂等键、结果 read-back；不能把 post-hook 当 rollback。
  5. SDK / App Server 必须 pin runtime 与 schema，版本协商应成为产品契约。
  6. 为 Domain UI 提供 agent，而不是把所有工作强迫进一个通用聊天框。
  7. 如果目标是生态化，再向 DSH 学习开放组合权；如果目标是可靠产品，先向 Codex 学习意见明确的 runtime 和 lifecycle。

15. 建议的学习顺序与第一个动手实验

第一遍：只建立运行链路

  1. codex_thread.rs：看 submit(Op) / next_event()。
  2. session/turn.rs：从 run_turn() 追到 build_prompt()、run_sampling_request()、try_run_sampling_request()。
  3. tools/parallel.rs + tools/registry.rs：看并发屏障、hook 和 tool result 回流。
  4. approvals.rs + sandboxing/manager.rs：分开理解 consent 与 enforcement。
  5. thread-store/README.md：理解 canonical history 与 SQLite metadata。
  6. app-server/README.md：把 core 心智模型映射到 Thread / Turn / Item / Event。

第二遍：做一个最小 Event Tracer

目标不是造聊天 UI，而是写一个约 50–100 行的本地 client：

  1. 启动 codex app-server（stdio）；
  2. 发送 initialize / initialized；
  3. 用 read-only sandbox 创建 Thread；
  4. 启动一个只读 Turn；
  5. 把每个 item/* event 按时间写入本地 trace；
  6. 遇到 approval request 一律 decline；
  7. 对照 JSONL rollout，画出一次 Turn 的状态机。

本机查询时 codex-cli 是 0.142.5，低于上游最新稳定版 0.149.0。正式动手前应先决定是按本机版本学习，还是隔离安装并 pin 0.149.0；不要直接拿最新文档 schema 假设旧 binary 完全兼容。
