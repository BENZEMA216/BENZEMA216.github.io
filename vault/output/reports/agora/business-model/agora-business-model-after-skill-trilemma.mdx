# Agora 商业模式修正：Agent Skill 商业化三角之后

> [!note] 状态说明（2026-07-17）
> 本文保留“本地加密不能单独成为商业壁垒”的原则，不再代表 Combo 当前完整商业模式。当前经营口径见 [combo-unit-economics-v0-2026-07](/output/reports/combo/business-model/combo-unit-economics-v0-2026-07/)。

> 查询归档：用户要求阅读 `Clippings/Agent Skill 商业化三角不可能定理.md`，并重新思考 Agora / Agent 能力包项目的商业模式。  
> 来源已归档：`raw/articles/agent-economy/agent-skill-commercialization-trilemma.md`

## 核心结论

这篇文章对 Agora 的最大价值，是把一个容易误判的商业假设打掉：

**不要把 Agora 的商业模式建立在“本地标准 runtime 里卖加密 skill 包”上。**

原因是三角不可能：

> 标准化 agent runtime × 客户端本地运行 × 源码保护，三者不可兼得。

如果一个 Agent / Skill 在用户本地的标准 runtime 里运行，模型就必须读到它的 prompt、workflow、tool instruction 或关键逻辑；只要模型能读，用户就有办法通过 prompt injection、日志、session history、runtime 文件或调试手段把内容抽出来。加密可以提高摩擦，但不能成为商业护城河。

因此 Agora 的商业模式应从“卖一个受保护的本地包”改成：

**卖持续可用的能力契约：访问权、更新、兼容、验证、支持、托管执行、结算和分发。**

## 对 Agora 的直接修正

### 1. 能力包不是 DRM 商品

能力包可以有签名、license、activation、token、日志和水印，但这些不是绝对防盗版机制。

它们的真实作用是：

- 控制 entitlement
- 做版本和更新管理
- 给退款和争议处理提供证据
- 降低普通用户复制和滥用的概率
- 让 creator 的商业关系可追踪

它们不能保证“用户永远看不到本地运行的 prompt / skill / workflow”。

### 2. 商业模式要拆成三种执行-保护模式

Agora 不应该强行把所有能力包塞进一种计费/执行模型，而应该允许 creator 按能力类型选择商业化模式。

| 模式 | 保留什么 | 放弃什么 | 适合什么 | 收费方式 |
|---|---|---|---|---|
| Open-local package | 标准 runtime + 本地执行 | 强源码保护 | 用户隐私强、可接受开源/半开源的 workflow | 订阅更新、support、community、certification、team license |
| Hosted-protected capability | 标准分发 + 核心 IP 保护 | 完全本地执行 | 高价值 know-how、专有算法、动态数据、creator 不愿公开的逻辑 | usage、seat、subscription、take rate |
| Managed runtime package | 本地/近端执行 + 更强保护 | 完全开放 runtime | 下沉市场、垂直场景、企业私有部署 | managed seat、private registry、enterprise fee |

Agora 的策略不是在三角里假装全都要，而是做 **mode-aware marketplace**：每个能力包的 listing 明确标注它属于哪种模式，哪些步骤本地运行，哪些步骤托管，哪些内容开源，哪些内容只通过服务调用。

### 3. Hybrid execution 应该从“隐私架构”升级为“商业架构”

之前我们讲 hybrid execution 主要是为了隐私：用户 cookie、本地文件、账号环境不上云。

这篇文章提醒我们，hybrid execution 还有商业意义：

- 用户私域数据留在本地
- creator 核心 know-how 可以作为 hosted protected step
- 本地 runtime 负责浏览器、文件、账号和工具调用
- 云端服务负责不可泄露的策略、模型路由、动态数据、后处理、授权和结算

这比“把整个 skill 加密发到用户机器”更诚实，也更可持续。

### 4. 订阅费的理由更清楚了

用户不是为“看不见源码”付费，而是为这些东西付费：

- creator 持续迭代
- runtime / model / API / 网站变化后的兼容维护
- canonical tests 和回归验证
- 高质量社群和 support
- 受保护的 hosted steps
- 分发、安装、权限和退款体验

这和 Salesforce、Stripe、Linear 的逻辑更接近：客户不买源码，客户买持续在线、持续更新、持续可信的服务。

## 对 BP 叙事的改法

BP 里应该明确写：

**Agora does not rely on encrypted local packages as the moat.**

Agora 的护城河来自：

1. runtime compatibility matrix
2. package compiler
3. canonical tests
4. entitlement / billing / event ledger
5. creator update channel
6. hosted protected components
7. reputation and distribution graph

这比“源码保护”更能经得起投资人追问。

## 对 Agent-VM 的影响

Agent-VM 仍然成立，但定位要更准确：

- 它是 local activation layer，不是 DRM layer
- 它验证 Agent Profile、runtime adapter、mapping status、managed paths、export/import
- 它不应该承诺保护本地 skill 源码
- 它可以成为 Agora 的 install / activation / entitlement enforcement 前端

下一步 Agent-VM 可以补的方向：

- package manifest 的 license / entitlement 字段
- hosted protected step 的 endpoint binding
- local resource binding 与 redaction
- runtime mapping status 中加入 `ip_exposure_level`
- export/import 区分 open payload 与 protected reference

## 推荐的 BP 主句

> Snapshot 生成版本，订阅绑定能力线；本地运行的能力不靠加密成为护城河，真正的商业价值来自持续更新、兼容维护、测试验证、托管保护步骤和可信结算。

这句话能把 versioned snapshot、subscription、hybrid execution 和商业化三角统一起来。
