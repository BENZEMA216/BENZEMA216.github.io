## 第 1 章：2026 年的创业生命周期重启

AI 正在重塑创业公司被建立的方式。今天，从未写过一行代码的创始人也能交付生产级应用；而精简到只有 10 人的独角兽，已经不再只是一个草根逆袭故事，而是一套可以被有意执行的行动方案。

到 2026 年，AI 可以编写生产代码、开展市场研究、综合竞争格局、起草投资人材料，并自动化运营工作流。过去，即使是经验丰富的技术创始人，也要跨过很陡的学习曲线，才能把想法落地所需的工具、平台和系统整合起来。AI 消除了这道障碍，最重要的是，它拉平了「谁能够启动一家创业公司、谁能够做出一个产品」这件事上的门槛。

在 2026 年，一个好想法能把创始人带得比以往更远。Agentic coding 将过去需要一支工程团队完成的工作，压缩成创始人自己就能交付的东西。

传统的创业增长弧线默认，从想法到规模化的路径是：验证 → 融资 → 招人 → 构建 → 再融资 → 增长 → 再招人 → 重复。现在，AI 已经抹掉了一个旧预期：创业生命周期的每个新阶段，都必须配一个更大的团队、一套不同的技能、以及新一轮融资。

本手册会根据这些新现实，重新映射创业旅程的四个核心阶段：构想、MVP、发布和规模化。我们会考察：当 AI 成为技术开发和组织建设的核心时，每个阶段会是什么样；每个阶段适合什么工具；以及使用这些工具的创始人如何压缩时间线。如果你已经准备好寻找从想法到退出的最短路径，请继续阅读。

## 第 2 章：创始人的含义正在变化

过去，创始人通常由「他们能做什么」来定义：技术创始人写代码，非技术创始人跑业务运营、谈交易。但到 2026 年，创始人可用的模型、系统和 AI Agent 已经拆掉了「会构建的人」和「有值得构建的想法的人」之间的墙。

AI 原生创业公司正在从根本上改变「成为创始人」的含义。现在，一个没有工程背景的人可以构建生产级软件，让自己的想法落地；而一个技术能力强但商业知识有限的创始人，也可以轻松产出 go-to-market 策略、财务模型和打磨精良的融资 deck。

历史上，创始人大部分时间都处在执行模式里：写代码、管人、处理日常运营工作。在 AI 原生创业公司里，创始人角色会少很多 individual contributor 的成分，多很多 Agent 编排者的成分。这里的 Agent，是可以读取文件、运行命令、执行代码，甚至浏览网页的专业化 AI 助手。创始人的注意力会向上移动，转向更高阶的工作：生成想法，并指挥那些负责把想法执行出来的系统，包括 AI Agent、工具，以及任何存在的小团队。

不过，把 AI 作为核心基础设施，最具革命性的结果，是释放了那些拥有领域专业知识的非技术创始人。当创始人池子不再局限于工程背景的人，你就会看到拥有截然不同生活经验的人开始创建公司，去解决传统技术创始人路径从未优先考虑，甚至可能从未注意到的真实问题。

### 精益创业公司的 AI 工具能力

传统创业模型假设，你需要雇工程师来构建，雇销售来销售，雇运营来经营公司。员工数量被看作组织动能和产品成熟度的标志。

2026 年的早期创业公司完全不同。它们在设计上就极其精简，经常只有创始人一个人，或者再加上少数几个人。通过把技术开发和组织建设都建立在 AI 基础设施之上，它们可以在扩张团队之前，就达到产品验证、早期收入，甚至盈利。尤其有三个方面，AI 能让一家创业公司像更大的组织一样运转：研究、Agentic coding，以及关键业务运营的工作流自动化。

### 对话智能与研究

可以理解为：每个领域都有一位随叫随到的专家。

想想创始人在第一年需要知道的所有东西，而他们几乎肯定一开始都不知道：我该如何设置 payroll？我该如何规划产品开发 sprint？我该如何写一份紧凑有力的投资人 memo？

过去，这类早期创业问题的答案往往都是同一个：找一个懂的人。对于 bootstrapped 或 pre-seed 阶段的创始人来说，这可能意味着把本该用于构建的时间花在找知识上，也可能意味着烧掉一部分早期资本去请顾问。现在，他们拥有了 AI，作为覆盖几乎所有领域的随叫随到的专家。

- 深度研究：竞争分析、市场规模测算、财务建模
- 文档起草：融资 deck、案例研究、投资人 memo、PRD
- 战略思考伙伴：反方分析、premortem、情景规划、路线图优化

### Agentic Coding

可以理解为：永远在线、从不被阻塞的工程师。

过去，构建软件需要一个技术联合创始人、一个外包开发团队，或者足够长的 runway，让你在写出第一行生产代码之前先雇起一个工程团队。

Agentic coding 工具现在允许每一个有创业想法的人，用自然语言描述自己想构建什么，并指挥 AI 以一支完整工程团队的速度和规模，生成、测试、调试并重构生产级代码库。从「我有一个想法」到「我有一个产品」的时间线已经被压缩。创始人的角色现在集中在「构建什么」和「为什么构建」上，而真正可供真实用户使用的基础设施，则由 AI 负责实际建造。

### 工作流自动化

可以理解为：按需运转的自动化运营团队。

即使一个创始人可以像顾问一样研究、像工程团队一样构建，仍然有一整类既不属于战略规划、也不属于产品开发的工作必须完成。排日程、更新 CRM、拉周报、保持文档最新、发布内容、跟踪合规要求，以及管理公司赖以运转的各类工具和系统之间的连接组织，这些也都要发生。在一家精益创业公司里，这些负担主要落在创始人身上，并且会显著占用本应投向高阶决策的时间和注意力。

AI 工具驱动的工作流自动化可以卸下这部分负担。重复性的运营任务可以被配置为自动发生：当一笔交易移动时 CRM 自动更新；周报自动汇总；产品文档随产品变化同步更新。关键在于，Claude Cowork 能够与一家创业公司实际使用的互联系统集成，包括项目管理工具、沟通栈、数据源，而不需要某个人去构建并维护这些集成。在 Day Zero startup 里，这个人几乎总是创始人本人。

### 时机与编排就是一切

能有效利用 AI 的研究、自动化和 Agentic coding 能力的创始人，可以构建出一家杠杆远超员工数量的创业公司。他们也能把绝大部分时间和精力投入到真正重要的工作上。

但这些事情不会自动发生。编排这些 AI 工具的创始人，需要知道如何使用它们，以及何时使用它们。本手册余下部分会探索：创始人在沿着 AI 原生创业路径前进时，会遇到什么目标和挑战；以及如何在旅程的每个阶段有效应用 AI 工具。

## 第 3 章：构想阶段

每个创业创始人的起点都一样：一个让他们无法停止思考的问题。这个阶段，是想法与现实相遇的地方。2026 年的创业成功，要求创始人具备一种纪律：在证据足以支撑之前，不要急着构建。

这一阶段的工作是研究、客户发现、竞争分析，以及诚实评估反证证据。所有这些都应该发生在你让 Claude Code 生成第一行生产代码之前。

### 构想阶段目标

在构想阶段，创始人的主要目标是以研究为导向的验证：在投入资源构建之前，收集扎实证据，证明一个真实问题确实存在，并且你提出的解决方案能够有效解决它。

实际来说，构想阶段就是创始人必须大致按顺序回答的一系列问题：

- 这个问题是否真实、具体，并且发生频率足以支撑围绕它创业？
- 到底是谁有这个问题？这些人是否构成一个市场？
- 是否已经有人在解决它？如果有，他们如何解决，解决得好不好？
- 一个解决方案到底需要做什么，才能真正解决这个问题？我的想法做到了吗？

这些问题的结果最终汇总成一个终极问题：这件事值得构建吗？

这意味着，在行动之前先做到具体。「人们在报销上很痛苦」只是一个观察。「中型企业的财务经理每周花 4 小时以上核对报销提交，因为他们当前的工具无法与会计软件集成」才是一个可测试的假设。

### 构想阶段退出标准

构想阶段的退出条件，是找到 problem-solution fit。也就是说，在开始构建解决方案之前，你已经建立了定性证据，主要来自真实的人类对话，证明你正在为真实的人解决真实问题。

当你能够对以下三个问题都回答「是」时，就可以离开构想阶段：

1. 这个问题是否真实且具体？要肯定回答这个问题，你必须能够准确说出谁经历这个问题、他们多频繁遇到它、它对他们造成多严重影响，以及他们现在如何处理它。
2. 你的解决方案是否解决了真正的问题？不是你最初假设的问题，而是验证过程揭示出来的问题。有时两者相同，但并不总是如此。
3. 你是否有足够信号来证明值得构建？在这个阶段你永远不会拥有确定性，等待确定性本身也是一种失败模式。但你需要足够的定性证据，让投入 MVP 成为一个经过推理的决定，而不是信仰行为。

### 构想阶段挑战

构想阶段是创业旅程中最重要的工作发生的地方，因为最具后果的问题也往往在这里犯下：现在犯错，可能很快让刚刚萌芽的创业项目脱轨。不过，构想阶段的大多数挑战，都来自行动速度快过理解速度。因此，带着思考和审慎推进的创始人，通常会获得稳定进展。

### 把构建误认为验证

挑战：当技术阻塞被移除，充满激情的创始人就有风险跳过创业旅程中最重要的工作：验证自己的想法确实是人们需要并会使用的解决方案。

即使在当前 Agentic coding 时代之前，也有 42% 的创业公司失败，是因为它们构建了没人想要的东西。现在，像 Claude Code 这样的 Agentic coding 解决方案大幅压缩了「我有一个想法」和「我有一个产品」之间的距离，这个失败率只会继续上升。

对于一个有着好到让神经元震颤的想法的创始人来说，现在从未如此适合创业。但反直觉的是，快速、轻松地启动一个看起来像产品的原型，也为 AI 原生创业公司带来了真正危险的生存风险。

直到最近，构建还需要真实的开发时间和预算，即使做出一个基础原型通常也要几个月。现在技术开发门槛基本消失，AI 让创始人太容易跳过现实世界效用验证，直接进入构建。

要达到 problem-solution fit，必须先验证假设，再开始构建。但很多第一次创业的创始人，甚至一些有经验的创始人，会错误地认为 AI 可以绕过这个要求，把流程变成：有一个想法 → 立刻构建一个原型 → 把原型存在本身当作验证。原型变成了相信假设一直正确的理由，而没有真正测试它是否为真。

一个能跑的原型很容易被误认为你正在解决真实问题的具体证据，但它不是。你的原型更适合作为一个有用的压力测试道具，用来和潜在用户对话。真正的证据，是这些对话本身。

### 过早规模化

挑战：当构建变得轻松且即时，你可能会让执行规模远远跑在业务需求之前。

过早规模化，意味着在还没有真正验证某条产品路径是否值得投入之前，就已经承诺走上这条路径。

这一直是创业公司的杀手，但 AI 让创始人更容易在毫无察觉的情况下落入过早规模化陷阱。Agentic coding 助手能力太强，以至于你可以在没有验证 problem-solution fit 的情况下，让执行速度大幅领先，而且自己并没有意识到已经偏航。

它会围绕一个根本错误的前提生成、测试、调试和重构代码库，并且热情与面对一个伟大想法时完全一样。系统中的智能来自你。这个阶段的最高指令，是让你的 sense-making 始终领先于你的 building，尤其是在构建如此快速、感觉如此轻松的时候。

### 失去客观性

挑战：如果你让 AI 工具寻找支持你既有信念的证据，它就会找到。确认偏误现在配上了一台研究引擎。

确认偏误一直是创业中的职业风险：创始人天生对自己的想法充满热情。现在，AI 工具给确认偏误加了一个强力外挂。让 AI 验证你的创业想法，它会找到支持证据；让它测算你的潜在市场，它会找到一个让 TAM 看起来适合融资的数字。

AI 会遵循你的方向。这意味着，如果创始人不提出尖锐问题，现在可以比以往更快地为一个坏想法构建出一套复杂、看起来研究充分的论证，同时还完全相信自己确实在做尽职调查。解药是同一个工具，只不过要把它指向相反方向：AI 同样可以彻底压力测试一个想法，就像它可以验证一个想法一样。

当研究和结构化的反向思考浮现出你的想法需要修订的证据时，这就是该 pivot 的信号。

### Claude 如何帮助构想阶段的创始人

推动一个 AI 原生创业想法走过构想阶段，可能会让人觉得永远看不到头。你是创始人，你只想构建。但这个极其重要的起步阶段，本质上是研究和验证练习，所以你应该先使用那些能帮助你更严谨思考的工具，然后再全力写代码。下面是如何在 Claude 的不同产品表面中使用 Claude，包括 Chat、Claude Cowork 和 Claude Code，以尽可能快、同时又尽责地走过构想阶段。

### Chat、Claude Cowork 或 Claude Code：选择正确的 Claude 表面

AI 让创业创始人更容易更快发货、自动化琐碎工作流，并以更大规模运营。但你使用哪个表面很重要。下面是根据任务选择 Chat、Claude Cowork 或 Claude Code 的方式。

Chat 适合在不离开当前应用的情况下做快速交换。用它处理公司运营中持续不断的小任务：从一份密集的投资人 memo 中提取一句话 takeaway，在董事会会议前 sanity-check 一个论断，或者理解团队里一条很长的 Slack 讨论串。

Claude Cowork 适合真正耗时的知识工作：从多个来源抓取信息，理解它们，并产出一个完成品，比如文档、deck 或 spreadsheet。可以把它想象成：把一文件夹客户访谈记录转成下一次产品评审用的主题发现文档；在融资前从十几个供应商网站构建竞争格局；或者设置一个每周一早上的固定任务，从连接的工具中拉取指标，并把每周 KPI brief 放进共享文件夹。

Claude Code 是给团队工程师使用的 Agentic coding 环境：直接访问代码库、Plan Mode、git 集成，以及本地、IDE 或沙箱云环境。精益团队在这里跨一个不断增长的代码库交付功能，把 MVP 时代遗留代码迁移到新架构，并在不等待更多人手的情况下，从原型走向生产。

| 如果任务是 | 选择 | 原因 |
|---|---|---|
| 一个问题、一次改写、一次快速 brainstorm | Chat | 快速、对话式、无需设置 |
| 基于你的文件和系统完成研究、分析或正式文档 | Claude Cowork | 文件夹访问、连接器、skills、定时运行 |
| 编写、测试或交付软件 | Claude Code | 代码库访问、diff、git、开发环境 |

三者底层使用的是同一个 Claude；变化的是围绕它的工作空间。

### 定义并压力测试问题假设

你自己的领域专业知识和前期研究，已经生成了一个假设。第一项工作，是把它打磨到真正可测试。Claude 在这里特别有用，因为它能迫使你具体化：到底是谁有这个问题？多频繁？多严重？他们现在如何处理？一个不能精确回答这些问题的问题陈述，还没有准备好进入验证。

- 练习：和 Claude 一起打磨你的问题陈述，直到它成为一个可测试假设。例如，「合同审查太慢」并没有可测试性。但「中型企业的法务团队每个合同审查周期要花 3 天以上，因为 redline 分散在邮件线程中，而不是集中在一个带版本控制的文档里」，就是高度可测试的。

你的下一步，是让 Claude 反驳你的想法，并寻找能够否定你假设的反证证据。这可以浮现负面的市场信号、失败的竞争对手、客户行为模式，以及那些支持性综合分析可能悄悄降权的结构性障碍。

目标是：在进入客户发现之前，你已经用最强的可得反论压力测试过自己的假设。这样，信息型用户访谈才会真正开放，而不是变成寻找确认的过程。

注意：把 Claude 用作结构化反方，是 AI 创业生命周期每个阶段的核心用例。

### 市场研究与竞争格局映射

#### 评估你的竞争对手

创业中有一个特有现象叫 competitor neglect：你过度聚焦自己的愿景和执行，以至于系统性低估同一空间里其他人在做什么。幸运的是，AI 提供了解药：让 Claude 给出一个最有力的论证，说明为什么这个解决方案空间中的某个竞争对手会成功，而你不会。

Claude 可以分析为什么他们的方法其实更好，为什么客户会选择他们，以及为什么你潜在的差异化可能没有你想象中那么防御性强。

- 练习：让 Claude 按层级绘制你的竞争格局：直接竞争对手、间接竞争对手、潜在收购方，以及可能进入你所在空间的相邻玩家。然后让它论证为什么每一层都对你的成功构成真实威胁，而不是只讨论那个最容易被你驳回的威胁版本。

#### 市场研究

Claude Code 可以综合公开可得的客户反馈，浮现反复出现的抱怨和未被满足的需求。额外好处是：这基本等同于免费对竞争对手客户进行定性研究。

- 练习：指挥 Claude Cowork 综合你关键来源中的竞争对手评论，并识别现有解决方案尚未解决的主要抱怨。如果你的假设解决其中一个或多个问题，那就是 problem-solution fit 的强证据。如果没有，这同样值得知道。

Claude Cowork 还可以从密集的行业报告、分析师文件和市场研究文档中提取相关信息和数字。随后，这些干净、综合后的输入，会成为 Claude 做分析工作的理想上下文。

- 练习：基于公开数据构建 TAM/SAM/SOM 模型，并压力测试背后的假设。识别市场是在扩张、整合还是成熟；这个上下文会影响你如何思考时机和差异化。映射买方格局：谁掌握预算，谁影响决策，以及这两者是否是同一个人。

#### 趋势分析

最后，用 Claude 倾听那些能告诉你是否在正确时刻进入市场的早期指标。跟踪与你的问题相关讨论已经发生的 subreddit 和 LinkedIn 群组，以及用户描述自己问题时使用的具体语言。让 Claude 识别解决过类似问题的相邻市场，并提取哪些做法有效、哪些无效。浮现那些可能加速或威胁机会的监管、技术或人口结构趋势。

- 练习：让 Claude 识别三条外部趋势，监管、技术或人口结构均可，这些趋势可能在未来两年显著影响你的市场；并评估每一条趋势对你的具体假设是顺风还是逆风。

注意：本节的市场研究和竞争映射不是一次性练习。你会在 MVP 和发布阶段继续发现新东西、演化自己的思考。因此，每当你的假设演化时，都要重复这些练习。

### 规划并设计客户发现

通过与潜在产品用户交谈，你能学到什么，取决于两件事：你问的问题质量，以及你是否把这些问题问给了正确的人。Claude 对客户发现特别有帮助，包括该找谁聊、该问什么、以及如何理解你听到的内容。

#### 找谁聊

一个精确的目标画像，远比一长串联系人列表更有价值。它应该包括最可能强烈经历这个问题的具体职位、公司类型、团队结构和资历层级。然后，识别这些人实际能在哪里被触达，包括他们聚集的社群、活动、LinkedIn 群组和 Slack workspace。再基于他们与问题的接近程度，构建一个先联系谁的优先级框架。

#### 问什么

目标确定后，用 Claude 构建访谈框架本身：正确的问题、正确的顺序，以及能够浮现人们实际行为，而不是他们认为自己将来会怎么做的结构。新手创始人的常见错误，是提出一个泛泛的、面向未来的开放问题，比如「你会用这样的东西吗？」而不是具体追问相关的过去：「告诉我上一次你处理这个问题是什么情况。」

Claude 还可以标记你的草稿问题哪里在引导受访者、哪里太宽泛，或者哪里更可能产生噪声而不是信号。Claude 也可以帮助你设计追问，用来探查回避，或深入挖掘重要问题上的模糊回答。

如果你的假设涉及不止一个 persona，Claude 还可以为每个 persona 设计不同的问题组。财务经理和 CFO 对同一个问题的关系不同，单一访谈框架会抹平这种差别。

- 练习：先手写你的访谈问题，然后让 Claude 审核。请它专门标记任何引导性、面向未来、过于宽泛，或可能诱导出社会期望答案而不是诚实答案的问题。然后让它为访谈中最可能产生回避的两三个时刻，建议后续追问。

#### 访谈后分析

每次对话后，用 Claude 做 debrief：把你的笔记喂给它，让它识别哪些内容确认了你的假设，哪些内容挑战了它，哪些内容真的令人意外。当你收集到一批访谈后，把完整访谈笔记交给 Claude Cowork，让它浮现反复出现的主题、矛盾，以及正反两个方向上最强的信号。然后把综合输出拿回 Claude，请它标记你对数据的解读哪里可能是在按自己想听的东西做 pattern matching，而不是在读真实存在的东西。

- 练习：每完成五次访谈后，指挥 Claude Cowork 综合你的笔记并产出两张清单：支持你假设的证据，以及挑战你假设的证据。如果第一张清单明显长于第二张，请让 Claude 判断这种不对称反映的究竟是数据本身，还是你希望找到的东西。

### 客户外联与日程安排

用 Claude Cowork 自动化构建联系人列表、开展外联和安排用户访谈的运营负担。

Claude Cowork 可以使用你和 Claude 定义的目标画像，包括职位、公司类型和资历层级，研究并编制结构化的潜在受访者列表和经验证的联系方式。然后，它可以批量起草个性化外联邮件，根据每个人的角色和上下文定制内容。随着回复到来，它可以通过 MCP 连接 Gmail 和 Google Calendar，管理邮件线程、处理排期请求，并把访谈放进日历。工作流还会继续：Claude Cowork 可以按既定节奏生成 follow-up 草稿，例如给未回复联系人发第 7 天跟进，并在每一步完成时更新你的追踪表，让你始终知道每个 prospect 在 pipeline 中处于什么状态。

- 练习：把你已经验证过的访谈目标画像交给 Claude Cowork，让它构建 prospect 列表、起草个性化外联序列，并设置一个 tracking sheet，包含外联状态、follow-up 节奏和访谈完成情况等列。然后让它运行协调工作，而你专注准备对话本身。

### 设计最终解决方案概念

你已经完成了验证工作：问题是真实的，你知道谁有这个问题，也有一个被证据支持的解决方案概念。用 Claude 从各个角度发展并挑战你的解决方案概念：缺口在哪里？有哪些替代方案？这个方案要在规模化后仍然成立，必须满足什么条件？

这是一个重要的现实检查点：这个设计是否真的解决了验证过程揭示的问题，而不是你最初带着进入验证的问题？

- 练习：把你的解决方案概念交给 Claude，请它识别这个设计最依赖的三个假设。然后问它：每个假设要成立，必须满足什么条件？如果其中任何一个不成立，后果是什么？

### 用 Claude Code 构建轻量原型

现在到了有趣的部分：有了经过验证的假设和压力测试过的解决方案概念，你终于准备好构建点什么。

这是构想阶段里 Claude Code 正式登场的时刻。即使你此前一直在 tinkering，现在才是生成官方轻量原型的节点：一个最小表面积，足以把你的想法放到真实人类面前，并获得真实反应。

你还不是在构建真实世界产品；你是在构造一个功能样本，用于客户和投资人对话。真实用户与他们真正能触碰的东西互动，会告诉你十几场 problem-solution discovery 访谈都无法告诉你的事情。之前，你是在确认自己解决的问题是真实的；现在，你是在邀请潜在用户接触你提出的解决方案。

- 练习：定义你的解决方案最依赖的那个单一核心交互。指挥 Claude Code 只构建这个。当你拥有它后，把它放到你已经验证过的目标画像中的五个人面前，让他们试用。你在这五场对话中学到的东西，会决定你继续构建，还是回到画板。

走到构想阶段的终点，是 AI 创业竞赛中的一次巨大跃迁。因为你现在不再押注直觉，而是在依据证据执行。接下来是 MVP 阶段。在这里，创始人的引导问题会从「这值得构建吗？」变成「我们究竟应该先构建什么？」而 AI 的主要角色，也会从研究伙伴转向施工队。

## 第 4 章：MVP 阶段

很多创始人把 MVP 阶段当作建设阶段，但 MVP 阶段本质上仍然是证据收集练习。区别在于，你现在收集的是关于解决方案的证据，而不是关于问题空间的证据。具体来说，你要验证的是：是否存在一个真实、可识别的人群，认为这个解决方案足够有价值，值得使用、再次使用、付费，或者告诉别人。

### MVP 阶段目标

作为 AI 原生创业公司的创始人，你的目标是把已经验证过的问题转化为一个真实用户会实际使用的工作产品。这不是包含路线图上所有功能的完整版，而是你想法中最小、最聚焦的一次迭代：把真实解决方案放到真实用户面前，并生成关于 product-market fit 的真实证据。

与此同时，你现在如何构建，会决定以后什么是可能的。这意味着 MVP 阶段有第二个同等重要的目标：在快速推进的同时，不累积那种会复利增长、并在真实用户大规模到来时立刻困扰你的技术债。

最后，从第一天起投资持久上下文，是让 AI 保持为 force multiplier，而不是变成熵源的关键。在 AI 原生创业公司中，代码库是你一轮又一轮 session 与 AI 协作的对象，因此可读性是基础。跳过 spec、架构决策和上下文文件（例如 `CLAUDE.md`）的创始人，会遇到一个可预测的墙：每个新 session 都要重新解释代码库，而且 AI 生成的修改会逐渐偏离最初愿景。

### MVP 阶段退出标准

MVP 阶段的退出条件是真正的 product-market fit 证据：证明某个具体、可识别的用户群体，认为产品有足够价值，愿意回访（留存）、付费（收入），或者告诉别人（推荐）。

### MVP 阶段挑战

在 MVP 阶段，创始人的最高指令是速度和判断力。这里的挑战集中在：你能否足够快地构建正确的东西、以正确方式构建，并且不偷那些以后会付出代价的懒。

### Agentic 技术债

挑战：AI 本质上移除了过去控制哪些东西能进入生产环境的所有自然瓶颈，因此速度已经被保证。但当速度成为创始人在 MVP 构建中唯一考虑的变量时，他们会冒着累积难以偿还的技术债的风险。

MVP 阶段有些技术债是合理的，前提是你理解它必须在规模化前被管理。传统技术债通常逐渐积累，可以随着时间清理，或者在一次专门 sprint 中清掉。但 AI 技术债会复利增长。

如果没有把 spec 和架构约束写在 AI 能读到的地方，每个 session 都会从零重新推导基础决策，而这些决策会漂移。最后你得到的是一个背后没有一致 mental model 的代码库。问题不在于单个片段都坏，而在于这些片段从未被设计成能够相互配合。这是真问题，而且往往会很晚才暴露。

### 被虚假的 product-market fit 迷惑

挑战：AI 工具可以生成令人印象深刻的早期数字，但这些数字并不保证市场需要你的产品。

早期动能是创始人能经历的最强心理体验之一。经过数周或数月的验证工作和谨慎、有纪律的构建后，发出一个产品会让人感觉像是在确认：你从一开始就是对的。

Agentic coding 工具可以帮助你比以往更快到达这个时刻，但早期 traction 并不等于 product-market fit。发布能量可能来自一些短暂因素，例如创始人的朋友、投资人其他 portfolio company 中的潜在买家，或者 Hacker News 头条带来的峰值流量。不幸的是，这些都不能可靠预测第六周或第十二周会发生什么，尤其是在最初 boost 消退后。

### 零摩擦 scope creep

挑战：当构建感觉毫不费力、成本近乎为零，总会有一个很酷的新功能可以加，或者还有一个边缘情况可以处理。这种 scope creep 可能弊大于利。

Scope creep 一直是创业风险。现在的区别在于，过去制衡它的传统 forcing function，也就是真实的工程时间成本，在「加一个功能只要一个下午而不是一个 sprint」时，已经不再以同样方式存在。

这里的挑战是，每一个单独的新增项看起来都站得住脚。产品当然应该处理那个边缘情况；用户当然会想要那个工作流。由于使用 Agentic coding 构建每一项都几乎不费力，它们在当下并不像 scope creep。但当你的产品蔓延到原有边界之外，你会冒着失去方向和动能的风险。

解药是在构建开始之前写下 scope definition：产品做什么，故意不做什么，以及来自真实用户的哪些具体证据，能够证明此刻应该新增东西。这会把决策点从「我们要不要构建这个？」移到「已经有足够多关键用户告诉我们，没有这个他们无法从产品中获得价值」。

### 由于缺乏经验而不安全

挑战：创始人使用 AI 工具匆忙把应用推向市场，却没有先理解基础安全原则，最终会让用户暴露在本可避免的风险中。

一个严酷事实是：Agentic coding 工具生成的是能工作的代码，而不是天然安全的代码。功能代码很容易判断，因为功能要么能用，要么不能。安全漏洞在被利用前是不可见的，这意味着没有自然反馈回路告诉第一次创业的创始人哪里出了问题。然而，把一个 live MVP 发给真实用户，意味着真实数据、真实暴露面，以及出问题时的真实后果。

忽视安全并不是 AI 原生项目才有的新问题。各个时代的 bootstrapped startup 都常常把安全考虑推迟到构建后期，有时甚至等到生产发布前夕。任何用户接触你的 app 或解决方案之前，进行一次安全审查，是把最低可行产品发布到世界上所需的最低负责门槛。

### Claude 如何帮助 MVP 阶段的创始人

#### 构建前先定义架构

在 Claude Code 写下第一行生产代码之前，先用 Claude 定义并记录会支配这个阶段所有构建工作的架构决策：要遵循的模式、要避免的依赖、正在做出的 tradeoff 以及原因。这个输出会成为一份聚焦的架构上下文文档，并建立 Claude Code 将在其中运作的护栏。

没有这个上下文，每个 session 都会从零开始，Claude Code 被迫推断自己的结构性假设。让 Claude Code 在没有护栏的情况下构建，会产生一个功能可用但结构不一致的代码库。迭代和扩展这种不一致的代码库，本质上是在浪费时间和 token。迟早会到某个点，代码不可避免地崩塌，迫使你从头重建。

- 练习：在打开 Claude Code 之前，先打开 Claude，并描述你要构建什么：它解决的核心问题、服务的用户，以及你现实预计未来六个月的规模。让它帮助你定义应当支配 MVP 构建的架构原则、在当前约束下应避免的依赖，以及你在这个阶段有意识接受的 tradeoff。

接下来，把这个输出保存为 `CLAUDE.md` Markdown 文件。这是你的架构上下文文档：构建的第一个 artifact，也是后续每个 session 依赖的 artifact。`CLAUDE.md` 文件作为 Claude Code 的项目级指令，提供项目特定的上下文和指令，并在 Agent SDK 于某个目录运行时被自动读取。在功能上，它们就是项目的持久「记忆」。

#### 定义并执行 MVP scope

无摩擦的 scope creep，是 AI 时代 MVP 的典型失败模式之一。正如你定义并记录了产品的应用架构，也需要在任何功能被构建之前，定义 MVP 的 scope。

Claude 可以帮助你创建一份 scope 文档，描述你的 MVP 产品做什么、明确不做什么，以及 feature amendment criteria：此时来自真实用户的哪些具体证据，可以证明值得新增某些东西。

当新功能想法出现时，而且它们一定会出现，你可以用 Claude 压力测试：这究竟是真正来自用户的信号，还是披着产品思考外衣的创始人热情。

#### 用 Claude Code 构建你的 MVP

一旦架构和 scope 被定义，Claude Code 就会成为主要的 MVP 构建工具。用它生成、测试、调试并迭代你的代码库，但要把每个 session 视为执行你已经做出的产品决策，而不是趁机丢进一些新的决策。

每次 Claude Code session 开始时，先做两件事：回看你的 scope 文档，并向模型提供你的 `CLAUDE.md` 架构上下文文档。每次 session 结束时，用本次 session 浮现出的任何决策更新它。目标是得到一个你能解释其结构的代码库，而不只是一个能跑的代码库。

- 练习：为你的 Claude Code 工作创建一个简单 session 模板，其中包括架构上下文文档、本次 session 的具体任务，以及要遵守的任何约束或模式。在每次 session 结束时，在上下文文档中增加一条简短日志，详细说明构建了什么、做出了什么决策、引入了什么假设。每次 session 花五分钟写文档，是防止架构漂移复利增长成不可管理代码库的廉价保险。

#### 任何用户接触前先做安全审查

作为 AI 原生创业公司的创始人，你有责任知道代码库里有什么，理解任何潜在暴露向量，并且不要把明显漏洞交付给用自己的数据信任你的真实用户。

Claude 可以对 AI 生成的代码做有用的第一轮安全审查，并帮助识别常见漏洞。在发货之前，把它纳入循环是一个好习惯。不过，它不能替代安全工具，或在更高风险情境下替代人类审查者。把它当替代品的创始人，往往会成为 breach story 的主角。

Claude Code Security 更进一步：它扫描代码库中的安全漏洞，并为人类审查提出有针对性的补丁，浮现传统方法可能漏掉的问题。

注意：在本电子书发布时，Claude Code Security 仍是 limited beta，因此在把它纳入工作流之前，要检查当前可用性。

- 练习：在部署给任何真实用户之前，用一个具体 brief 让 Claude 审查你的核心应用代码：检查认证与 session 处理、API 响应中的数据暴露、输入校验与注入风险，以及有已知漏洞的依赖。认真对待每一项发现，并评估是否需要修复。任何涉及认证、密钥或数据处理的内容，都应有人类审查。

#### 发布前先构建度量框架

那些把早期 traction 误判为 product-market fit 的创始人，通常也是那些在发布后才开始跟踪数据的人，而且他们选择的指标往往用于评估什么在起作用，而不是浮现什么没有起作用。解药是在第一个用户出现之前建立度量框架。

用 Claude 定义对你的具体产品而言哪些指标重要、基准是什么，以及数据中什么模式构成真正的 product-market fit，而什么只是好看的噪声。具体来说，在发布 MVP 之前就设定留存基准、激活标准，以及 Day 7 和 Day 30 目标。

接着，为你的具体产品定义 false positive 长什么样：例如有注册但没有激活，有收入但没有留存，或者有初始热情但没有重复使用。当数据到来时，让 Claude 站在反方论证你的 traction：怀疑者会如何解读这些数字？

#### 管理 discovery 与用户反馈物流

一旦真实用户进入产品，运营层会迅速膨胀。Claude Cowork 可以处理重要但繁琐的工作，比如构建并维护用户联系人列表、运行外联序列、安排反馈 session、分诊 bug 报告，以及跟踪迭代周期。构想阶段管理 discovery 物流所用的那些 MCP 集成，在这里同样适用。

对于需要细致探索的用户反馈，要让人类留在采集循环中。例如，用户说「这个很好，但我希望它也能……」，这需要解释：这是核心需求还是 nice-to-have？这是这个客户特有的，还是代表某个 segment？缺失的功能是真问题，还是 onboarding 上游出了问题？没有工具能替你回答这些问题。

- 练习：配置 Claude Cowork 运行你的 MVP 阶段反馈循环：向早期用户列表起草外联、安排反馈 session、设计 bug 报告和功能请求的结构化 intake 流程，并每周写一份进入信息的综合摘要。先由你自己审阅摘要；之后，你可以让 Claude 分析这些信息，捕捉你可能漏掉的重要点。

#### 向证据迭代，而不是向完整性迭代

MVP 阶段在你拥有真正 product-market fit 证据时结束，而不是在产品感觉「完成」时结束。宣布你已经达成 product-market fit，可以从 MVP 阶段进入发布阶段，本质上是一项判断练习，它结合了创始人直觉和收集到的证据。不过，有一些有用的试金石：

- Sean Ellis test：问你的活跃用户：「如果你不能再使用这个产品，你会有什么感受？」如果超过 40% 的人回答「非常失望」，那就是一个有意义的 PMF 指标。
- effort test：在 product-market fit 之前，留存需要持续干预，包括频繁外联、激励、个人跟进，以及创始人花费英雄式精力维持用户参与。Product-market fit 之后，产品开始自己做这些工作。当事情开始从「推」变成「拉」，这种努力方向的变化就是最清晰的信号之一：某些真实变化已经发生。

最终，没有任何单一数据点能确认 product-market fit，因为它必须在多个迭代周期中持续成立，你才能明确说它存在。

#### 当证据要求时 pivot

如果即使投入了所有这些工作，你仍然无法到达 product-market fit 呢？你的结果没有确认最初方向，并不是失败，而是系统在正常工作：MVP 阶段的目的，就是在你过度投资错误答案之前，浮现这类信息。

当数据不支持你当前产品时，用 Claude 梳理这些数据正在告诉你什么。

- 探索替代客户 segment。也许那些没有转化的用户，一开始就不是正确目标。正确受众往往已经在你的数据中，只是权重不足。
- 调整产品 value prop。也许你有正确受众，但 MVP 没有与用户产生共鸣。调整 onboarding、messaging 或核心功能强调，可能在不改变已构建内容的情况下解决问题。

也要保持开放：这种断裂可能足够深，需要更根本的改变。

- 练习：如果你已经完成三个或更多迭代周期，却没有向 product-market fit 基准产生有意义进展，在决定下一步之前，用 Claude 做一次诊断。把留存数据、用户反馈和最初的问题假设交给它，并问三个问题：
  - 这些数据中是否有某个 segment 的反应与其他人不同？
  - 设计价值与体验价值之间的差距，是 positioning 问题还是产品问题？
  - 当前产品要找到真正 PMF，必须满足什么条件？根据你看到的情况，这个场景现实吗？

让答案决定你是调整、pivot，还是回到构想阶段。

## 第 5 章：发布阶段

如果 MVP 阶段是证明你的产品值得存在，那么发布阶段就是证明你的业务值得增长。

### 发布阶段目标

在发布阶段，创业创始人必须把早期 traction 转化为可重复、可持续的增长引擎。除了让产品 production-ready，你还必须加固其下方的基础设施，同时围绕产品构建一家真正的公司。

在构想和 MVP 阶段，创业公司天然以创始人为中心，因为你需要完整的情境感知和紧密反馈回路。但现在，如果创始人仍然试图亲自握住每一条线，他们就会成为发布阶段瓶颈。目标不是把你自己从公司中移除，而是构建运营系统，释放你的注意力，让它用于只有创始人才能做的决策。

### 发布阶段退出标准

发布阶段的退出条件有三个要素：

1. 增长是可重复且由渠道驱动的。你不只是留住用户，还能通过具体渠道可预测地获取用户，并且理解 unit economics：CAC、LTV 和 payback period 是你知道且能捍卫的数字。
2. 产品能承受生产负载。基础设施已经加固，安全和合规到位，可靠性在真实生产条件下成立，而不只是你测试过的条件下成立。
3. 运营不再依赖创始人作为瓶颈。流程存在，自动化到位。你不再是那个亲自处理支持、分诊、sprint planning 或 reporting 的人。

### 发布阶段挑战

找到 product-market fit 是早期创业生命周期中最难的问题。现在，创始人的挑战变成了保住它。发布阶段是一个节点：即使公司已经找到真实产品 traction，如果围绕并支撑产品的组织跟不上，它仍然可能崩塌。下面是需要警惕的失败模式。

### 技术债到期

挑战：为速度和验证而构建的 MVP 代码库，足以证明产品能工作。但生产流量、新功能和不断增长的复杂性，正在暴露之前的捷径。

在 MVP 阶段，累积一些技术债是为了速度作出的合理 tradeoff。到了发布阶段，这些债开始计息，而且拖得越久，修复成本越高。

解决方案包括：系统性架构审计，以识别结构性弱点；针对性重构，解决最糟糕的问题；以及有意义地扩展测试覆盖，让下一轮功能工作不会重新引入同样问题。

### 创始人成为瓶颈

挑战：在 MVP 阶段，创始人在每个循环里都是资产。到发布阶段，随着支持量增长、产品决策堆积、运营复杂性倍增，同样的本能会变成约束。

从亲自做工作，转向设计做工作的系统，是创业生命周期中最困难的转变之一。因为很少有一个明确时刻告诉你它已经发生，风险就在于你完全错过它，并在组织围绕你停滞时仍然待在 builder mode。

一些正在发生这种情况的典型信号包括：本来一小时能做的决定，现在要等你一周才轮到；支持请求堆积，因为只有你知道答案；运营任务只有在你本人想起来时才发生。

补救办法是对你亲自处理的一切进行彻底审计，从最小任务到最高风险决策，识别什么可以系统化、什么可以委派、什么确实仍然值得创始人投入时间和注意力。

### 安全和合规不再能推迟

挑战：MVP 阶段保持安全和合规措施简单还可以接受，但现在，有了真实用户、真实数据，甚至潜在企业合同摆在桌上，它就会变成负债。

在 MVP 阶段，只有少数 beta 用户，生产环境里没有敏感数据，安全漏洞还是理论风险。但当你的产品进入生产环境，并有真实用户依赖它时，这个假设就会变成非常真实的暴露风险。此外，原型阶段不适用的合规要求，一旦你处理客户数据、处理支付，或卖进受监管行业，就必然适用。

补救办法是在生产规模到来之前，而不是之后，进行系统性安全和合规审查，并把浮现出来的所有问题都当作下一波用户到来前必须完成的整改，而不是建议。

### 准备好之前就扩张

挑战：新市场和融资机会看起来像增长机会。但它们也可能是 product-market fit 死去的地方。

你已经建立的初始 traction 是真实的，但它也特定于你的早期受众。太早扩张到一个与原始市场有实质差异的市场，会引入新的用户行为、合规要求、支付基础设施和基线预期，而你的产品并不是围绕这些设计的。突然之间，新变量太多，你会失去清晰解释自己数据的能力。你也会在追逐一个未经验证的新受众时，忽视原有用户基础。

### Claude 如何帮助发布阶段的创始人

在发布阶段，三种 Claude 形式都会被充分使用，并且相互支持：每个工具的输出都会成为另外两个工具的输入。结果会自然复利。把三个工具一起使用的创始人，得到的不只是各部分之和。

这正是超精益创业模型在结构上成为可能的原因。当 Claude Code 构建产品，Claude Cowork 构建围绕产品的公司，而 Claude 帮助把产品知识和组织知识 operationalize，一个小团队就可以像数倍规模的公司一样运转。

#### 在技术债复利增长前修复它

你的 MVP 代码库能工作，但它也需要一次系统性的修复扫描，寻找任何可能变成结构性负债的技术债。

首先，用 Claude Code 运行一次完整架构审计：识别代码库哪里脆弱，哪些捷径会变得昂贵难维护，哪里测试覆盖太薄，以至于下一轮功能工作会重新引入同样问题。

把 Claude Code 的审计发现喂回 Claude，让它分诊并排序修复工作：哪些必须在下一次 release 前修好，哪些可以等一个 sprint，哪些在你当前阶段属于可以接受的持续债务。

这也是记录你在 MVP 阶段做出的架构决策的时刻，那些因为没时间写下来而一直存在你脑子里的决策。现在把它们写进 `CLAUDE.md`，可以确保未来每个 Claude Code session 都从一个共享理解开始：系统是如何设计的，以及为什么这么设计。

- 练习：指挥 Claude Code 审计你的 MVP 代码库，并产出一份按优先级排序的结构性弱点、测试覆盖缺口和重构候选清单。然后把这份清单交给 Claude，请它把修复工作安排到接下来几个 sprint 中：哪些重大问题要先处理，哪些可以和功能开发并行，哪些可以等待。

#### 构建替代创始人注意力的系统

要构建那些能释放你注意力、让你处理只有创始人才能承担责任的运营系统，首先需要准确知道你的注意力正在流向哪里。用 Claude Cowork 对当前运营负载做一次结构化审计：记录每个重复任务、每个落到你桌上的决策，以及每个只有因为你本人记得才会发生的工作流。然后让 Claude Cowork 把这个 inventory 分类：哪些可以完全自动化，哪些需要人但不一定是你，哪些确实需要创始人判断。

审计完成后，用 Claude Cowork 为自动化候选设计工作流逻辑：每个工作流由什么触发，决策规则是什么，输出长什么样，完成后流向哪里。

#### 把安全和合规做成产品工作流

用 Claude Code 浮现代码层面的问题，这些问题经常出现在 SOC 2、GDPR、HIPAA 审计中，或出现在目标市场要求的标准中。这会同时浮现漏洞和合规缺口。把这些发现交给 Claude，帮助你排序修复工作，并设计企业买家在签约前会询问的控制措施、审计日志和访问管理。注意：AI 扫描是辅助，不是合格合规审查的替代品。

接着，把合规工作流纳入你的开发周期，而不是把它当成一次性项目；合规文档需要持续维护和更新。对于正在接近企业合同或国际市场的创始人来说，这也是 Claude Code 安全扫描可以帮助你准备独立安全评估的时刻。

- 练习：用 Claude Code 做一次代码层安全审查，面向你的目标市场所需框架。把输出交给 Claude，请它产出两件事：一份按优先级排序的安全修复序列，以及一份文档和控制清单，说明你需要准备什么，才能满足潜在企业买家的合规审查。

#### 建立你一直跳过的产品管理流程

发布阶段需要一组轻量、可重复的流程，它们无需创始人介入就能被触发并运行。用 Claude 设计你的产品时间线和工作周期如何组织，一个 spec 在 Claude Code 触碰功能前必须包含什么，bug 报告如何分诊和路由，每周指标报告覆盖什么，以及如何分发。

流程设计完成后，用 Claude Cowork 构建并运行运营层：安排 sprint 仪式，把进入的 bug 报告路由到正确位置，从连接的数据源汇总每周指标，并维护把用户信号持续带入产品决策的反馈回路。

- 练习：让 Claude 设计一个轻量产品管理操作系统：明确的 sprint cadence、最小 spec 模板、bug 分诊决策树，以及一份从实际数据源拉取数据的每周 metrics brief。然后设置 Claude Cowork 去实现并运行系统中的重复运营元素，例如排期、路由和报告汇总，让它们在没有你的情况下按时发生。

## 第 6 章：规模化阶段

在规模化阶段，创始人的角色会从 builder 重新定位为面向公众的 executive。产品仍然是核心，但你个人每天的工作会越来越围绕公司本身展开。即使你努力保持精益、AI 中心化的结构优势，你的注意力也必须扩展到规模化阶段的新活动，例如分析师 briefings 和 IPO roadshow。

### 规模化阶段目标

扩展技术基础设施的工作仍在继续，同时加入了扩展组织本身、并把它成熟为一家真正业务的工作。

到规模化阶段，你面对的是从数千用户到数百万用户，从一个市场到多个市场。此前每个阶段，增长都可以靠贴近用户、根据紧密反馈回路中的数据加上健康的创始人直觉来摸索前进。但现在，目标是建立由成熟组织运营支撑的系统性增长。

对于 AI 原生创业公司，你的目标应当是通过累积深度建立防御性 moat。这种深度来自：你构建进产品里的专业知识、你的产品与用户依赖的其他工具和平台的深度集成，以及专有的系统数据和工作流。那些一直沿着一致方向、基于一致基础设施构建的创始人，现在拥有了真正难以复制的东西。

在这个阶段，公众投资人、分析师、监管者、企业采购团队和收购方会施加更大压力，也会带来更强怀疑，因为现在 stakes 更高。你的产品和组织必须经受外部审查：不仅是你构建的能力本身，还包括围绕它的治理、合规姿态、财务控制和战略叙事。

### 规模化阶段退出标准

规模化阶段的退出条件不再是单个里程碑，而是一个阈值事件：即使创始人越来越不直接运营日常工作，公司仍然可持续。你已经证明了系统性增长；构建了能够满足最严苛外部审查者的组织治理和合规基础设施；并且对这个问题有坚实答案：「如果一个资金充足的 incumbents 今天复制你的产品，你的用户会留下吗？」

实践中，这个阈值通常会采取三种形式之一：达到不再需要外部资本的规模化可持续盈利、准备好 IPO，或被收购。三者都要求你的增长是系统性且可审计的，你的产品 moat 经得起审查，你的组织在运营上成熟且可持续。

当这些成立时，就值得恭喜了：你的创业公司已经从一个 bet 变成一家 business。

### 规模化阶段挑战

#### 委派运营层

挑战：规模化阶段的运营系统，必须在没人盯着的情况下可靠、可持续地运行。对于从第一天起一直亲力亲为的创始人来说，这种转变不仅是结构挑战，也可能是心理挑战。

发布阶段的工作是创建系统；规模化阶段的工作变成两件事：第一，把这些系统成熟到完全值得信任；第二，真正信任它们。

这比听起来更难。即使你是一个擅长委派的创始人，也不总是显而易见哪些该交出去、哪些该留在自己盘子里。交得太多、太快，尤其是交给 AI 自动化系统，关键决策可能会在缺少只有创始人拥有的关键上下文时被做出。但如果抓得太久，你又会成为瓶颈。

这里的根本挑战，是识别那些只存在于创始人脑中或未文档化工作流中的机构知识，并把它们 codify 到有文档、可审计、可转移的系统中。

#### 扩展技术运营

挑战：客户不再只评估你的产品；他们想知道你的组织是否能成为可靠的基础设施伙伴。

创业前三个阶段的技术挑战集中在代码库：在不累积技术债的情况下构建正确解决方案，然后为真实用户加固安全和合规。到了规模化阶段，挑战变成代码库周围的一切：创建支持基础设施、文档和可靠性承诺，用它们传递成熟信号。

签多年期合同的大规模客户和机构买家会在签约前要求这些东西，一旦签约，他们也会用这些来约束你。

不过，帮助你走到这里的同一套 AI 基础设施，也能帮助你建立专门支持职能，定义响应时间，并提供新客户工程团队真正能使用的文档。

#### 扩展组织职能

挑战：规模化阶段的公司通常需要招聘、payroll、会计和法律运营等组织基础设施，不管实际有多少人在运行它。

在发布阶段，系统化运营意味着自动化那些消耗创始人注意力的工作流。到了规模化阶段，创业公司需要发展一组更广、更重要的运营职能，包括财务报告、合规监控、合同管理和客户支持，等等。

#### 构建 GTM 职能

挑战：有机增长有天花板。多数规模化阶段创始人会在自己真正构建 go-to-market 职能之前就撞上它。

构想、MVP 和发布阶段的增长，往往来自 founder-led selling：一次时机恰好的 Product Hunt 发布，或与早期客户的个人关系。这种有机增长只在一定点之前有效，多数创业公司会在规模化阶段触达这个上限。信号包括用户曲线趋平、客户获取成本上升，以及 pipeline 只有在创始人亲自参与时才推进。

规模化阶段的增长，需要构建一个专门的增长引擎，把你的产品带给新的、更广的受众。不过，多数创业创始人可能从未真正运行过 marketing、sales 和 analyst relations 这类项目。一套正经的 GTM motion 不只是建立新系统和流程，还要创造一种品牌声音和故事，说明你想如何谈论你的产品。因为在创业生命周期这个阶段，你不仅需要触达个人新用户，还需要触达投资人和企业买家这样的完整目标受众。

幸运的是，GTM 职能不必很大才能有效。同一套构建产品的 AI 基础设施，也可以 bootstrap 它的市场化。

### Claude 如何帮助规模化阶段的创始人

早期创业阶段把 Claude 用作产品本身的基础设施：验证想法的研究伙伴，设计和构建原型的工程团队，以及让单人创业公司成为可能的 AI 运营层。到达规模化阶段的 AI 原生创业创始人，现在可以用 Claude、Claude Code 和 Claude Cowork 以他们构建公司的同样方式继续扩张。

#### 把日常任务交给 Claude Cowork

以清醒视角开始规模化阶段：现在你最需要把时间和注意力投在哪里？对于从未建立过业务的第一次创业者来说，这可能是挑战。Claude 可以通过构建「这个阶段只有你应该做的事情」清单来提供帮助，这可能包括产品叙事决策、董事会关系、企业交易，以及 founder-to-founder 对话。不在这张清单上的任何东西，都是委派或 Claude Cowork 自动化的候选。

- 练习：用 Claude 产出你当前运营层的 bottleneck map：目前所有流经你的工作流、决策和审批。然后，让 Claude 推演当你一周不可用时，每一项会发生什么。那些停滞的工作流，就是你仍然足够 hands-on、足以让进展脱轨的地方。

这些如何映射到你用 Claude 制作的创始人优先级和职责 inventory？

接下来，是压力测试你已经构建的系统是否真的准备好随业务增长而规模化。

- 练习：用 Claude 映射你当前的工作流，然后问它当你一周不可用时，每个工作流会发生什么。那些停滞的工作流，就是 handoff criteria、escalation paths 或 exception handling 仍需要收紧的地方。Claude 可以帮助分析失败点，并推荐适当修复方式，让你根据需要更新或替换 Claude Cowork 自动化。

#### 将技术运营扩展为企业级基础设施

当你规模化时，买家需要确信你的产品和组织都可以作为长期基础设施被信任。代码库内部的技术工作照常继续，但现在也要处理代码库周围的技术工作。

第一步，是把机构知识转化为可扩展的系统。用 Claude 起草并维护企业采购预期看到的书面基础设施，包括产品文档、支持 playbook 和 SLA。

与此同时，指挥 Claude Code 审计并加固代码库，使其满足企业合同要求的具体可靠性和安全标准；并构建 Discord 社群式支持从未需要提供的技术支持基础设施：日志、监控、incident response tooling，以及让 SLA 真正可执行的 observability layer。

随后，Claude Cowork 运行企业支持本身的运营层：ticket 路由、升级工作流、由产品变化触发的文档更新、renewal tracking，以及企业客户成功所依赖的 reporting cadence。三者结合起来，可以让小团队拥有大得多的组织才有的支持姿态，而这正是签下多年期企业合同时你必须证明的能力。

- 练习：选择你最苛刻的三个 prospect，或识别你最想签下的三个理想客户。让 Claude 产出 gap analysis：每个账户的企业采购团队在签多年期合同前，会期待看到哪些文档、SLA 和支持基础设施？你当前哪里不足？用输出结果安排 Claude Code 和 Claude Cowork 的技术与文档工作顺序。

#### 构建真正的 GTM 职能

创始人的 hustle 把你带到了这里，但扩展创业公司需要创建并执行真正的 go-to-market 策略。AI 可以帮助你构建并运行完整的 GTM 引擎。

Claude 可以帮助从零构建基础 GTM 资源：市场 segmentation、messaging architecture、analyst relations strategy、sales playbook，以及当你面对公众投资人、企业买家和华尔街分析师时重要的 investor-facing metrics narrative。每类受众都有自己的词汇，并根据自己的标准评价你；Claude 的工作，是把你产品的 value prop 翻译成对每个受众 segment 都相关的产品营销方法。

现在，Claude Cowork 可以成为你的战术执行层：内容 pipeline、outbound sequence、analyst briefing 物流、newsroom 和 PR cadence、CRM hygiene、pipeline reporting，以及把 GTM strategy 转化为真实商业动作的众多重复周期。

当 GTM motion 需要产品营销基础设施时，例如交互式 demo 环境、集成文档、sandbox tenant、API reference、技术 one-pager，Claude Code 可以为你构建。买家期待能从技术层面评估你的产品，而在规模化阶段，一个 Loom 视频和一份销售 deck 已经不够了。这也是让你的 GTM motion 能够异步运行的基础设施：一个构建良好的 demo 环境，可以在你开董事会时帮你成交。

#### 把领域专业知识和机构知识转化为 AI 上下文

许多超精益创业创始人，正在为他们在特定行业中亲身经历或一手观察到的真实世界问题，构建高度具体的 app 或工具。Agentic AI 现在让从未写过一行代码的创始人，也能用自己的领域专业知识构建解决复杂问题的产品。Claude、Claude Code 和 Claude Cowork 各自承担一部分，将创始人知识转化为可复利增长的产品具体性。

用 Claude 捕捉、组织并打磨创始人知识，会把领域专业知识放到产品可以触达的位置。通过延展对话、projects 和 memory，创始人可以分享他们知道的一切：行业黑话、监管陷阱、边缘情况、挫败点，以及为什么这个问题的显而易见答案不起作用。所有这些都可以进入结构化、可搜索的上下文。Skills 随后可以把重复工作流 codify 成可复用 routine，例如「我如何审计一份商业租约」「我如何分诊患者 intake 表」，让 Claude 每次都按同样方式运行。几个月后，这会成为一个通用 AI 无法匹配的专有知识基底。

用 Claude 外部化你的领域知识，对于把行业特定 edge case 编码进产品非常宝贵。例如，一个通用 AI 医疗账单工具可能会在 340B 药品项目 claim 上出错，但你的产品有针对它们的具体逻辑。Claude Code 可以帮助你把你所在领域其他专业人士经历的常见挫败，翻译成验证逻辑、prompt refinement，或者与你竞争对手未曾听过的小众行业系统的 MCP 集成。结果是，你的 app 或工具在深度和广度上都会持续复利增长，竞争对手无法简单复制。

- 练习：识别你所在 vertical 中，一个通用竞争对手一定会做错的 edge case。和 Claude Code 一起基于你实际见过的场景，为它构建一个专门 test case（不是 unit test）。每当类似 edge case 浮现，就把它加进去。你的 test suite 会变成 moat 的地图。

#### 把累积用户数据复利成防御性优势

当用户与你的产品互动时，他们会生成行为信号，例如他们接受哪些输出、拒绝哪些输出，这会影响产品路线图。随着时间推移，你会学到自己特定用户基础的具体模式、偏好和边缘情况。这就是所谓的复利价值：每次改进都会让产品更有用，带来更多使用，产生更多反馈，再推动更多改进。

这种数据被时间锁定、上下文特定，并且对模仿者来说无法重建：你无法买到数千名用户在你的产品中精炼其工作流所留下的行为指纹。

Claude 可以帮助审计你收集到的任何用户互动数据，识别其中最高信号的行为模式，并设计反馈回路，把持续使用转化为系统性模型改进。

- 练习：向 Claude 提供你的产品互动数据摘要：你在收集什么、收集了多久，以及你知道用户如何随着时间与你的产品互动。让它识别数据中三个最高信号的行为模式，并设计一个反馈回路，将每个模式转化为系统性模型改进。然后让它帮助你起草一页 moat narrative，用于产品营销：讲清楚你的数据飞轮如何运转、已经运转了多久，以及为什么一个今天才开始的资源充足竞争对手无法在两年内复制它。

#### 创造工作流锁定

复利的数据网络效应让你的产品更难被复制，而用户工作流锁定让你的产品更难被离开。用户在日常运营中运行你的产品越久，它就越深地嵌入他们实际工作的方式。他们在它之上构建了自动化，培训员工使用它，并把它连接到自己的数据源和其他工具。他们开发的 prompts、精炼的工作流和标准化的输出，都围绕你的产品做什么、如何做而形成。到了这个点，切换不再是产品决策，而是完整的运营项目。

创造工作流锁定的第一步，是让 Claude 按集成深度映射你当前客户基础。对每个客户 segment，识别他们在你的产品之上构建了哪些工作流，以及他们依赖哪些集成。这会显示你的产品在哪里黏住了用户，以及哪里需要更深入。

你提供的集成越多，客户就有越多表面积构建依赖你产品的工作流。Claude Code 可以帮助你快速启动与目标用户依赖的数据 pipeline、项目管理工具和其他系统的原生集成。Claude Code 还可以构建 API、webhook 和 SDK，让客户不只是使用你的产品，而是在它之上构建。这是最深形式的锁定。

- 练习：让 Claude 帮你为前十名客户构建一次工作流集成审计。对每个客户，记录他们构建了哪些自动化、依赖哪些集成、哪些团队工作流通过你的产品运行，以及你估计的切换成本。然后让 Claude 识别这个群体中的模式：对你的具体产品而言，哪些类型的集成创造了最深锁定？你可以构建或启用什么，来加深那些目前仍停留在表层的客户集成？

## 第 7 章：同一份工作，新的规则

在 AI 时代，创始人的工作没有变：找到一个真实问题，构建能解决它的东西，并把它扩展成一家重要的公司。改变的是抵达那里的路径。横跨构想、MVP、发布和规模化四个阶段，AI 把原本按季度计算的周期压缩成按周计算。

过去需要几个月的验证周期，现在可以在几个下午完成。一个能工作的原型不再要求你有一个掌握正确技术栈的联合创始人；它需要的是一个清晰问题，以及和 coding agent 的几次聚焦 session。发布准备从发布前 scramble，压缩成一个持续 workstream。到了规模化阶段，过去迫使早期招聘进入 firefighting 角色的运营重量，越来越可以交给 AI，从而释放团队注意力，让它们投入那些会成为你 moat 的判断题。

瓶颈不再是你能构建什么，而是你选择构建什么。
