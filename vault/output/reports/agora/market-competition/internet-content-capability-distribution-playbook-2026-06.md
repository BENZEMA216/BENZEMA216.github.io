# 互联网内容/能力分发做法全景：机制 × 场景 × 效果（含 Agora 映射）

> Query：在内容或者能力的分发上，互联网有哪些做法，分别对应什么场景，取得了哪些效果？
> 日期：2026-06-24
> 方法：10 个分发范式并行 web 调研 → 逐簇关键数据核验 → 合成框架/横切规律/Agora 映射（21 个 subagent，多源核实，数据已标注校验注记）。

## TL;DR

互联网三十年的分发史，本质是一条主线：**做法（用什么机制把东西推到人面前）→ 场景（在什么消费频率、信任门槛、内容/能力性质下用它）→ 效果（触达规模 vs 真正变现）**。机制的演进路径是 **策展 → 搜索 → 社交 → 算法 → 协议 → 市场**，越往后分发的"边际触达成本"越低、但"信任与治理"越难内生。

而最关键的分水岭是**分发单元的性质**：**内容（content）边际复制成本≈0、消费即验证、可"先分发后信任"**；**能力（capability）调用前不可见、效果依赖买家自身上下文、必须"先信任后分发"**。互联网把内容分发做到了极致，但能力分发的 auth / 归因 / 验证 / 结算这套"新环节"至今没有标准答案——这正是 AI / Agent 时代和 Agora 的真问题。

- **做法主线**：门户编辑策展（Yahoo 单日 9500 万 PV）→ 搜索 PageRank（Google 全球 85-90% 份额）→ 社交 Feed（自然触达跌破 1%）→ 纯算法推荐（TikTok DAU 破 10 亿）→ 开放协议（SMTP/HTTP 撑起整个 Web）→ 策展市场（App Store 累计为开发者创收 5500 亿美元）。
- **场景决定机制**：高频轻量内容走 Feed/推荐；明确意图的长尾走搜索；深度低频内容走订阅/Newsletter；高权限重资产能力走带评审的市场（App Store/AppExchange）。
- **效果有两层**：触达（reach）几乎都能做大；**变现（monetization）只在信任和结算被解决时才成立**——这是大多数"AI 能力商店"翻车的根因。
- **内容 vs 能力的根本差异**：内容"看了就知道好不好"，能力"装了、跑了、还得对你的场景有用才算数"。前者支持病毒裂变与广告变现，后者必须先建立信任与可验证交付。
- **viral 只在低信任 + 高频时成立**：Hotmail 签名、Dropbox 双向奖励能病毒裂变，是因为产品本身零信任门槛、即用即得；高客单企业软件（AppExchange）从来不靠 viral。
- **平台抽成 ↔ 创作者变现是永恒张力**：GPT Store 上线两月 300 万 GPT 却"分成机制失败、多数创作者零收入"；反观 Apify（BYOC + 平台代收、80% 分成、月 payout 近 50 万美元）是少数验证"创作者能赚钱"的形态。
- **开源是关键反证**：代码可无限免费复制，但 Red Hat 340 亿被收购、MongoDB Atlas 占营收 70%——证明"可复制 ≠ 卖不掉"，变现锚点必须移到拷贝之外的环节（托管/支持/治理/可验证交付）。
- **能力分发比内容分发多出四个环节**：auth（权限）、归因（attribution）、验证（verification）、结算（settlement）。这四件事内容分发天生不需要，却是能力分发能否变现的命门。

# 一、总框架

把全部做法放进一个三维坐标，每一维回答一个独立问题：

| 维度 | 含义 | 取值（光谱） |
|---|---|---|
| **D1 分发动力（Engine）** | 谁/什么把东西推到人面前 | 策展 Curation → 搜索 Search → 社交 Social → 算法 Algorithm → 协议 Protocol → 市场 Marketplace |
| **D2 分发单元（Unit）** | 被分发的是什么 | 内容 Content ←→ 能力 Capability（中间地带：可执行内容/制品 Artifact） |
| **D3 触达路径（Path）** | 创作者通过谁触达消费者 | 自有受众 Owned → 借宿主寄生 Embedded/Host → 平台中介 Platform-mediated |

**核心判断**：D1 是"演进时间轴"（机制越来越自动化、去中心化）；D2 是"分水岭"（决定能否 viral、能否广告变现、信任在分发前还是分发后）；D3 是"权力结构"（决定谁掌握流量、谁有被收回 API 的风险）。

### 分发动力 × 分发单元 象限（10 簇定位）

| 分发动力 ↓ \ 单元 → | 内容 Content | 能力 Capability |
|---|---|---|
| **策展 Curation** | 簇1 门户/目录（Yahoo、hao123、DMOZ） | 簇5 策展市场（App Store、Steam、AppExchange） |
| **搜索 Search** | 簇1 搜索/SEO/SEM（Google、百度竞价） | （能力侧弱：GitHub Trending 算半个） |
| **社交 Social** | 簇2 关系链 + 病毒裂变（Hotmail、Dropbox、拼多多） | 簇2 邀请制能力裂变（Clubhouse、Superhuman） |
| **算法 Algorithm** | 簇3 推荐信息流（抖音、小红书、Netflix） | （能力侧几乎空白——能力难"赛马"） |
| **协议 Protocol** | 簇4 订阅/推送 + 开放协议（RSS、Substack、SMTP、ActivityPub） | 簇4/10 能力协议（OAuth、Webhook、MCP、A2A） |
| **市场 Marketplace** | 簇9 广告网络/联盟（AdSense、淘宝客、CDN） | 簇5/6/7/8 商店·包仓库·API·插件（App Store、npm、Stripe、Chrome 扩展、Shopify） |

### 触达路径维度（D3）映射

- **自有受众 Owned**：Substack/Newsletter（creator 拥有 email 列表）、平台内关注订阅、App Push——最抗算法、变现最直接，但冷启动最难。
- **借宿主寄生 Embedded**：嵌入式 widget（GA 占全网 55% 站点）、OAuth 登录、CMS/浏览器/IDE 插件、小程序、CDN/广告网络——借宿主流量零成本分发，但**有被宿主收回 API/涨价的系统性风险**（X API 2023、Google Maps 涨价 1400%）。
- **平台中介 Platform-mediated**：App Store、npm、Hugging Face、GPT Store、Shopify App Store——平台提供发现+信任+结算，代价是抽成与"分成机制是否兑现"。

### 簇10 的特殊地位

簇10（AI/Agent 时代）不是新增一行，而是把整个矩阵**沿 D2 向右推**：过去能力分发只解决了"发现+安装"（registry/directory，如 MCP 10,000+ server、Skill 66,500+），但停在了"可复制≠能变现"。它必须补上内容分发从不需要的新列——**auth / 归因 / 验证 / 结算**（Composio、Arcade、A2A/AP2、Apify BYOC 代收）。这正是从"注册表"到"可验证交付"的跃迁，也是 Agora 的战场。

# 三、十大分发范式详解

## 1. 编辑门户/目录分发 + 搜索与 SEO 分发：从"人工策展"到"算法检索"的范式转移

这一簇覆盖互联网分发史上最关键的一次范式转移：分发权从**人（编辑/目录维护者）**手里，转移到**算法 + 商家出价**手里。它解决的核心问题是"信息过载时代，用户怎么找到该看的东西"——而这套基础设施后来同样定义了所有内容/商品的分发逻辑。两个阶段：① 人工策展（门户首页、人工目录）靠编辑判断和有限的版面把内容推给用户；② 算法检索（搜索 + SEO/SEM）靠爬虫、链接图和竞价把分发规模化、去人工化、可货币化。

### 一、门户首页与人工编辑分发

**机制做法**
- 分发单元是**首页版面位 / 频道位 / 头条位**。一小群编辑从海量来源中挑选、排序、置顶内容，用户打开浏览器默认主页就被动接收。
- 触达靠"开机即见"的入口垄断 + 编辑的人工判断。本质是**报纸头版逻辑的电子化**：稀缺版面 × 编辑权力 × 海量眼球。
- 中国门户（新浪/搜狐/网易）叠加了"新闻 + 邮箱 + 论坛 + 频道"的综合入口，靠 CCTV、新华社、人民日报等媒体合作供稿，编辑分类置顶。

**适配场景**
- 最有效于**互联网早期、内容总量有限、用户不知道去哪找信息**的阶段；内容形态偏新闻/资讯（高频更新、低个性化需求、信任来自"权威编辑背书"）。
- 目标人群是"刚上网、需要被引导"的大众，对"全网最重要的几条"有需求而非"我专属的内容"。

**取得效果**
- Yahoo 起家于 1994 年的人工目录"Jerry and David's guide to the WWW"，到 1998 年成为最受欢迎的搜索入口，**单日 9500 万次页面浏览，是 Excite 的 3 倍**（searchengineland/Wikipedia）。
- 中国三大门户在 **2000 年 4-7 月相继登陆 Nasdaq**（新浪 4 月 13 日首家），新浪靠快速全面的新闻服务长期占据中国访问量第一。门户首页一度是中文互联网最值钱的版面。
- 改变了什么：第一次把"分发"做成可规模化的生意，确立了"入口 = 流量 = 广告变现"的互联网商业母模型。

**代表案例**
- Yahoo 首页/目录（美国）、新浪/搜狐/网易门户（中国）、Drudge Report（单人编辑的政治头条聚合）、AOL 首页（ISP 捆绑入口）。

**适用条件与边界**
- 成立前提：**内容总量可被人工覆盖** + **入口稀缺**（默认主页/导航位垄断）。
- 不成立时机：当内容呈指数级爆炸、长尾需求兴起、个性化预期提高后，少数编辑的判断既覆盖不全也满足不了"我要的"，版面位成为分发瓶颈。

**失败/衰退案例**
- **门户首页模式整体衰落**：搜索（按需检索）和后来的信息流（个性化推荐）把"被动接收编辑选的几条"替换成"主动搜我要的 / 算法喂我爱的"。门户没有死但沦为二线入口，编辑版面不再是流量中枢。
- 这是**内容分发**。

### 二、人工目录 / 社会化策展

**机制做法**
- 分发单元是**目录条目（分类树里的一个 listing）**或**被顶上首页的一条链接**。
- Yahoo Directory / DMOZ（Open Directory Project）靠人工/志愿者把网站归类到层级目录里；Digg 靠用户"顶（digg）"投票把链接推上首页——是从"专业编辑策展"向"群众众包策展"的过渡形态。
- 触达靠用户主动浏览目录分类，或首页聚合的"今日热门"。

**适配场景**
- 网站总量还在"可被人工/众包穷举"的量级时最有效；适合**导航型、发现型**需求（"这个领域有哪些好网站"），信任来自人工审核或群体投票。

**取得效果**
- DMOZ 关停时（2017 年 3 月）累计 **91,929 名志愿者编辑、1,031,722 个分类、收录 3,861,210 个网站、90 种语言**（Wikipedia/Search Engine Land）——展示了众包策展能达到的规模上限。
- Digg 在 2008 年巅峰**日访问量超过 100 万、接近《纽约时报》网站**，曾被 Google 以约 2 亿美元接洽收购。

**代表案例**
- Yahoo Directory、DMOZ/ODP、Digg（美国）；hao123、265 上网导航（中国，详见下条）；Reddit（继承并放大了 Digg 的众包策展逻辑）。

**适用条件与边界**
- 成立前提：网站量级可穷举 + 用户愿意"逛目录/逛首页"。
- 不成立时机：网站数从百万级爆炸到十亿级，人工目录覆盖率坍塌；搜索一旦做到"按需即得"，"逛目录"的行为本身就消失了。

**失败/衰退案例**
- **Yahoo Directory 2014 年 12 月 31 日关停**；**DMOZ 2017 年关停**（AOL 不再支持）。
- **Digg 的 v4 改版翻车（2010 年 8 月）**：新版削弱用户众包内容、偏向出版方供稿，激怒核心用户，引发大规模出走；当月 Digg 流量掉约 25%，而 Reddit 当年流量增长 230%。**2012 年 7 月 Digg 品牌+网站+技术仅以 50 万美元卖给 Betaworks，月独立访客较巅峰跌 90%**。教训：策展型分发的护城河是社区与编辑信任，一旦动了分发规则的"民意基础"就会崩盘。
- 这是**内容分发**。

### 三、上网导航站（中国特色的目录分发）

**机制做法**
- 分发单元是**导航页上的一个网址链接位**。hao123 把最常用的网站做成一张纯链接的"网址大全"页面，给不会用搜索的新网民当"互联网遥控器"。
- 触达靠被设为浏览器默认主页 + 网吧预装 + 装机捆绑——这是极强的"入口卡位"分发。

**适配场景**
- 完美适配**中国 2000 年代初网民激增、大量小白用户不会拼写网址/不会用搜索**的阶段；内容形态是"高频访问的头部网站集合"，信任来自"大家都用这个开机页"。

**取得效果**
- **2004 年 8 月 31 日百度以 5000 万人民币 + 部分股权收购 hao123**，是当时中国较大的网站收购案。
- hao123 巅峰期**为百度贡献了高达 40% 的搜索流量**，是百度联盟里最大的流量来源——证明"导航站"在小白市场是比搜索框更原始也更高效的分发入口。
- 改变了什么：用最朴素的"链接列表"完成了对增量新网民的低成本获取，是中国互联网"渠道为王/装机量为王"打法的早期范本。

**代表案例**
- hao123、265 上网导航（蔡文胜，后被 Google 收购）、2345 网址导航、360 导航（中国）。

**适用条件与边界**
- 成立前提：大量"低网络素养"增量用户 + 浏览器/装机入口可被卡位。
- 不成立时机：当用户学会用搜索框、移动端 App 取代浏览器主页后，导航站的入口价值随 PC 时代一起衰退。

**失败/衰退案例**
- 导航站在移动时代整体边缘化：手机没有"默认主页"这个卡位，超级 App（微信/支付宝/抖音）取代了"开机第一屏"的入口地位。
- 这是**内容分发**（分发的是"去哪个网站"的指针）。

### 四、搜索引擎分发（PageRank / 算法检索）

**机制做法**
- 分发单元是**一条搜索结果（SERP 上的一个位置）**。不再是"编辑推给你"，而是"你提需求、算法按相关性排序后给你"——**从 push 变成 pull**。
- 核心创新是 **PageRank（1998，Page & Brin）**：把网页间的链接当作"投票"，用链接图的数量和质量估算页面权威性，从而在无人工干预下对全网排序。
- 触达靠"用户带着明确意图主动来"，分发是按需、实时、长尾全覆盖的。

**适配场景**
- 最有效于**内容总量爆炸、长尾需求海量、用户有明确意图（"我要找 X"）**的场景。相比门户"猜你想看几条",搜索精准命中"你已经知道要什么"。
- 信任来自"算法相关性 + 链接背书"，而非编辑权威。

**取得效果**
- Google 处理量从 **1998 年日均约 1 万次**飙到 **1999 年日均超 300 万次**；十年内承接全球约 4/5 的查询。
- **2020s Google 全球搜索份额长期在 85-90%**（Statcounter），2025 年才首次跌破 90%（自 2015 年来首次），因 AI 原生工具（ChatGPT 等）分流。
- 改变了什么：把分发权**彻底从编辑手里夺走交给算法**，使"全网任意长尾内容都可被即时检索到"，并催生了围绕"如何被算法找到"的全新产业（SEO/SEM）。

**代表案例**
- Google（全球）、百度（中国，2010 年 8 月占中国搜索广告收入约 70%）、Bing、早期的 AltaVista（被 PageRank 超越的前辈）、Yandex。

**适用条件与边界**
- 成立前提：用户有**明确检索意图** + 内容是"可被索引的网页/文档"。
- 不成立时机：当需求是"我也不知道想看啥、给我推点东西"（兴趣/娱乐/打发时间）时，搜索的 pull 模型失效——这正是信息流推荐崛起的缺口。

**失败/衰退案例**
- **百度在中国份额从 2010s 巅峰约 70-78% 跌到 2020s 的 45-56%**（Statcounter/Statista，2024 年约 45.73%），被 Bing 逼近、被内容散落到微信/抖音等"信息孤岛"侵蚀——搜索引擎索引不到 App 内的封闭内容，是其衰退的结构性原因。
- 这是**能力/内容分发的混合，但本质偏内容分发**——它分发的是"通往内容的指针"。

### 五、SEO / SEM：把分发权货币化（算法分发的副产物）

**机制做法**
- **SEM（竞价排名 / AdWords）**：商家对关键词出价，搜索引擎按"出价 × 质量分"决定广告位排序——**分发位被明码标价、实时拍卖**。分发单元是"关键词上的一个广告位"。
- **SEO（搜索引擎优化）**：内容方反向迎合排序算法（关键词、外链、结构化数据等）来争取自然排名——是"如何让算法把我推给用户"的一整套博弈。
- 触达仍是搜索的 pull，但**谁排在前面**由出价（SEM）和算法迎合度（SEO）共同决定。

**适配场景**
- SEM 最适配**高商业意图关键词**（"装修报价""留学中介""医疗""保险"——用户即将消费、单次转化价值高）。
- SEO 最适配**内容型/工具型站点长期低成本获客**（攻略、评测、问答、模板）。

**取得效果**
- 这套机制把搜索变成印钞机：**Google 2023 年搜索广告收入约 1750 亿美元、2024 年总广告收入约 2645 亿美元**，占 Alphabet 营收逾 3/4（Statista/Oberlo）。这是人类历史上规模最大的单一分发变现机器。
- 改变了什么：确立了"**分发位 = 可拍卖的资产**"这一互联网广告底层逻辑，后来被电商竞价（淘宝直通车）、信息流广告全面复用。

**代表案例**
- Google AdWords/Ads（全球）、百度竞价排名（中国）、Demand Media/eHow（SEO 内容农场的极端形态）、各类 SEO 服务商。

**适用条件与边界**
- 成立前提：搜索掌握**入口垄断** + 商家愿为流量付费 + 算法排序可被影响。
- 不成立时机：当算法升级到能识别"为排名而生产的低质内容"时，纯 SEO 套利崩塌；当入口从搜索转向 App/信息流时，SEM 的总盘子见顶。

**失败/衰退案例（两个标志性翻车）**
- **内容农场被算法清洗**：Demand Media/eHow 靠数据驱动批量生产 SEO 内容冲排名，**2011 年 2 月 Google Panda 更新**专打低质内容农场，eHow 自然搜索可见度损失约 42%-66%（不同口径），Demand Media 股价两周内跌约 38%，2011 全年由盈转亏、亏损 1850 万美元。教训：**靠迎合算法套利的内容分发不可持续，算法会反向绞杀**。
- **竞价排名的信任崩塌——魏则西事件（2016，中国）**：百度把医疗关键词广告位卖给莆田系/部队医院，付费结果与自然结果混淆，导致患者魏则西误信无效疗法去世，引发全国性声讨。监管认定百度竞价机制"商业推广权重过高、标识不清、影响公平客观、易误导用户"；百度下架军警医院广告，李彦宏称季度营收因医疗整改损失约 20 亿元。教训：**当分发权被纯粹出价绑架、信任校验缺失时，能力/服务分发会造成真实伤害并触发监管反噬**。

### 范式转移的核心：内容分发 vs 能力分发

- **门户/目录/导航/搜索本质都在分发"内容（或通往内容的指针）"**——用户消费的是信息本身，分发链条只需解决"触达 + 排序 + 信任背书"。
- **但 SEM（尤其是医疗/金融/服务类竞价）已经在分发"能力/服务"**——用户点进去是要买一项服务、做一台手术、报一个班。这时分发比纯内容分发多出了致命的几环：**信任、验证、结算、(线下)履约**。魏则西事件的本质就是：搜索沿用"内容分发"的逻辑（谁出价高谁靠前）去分发"医疗能力"，却没有补上"资质验证 + 责任结算"这几环，于是分发越高效、伤害越大。
- 这条裂缝正是后续所有"能力分发"（应用商店审核、API 网关、Agent/Skill 市场）必须补齐"安装/权限/验证/分成结算"的根本原因——也是当下 AI 能力分发要吸取的最重要历史教训。

## 2. 社交关系链分发 + 病毒裂变/邀请增长循环

这一簇的共同内核：**让用户成为分发节点**。平台不再靠采买流量触达每一个人，而是借用人与人之间已经存在的社交关系链（或临时撮合的关系链），让内容/能力沿着关系图谱自动扩散。两条主线：一是**关系链分发**（Feed / 转发 / 朋友圈），把分发的边际成本压到接近零；二是**病毒裂变与邀请循环**（referral loop），用奖励或机制设计驱动老用户主动拉新，核心指标是 viral coefficient（K 因子）。

---

### 1. 社交关系链 / Feed 分发（Facebook News Feed、Twitter 转发、微信朋友圈/公众号、LinkedIn）

**机制做法**
- 分发单元是"一条更新/一篇内容/一次转发"。平台不主动推给陌生人，而是把内容注入到**好友/关注者的信息流**里。
- 触达靠两层：① 社交图谱（谁关注谁、谁是好友）；② 排序算法决定图谱里的内容谁能露出。Facebook 2006 年 9 月推出 News Feed，2010 年前后用 **EdgeRank**（affinity 亲密度 × weight 互动权重 × time decay 时间衰减）三因子排序，2013 年起换成含 10 万+ 因子的 News Feed Ranking。
- 微信生态是三个分发面叠加：公众号（订阅 push）、朋友圈（关系链曝光）、社群/转发（点对点扩散）。公众号文章靠用户**转发到朋友圈/群**二次扩散，形成"内容找人"。

**适配场景**
- 高频、轻量、需要时效性的内容（动态、新闻、观点、图文）。
- 信任要求中等——内容是否被看，取决于发送者与接收者的社交亲密度，关系链本身提供了天然背书。
- 目标人群是已经有社交账号、愿意公开表达/围观的用户。

**取得效果（具体数据）**
- Facebook News Feed 把"主动逛 profile"变成"被动刷 Feed"，奠定了信息流这一互联网最大的内容分发范式，至今支撑 Meta 数千亿美元广告盘子。
- 微信合并月活账户 2025 Q3 达约 14.14 亿，朋友圈渗透率长期超 75%，官方称每天有 7.8 亿用户进入朋友圈、1.2 亿用户发布内容——这是地球上规模最大的关系链分发场。
- 关系链分发把**触达边际成本降到接近零**：一篇 10 万+ 文章的传播不需要平台买量，靠用户转发自然完成。

**代表案例**
- Facebook News Feed（信息流鼻祖）、Twitter/X 转发（Retweet 让一条推文跨关系链跳跃式扩散）、微信朋友圈+公众号（中国最强关系链分发）、LinkedIn Feed（职业关系链分发，B2B 内容首选）。

**适用条件与边界**
- 成立前提：平台已积累足够稠密的社交图谱（冷启动期没有关系链就没有分发）。
- 不成立的情况：① 内容需要陌生人大规模触达（关系链有边界，破不了圈，这正是抖音"兴趣推荐"超越关系链分发的切口）；② 平台为了广告收入压低**自然触达率**——Facebook 公共主页自然触达已跌到 10% 以下、大号常低于 1%，逼商家买广告。

**失败/衰退案例**
- **微信朋友圈与公众号红利衰退**：公众号平均打开率从前几年的约 5% 跌到 3% 以下，意味着 100 万粉丝大号单次推送阅读量可能只有 3 万；朋友圈日均发布量较 2021 峰值下降 37%，主动点赞率跌破 10%，超 70% 用户开启"三天可见"，一半用户半年没打开过朋友圈。关系链分发的天花板是**关系链疲劳**：当所有人都在分发，信息过载导致每条内容的注意力被稀释，红利消失。

**内容还是能力分发**
- **内容分发**。关系链 Feed 天然适合内容（看一眼即消费，零安装、零信任门槛）。它**不适合直接分发能力**——一个工具/应用在 Feed 里只能展示"链接"，用户要真正使用还得跳出 Feed 去下载、注册、授权、付费，多了好几道环节。这正是能力分发比内容分发难的根因。

---

### 2. 病毒裂变 / 邀请增长循环（Hotmail 签名、Dropbox 双向奖励、PayPal 现金、拼多多砍一刀、滴滴红包、Clubhouse 邀请制）

**机制做法**
- 核心是构造一个**自我循环（referral loop）**：老用户使用产品 → 触发分享/邀请 → 新用户进入 → 新用户又成为分享者。
- 衡量指标是 **viral coefficient（K 因子）= 每个用户发出的邀请数 × 邀请转化率**。K>1 即每个用户带来多于一个新用户，理论上可指数式自增长；K 接近 1 也能大幅放大付费获客效果。
- 分发单元是"一个邀请/一个砍价链接/一个红包"。触达靠**把社交关系链当渠道**（邮件签名、微信群/朋友圈），而非平台自有流量。
- 三种激励范式：① **隐性嵌入**（Hotmail 每封邮件底部自动带签名，零摩擦）；② **双向奖励**（Dropbox 邀请双方各得 500MB；PayPal 双方各得现金）；③ **任务/游戏化裂变**（拼多多砍价、滴滴红包，靠"差一点就免费"的损失厌恶驱动疯狂拉人）。

**适配场景**
- 冷启动 / 无营销预算 / 需要快速规模化的早期阶段。
- 产品本身带社交属性或协作属性（Dropbox 共享文件、PayPal 转账、打车红包），分享是自然使用动作的延伸时效果最好。
- 适合高频或强利益驱动的场景；信任要求可以很低（一个免费链接，点开没什么损失）。

**取得效果（具体数据）**
- **Hotmail**（1996）：每封外发邮件底部加一行"Get your free email at Hotmail"，**18 个月获取 1200 万用户**（当时全球互联网用户约 7000 万），单用户获客成本估计低于 1 美元（传统互联网公司当时 CAC 高达 50–300 美元）；1997 年 12 月被微软约 4 亿美元收购。"viral marketing"一词由投资人 Tim Draper 提出。
- **Dropbox**（2008–2010）：Drew Houston 2010 年公开数据——双向奖励的推荐计划让**注册量永久提升 60%**，35% 的日注册来自推荐计划；15 个月内用户从 10 万增至 400 万，**增长 3900%**。
- **PayPal**（1999–2000）：新用户注册给 10 美元、推荐人再给 10 美元，靠现金激励实现早期约每天 7–10% 的复合增长，总计花费约 6000 万美元买来千万级用户基础，被公认为现金裂变的开山之作。
- **拼多多**（2015 起）：靠"砍一刀/砍价免费拿"在微信关系链里裂变。2018 年活跃买家达 3.44 亿，微信为其贡献约 61.9% 的流量；2021 Q4 年活跃买家 8.687 亿。社交裂变让其获客成本远低于行业。
- **滴滴红包**（2014）：与微信合作，红包在微信群/朋友圈病毒式扩散，叠加补贴大战。滴滴乘客用户从 2000 万激增到 1 亿，1–5 月斥资 14 亿元补贴，滴滴+快的合计市占一度达 98%。

**代表案例**
- 中外：Hotmail（隐性签名）、Dropbox（双向存储奖励）、PayPal（现金裂变）；中国：拼多多（砍一刀，社交裂变天花板级玩法）、滴滴红包（关系链+补贴）、美团/饿了么红包、Clubhouse（邀请制稀缺性裂变）。

**适用条件与边界**
- 成立前提：① 产品对新用户有真实价值（否则拉来即流失）；② 存在低摩擦的关系链通道（邮件、微信）；③ 奖励经济模型可持续（LTV > 激励成本）。
- 不成立的情况：① 低频/弱社交产品硬做裂变，K 因子上不去；② 平台渠道方反制（微信封杀诱导分享后，砍价裂变直接断流）；③ 单纯靠补贴买来的用户没有留存，补贴一停就走（打车补贴大战的教训）。
- **viral coefficient 的天花板**：K 因子会随关系链饱和而衰减——早期每个人的好友里都是"没用过的人"，K 高；当渗透率上升，邀请落到已是用户的人身上，转化率骤降，增长曲线自然封顶。裂变是**加速器不是永动机**。

**失败/衰退案例**
- **Clubhouse**（2021）：邀请制制造稀缺性，2021 年 2 月几周内冲到 1000 万用户（2 月 1–16 日就涨了 460 万），估值一度 40 亿美元。但开放注册后稀缺性消失，加上疫情红利退潮、留存差，到 2021 年 9 月活跃用户从峰值约 1000 万跌到 350 万，**半年掉超 60%**。教训：邀请制能引爆增长，但**稀缺性是借来的增长，无法替代产品留存**。
- **拼多多砍一刀反噬**：2021 年上海律师刘宇航起诉拼多多，"砍价免费拿"邀请大量好友后永远差 0.09%（拼多多辩称页面只显示有限小数位，实际还差 0.9996%），引发对**侵害消费者知情权**的诉讼；2021 年 5 月上海市消保委约谈拼多多。社交裂变滑向"套路用户、骚扰好友"，透支信任。
- **微信封杀诱导分享**：2019 年 10 月微信修订《外部链接内容管理规范》，明确禁止用红包/优惠券/积分等奖励诱导分享，禁止"助力、砍价、加速、集赞、集卡"等裂变玩法，朋友圈一律禁止分享拼团外链；重复违规可永久封号。这直接掐断了中国移动互联网最凶猛的裂变通道——**裂变越极致，越依赖渠道方的容忍，渠道方一旦关门，整套增长引擎熄火**。这是中国式裂变最大的结构性风险。

**内容还是能力分发**
- **两者皆可，但本质是把"能力/产品的获取动作"塞进关系链**。裂变分发的标的通常是一个**产品/服务（能力）**——Dropbox 存储、PayPal 账户、拼多多商品、打车服务。
- 关键差异（也是这一簇对"能力分发"最有启发的地方）：内容沿关系链传播只需"点开看一眼"，零成本消费；而能力沿关系链传播，新用户必须穿过 **注册→安装→授权→（首次使用/付费）→结算** 的多道环节才算真正转化。裂变机制（双向奖励、预填邮箱、一键落地页、砍价进度条）的全部设计巧思，本质上都是在**降低这几道环节的摩擦、用利益对冲信任成本**。这解释了为什么能力分发的裂变远比内容分发的转发难做、也更容易因摩擦或信任崩塌而失败。

## 3. 算法推荐信息流分发

算法推荐信息流是当代**内容分发的主引擎**。它的范式革命在于：用 **interest graph（兴趣图谱）取代 social graph（社交图谱）**——分发不再取决于"你认识谁/谁关注你"，而取决于"系统判断你会看完什么"。分发单元被压缩到**单条内容**（一条视频、一篇笔记），每条内容独立进入"流量赛马"，由完播率、时长、CTR 等行为信号决定它能爬到多大的流量池。这从根本上**打破了冷启动的粉丝门槛**：无名创作者无需积累粉丝，第一条内容就可能爆。

下面拆解这一簇内的几种具体做法。

### 1. 纯推荐信息流（无社交关系的内容引擎）

**机制做法**
- 谁推给谁：平台（算法）→ 用户，不依赖关注关系。新内容先投放给一个**小流量测试池**（TikTok 约 200–500 个兴趣相关账号；小红书初始池约 500–1000 次曝光），看完播/互动是否过线，过线就逐级放大到更大流量池（"赛马机制"）。
- 触达靠什么：用户的隐式行为信号——完播率、停留时长、CTR、点赞/收藏/评论/转发——实时回流，模型据此预测"下一条该推什么"。
- 分发单元：**单条内容**，与账号粉丝量解耦。

**适配场景**
- 内容形态：短、可快速判断好坏的形态（短视频、图文笔记），适合高频消费、低单次信任成本。
- 频率/人群：日活高频、海量长尾内容、用户主动消费意愿强但不知道自己想看什么。
- 最有效阶段：内容供给已经海量、人工编辑/社交推荐无法覆盖长尾时。

**取得效果（带年份）**
- 今日头条（2012 上线）：用兴趣图谱做冷启动，绑定微博 5 秒内建立兴趣 DNA。到 2016 年 8 月装机超 5.5 亿、月活超 1.3 亿——证明"不需要关注、不需要选择"也能精准分发。
- 抖音：2024 年 7 月 DAU 达 5 亿，单 DAU 日均使用时长约 125 分钟；短视频行业抖音占据近七成用户时长（占比约 50.8%）。
- TikTok：2025 年底全球 DAU 首次突破 10 亿，全球日均使用时长约 95 分钟（高于所有其他社交网络），2024 年营收估 200–260 亿美元。
- 它**改变了什么**：把"分发权"从粉丝/编辑手里转移到算法手里，让"内容质量（被看完的能力）"而非"账号存量"成为分发的硬通货。

**代表案例**：今日头条、抖音/TikTok、快手、YouTube 推荐流。

**适用条件与边界**
- 成立前提：①海量内容供给（否则推荐无可推）；②高频、可被行为信号快速评判的内容形态；③大用户量提供训练数据。
- 不成立：低频、高单次信任成本的内容（如医疗诊断、法律意见、企业级软件），用户不会"无脑刷"，也无法靠几秒完播判断好坏。

**失败/衰退案例**
- **门户/编辑分发的衰落**：新浪/搜狐/雅虎式人工编辑首页，被今日头条式个性化推荐取代——人工无法覆盖长尾、无法千人千面。
- **内容农场与标题党（clickbait）**：纯优化"点击/完播"会奖励标题党、UC 震惊体、低质内容农场。研究（PNAS Nexus 2024）发现 engagement-based 算法会放大情绪化、党派对立、对外群体敌意的内容；另有研究指出"用户点击的内容"与"用户反思后认可的内容"系统性背离——算法优化的是 clicks 而非 satisfaction。
- **信息茧房争议**：是否真造成"激进化/回音室"学界有分歧。PNAS 2024 一项近 9000 人的自然实验发现，短期推送更党派化的 YouTube 视频对态度无可检测的极化效应；Northeastern 2024 研究指出 YouTube 改算法后，站外社群和订阅比推荐更能驱动激进化——即茧房叙事被夸大，但"奖励即时刺激、压制深度内容"的结构性偏向仍真实存在。

**这是内容分发还是能力分发**：**内容分发**。用户消费的是成品内容本身，分发链路止于"看一眼"，没有安装、权限、结算环节。

---

### 2. 兴趣推荐 + 弱社交/普惠流量（社区型推荐）

**机制做法**
- 在纯推荐之上叠加**社区信号和普惠分配**：除了完播，还看收藏率、搜索渗透、评论质量等"种草/有用"信号；并刻意把一部分流量保底分给**普通人/素人**，而非全压给头部。
- 小红书用 CES 评分（Community Engagement Score）动态调权，笔记需在初始池内达基准线才进更大池；约 50% 社区流量分给普通用户。快手主打"老铁/普惠"，冷启段对过审作品普惠给量，再层层赛马。

**适配场景**
- 信任要求略高的"决策型内容"（买什么、去哪玩、怎么做），需要"真实素人经验"背书，因此普惠素人比纯头部更有价值。
- 下沉市场、强地域/人情连接的人群（快手老铁文化）。

**取得效果（带年份）**
- 小红书：2024 年底月活超 3.5 亿，内容分享者超 1 亿，月均搜索渗透率约 70%；2025 上半年日均新增笔记约 700 万篇——"素人爆款"成为常态。
- 快手：2024 Q4 月活 7.36 亿、DAU 4.01 亿；新作者作品 2 天内达 5 万播放的比例提升 139%；月收入过万创作者数量同比增 14%——普惠机制让新人更易被分发。
- **改变了什么**：证明推荐分发不必然导致赢家通吃，可以用产品/算法设计主动给长尾留口子（但只是缓解，未消除两极分化）。

**代表案例**：小红书、快手、（早期）B 站推荐。

**适用条件与边界**
- 成立：内容的价值来自"可信的普通人经验"，平台愿意牺牲部分短期时长换取生态健康。
- 不成立：纯娱乐/纯时长场景下，普惠会被时长 KPI 反噬，最终仍滑向头部集中。

**失败/衰退案例**
- 即便普惠，**创作者收入仍极度两极分化**：2025 年头部 10% 创作者拿走 62% 广告分成（2023 年为 53%），中位数创作者收入从 3500 美元降到 3000 美元；73% 创作者年入低于 3 万美元，仅 4% 超 10 万美元。"人人可被分发"不等于"人人可赚钱"。
- 快手 2025 年底起从"平等普惠"转向"分层精准"，普惠路线本身也在退潮——说明纯普惠在商业化压力下难以为继。

**这是内容分发还是能力分发**：**内容分发**（消费成品笔记/视频）。但小红书的"种草→站内电商"已经在向"能力/交易"链路延伸，是内容分发向交易分发过渡的样本。

---

### 3. 推荐驱动的留存/订阅（推荐当作产品内核）

**机制做法**
- 推荐不用于"发现海量 UGC"，而用于**在有限自有内容库内最大化单用户的消费与留存**。谁推给谁：平台 → 订阅用户，目标是降低流失（churn）。
- 触达单元：自有片库里的影片/剧集，用协同过滤 + 内容画像（250+ 内容属性、1000+ 用户分群）排序首页与封面。

**适配场景**
- 封闭内容库 + 订阅制（subscription）：内容供给可控、目标是 LTV 而非曝光量；电商场景则是"猜你喜欢"提升转化与客单。

**取得效果（带年份）**
- Netflix：超 80% 的观看来自推荐，推荐内容完成率约 75%；推荐系统每年为公司节省/创造超 10 亿美元价值（主要来自降低流失、提升订阅生命周期）。
- 淘宝"猜你喜欢"：智能推荐对电商 GMV 贡献占比超 35%，典型可带来点击率 +30%–50%、转化率 +20%–40%、GMV +25%–60%。
- **改变了什么**：把推荐从"涨用户"工具变成"留用户/提客单"的核心商业引擎，直接挂钩营收与留存。

**代表案例**：Netflix 推荐、淘宝"猜你喜欢"、亚马逊商品推荐、Spotify Discover Weekly。

**适用条件与边界**
- 成立：有可控内容/商品库 + 明确变现（订阅费/GMV），推荐目标是经济指标而非纯时长。
- 不成立：库存太小（推荐无空间）或本身是开放 UGC 海洋（更接近做法 1/2）。

**失败/衰退案例**
- 过度优化推荐导致**首页同质化、长尾被埋**：电商里若只推爆款，新品/长尾商家无曝光，平台不得不反向做"多场景召回"补救长尾。Netflix 的"千人千面封面"也曾因误导性封面（同一片给不同人换主角海报）引发用户不满，说明推荐优化点击与用户预期之间存在张力。

**这是内容分发还是能力分发**：内容分发（Netflix）/ 偏交易分发（淘宝）。淘宝"猜你喜欢"已经跨到**交易**——分发的不是"看"而是"买"，多了下单、支付、履约环节，是内容分发与能力/交易分发的分界点。

---

### 跨做法小结：内容分发 vs 能力分发的机制差异

算法推荐流是**内容分发的当代主引擎**，其核心优势恰恰来自"轻"：分发链路止于"看一眼/划走"，几乎没有信任、验证、安装、权限、结算等摩擦，所以能把分发单元压到单条内容、靠完播率秒级赛马、让无名创作者一夜爆发。

而**能力分发**（分发一个 Agent/Skill/App/工具，让别人能用它干活）比内容分发多了**信任、验证、安装、权限、结算**五道环节——用户不是"看一眼"就能消费，而要安装、授权、信任它不会出错、并完成付费/交付。这正是推荐流范式难以直接照搬到能力分发的原因：完播率可以秒判一条视频好坏，但"这个 Skill 靠不靠谱"无法靠 3 秒停留判断，需要可验证的交付结果作为信任凭证。这也解释了为何 GPT Store 式"内容化"地堆 GPTs 失败——能力的分发不能只靠展示曝光，必须解决验证与结算。

## 4. 订阅/推送分发 + 开放协议与标准分发

这一簇的共同逻辑是：**分发权从平台算法手里，部分转移到「关系」与「协议」手里**。订阅让创作者/服务方"拥有受众、直连用户"，绕开算法把关人；开放协议则把"触达"标准化成任何客户端都能消费的接口。两者都对抗中心化平台的分发垄断，但商业化命运截然不同——email 长青、RSS 商业化失败，这个对比是理解"能力分发"未来的关键样本。

---

### A. 订阅与推送（Subscription & Push）

#### A1. RSS 订阅（开放聚合订阅）
- **机制做法**：分发单元是 feed（XML 文档）。发布者在站点暴露一个 RSS/Atom 地址，用户用任意阅读器（Reader）订阅，客户端轮询拉取（pull）更新。没有中心服务器、没有算法排序，是纯粹的"时间线 + 全量推送"。
- **适配场景**：高更新频率的文本内容（博客、新闻、技术站），重度信息消费者，要求"不漏掉任何一条"且抗算法操纵的人群。
- **取得效果**：2005–2012 是 RSS 黄金期，Google Reader 是最流行的阅读器。但商业化彻底失败——RSS 广告无效（阅读器内渲染全文，用户不回源站，丢失 pageview/点击，且阅读器普遍带 ad-block）。**2013-07-01 Google Reader 关停**，官方理由是"忠实但下滑的用户群 + 聚焦更少产品"，分析普遍认为真因是 RSS 是开放标准、难变现、且 Google 想推 Google+。这次关停被视为消费级 RSS 衰落的标志性事件。
- **代表案例**：Google Reader、Feedly、Inoreader；中国的鲜果阅读、抓虾（均已消亡）、以及微信"订阅号"本质是 RSS 思路的封闭再造。
- **适用条件与边界**：成立前提是"内容免费 + 靠流量/广告变现"。一旦需要把读者变成可结算的用户，开放 pull 模型就崩了——发布者既不知道谁在读，也无法在 feed 里完成转化。
- **失败/衰退案例**：RSS 本身就是本簇最大的"一度有效后衰退"样本。技术活着（播客、newsletter 底层仍是 RSS），但作为面向大众的独立产品形态死了。
- **内容还是能力**：纯**内容分发**。它恰恰证明了：缺了"识别用户/结算"环节，分发再开放也无法商业化。

#### A2. Email Newsletter / Substack（拥有受众的订阅）
- **机制做法**：分发单元是一封 email，靠 SMTP 直投用户收件箱（push）。关键差异在于发布者**拥有订阅者的 email 地址**——这是一份可导出、可迁移、不依赖任何平台算法的"受众资产"。Substack 在此之上叠加了付费墙与一键订阅。
- **适配场景**：深度、低频（周更/日更）、高信任的内容；创作者经济中需要把"读者关系"资本化、做付费转化的场景。
- **取得效果**：email 是互联网最持久的分发渠道——**2024 年全球 email 用户约 44.8 亿（接近全球人口一半）；email 营销平均 ROI 约 $36–$40/每 $1（DMA 数据 3800%+）**。Substack：**2024 年作者总收入 3.7 亿美元（2023 为 3 亿），平台抽 10%、自身收入约 3700 万美元；付费订阅数 2024 年约 200 万，2025 翻倍至 500 万+；2026 年初近 10 万个出版物在赚钱**。它把"邮件列表"从营销工具升级成了创作者的核心资产。
- **代表案例**：Substack、Mailchimp、ConvertKit/Beehiiv；中国对应物较弱（email 文化薄弱），最接近的是"知识星球"和微信公众号订阅。
- **适用条件与边界**：成立的核心是"creator 拥有 email 列表 → 可随时换平台带走受众"。边界：email 打开率天然下滑（收件箱过载），且这是**内容**分发，结算靠平台代收，不涉及安装/权限。
- **失败/衰退案例**：RSS-to-email 的早期尝试（如 FeedBurner，Google 2007 收购后于 2021 基本停摆）说明：把开放 RSS 强行套进 email 也救不了 RSS 的变现。
- **内容还是能力**：**内容分发**，但比 RSS 多了"身份（email=用户 ID）+ 结算（付费墙）"，这正是它能商业化而 RSS 不能的根因。

#### A3. 平台内关注订阅（YouTube/Bilibili/微信公众号）
- **机制做法**：分发单元是"创作者→粉丝"的关注关系。用户点"订阅/关注"，平台把新内容推到关注页/通知。但**关注 ≠ 触达**：平台算法仍是把关人，订阅只是"召回信号"之一。微信订阅号被折叠进二级入口，触达进一步被平台收回。
- **适配场景**：视频/图文等富媒体，需要平台 CDN、推荐冷启动、内置变现（广告分成、打赏、电商）的创作者。
- **取得效果**：YouTube 创作者经济规模巨大；B 站以"关注+三连"构建 UP 主生态。但订阅的"分发权"在持续被算法稀释——这也是 creator 转向 newsletter"拥有受众"的直接动因。
- **代表案例**：YouTube、Bilibili、微信公众号、抖音/快手关注。
- **微信服务号的特殊机制**：**服务号每月仅限 4 次群发推送（每次最多 8 篇）**，订阅号每天 1 次。这种"稀缺推送权"反而把每次触达变成高价值事件，催生了服务号做 CRM/会员/支付的"半能力分发"形态。
- **适用条件与边界**：依赖平台流量红利期。红利退潮后，订阅数变成"虚荣指标"，真实触达需买量。
- **失败/衰退案例**：微信订阅号打开率从早期 30%+ 跌到个位数（信息流改版+折叠所致），是"平台收回订阅触达权"的典型。
- **内容还是能力**：主要是**内容分发**；微信服务号因绑定支付/会员，开始带有**能力分发**色彩（需授权、可结算）。

#### A4. App Push / 系统级推送（夺回主动触达）
- **机制做法**：分发单元是一条推送通知，经 APNs（iOS）/FCM（Android）系统通道直达锁屏。这是 App 绕开"被动等用户打开"、主动召回的渠道，需用户**显式授权**。
- **适配场景**：高频、时效性强的提醒类内容（新闻、社交、电商促销、工具提醒）；以"留存/召回"为目标。
- **取得效果**：**整体 push opt-in 率约 60%（Android 因 Android 13 跟进 iOS 授权模型，opt-in 从 85% 跌至 ~67%，iOS ~56%）。首 90 天内收到 ≥1 条推送的用户留存约为零推送用户的 3 倍；opt-in 但 90 天内没收到推送的用户 95% 流失**。推送把"留存"从被动变主动，是移动时代最有效的召回杠杆之一。
- **代表案例**：OneSignal、Airship（Urban Airship）、Firebase；中国因 FCM 不可用，催生个推、极光（JPush）、厂商联盟推送（小米/华为/OPPO/vivo 统一推送联盟，2017 起）。
- **适用条件与边界**：成立前提是用户授权 + 推送相关性。滥发立刻反噬（关闭权限/卸载）。授权率受 OS 政策强约束（苹果/安卓收紧授权后整体下滑）。
- **失败/衰退案例**：垃圾推送泛滥导致 iOS/Android 先后引入"延迟授权""分级通知"，opt-in 率系统性下降——推送的分发权同样被 OS 这个更高层"把关人"收回。
- **内容还是能力**：**内容/召回分发**，但"授权"环节已是能力分发的雏形（用户必须先 grant permission 才能被触达）。

### B. 开放协议/标准作为分发底座（Open Protocols as Distribution Substrate）

> 核心命题：**协议标准化让"能力"可被任意客户端消费，无需双边定制集成。** 这是从"内容分发"跨到"能力分发"的关键——能力分发比内容分发多了「信任 / 验证 / 安装 / 权限 / 结算」五个环节，而协议正是为了把这五环标准化。

#### B1. 基础互联网协议（SMTP / HTTP / RSS）
- **机制做法**：分发单元是协议定义的报文。SMTP 让任意邮件服务器互投；HTTP 让任意浏览器消费任意服务器的内容；RSS 让任意阅读器订阅任意 feed。**"任意客户端 × 任意服务端"的 N×M 互通，是开放协议最大的分发杠杆**。
- **适配场景**：需要跨厂商、跨客户端、长期稳定互通的基础设施层。
- **取得效果**：HTTP/SMTP 撑起了整个 Web 和 email（44.8 亿用户），是人类史上最成功的分发底座。它们的成功证明：协议越中立、无单一所有者，互通网络越大。
- **代表案例**：SMTP（email）、HTTP/HTML（Web）、RSS（聚合）。
- **适用条件与边界**：开放协议擅长分发"内容/文档"，但**对治理与变现天然薄弱**——谁来防垃圾邮件、谁来变现、谁来升级协议都没有主体。
- **失败/衰退案例**：RSS（见 A1）是开放协议"分发成功但治理/商业化失败"的最痛样本；SMTP 则因无内置反垃圾，长期被垃圾邮件困扰，最终靠 SPF/DKIM/DMARC 等补丁和大厂寡头（Gmail）治理才稳住。
- **内容还是能力**：**内容分发为主**（HTTP 可承载能力调用，但协议本身不管权限/结算）。

#### B2. 授权与回调协议（OAuth / Webhook）
- **机制做法**：OAuth 标准化了"用户授权第三方访问其数据/能力"的握手（access token、scope、refresh）；Webhook 标准化了"服务端事件主动 push 给订阅方"的回调。两者合起来，让一个服务的能力可以被另一个服务安全消费。
- **适配场景**：SaaS 之间的能力互通、第三方登录、事件驱动集成（支付成功→发货、PR 合并→部署）。
- **取得效果**：OAuth 2.0（2012 RFC 6749）成为全网"用 Google/微信/GitHub 登录"的事实标准，把"身份与授权"从每家自建变成标准握手，极大降低了集成成本。Webhook 成为 Stripe/GitHub/Slack 等平台事件分发的默认方式。
- **代表案例**：OAuth（Google/Facebook/微信/支付宝开放登录）、Webhook（Stripe、GitHub、飞书/钉钉开放平台）。
- **适用条件与边界**：成立前提是"有可信的授权方 + 明确 scope"。它首次把**信任/权限/验证**写进协议——这正是能力分发区别于内容分发的分水岭。
- **失败/衰退案例**：OAuth 配置复杂、scope 滥用、token 泄露事件频发；很多开放平台（如早期 Twitter API、Facebook 平台）一度开放后又大幅收紧权限，证明"能力分发"的开放度高度依赖平台方意愿，可随时被收回。
- **内容还是能力**：**能力分发**。这是本簇里第一个真正把"权限/验证/结算握手"标准化的协议层。

#### B3. 联邦/去中心化社交协议（ActivityPub / Fediverse）
- **机制做法**：分发单元是用户和帖子（actor/object）。ActivityPub 让独立运营的服务器（instance）互相联邦（federate），用户在 A 实例关注 B 实例的人、跨实例互动，如同一个网络。
- **适配场景**：抗平台垄断、要求数据主权与可迁移性的社交场景。
- **取得效果**：**2024 年 2 月整个 fediverse 月活约 160 万，同期 Threads 月活约 1.3 亿**——开放协议的网络规模远小于中心化平台。但 **2024-03 Meta 的 Threads 接入 ActivityPub**（可让 fediverse 用户看到/点赞 Threads 帖子），是开放协议被超大平台采纳的标志性事件，瞬间放大了协议的潜在覆盖。
- **代表案例**：Mastodon、Threads（部分联邦）、Pixelfed、PeerTube；底层均为 ActivityPub。
- **适用条件与边界**：成立前提是用户愿意为"数据主权"牺牲"网络效应/便利"。边界：实例运维成本、内容审核责任分散、冷启动难——开放协议的治理难题在去中心化社交上被放大到极致。
- **失败/衰退案例**：Mastodon 在 2022 推特动荡期暴涨后又大幅回落，留存差，印证"开放协议解决了分发互通，但解决不了产品体验和增长"。
- **内容还是能力**：**内容分发**（社交内容），但带有"身份可迁移"的能力色彩。

#### B4. AI 时代的能力分发协议（MCP / A2A）
- **机制做法**：MCP（Model Context Protocol）标准化"AI 模型/客户端 ↔ 工具/数据源"的连接：一个 MCP server 暴露 tools/resources/prompts，任意 MCP 兼容的 host（Claude、ChatGPT、IDE）都能消费。A2A（Agent2Agent）标准化"agent ↔ agent"的发现、认证与协作。**分发单元从"内容/帖子"变成了"可调用的能力（tool/agent）"。**
- **适配场景**：AI agent 需要消费外部能力（查数据库、调 API、操作 SaaS）、且要避免 N×M 双边定制集成的场景。这是"能力分发"的当代主战场。
- **取得效果**：**MCP 2024-11 由 Anthropic 发布；2025-03 OpenAI 官方采纳、2025-04 Google 确认 Gemini 支持；到 2025 年已有 1 万+ 公开 MCP server，SDK 月下载从发布时约 10 万增至 2026-03 约 9700 万（约 970 倍）；2025-12 Anthropic 把 MCP 捐给 Linux 基金会下的 Agentic AI Foundation（与 Block、OpenAI 共建，Google/微软/AWS/Cloudflare 支持）**。A2A：**2025-04 Google 发布、50+ 创始伙伴；2025-06 捐给 Linux 基金会，支持方增至 150+ 组织**。MCP 在一年内从内部实验变成行业标准，是"开放协议作为能力分发底座"最快的一次成功。
- **代表案例**：MCP（Anthropic/OpenAI/Google）、A2A（Google 主导）；中国侧阿里、腾讯、字节等也在跟进 MCP 生态与各自 agent 协议。
- **适用条件与边界**：成立前提是"模型有调用能力的需求 + 中立治理（Linux 基金会托管避免单一厂商控制）"。能力分发必须解决的五环——**信任（这个 server 安全吗）/ 验证（输出可信吗）/ 安装（如何接入）/ 权限（OAuth 授权 scope）/ 结算（调用如何计费）**——MCP 目前只标准化了"连接与权限"，验证与结算仍是开放难题。
- **失败/衰退案例**：参照物是 **GPT Store（2024-01 上线）**——它本想做 AI 能力的应用商店，但分成机制模糊、GPTs 不可跨平台消费（封闭、非协议化），创作者赚不到钱、生态迅速冷却。这反向证明：**能力分发若不走开放协议、不解决结算，就重蹈"封闭商店"覆辙**，而 MCP 正是吸取教训走的开放路线。
- **内容还是能力**：纯**能力分发**，且是本簇的终点形态——它把"内容分发"积累的协议经验（开放、中立、N×M 互通）+"能力分发"新增的五环（信任/验证/安装/权限/结算）首次系统化。MCP 标准化了"连接/权限/安装"，"验证/结算"是下一个待攻克的环节，也正是创作者能否在能力分发里赚到钱的关键约束。

> **数据校验注记**
> - [已修正] App Push opt-in: 整体约60%；Android 因 Android 13 跟进 iOS 授权模型，opt-in 从 85% 跌至 ~67%，iOS ~56%（A4 取得效果） → 方向与数字均错。Airship 2023 基准（约5000 app、6650亿条推送、25亿用户）显示 Android 13 后 opt-in 不降反升。实际中位数：Android ~80.3%，iOS ~51.6%（与草稿的『Android 跌到67%、iOS 56%』相反——Android 远高于 iOS，因 Android 历史上是默认 opt-in）。当年业界曾担心 Android 掉约30%，但并未发生。建议改为：iOS opt-in 约52%、Android 约80%，且 Android 13 落地后整体 opt-in 仍上升。（来源：https://www.airship.com/blog/brands-on-notice-with-android-13-default-opt-out/ ; https://www.airship.com/blog/mobile-app-push-notification-benchmarks-for-2023-have-arrived/）
> - [已修正] Substack 付费订阅 2024 年约 200 万，2025 翻倍至 500 万+ → 时间线错。付费订阅 2023≈200万，2024-11≈400万，2025-03 超 500万。所以『2024 约200万』偏低（200万是2023的数字），『2025翻倍到500万』口径也不准（是从2023的200万到2025的500万，约2.5倍/跨两年）。建议改为：2023≈200万 → 2024≈400万 → 2025≈500万+。（来源：https://www.reallygoodbusinessideas.com/p/substack-statistics ; https://backlinko.com/substack-users）

## 5. 应用商店 / 策展市场分发（Curated Marketplace）

### 范式总览：策展市场为什么是"能力分发"的范式锚点

策展市场（curated marketplace）是平台用一套**审核 + 榜单 + 搜索 + 评分 + 抽成**的标准化机制，把第三方开发的"能力"（可安装、可调用、有状态、能联网/收费的程序）分发给海量终端用户。它和内容 feed 的本质区别在于：内容 feed 分发的是"看一眼就消费完"的信息（图文/视频），而商店分发的是**要被安装、授予权限、长期驻留、并产生交易结算的能力单元**。因此商店在分发链路上比 feed 多了五个环节——**信任背书、安全审核、权限授予、计费结算、评分问责**——这正是"能力分发比内容分发更重"的根因，也是平台能收 15–30% 抽成的合法性来源。

下面按"原生操作系统商店 → 超级 App 内的小程序市场 → 垂直/PC 商店 → AI 时代的能力商店"四组展开。

---

### 1. 操作系统级应用商店（App Store / Google Play）

**机制做法**
- 分发单元 = 一个可安装的 App（IPA/APK）。开发者上传二进制 → 平台**人工+自动审核**（隐私、安全、合规、性能）→ 上架后通过四条触达路径分发给用户：①**编辑策展榜单**（Today 标签、精品推荐）②**算法搜索/ASO**（关键词、下载量、评分）③**排行榜**（免费/付费/畅销 Top Charts）④**用户评分与评论**作为信任信号。
- 平台垄断结算：iOS 上 IAP（应用内购买）必须走苹果通道，标准抽成 **30%**（即"苹果税"），订阅第二年降至 15%，2021 年起小企业（年收入 < 100 万美元）降至 **15%**。

**适配场景**
- 高频、需常驻设备、需调用系统权限（相机/定位/推送/支付）、需建立长期用户关系的能力。信任要求高——用户愿意把支付凭证、隐私数据交给一个 App，前提是商店做了背书。
- 对长尾开发者最有效的是"被算法/榜单发现"这一冷启动通路；对头部则是"品牌词搜索 + 留存复购"。

**取得效果（数据 + 年份）**
- 苹果 App Store：自 2008 年上线至 2025 年，累计为开发者创造 **5500 亿美元**收入（2021 年时为 2600 亿，四年新增近 2900 亿）。2024 年全球生态促成 **1.3 万亿美元**开发者账单与销售额，2025 年突破 **1.4 万亿美元**；仅美国 App Store 2024 年就促成 **4060 亿美元**。苹果 2024 年从美国 App Store 佣金一项收入超 **100 亿美元**。
- Google Play：2024 年约 **230 万**款应用在架，可触达全球约 **39 亿** Android 用户，平台总营收约 **467 亿美元**（同年苹果 App Store 营收约 1034 亿，验证了"安卓装机量大但变现弱"）。日均约 **1205** 款新应用上架。
- 改变了什么：把"软件分发"从光盘/官网下载（CAC 极高、信任难建）变成**一键安装 + 平台背书 + 自动更新 + 内置结算**，让独立开发者第一次能以零边际成本触达十亿级用户。

**代表案例**
- 苹果 App Store、Google Play（双寡头）；中国：华为应用市场、小米/OPPO/vivo 应用商店组成的"硬核联盟"安卓分发体系（因 Google Play 在华缺位而形成的本土替代）。

**适用条件与边界**
- 成立前提：平台掌握操作系统/设备入口，能强制所有第三方走它的审核与结算。一旦失去入口控制（如监管强拆），抽成逻辑崩塌。
- 不成立场景：纯网页能力（PWA）、企业内部工具、需要绕开 30% 税的高 ARPU 订阅（Spotify/Netflix 长期把购买引导到 App 外）。

**失败/衰退案例**
- **"苹果税"的合法性正在被侵蚀**：2020 年起 Epic Games 起诉苹果；2025 年 4 月美国法院永久禁止苹果阻止开发者引导用户走外部支付、并禁止对外链购买抽成；2025 年 12 月第九巡回上诉法院部分推翻，允许苹果对外链购买收取"合理、非惩罚性"费率，案件发回重审。欧盟 DMA 同步强制 iOS 开放第三方商店与侧载。这意味着"商店强制结算 + 30% 抽成"这一变现根基首次出现结构性松动。

**内容 vs 能力分发**
- **能力分发**。和图文 feed 相比，多出：审核（安全/合规）、权限（用户授权系统能力）、计费（IAP 结算）、信任评分（评论体系）四道闸。正是这四道闸让平台能收 30% 而内容平台只能收广告分成。

---

### 2. 超级 App 内的小程序市场（微信 / 支付宝小程序）

**机制做法**
- 分发单元 = 免安装的"小程序"（轻能力，即用即走，挂在超级 App 内）。分发触达比 OS 商店更"社交化、场景化"：①**线下扫码**（餐厅点单、共享单车）②**社交分享/群转发**③**搜索 + 服务直达**④**附近的小程序/支付后推荐**。没有独立"商店首页"的强榜单，而是把分发嵌进微信/支付宝的高频使用场景里。
- 微信对虚拟支付走微信支付，小游戏等品类有分成；但整体抽成远低于苹果 30%，平台主要靠生态绑定与支付变现。

**适配场景**
- 低频长尾服务、不值得让用户专门下载 App 的轻能力（一次性政务办理、景区购票、临时点餐）；以及需要借社交链裂变的电商/小游戏。信任由超级 App 整体背书，用户无需重新授权/绑卡。

**取得效果（数据 + 年份）**
- 微信小程序：2024 年日活约 **6.89 亿**（2025 年预计约 7.64 亿）；2024 年 3 月月活突破 **9.46 亿**，用户日均使用约 68 分钟。是中国"App 之上再造一个分发层"的标志。
- 支付宝小程序：2024 年 5 月月活约 **6.61 亿**，占支付宝用户的三分之二以上；日常服务类是最大品类。
- 三大平台（微信+支付宝+百度）小程序合计 MAU 早已突破 **10 亿**。改变了什么：把"装 App"这一最重的转化漏斗整体跳过——用户**零安装成本**即可调用第三方能力，分发摩擦逼近于零。

**代表案例**
- 微信小程序、支付宝小程序、百度智能小程序、抖音小程序（中国独有范式）；海外对标较弱，Snapchat Minis、印度 Paytm Mini App Store 是仿效但规模远不及。

**适用条件与边界**
- 成立前提：存在一个国民级超级 App 掌握支付 + 社交 + 流量入口，能把小程序嵌进高频场景。这是**中国特有**的结构（监管允许超级 App 横向扩张 + 移动支付普及）。
- 不成立场景：需要后台常驻、复杂本地计算、深度系统权限的重能力（仍要回到原生 App）；海外因没有同等超级 App + 反垄断更严，小程序范式难复制。

**失败/衰退案例**
- 早期"小程序流量红利"被高估：大量企业一窝蜂做小程序，但缺乏入口的小程序留存极差（即用即走的另一面是用完即弃），多数沦为"摆设"。真正活下来的是嵌入了**真实线下场景或社交裂变**的少数（拼多多、瑞幸、政务）。

**内容 vs 能力分发**
- **能力分发**，但比 OS 商店"轻"：免安装、免重新授权（继承超级 App 的身份与支付）。它证明了——当**信任与结算由宿主 App 统一兜底**时，能力分发的安装/权限摩擦可以被极度压缩，这是对 Agent 时代"能力即调用"的重要先例。

### 3. 垂直 / PC 平台商店（Steam / Chrome Web Store / AppExchange）

**机制做法**
- **Steam（PC 游戏）**：分发单元 = 一款游戏。机制 = 商店页 + 愿望单 + 评测（"好评率"）+ 折扣季 + 算法推荐 + 鉴赏家。抽成阶梯：前 1000 万美元 **30%**，1000 万–5000 万 **25%**，5000 万以上 **20%**。
- **Chrome Web Store（浏览器扩展，作为 store）**：分发单元 = 扩展（crx）。审核 + 评分 + 分类 + 搜索；权限模型是核心（扩展能读改网页、需用户授予高危权限），但 Google 已**取消向开发者抽成**，定位为生态护城河而非利润来源。
- **Salesforce AppExchange（B2B SaaS 市场）**：分发单元 = 装进 Salesforce 的企业应用/组件。审核（安全评审 Security Review）+ 客户评价 + 分类，面向 IT 采购决策者；典型 ISV 抽成约 15–25%。

**适配场景**
- Steam：买断/重度内容型能力，决策靠评测与社区信任。
- Chrome Store：高频、轻量、嵌入工作流的扩展（广告拦截、密码管理、AI 助手侧边栏）。
- AppExchange：B2B、高客单、长销售周期、信任要求极高（涉及企业数据），评分 + 安全评审是采购门槛。

**取得效果（数据 + 年份）**
- Steam：2024 年新发售游戏中 **500+** 款首发收入超 25 万美元（同比 +27%），**200+** 款超 100 万美元（同比 +15%）；Valve 2024 年从 Steam 获利约 **141 亿美元**。
- AppExchange：2024 年约 **5141** 款应用、3122 家厂商，累计客户安装超 **600–700 万**次、约 8 万条同行评价；IDC 估算 2024 年 Salesforce 每赚 1 美元，其生态赚 **5.8 美元**（生态规模约 210 亿美元级别）。是 B2B"能力分发靠信任评分而非榜单"的范本。

**代表案例**
- Steam、Chrome Web Store、Salesforce AppExchange、JetBrains/VS Code Marketplace（插件市场）；中国：腾讯 WeGame（PC 游戏，对标 Steam，但规模有限）、钉钉/飞书应用市场（B2B 对标 AppExchange）。

**适用条件与边界**
- Steam 成立前提：掌握 PC 玩家社区 + 评测/社交资产，新平台（Epic Games Store 砸钱补贴 + 只抽 12%）也难撼动其网络效应。
- AppExchange 成立前提：宿主 SaaS（Salesforce）本身是企业系统核心，应用必须"长在它上面"才有价值——平台依附性强。

**失败/衰退案例**
- Epic Games Store 用 **12% 抽成 + 独占金 + 白送游戏**强攻 Steam 多年，仍未撼动其地位——证明在策展市场里，**社区/评测/库存网络效应**比单纯降抽成更难复制。Chrome Web Store 则长期被恶意扩展、权限滥用、僵尸扩展困扰，Google 多次清洗，暴露"审核宽松 + 高危权限"组合的安全代价。

**内容 vs 能力分发**
- 三者均为**能力分发**。AppExchange 把"信任/验证"这一环做到极致（强制 Security Review），最接近未来 Agent 能力市场需要的"可验证交付"模型——这也是企业级能力分发与消费级的关键差异。

### 4. AI 时代的能力商店（GPT Store / 兴起中的 Agent/MCP 市场）

**机制做法**
- 分发单元 = 一个 Custom GPT（系统提示 + 工具 + 知识库的"软能力"封装）。机制照搬商店范式：分类 + 榜单（Featured/Trending）+ 搜索 + 创作者署名。OpenAI 2024 年 1 月推出 GPT Store，并承诺基于"用户参与度"向美国创作者分成（而非按销售额抽成）。

**适配场景**
- 理论上适配"把 prompt/工作流封装成可复用能力"的轻量场景；但因为 GPT 多为对基座模型的薄封装，**缺乏真正的能力壁垒与可验证交付**。

**取得效果（数据 + 年份）**
- 上线两个月内用户创建了 **300 万+** 个 Custom GPT——**分发热度极高**。
- 但**变现极差**：分成机制迟迟不落地、且门槛苛刻（需达到对话量阈值，多数创作者拿不到钱）；成功创作者普遍**绕过商店**直接卖访问码/订阅/服务，自留 95%+ 收入。2025 年底有迹象 OpenAI 将把 GPT Store 转向更偏自动化的"Agent Store"。

**代表案例**
- ChatGPT GPT Store（标志性失败的能力商店）；对照：Anthropic 的 MCP 生态、各 Agent 平台的 skill/工具市场正在重建这一层；中国：字节扣子（Coze）Bot 商店、百度文心智能体广场是同范式探索。

**适用条件与边界**
- 成立前提（GPT Store 没满足）：能力需有**真实壁垒 + 可验证交付 + 可计费结算**。当能力只是 prompt 薄封装、人人可复制、且平台不给可信结算时，"商店"退化成 SEO 关键词刷榜的内容农场。
- 这恰好回到本知识库的核心命题：**Skill/能力创作者赚不到钱的 binding constraint 是"可验证交付"**——GPT Store 正是缺了这一环的反面教材。

**失败/衰退案例**
- **GPT Store 本身**：分发火（300 万 GPT）但变现塌（多数创作者零收入），被"PDF 总结器""恋爱教练"等薄封装刷屏，沦为关键词优化的垃圾场。根因 = 既无能力壁垒、又无可验证交付、又无可信结算三件套，把"能力分发"做成了"内容农场"。

**内容 vs 能力分发**
- 名义上是**能力分发**，实质退化为**内容分发**——这正说明：商店的形（榜单/搜索/分类）不等于商店的魂（审核/权限/计费/验证）。**少了"信任/验证/安装/权限/结算"这五环中的结算与验证，能力分发就会坍缩成内容分发，并继承内容农场的全部病症（刷榜、同质化、零变现）。**


> **数据校验注记**
> - [已修正] 微信小程序 2024 日活约 6.89 亿（2025 预计约 7.64 亿）；2024年3月月活突破 9.46 亿 → DAU 6.89亿/7.64亿 无法在公开来源核实——查不到任何报告给出这两个数字。可核实的权威数据是：QuestMobile《2024微信小程序年度报告》给出的是用户规模(MAU量级)约 9.49亿（非9.46亿，且是月活/用户规模而非'3月月活'），月人均使用近70次。腾讯官方披露的小程序DAU是2022年的'超6亿'。建议改为：'微信小程序用户规模约9.49亿(QuestMobile 2024)，日活早在2022年已超6亿'，删除无法溯源的6.89亿/7.64亿。（来源：https://www.questmobile.com.cn/research/report/1866333408126406658/ ; https://finance.sina.com.cn/tech/roll/2024-01-04/doc-inaakiew3740431.shtml）

## 6. 软件包管理器 + 开源生态分发（package registry / semver / 依赖解析 + 开源变现）

这一簇是互联网上**能力分发**最成熟、最被低估的范式。它把"代码/模型/镜像"封装成带版本号的可寻址单元，通过中央 registry + 语义化版本（semver）+ 依赖解析，让"能力"以接近零边际成本被全球任何一行 `install` 命令拉取。它的关键悖论——**可被无限免费复制，却仍能撑起数十亿美元的生意**——正是 Agora 命题的反证：分发零成本不等于变现零希望，但变现必须从"卖拷贝"转移到拷贝之外的环节（hosting / support / 双授权 / open-core）。

### 1. 编程语言包仓库（npm / PyPI / Maven / RubyGems / crates.io）

- **机制做法**：中央 registry 存放带 semver 版本号的包；`npm install` / `pip install` 触达，包管理器自动做**依赖解析**（递归拉取依赖树）。分发单元 = 一个版本化的代码包。推送方是"任意维护者 publish"，拉取方是"任意开发者 + 任意 CI/CD 机器人"——分发由机器自动触发，无需人工发现。
- **适配场景**：可被复用的通用能力（工具库、框架、SDK）；高频复用、信任以"下载量 + 社区背书 + 源码可读"建立。对开发者人群、自动化构建链路最有效。
- **取得效果**：
  - npm：截至 2025 年 9 月约 **364 万个包**，被超过 1700 万开发者使用；2020 年被 GitHub 收购时已是约 130 万包、**每月约 750 亿次下载**，到 2025 年仅 18 个热门包每周就被拉取 **26 亿次以上**。
  - PyPI：2025 全年新增 **13 万个项目**、发布 390 万个文件，**累计传输 1.92 EB（艾字节）数据、处理 2.56 万亿次请求（平均每秒 8.1 万次）**——这是"能力分发"的纯基础设施规模。
  - 它改变了软件构建方式：现代应用 80%+ 代码来自第三方依赖，"造轮子"被"装轮子"取代。
- **代表案例**：npm（JS）、PyPI（Python）、Maven Central（Java）、crates.io（Rust）、RubyGems。中国侧：npmmirror（前 cnpm，阿里维护的国内镜像，解决跨境拉取慢）、清华 TUNA / 中科大 PyPI 镜像（高校镜像站是中国开发者的事实分发入口）。
- **适用条件与边界**：成立前提是**能力可被纯代码封装、接口稳定、依赖可声明**。当能力依赖私有数据、需要权限/结算、或交付物不可验证时，registry 模式失效——这正是从"分发库"到"分发服务/Agent"要补上信任与结算的根因。
- **失败/衰退案例**：① **left-pad（2016-03）**：一个 11 行的包被作者一气之下 unpublish，连锁导致 Babel、React 等数千项目构建失败，下载量曾超 1500 万次——暴露"零成本复用 = 零成本单点故障"。npm 此后禁止 24 小时后撤包。② 供应链投毒：2025 年 9 月一次 npm 大规模供应链攻击波及每周数十亿下载量的包。
- **内容还是能力分发**：**能力分发**。与内容分发的关键差异：内容拉下来即消费（读完即止）；能力拉下来要**安装、解析依赖、在你的运行时里执行**，因此多了"信任（这段代码会跑在我机器上）、验证（版本/校验和/签名）、安装（依赖树解析）"三个环节——供应链攻击之所以致命，正因为分发的是"会执行的能力"而非"被动的内容"。

### 2. 容器镜像仓库（Docker Hub / GHCR / Quay）

- **机制做法**：把"整个运行环境（OS + 依赖 + 应用）"打包成分层镜像，按 tag 版本化，`docker pull` 触达；分层缓存让增量分发极省带宽。分发单元 = 一个可直接运行的镜像。
- **适配场景**：交付的不是"一段代码"而是"一个能跑起来的完整能力/服务"；适合微服务、CI 基础镜像、一键自托管软件。信任靠 Official / Verified Publisher 标签分级。
- **取得效果**：2024 年 3 月 Docker Hub **每月约 250 亿次拉取**，覆盖约 1500 万个仓库、2600 万月活 IP；160+ 个 Official Images 占全部拉取的 20% 以上；平台存储超 60 PB。它把"部署一个服务"从小时级降到一行命令。
- **代表案例**：Docker Hub、GitHub Container Registry、Red Hat Quay。中国侧：阿里云容器镜像服务 ACR、腾讯云 TCR、网易 / DaoCloud 镜像加速器（同样因跨境拉取问题而成为国内事实入口）。
- **适用条件与边界**：适合"自包含、可独立运行"的能力；不适合需要中心化状态/多租户结算的 SaaS 能力。2024 年起 Docker Hub 对匿名/免费用户**限流（rate limit）**，说明"完全免费分发能力"在带宽成本下不可持续——这本身是 Agora 该关注的信号：分发可以零成本对用户，但对平台从不免费。
- **失败/衰退案例**：Docker 公司本身一度商业化失败——2019 年被迫拆分卖掉企业业务（Docker Enterprise 卖给 Mirantis），因为"分发镜像"这件事极有价值却极难直接收费，价值被云厂商（AWS ECS/EKS）截走。
- **内容还是能力分发**：**能力分发**。比 npm 又多了"运行时隔离与权限"环节——镜像里是可执行的整机环境，所以平台必须做镜像扫描、签名（cosign / Notary）、权限分级，分发链路上的"验证/信任"成本更重。

### 3. 系统级包管理器（apt / yum / Homebrew / Conda）

- **机制做法**：发行版/平台维护**官方仓库 + 镜像网络**，包经维护者审核签名后入库；`apt install` / `brew install` 触达，做依赖解析 + GPG 签名校验。分发单元 = 经过策展、签名的系统级软件包。
- **适配场景**：面向"装在我系统上、要长期信任"的软件；信任要求最高（要 root 权限），所以引入**官方策展 + 签名**这道闸。频率低但信任极强。
- **取得效果**：Homebrew 是 macOS 事实标准包管理器，被绝大多数开发者使用；apt/yum 支撑了几乎所有 Linux 服务器的软件分发。它把"信任"从"个人判断"上移到"发行版背书"。
- **代表案例**：Debian/Ubuntu APT、Red Hat/Fedora DNF/yum、Homebrew（macOS）、Anaconda/conda-forge（数据科学）。中国侧：清华 TUNA、阿里 / 华为 / 中科大开源镜像站（apt/yum 源的国内加速）、深度操作系统 deepin 的应用商店。
- **适用条件与边界**：策展模式保证质量但牺牲速度——官方仓库版本常滞后，催生了 PPA、AUR、Homebrew Tap 等"长尾旁路"。说明**策展（高信任低长尾）与开放（低信任高长尾）是一对永恒权衡**。
- **失败/衰退案例**：AUR（Arch 用户仓库）等"开放旁路"屡次出现恶意包；说明一旦绕过官方策展闸，信任成本立刻回落到用户身上。
- **内容还是能力分发**：**能力分发**。核心特征是**权限**——装系统包通常要 root，所以"签名/验证"在这一簇里被推到极致（GPG 签名 + 可信密钥链）。

### 4. GitHub 作为分发与发现层（源码 + Release + Star/Trending）

- **机制做法**：GitHub 既是源码托管，也是**事实上的分发与发现层**：Release/Tag 直接分发二进制；Star、Trending、README、Topics 构成"社会化发现"；`go get`、`pip install git+...` 可直接以 repo 为分发源。分发单元 = 一个 repo / 一个 release。
- **适配场景**：新项目冷启动、需要"社会证明"才能被信任的能力；Star 数 = 可见的信任货币。
- **取得效果**：GitHub 2024 年宣布超过 **1.5 亿开发者**、用户基数全球第一；Star/Trending 成为开发者发现新工具的主入口，许多项目"靠一条 Hacker News + GitHub Trending"完成冷启动分发。它让"分发"和"信任建立"合并到同一个面上。
- **代表案例**：GitHub Releases（分发二进制）、Awesome-* 列表（人工策展发现）、GitHub Trending。中国侧：Gitee（码云，国内 GitHub 替代）、GitCode（CSDN），以及"GitHub 中文热榜"类二次发现产品。
- **适用条件与边界**：Star 是滞后且可刷的信任信号，对"能不能跑、能不能信"无直接保证；所以 GitHub 解决"发现 + 社会信任"，但"验证/结算"仍要下游 registry 或商业层补。
- **失败/衰退案例**：Star 通胀与"Star 农场"使其信任价值稀释；大量高 Star 项目长期 unmaintained，发现层无法反映真实可用性。
- **内容还是能力分发**：**两者兼具**。源码本身是内容（可阅读学习），但作为分发源时是能力（可执行）。GitHub 的独特之处是把"内容式发现（读 README/Star）"嫁接到"能力式分发（拉下来就能跑）"。

### 5. 模型/数据/应用 Hub（Hugging Face：Models / Datasets / Spaces）—— AI 时代的"npm for models"

- **机制做法**：把模型权重、数据集当作版本化的 git-LFS 仓库分发，`from_pretrained("org/model")` 一行拉取；Spaces 直接把模型托管成可交互的在线应用。分发单元 = 一个模型/数据集仓库，或一个可运行的 Space。
- **适配场景**：AI 能力的复用与微调——基础模型 + 海量衍生（fine-tune/quantize）模型的分发；信任靠下载量、leaderboard、社区与厂商背书。
- **取得效果**：截至 2025/2026 春，HF 托管 **200 万+ 公开模型、50 万+ 数据集、约 150 万 Spaces**，**1300 万用户**。下载高度集中：**Top 200 模型（占总量 0.01%）吃掉 49.6% 的下载量，约一半模型一生下载不足 200 次**——这是头部极度集中的幂律分发，与 npm 高度同构。2025 年**中国下载量占比 41%、超过美国**；独立开发者下载占比从 17% 升至 39%，产业界从 70% 降到 37%——能力分发的供给侧正在去中心化。
- **代表案例**：Hugging Face（Models/Datasets/Spaces）。中国侧：阿里 **ModelScope（魔搭）**、**Qwen 系列在 HF 上有 11.3 万+ 衍生模型**（含标签超 20 万）——证明中国开源模型已成全球分发主力；以及百度 AI Studio 模型库。
- **适用条件与边界**：模型权重可像代码一样被无限复制，所以"卖模型本身"几乎不可行——变现被迫转向 Inference Endpoints（托管推理）、企业版 Hub、Enterprise 算力——再次复刻"开源免费 + 服务收费"。
- **失败/衰退案例**：模型供应链投毒（恶意 pickle 反序列化、含后门权重）已被反复披露；HF 不得不引入 safetensors 格式和扫描——说明能力分发规模化后，"验证"成本必然反弹。
- **内容还是能力分发**：**能力分发**（Spaces 更是直接分发"可调用的服务"）。比代码 registry 还多一层：模型是"黑箱能力"，源码可读但权重不可审，"验证"更难——这恰好预示 Agent/Skill 分发的核心难点。

### 横向洞察：开源如何"可无限复制却仍能变现"（Agora 的反证）

同一份代码/模型可被零成本复制，分发本身赚不到钱；但围绕分发的四种结构稳定地变现：

- **Hosting（托管）**：卖"我帮你跑"。MongoDB 的托管版 Atlas 到 2024 年占其约 **70% 营收**（FY2025 指引 19.2–19.3 亿美元）；HF 卖 Inference Endpoints；Docker 价值被 AWS ECS 截走正是反面教材。
- **Support / 订阅（支持与认证）**：卖"出事我兜底"。**Red Hat FY2019 营收 34 亿美元，2019 年被 IBM 以 340 亿美元收购**——纯靠"免费软件 + 付费支持/认证"撑起的最大单笔开源收购。
- **Dual-license / 重新授权（双授权）**：免费给个人、收费给商用/云厂商。**MongoDB 2018 改 SSPL、HashiCorp 2023 改 BSL（2025 年被 IBM 以 64 亿美元收购）**，都是为防云厂商白嫖而把"分发免费"与"商用变现"解耦。
- **Open-core（开放内核 + 商业外壳）**：核心开源做分发引流，企业功能闭源收费（GitLab、Elastic）。

**对 Agora 的直接启示**：能力的"分发"天然趋零成本，可验证、可复制的纯能力很难直接对拷贝收费；可持续变现一定锚在拷贝**之外**的环节——托管、信任背书、结算与权限。而"维护者 burnout"与"供应链投毒"（如 **2024 年 xz/CVE-2024-3094 这场近乎得手的两年期社工后门**）共同证明：当分发的是"会执行的能力"时，**信任与验证不是可选项，而是分发链路里最贵的那一段**——这正是内容分发不需要、而能力分发必须自建的环节。

## 7. API / SDK / 开放平台 / PaaS 能力分发 + 嵌入式能力

本簇的核心命题：**把一项能力做成"别人产品里的一个 API 调用、一个 SDK、或一段嵌入代码"，借宿主的流量和场景完成分发，按调用/用量结算。** 这是典型的**能力分发（capability distribution）**，与内容分发的根本区别在于：能力分发在触达之外多了一整条**信任 / 验证 / 安装(集成) / 权限 / 结算**链路——开发者要读文档、申请 key、做集成、过权限审核、绑卡计费，才算"用上"。这条链路既是护城河（集成深、迁移成本高），也是脆弱点（平台可随时收回权限或涨价）。本簇分两条支线：(1) 面向开发者的 API/SDK/云服务（"调用即分发"）；(2) 面向最终网站/App 的嵌入式即插即用能力（"一段 embed 即分发"）。

### 做法一：API / SDK 即分发（developer-led growth / PLG）

**机制做法**
- 分发单元是**一个 API endpoint 或一个 SDK 包**。供给方不直接面对终端用户，而是把能力卖给**开发者**，由开发者集成进自己的产品，能力随宿主产品一起触达终端用户。
- 触达靠**文档、quickstart、免费额度、SDK 包管理器（npm / pip / Maven）、Stack Overflow 答案**——即所谓 developer-led / bottoms-up growth：单个工程师不需采购审批就能 `curl` 跑通，自下而上渗透进组织。
- 结算是**按用量计费（usage-based / consumption pricing）**：每笔交易抽成（Stripe）、每条短信/分钟（Twilio）、每千 token（OpenAI）、每 GB·每核时（云）。用量增长 = 收入增长，与客户成功强绑定。

**适配场景**
- 适合**横切、高频、标准化、自己造极贵**的基础能力：支付、通信、地图、算力/存储、身份、大模型推理。
- 信任要求高（钱、隐私、合规），但能力本身是"水电煤"式的非差异化模块——开发者更愿意买而非自建。
- 目标人群是开发者/技术决策者，靠"省下 6 个月自研 + 合规"的价值主张转化。

**取得效果（具体数据 + 年份）**
- **Stripe**：2024 年总支付额（TPV）1.4 万亿美元（同比 +38%，约占全球 GDP 1.3%）；2025 年 TPV 升至 1.9 万亿美元（+34%，约占全球 GDP 1.6%），净收入约 58.4 亿美元，2026 年 2 月估值回到 1590 亿美元。每天处理 5 亿+ API 请求（约每月 150 亿）。Forbes AI 50 中 78% 跑在 Stripe 上——证明"几行代码接入支付"把支付从一个数月的银行对接项目变成一个下午的集成。
- **Twilio**：2024 全年营收 44.6 亿美元（+7% YoY），活跃客户账户从 2023 年底 30.5 万增至 2024 年底 32.5 万（定义为月内确认收入≥$5 的账户）。把"发短信/打电话"从电信运营商谈判变成一行 API。
- **AWS / 云 PaaS**：2024 年营收约 1070 亿美元，运营利润 249 亿美元，2024 Q3 占全球云基础设施市场 31%（Azure 20%、GCP 11%）。把"机房 + 服务器采购"分发成按秒计费的 API。
- **OpenAI API**：ARR 从 2023 年约 20 亿 → 2024 年约 60 亿 → 2025 年底 200 亿美元；API 业务一个月就新增 10 亿美元 ARR（约占总 ARR 5%）。把"训练大模型"这种万亿级 capex 能力压缩成每千 token 的调用。
- **微信/支付宝开放平台**：微信小程序 2021 年底 DAU 超 4.5 亿、第三方开发者超 150 万、2022 年 DAU 破 5 亿；支付宝小程序 2024 年月活约 6.5 亿（增速 6.3%、行业第一）、约 400 万个小程序；中国小程序开发者（微信+支付宝合计）2025 年 2 月超 600 万。把"开一家店触达 10 亿用户"分发成挂靠超级 App 的轻量能力。

**代表案例**：Stripe、Twilio、AWS/阿里云、OpenAI API（国外）；微信开放平台/支付宝开放平台、高德/腾讯地图 API、声网 Agora（音视频 API）、融云（即时通讯）（中国）。

**适用条件与边界**
- 成立前提：能力**标准化程度高、自建成本/合规门槛高、调用量大到值得按量付费**。
- 不成立：当能力是产品的**核心差异化**时（公司不会把命脉外包）；当调用量太小（不如自己写）；当延迟/数据驻留/合规要求让外部 API 无法满足（金融、政务自建）。

**失败 / 衰退案例**
- **Twitter/X API（2023）**：2023 年 2 月仅给 7 天通知就关停免费 API，新分层为免费（仅 1500 条/月）、Basic（$100/月）、Enterprise（传闻 $42,000/月）。超 250 个研究/公益项目瘫痪，大量 bot 和初创产品一夜失效——典型的**平台收回权限**风险：当宿主把开发者生态当成训练数据和广告竞争对手，分发渠道可被单方面切断。
- **Google Maps API（2018）**：2018 年 7 月定价上调超 1400%，免费额度从 75 万次/月砍到 2.5 万次/月，并强制绑卡。开发者被迫连夜重做或迁移到 OpenStreetMap/Mapbox。说明"先免费养大依赖、再涨价收割"对单一供应商依赖的开发者是结构性风险（lock-in tax）。

**这是内容分发还是能力分发**：**能力分发**。相比内容分发（推送即消费），它多了"读文档 → 申 key → 集成 → 过权限 → 绑卡计费"五道环节，转化漏斗更长、CAC 前置，但一旦集成进生产代码，迁移成本极高、留存和净收入扩张（NDR）远优于内容。

### 做法二：嵌入式 / 即插即用能力（embed / widget / OAuth）

**机制做法**
- 分发单元是**一段可粘贴的代码**：一个 `<script>` 标签、一个 iframe embed、一个 OAuth 按钮、一段 SDK 初始化。集成成本被压到"复制粘贴 5 分钟"，比 API 更轻。
- 触达靠**宿主网站的流量**：能力以"按钮/组件/浮窗"形态出现在别人页面里，终端用户在宿主语境内直接使用（点"用 Google 登录"、点 Stripe Checkout 付款、在文章下用 Disqus 评论）。供给方借宿主页面完成分发，自己几乎零获客成本。
- 结算分两类：交易型按笔抽成（Stripe Checkout）、或"免费铺量 + 数据/增值变现"（Google Analytics 免费换数据、Login with Google 免费换身份图谱与默认入口）。

**适配场景**
- 适合**通用、非差异化、每个网站/App 都需要但都不想自建**的功能：登录鉴权、收银台、评论区、客服、统计埋点、视频播放。
- 形态要求"零摩擦嵌入"——目标是让产品/独立开发者用最小工作量补齐一个标准功能。信任靠大厂背书（用户更信"Google 登录"而非陌生站点自建密码体系）。

**取得效果（具体数据 + 年份）**
- **Sign in with Google / 社交登录**：Google 占社交登录约 75%、占用社交登录的 App 约 78%（Auth0 数据）；约 18.6 万个活跃网站直接接入 Google Sign-in，约 53% 消费者偏好用 Google 登录。把"身份"做成一个按钮嵌进全网，既降低各站注册摩擦，又让 Google 成为默认身份层。
- **Google Analytics（嵌入式统计）**：2024 年约 1420 万个网站在用，约占所有网站的 55%，在用统计工具的网站中占 86%，W3Techs 口径 81.4% 市占。一段 `gtag.js` 让 Google 几乎免费拿到全网行为数据——"免费能力换数据资产"的范式。
- **Stripe Checkout / 嵌入式收银台**：作为 Stripe 1.9 万亿 TPV（2025）的入口之一，把"建一套 PCI 合规收银流程"压成一个托管页面/嵌入组件。
- **客服 / 评论 widget**：Intercom（客服浮窗）、Disqus（评论区，曾覆盖数百万站点）、YouTube embed（视频播放无需自建 CDN/转码）——都是"把一个完整子系统压成一段 embed"。

**代表案例**：Login with Google/Apple/Facebook、Stripe Checkout、Google Analytics、Intercom、Disqus、YouTube embed（国外）；微信登录（OAuth）、支付宝/微信支付的 JSAPI 收银、友盟统计（中国统计 SDK）、网易七鱼/美洽客服 widget（中国）。

**适用条件与边界**
- 成立前提：功能**高度标准化、用户对"第三方品牌出现在页面里"有信任**（甚至更信大厂）。
- 不成立：当嵌入会泄露核心数据/用户关系（电商不愿把支付与用户数据全交给嵌入方）；当合规要求数据本地化（GA 在欧盟一度被判违反 GDPR，2022–2023 多国数据保护机构裁定 GA 传输数据违规，倒逼自建/本地化方案）；当宿主想掌控全部体验时会自研替代。

**失败 / 衰退案例**
- **GPT Store / ChatGPT Plugins（2024）**：作为"AI 时代的嵌入式能力市场"尝试，2024 年 3 月 19 日停止用 Plugins 发起新对话、4 月 9 日全面下线；插件商店峰值仅 1000 余个插件。GPT Store 虽有数十万 GPT，但**没有真正的购买/分成机制，开发者无法变现**，叠加发现与质量问题，能力市场始终未跑通——印证能力分发若缺"结算/分成"这一环，开发者供给会枯竭。
- **Disqus 衰退**：曾是默认评论嵌入，后因第三方广告脚本、隐私追踪和拖慢页面加载，大量站点迁出/自建评论。说明"免费 widget 用广告/数据变现"一旦损害宿主体验，宿主会反向剔除嵌入。

**这是内容分发还是能力分发**：**能力分发**（其中 GA/Login 兼具"为供给方采集数据/身份"的双向性）。与做法一相比，嵌入式把"安装/集成"环节压到极薄（复制粘贴），但**权限**（OAuth scope）、**信任**（用户是否点那颗按钮）、**结算**（抽成或数据对价）三个环节依然存在，且对宿主的页面控制权和数据主权更敏感——这也是它比纯 API 更容易被宿主一键移除的原因。

> **数据校验注记**
> - [已修正] OpenAI API：ARR 从 2023 约 20 亿 → 2024 约 60 亿 → 2025 年底 200 亿美元；API 业务一个月就新增 10 亿美元 ARR（约占总 ARR 5%） → 数字混淆了两个不同对象。$20B 是 OpenAI 全公司总 ARR（2025 年底，2024=$6B、2023=$2B），不是 API 业务的 ARR——API 只是其中一小部分（早前估约 $5 亿级别）。'一个月新增 $10 亿 ARR、约占总 ARR 5%' 这条单独看是对的：Altman 称 API 业务上月新增超 $10 亿 ARR，约等于全公司 $20B 总 ARR 的 5%——但这是'当月增量占总 ARR 的比例'，不是 API 占总收入 5%，更不能推出'API ARR=$20B'。应改写为：OpenAI 全公司总 ARR 2023≈$20亿→2024≈$60亿→2025 年底超 $200 亿；其中 API 业务单月新增超 $10 亿 ARR（增量≈总 ARR 的 5%）。（来源：https://the-decoder.com/openais-api-business-grew-by-1-billion-arr-last-month/ ; https://www.pymnts.com/artificial-intelligence-2/2026/openais-annual-recurring-revenue-tripled-to-20-billion-in-2025/）

> - [已修正] Google Analytics：2024 年约 1420 万网站在用，约占所有网站 55%，在用统计工具的网站中占 86%，W3Techs 口径 81.4% 市占 → 网站数量/全网占比基本对（约 1420 万网站、约占所有网站 ~55%），但两个'占比'口径有误：W3Techs 实测口径为——在使用流量分析工具的网站中 GA 约占 78–81%（'86%'偏高、与来源不符）；GA 在'所有网站'中的绝对市占约 43–47%（不是 55%）。'81.4% 市占'对应的是'在用分析工具网站中的占比'这一口径，不是全网占比。建议改为：约 1420 万网站使用；在所有网站中绝对占比≈43–47%；在使用分析工具的网站中≈78–81%。（来源：https://w3techs.com/technologies/details/ta-googleanalytics ; https://electroiq.com/stats/google-analytics-statistics/）

## 8. 插件/扩展生态分发：在高频宿主之上做"能力增量"分发

这一簇的共性是：**不自己造流量，而是寄生在一个已经拥有海量高频用户的"宿主"（host）之上，把能力以"可安装、可卸载的增量模块"形式分发给宿主的存量用户**。分发单元不是一篇内容，而是一个"挂载点上的功能"（plugin / extension / app）。它本质上是**能力分发**——相比内容分发，它多了一整套"信任 / 验证 / 安装 / 权限 / 结算"的环节（审核上架、权限授权、API 兼容、版本升级、收费分账），这套环节既是门槛也是护城河。对 Agora（Claude Code Skill / MCP 即此形态）来说，这是最贴近的参照系，核心结论先行：**宿主选择决定生死，分发量天花板由宿主的 DAU 和"能力缺口"共同决定**。

### 1. CMS / 建站宿主插件（WordPress 模式）

- **机制做法**：宿主是开源 CMS（WordPress 内核），分发单元是 plugin（PHP 钩子注入功能）。官方 WordPress.org plugin directory 充当目录 + 一键安装 + 自动更新通道；商业插件走 CodeCanyon、独立站订阅。触达靠"建站者主动去目录搜功能"+ SEO + 口碑。
- **适配场景**：长尾、低频但刚需的功能补全（SEO、表单、电商、缓存、安全）。宿主本身是"半成品平台"，留出了大量未填的功能缺口，适合"一个痛点做成一个插件"。
- **取得效果**：WordPress 截至 2025 年驱动**全网约 43.4% 的网站**（W3Techs，2025-04），在所有用 CMS 的网站里占比 **61.3%**；官方目录有 **66,000+ 免费插件**（含商业市场全生态 90,000+），每周新增约 17 个。WooCommerce 单个插件就支撑了相当规模的独立电商。它把"建站"从开发外包变成"装插件搭积木"，极大降低了上线门槛。
- **代表案例**：WordPress + WooCommerce、Yoast SEO、Elementor（建站器，曾估值数亿美元）；中国侧对应 **Discuz!/帝国 CMS 的模板插件生态**、以及**有赞/微盟在 SaaS 电商上的应用市场**。
- **适用条件与边界**：成立前提是宿主开源 + 海量装机 + 功能故意留白。边界：宿主一旦升级（Gutenberg 区块编辑器）会让大批旧插件失效；插件质量参差、安全漏洞频发（WordPress 站点被黑多源于插件）。
- **失败/衰退案例**：大量"单功能小插件"在 WordPress 把功能并入内核后归零（如内核自带 SEO/缓存能力增强后，部分付费插件被边缘化）；CodeCanyon 一次性买断模式因缺乏持续收入而难以养活长期维护，许多插件烂尾。
- **内容 vs 能力**：**能力分发**。比内容多了"安装 + 权限（数据库写入）+ 版本兼容 + 升级维护"环节——一个插件若不随 WordPress 主版本升级就会"翻车"，这正是内容分发没有的负担。

### 2. 浏览器扩展（Chrome / Edge 扩展 + 油猴脚本）

- **机制做法**：宿主是浏览器（Chrome 占桌面 60%+ 份额），分发单元是 extension。Chrome Web Store 提供审核 + 一键安装 + 自动更新；权限模型（manifest 声明）是核心。油猴（Tampermonkey）是"扩展之上的二级宿主"——它本身是个扩展，再分发 userscript（JS 脚本），走 Greasy Fork 这类脚本库。
- **适配场景**：高频"伴随式"能力——挡广告、比价、翻译、密码管理、网页改造。用户在浏览过程中即时触发，对"无缝嵌入当前页面"要求极高。油猴脚本适合极客的长尾定制（某个网站的特定改造）。
- **取得效果**：Chrome Web Store 头部扩展（如 AdBlock、Grammarly）装机过亿；**Tampermonkey 单个扩展 2019 年即超 1000 万用户**，2022 年是 Chrome 商店仅有的 33 个破千万用户的扩展之一；Greasy Fork 托管 **10,000+ 脚本**。截至 2025，Chrome 商店中 **85%+ 活跃维护的扩展已迁移到 Manifest V3**。它把"改造任意网站"的能力下放给了非开发者。
- **代表案例**：AdBlock/uBlock Origin、Grammarly、1Password、LastPass；中国侧 **沙拉查词、Tampermonkey 脚本生态、以及曾经的"二师兄/购物党"比价插件**。
- **适用条件与边界**：成立前提是浏览器开放扩展 API + 高频使用。边界：权限越界即被下架，恶意扩展长期是安全重灾区。
- **失败/衰退案例**：**Manifest V3（2024 起强制）直接重创广告拦截类扩展**——`declarativeNetRequest` 限制了动态拦截规则，uBlock Origin 等被迫降级为 Lite 版，这是"宿主用平台规则一刀切重塑生态"的典型；油猴脚本则长期处于"宿主网站改版即失效"的脆弱状态。
- **内容 vs 能力**：**能力分发**。权限（读取/修改网页、读取浏览历史）是这里"信任/验证"环节最尖锐的地方——扩展能看到你所有网页内容，因此审核和权限模型比内容平台严苛得多。

### 3. 开发者工具宿主插件（VS Code 扩展模式）

- **机制做法**：宿主是 IDE（VS Code），分发单元是 extension（语言支持、Linter、主题、AI 补全）。VS Code Marketplace 提供搜索 + 一键安装 + 自动更新，扩展通过稳定的 Extension API 挂载。开发者在编码场景中"按需即装"。
- **适配场景**：垂直、专业、刚需的开发者工作流增强。用户技术能力强、对工具的信任建立快、迁移成本敏感。极高的"功能缺口密度"（每种语言、每种框架都需要支持）。
- **取得效果**：VS Code Marketplace **2025 年 5 月突破 100,000 个扩展**（含 36,000 语言扩展、19,000 代码片段、13,000 格式化器、8,700 主题）；VS Code 自身是全球最常用的编辑器（开发者使用率常年 70%+）。正是这套扩展生态让 VS Code 从"轻量编辑器"反超传统 IDE。AI 编码扩展（Copilot 等）借此通道成为分发量最大的 AI 能力之一。
- **代表案例**：GitHub Copilot、Prettier、ESLint、Python 扩展；中国侧 **通义灵码（阿里）、CodeGeeX（智谱）、Fitten Code** 等国产 AI 编码插件都以 VS Code 扩展为主分发通道。
- **适用条件与边界**：成立前提是宿主有稳定 API + 开发者高频驻留。边界：扩展受 VS Code 版本与 API 限制，宿主（微软）能优先把热门能力做进内核或自家产品（Copilot 与第三方 AI 扩展的竞争即是 Sherlocking 风险）。
- **失败/衰退案例**：微软把 Copilot 深度集成进 VS Code 内核（Chat、Agent 模式直接内置），第三方 AI 补全扩展的分发位置被系统性挤压——**"宿主自己下场做最赚钱的那个能力"**。此外开源版 VS Code（VSCodium）无法用微软官方 Marketplace，暴露了"宿主用许可证控制分发渠道"的风险。
- **内容 vs 能力**：**能力分发**。结算环节相对弱（多数扩展免费），但"安装 + 权限（读写代码/执行命令）+ API 版本兼容"环节齐全。这是与 Agora 的 Claude Code Skill 形态最同构的参照。

### 4. SaaS 应用市场（Shopify App Store 模式）

- **机制做法**：宿主是商业 SaaS 平台（Shopify 店铺后台），分发单元是 app（通过 API/嵌入式 UI 给商家加功能）。官方 App Store 提供审核 + 计费托管（Billing API 代收代付）+ 评分体系。触达靠后台内推荐 + 搜索 + 商家解决"具体生意痛点"的主动需求。**关键是宿主代结算**——开发者不用自己处理订阅收费。
- **适配场景**：直接关联商家"赚更多钱"的功能（营销、转化、物流、客服）。付费意愿强（功能能算 ROI）、信任由平台审核 + 评分背书、目标人群是有真实生意的商家。
- **取得效果**：Shopify **2024 年处理约 2923 亿美元 GMV**、服务 480 万活跃商家；App Store 有 **21,000+ 应用**；**开发者累计赚取超 15 亿美元**；商家平均装 **6 个 app**（部分多达 30 个）。2021 年 Shopify 把开发者**前 100 万美元年收入的分成降到 0%**（之上 15%，原为全额 20%），直接刺激生态繁荣。App 生态被普遍认为是 Shopify 相对竞品的核心护城河。
- **代表案例**：Klaviyo（邮件营销，靠 Shopify 生态成长为上市公司）、Oberlo、Judge.me；中国侧对应 **有赞应用市场、微盟、钉钉应用市场、企业微信第三方应用**——同样是"SaaS 宿主 + 第三方功能 + 平台代结算"。
- **适用条件与边界**：成立前提是宿主商业化成熟（商家愿为增收付费）+ 平台提供计费基础设施。边界：宿主可随时改 API、改分成、或自己下场做。
- **失败/衰退案例**：**Shopify 2024 年回滚了"前 100 万美元 0 分成"政策**，恢复对全部收入抽成，开发者收入预期受挫；更典型的是 Shopify 把热门第三方能力做进官方（Shopify Email、Shopify Markets、Shop Pay），直接 Sherlock 掉对应品类的第三方 app。
- **内容 vs 能力**：**能力分发，且五环节最完整**。信任（审核 + 评分）、验证（功能演示）、安装（OAuth 授权店铺数据）、权限（读写订单/客户）、结算（平台代收分账）全部齐备——这是与纯内容分发差异最大的一类，也是商业闭环最完整、最值得 Agora 借鉴的结算范式。

### 5. 协作/设计工具宿主插件（Figma / Notion / 飞书模式）

- **机制做法**：宿主是高频协作工具，分发单元是 plugin（Figma 操作画布）/ integration（Notion 连接外部数据）/ 应用（飞书开放平台）。Figma Community、Notion Marketplace、飞书应用目录提供发现 + 安装。触达靠社区 + 模板生态联动。
- **适配场景**：嵌入既有协作工作流的自动化与扩展（设计批量处理、文档自动化、内部审批/OA）。低频但高黏性，信任靠社区口碑和官方审核。
- **取得效果**：Figma Community 有 **12,686 个插件 + 896 个 widget**（Fig Stats）；头部插件如 Iconify、Stark（约 56.8 万用户）覆盖海量设计师；Notion 已接入 **100+ 第三方连接**；飞书/钉钉/企业微信应用目录承载了大量企业内部工具。它把"工具"延展成了"工作流平台"。
- **代表案例**：Figma 的 Iconify / Unsplash / Stark 插件、Notion + Zapier、**飞书开放平台应用 / 钉钉宜搭与第三方应用 / 企业微信服务商**。
- **适用条件与边界**：成立前提是宿主有开放 API + 活跃社区。边界：协作工具的插件多免费、缺结算，开发者商业化弱；宿主把热门插件能力内置（Figma 自带变量/Auto Layout 后部分插件失去价值）。
- **失败/衰退案例**：**Figma 修改插件用户计数口径**（2023 前后）曾让大量小开发者失去激励、退出生态；Adobe 收购 Figma 风波也一度让生态投入观望——说明**插件开发者的命运高度受制于宿主的政策与归属变动**。
- **内容 vs 能力**：**能力分发**（Notion 的模板分发偏内容、是"两者"）。安装/权限齐全，但**结算环节普遍缺失**，是这类生态商业化乏力的根因——这恰好反向印证了 Shopify"平台代结算"对生态繁荣的关键作用。

---

**贯穿全簇的两条结论（对 Agora）**：

1. **宿主选择 = 分发量天花板**。同样是"做能力增量分发"，寄生在 480 万付费商家的 Shopify 上、还是寄生在每天 6.89 亿 DAU 的微信小程序上（2024）、还是寄生在 70% 开发者用的 VS Code 上，结局完全不同。宿主的 DAU × 付费意愿 × 功能缺口密度，三者共同决定生态规模。

2. **能力分发比内容分发多五个环节，结算是分水岭**。信任/验证/安装/权限都决定"能不能用上"，但**只有结算决定"开发者能不能赚到钱"**。Shopify 因平台代结算 + 0 分成催生 15 亿美元开发者收入；Figma/Notion 因缺结算而生态商业化乏力。同时，所有宿主生态都共担一个系统性风险——**Sherlocking（平台吞噬插件）**：当某个第三方能力被验证为高价值，宿主有动机也有能力把它做进内核或自家产品，从 Watson→Sherlock 到 Copilot→VS Code 内置、第三方 app→Shopify Email，概莫能外。Agora 若做"能力分发层"，必须想清楚**靠什么对抗宿主的吞噬**（如跨宿主可移植性、创作者结算网络、社区信任资产）。

> **数据校验注记**
> - [已修正] Shopify 2024 回滚了"前 100 万美元 0 分成"政策，恢复对全部收入抽成（草稿第 4 节失败案例 + 贯穿结论） → 回滚发生在 2025 年（公告 2025-04，2025-06-16 生效），不是 2024 年。且并非"恢复对全部收入抽成"：政策从"每年重置的首 100 万美元 0 分成"改为"终身首 100 万美元一次性 0 分成"，超出部分仍 15%。草稿把年份和力度都说错了——0 分成并未取消，只是不再每年重置。（来源：https://betakit.com/shopify-app-developers-will-no-longer-be-exempt-from-sharing-their-first-1-million-usd-in-revenue-every-year/ ; https://shopify.dev/changelog/update-to-shopifys-app-developer-revenue-share）

## 9. 联盟分销/广告网络分发 与 CDN/基础设施层分发

这一簇的共同逻辑是"借别人的资产做分发"：联盟/广告网络借的是**别人的流量与受众**，按效果（CPS/CPA/CPC）结算，用激励对齐取代信任建立；CDN/基础设施层借的是**别人离用户更近的物理节点与带宽**，把"分发"从一个增长问题降维成一个可靠性/延迟问题。两者一个分发"谁来看内容"，一个分发"内容/代码怎么更快到达"，但都把分发变成了**可计量、可结算、可规模化的标准化交易**。

### 一、联盟/分销/CPS：按效果付费的"他人流量"分发

#### 机制做法
- **分发单元**：一条带追踪参数的链接（affiliate link / 推广位 ID / 优惠券口令）。点击经 cookie / deeplink 归因，成交后按 CPS（按销售额分成）、CPA（按行动）或 CPC（按点击）结算。
- **谁推给谁**：商家/平台把"流量采购"外包给海量第三方站长、博主、返利站、KOL、MCN。第三方用自己已有的受众触达，平台只在**结果发生后**付钱——分发风险从平台转移到分销方。
- **核心创新**：performance-based 把"建立信任→说服→转化"这条链路打包成一个**可竞价、可外包的市场**。平台不需要认识每个分销方，只需要一套归因 + 结算系统。

#### 适配场景
- 标品、高复购、决策链短、可被"种草/比价/优惠"驱动的品类（电商、3C、美妆、游戏充值、SaaS 订阅、信用卡/金融开户）。
- 适合**长尾内容创作者变现**：一个测评博客、一个垂类 UP 主就能接入，无需自建电商。
- 信任要求"借用"：消费者信任的是 KOL/站点，而非品牌本身，分发借的是这层既有信任。

#### 取得效果
- **Amazon Associates（1996 起，史上最早的网络联盟之一）**：把数百万独立站长变成 Amazon 的销售渠道。佣金率 2012 年中峰值约 **9.25%**，2020 年 4 月大砍后均值降到约 **3.14%**；2025–2026 年再砍**最高 50%** 并取消高产出者的里程碑奖金——说明平台一旦流量到手就持续压低分成。
- **Google AdSense / Network（2003 起）**：2023 年 Google Network（含 AdSense/AdMob）广告收入 **313 亿美元**，覆盖 **200 万+ 发布商**，标准内容分成约 **68%**。它让任何一个小网站当天就能靠内容变现，催生了整个独立博客/内容长尾经济。
- **淘宝客 / 阿里妈妈（2007 起）**：2018 年全年派发佣金约 **300 亿元**，全年活跃淘客约 **400 万**、从业者超千万；FY2019 淘客模式带动 GMV 约 **7540 亿元**，约占阿里当期 GMV 的 **13%**。把"私域种草→公域成交"标准化成了中国式 CPS 大市场。
- **直播带货 / MCN（2018 起爆发）**：2023 年中国直播电商 GMV 约 **4.9–5 万亿元**，约占电商大盘 **31.9%**；参与用户 **7.65 亿**（占网民 71%）。2024 年抖音电商 GMV 约 **3.5 万亿元**、同比 +30%。这是 CPS 的"主播化"升级——分发单元从链接变成"人 + 实时场景 + 信任"。
- **行业整体**：2024 年全球联盟营销规模约 **185 亿~323 亿美元**（口径不一），北美约占 40%，CAGR ~8%。

#### 代表案例
- 海外：Amazon Associates、Google AdSense/AdWords 展示网络、ShareASale/CJ/Rakuten 等 CPS 网络、Wirecutter（测评导购）。
- 中国：淘宝客/阿里妈妈、什么值得买（导购返利）、返利网/一淘、抖音/快手 MCN 与头部带货主播（李佳琦、辛巴）、拼多多分销。

#### 适用条件与边界
- **成立前提**：① 商品/服务可在线即时成交并精准归因；② 客单价与毛利能覆盖分成；③ 存在大量"有受众但无变现手段"的第三方愿意接入。
- **不成立的情况**：① 决策重、需深度信任的产品（企业级、医疗、大额金融）很难靠一条链接成交；② 归因被破坏时（iOS ATT/第三方 cookie 退场、跨设备）整套激励对齐失灵；③ 平台一旦掌握流量，会单方面压低分成，分销方议价权趋零。

#### 失败/衰退案例
- **内容农场 + SEO 套利（Demand Media / eHow）**：靠"按搜索价值批量生产低质内容→AdSense 变现"一度市值超 20 亿美元（2011 年 1 月 IPO 时短暂超过纽约时报）。2011 年 Google **Panda** 算法全球上线后 eHow 流量暴跌约 **66%**，Demand 整体站点流量掉最高 40%，股价两周跌 38% 再未恢复。**教训**：当分发激励只对齐"点击/成交"而不对齐"质量"，平台规则一变，套利型分发瞬间归零。
- **过度返利/羊毛党**：纯比价返利驱动的用户无品牌忠诚，平台补贴一停留存崩盘（早期返利网模式增长不可持续）。

#### 这是内容分发还是能力分发
**两者皆是，但以内容/商品分发为主**。AdSense 分发的是"内容的注意力变现"，CPS/淘宝客/直播分发的是"商品的成交"。它**不是能力分发**——分销方不需要"安装/获得"商家的能力，只需引流。这正是与能力分发的关键差异：能力分发比内容分发多了**信任建立、验证、安装、权限授予、结算责任**等环节（你要把"能跑的东西"交到对方手里并对结果负责），而 CPS 把这些全部省略，只保留"引流→归因→分钱"。

---

### 二、CDN / 基础设施层分发：以"离用户更近"做技术分发

#### 机制做法
- **分发单元**：缓存对象（图片/视频/JS 包/API 响应）或软件包（npm tarball、镜像、App 安装包）。
- **谁推给谁**：内容源头把资产推到**遍布全球的边缘节点（PoP / edge）**，用户请求被就近调度（anycast/DNS/GSLB）到最近节点命中缓存。源站只需上传一次，分发由网络物理拓扑完成。
- **核心创新**：把"分发"从"我要怎么让更多人看到/用到"这个增长问题，**降维成"内容怎么更快、更稳地到达已知用户"的可靠性/延迟问题**——分发的成败由命中率、p99 延迟、可用性等可度量工程指标定义。

#### 适配场景
- 高并发、大带宽、对延迟敏感的内容（视频流媒体、电商大促、游戏更新、直播）。
- 软件供应链分发（npm/PyPI/镜像站/容器 registry）：开发者一次发布，全球按需拉取。
- App 灰度/分发（应用商店、edge 配置下发、feature flag）：需要按地域/人群分批触达与回滚。

#### 取得效果
- **Akamai（1998 起，CDN 鼻祖）**：长期承载**全球约 30% 的互联网流量**，把"网站打得开吗"变成了背后看不见的工程问题。
- **Cloudflare（2010 起）**：覆盖**全球 330+ 城市 PoP**，**Top 100 万流量站点中约 48.7%** 使用其服务，2024 年营收 **16.7 亿美元**（+29% YoY）。它用**免费套餐**做分发飞轮——免费 CDN/DNS 让海量长尾站点接入，再向上转化为安全/Workers 等付费能力。
- **npm（2010 起）**：世界最大软件注册表，**310 万+ 包**，常用包每周下载约 **26 亿次**（2025 年）；2018 年即达**日均 10 亿次**下载。它让 JavaScript 生态的"能力复用"标准化——一行 `npm install` 就完成能力分发。
- **效果本质改变**：CDN/registry 把"分发"从市场营销动作，变成了**默认基础设施**——开发者/内容方不再"做分发"，而是"接入分发网络"，分发成为水电一样的公共品。

#### 代表案例
- 海外：Akamai、Cloudflare、Fastly、AWS CloudFront；npm、PyPI、Docker Hub、Vercel/Netlify 的 edge 分发。
- 中国：阿里云 CDN、腾讯云 CDN、网宿科技（ChinaNetCenter）、又拍云；npmmirror（淘宝镜像）、清华 TUNA 镜像源、华为/小米/OPPO 应用商店的灰度分发。

#### 适用条件与边界
- **成立前提**：① 被分发对象可缓存/可复制（静态化程度高）；② 全球/全国用户分布广，就近调度才有价值；③ 源头愿意为可靠性/速度付费或接受免费引流换升级。
- **不成立的情况**：① 强个性化、强实时、不可缓存的动态内容收益有限；② 一旦中心化基础设施故障，会引发"半个互联网瘫痪"的系统性风险（Cloudflare/Akamai 多次大规模宕机即为此）；③ registry 中心化也带来供应链攻击面（npm 投毒事件波及每周数十亿次下载）。

#### 失败/衰退案例
- **单点中心化风险**：Cloudflare/Fastly/Akamai 历史上多次配置错误导致大面积宕机，"分发越集中→单点故障影响越广"是这条路线的结构性代价。
- **镜像/registry 供应链翻车**：npm 多次出现恶意包/被劫持包，因下载量极大（每周 20 亿+ 次拉取仍含大量已废弃/有风险包），一次投毒即可全球扩散——"无信任、纯安装"的高效分发反过来成了攻击放大器。

#### 这是内容分发还是能力分发
**两者都覆盖，且 npm/registry 正是能力分发的早期范本**。CDN 缓存图片/视频是**内容分发**；而 npm/PyPI/Docker registry 分发的是**可执行能力**（库、镜像、组件）。后者恰好暴露了能力分发比内容分发"多出来的环节"：**安装（`install`/拉取）、验证（签名/校验和/锁文件）、权限（脚本执行/postinstall）、信任与供应链安全**。这也解释了为什么 AI 时代的能力分发（Agent/Skill/MCP/插件）天然更难——它在 npm 的"安装+验证+权限"之上，还要再叠加**结算与持续信任**，远比 CPS 式的纯引流内容分发复杂。

> - [存疑] FY2019 淘客模式带动 GMV 约 7540 亿元，约占阿里当期 GMV 的 13% → 未能独立查到 7540 亿这一具体数字的原始出处。可做合理性校验：阿里 FY2019 淘宝+天猫 GMV 为 5.727 万亿元，7540 亿对其约 13%——即该 13% 是对'淘系 GMV'而非'阿里全站 GMV'而言，内部自洽。建议补注口径来源或改述为'约占淘系 GMV 的 13%'，否则读者易误解分母。（来源：https://www.iyiou.com/news/20190515100181）

## 10. AI / Agent 时代的能力分发：从"注册表"到"可验证交付"，以及对 Agora 的映射

### 范式总览：能力分发为什么比内容分发多了五个环节

前面 9 个互联网范式（门户、SEO、信息流、应用商店、社交裂变、KOL、私域、电商货架、订阅）本质都在分发**内容**——一段已经成形、买家打开即可消费、且打开前就能大致判断好坏的产物（一篇文章、一段视频、一个 App 的截图）。买家的"验证成本"很低：标题、封面、评分、试看几乎就够了。

Agent 时代分发的是**能力（capability）**：一个"会替你干活的东西"。这把分发链条从"触达 + 消费"扩展成一条更长的链，新增了至少五个内容分发里不存在的环节：

1. **安装 / 跨 runtime（install / portability）**——能力不是一个静态文件，要落到某个 runtime（Claude Code、Cursor、ChatGPT、AgentCore）里才能跑；同一个 Skill 在不同宿主里行为不同。
2. **权限绑定（auth / permission binding）**——能力要访问用户的账号、cookie、文件、API key 才有价值，"敢不敢授权"成了分发的前置闸门（内容从不要求你交出账号）。
3. **可验证交付（verifiable delivery）**——买家**付钱前无法判断这个能力对自己有用**。这是 Agora Problem Statement v2 的 binding constraint：内容好不好打开就知道，能力行不行要在你的环境、你的数据、你的任务上跑一遍才知道。
4. **运行归因（run attribution / event ledger）**——多个能力包串联执行时，必须知道谁被调用、哪个版本、哪一步失败，才能分账、退款、排名。内容分发只需统计"播放/点击"。
5. **结算分账（settlement）**——按调用、按任务成功、revenue share、execution token——比"订阅一篇专栏"复杂得多，且本地执行天然防不住盗版。

一句话差异：**内容分发卖的是"已完成的产物"，能力分发卖的是"未来会不会替你完成"的承诺**。承诺无法在购买前被消费，所以信任/验证成了整个市场的瓶颈。下面把当下做法按"它解决了链条的哪一段"来拆。

---

### 做法 1：MCP / Skill 注册表（registry / directory）——"能力的应用商店货架"

**机制做法**：把能力包（MCP server、Agent Skill）放进一个可搜索、可分类、可一键安装的目录。分发单元是 **MCP server**（一组 tool 的动作接口）或 **Agent Skill**（procedural knowledge + 脚本模板）。触达靠搜索 + 榜单 + 宿主内的 `/install`；消费靠 BYOC（bring your own compute/runtime），即用户自己的 Claude Code / Cursor 去跑。

**适配场景**：开发者 / AI 重度用户；能力形态清晰、边界明确（查 API、读数据库、控浏览器、跑 code review）；高频、低信任要求的工具型能力。本质是"agent 时代的 npm / Chrome Web Store"。

**取得效果**：
- MCP 从 2024-11 发布到 2026 年已有 **10,000+ 个活跃公开 server**，并在 2025 年底被 Anthropic 捐给 Linux Foundation 旗下的 **Agentic AI Foundation（AAIF，与 Block、OpenAI 共同发起，Google/微软/AWS/Cloudflare 支持）**，被业界称作"AI 的 USB-C"，OpenAI、Google Gemini、微软 Windows 11/Azure 全部采纳。
- Smithery 从 2024-12 上线时约 **10 个 server** 增长到 2026 年的 **6,000–7,300 个**，提供 managed OAuth + observability。
- Claude Code 的 Skill/plugin 生态出现第三方市场（如 tonsofskills 收录 **2,800+ skills / 425 plugins / 200 agents**），Agent Skills 规范号称可跨 Claude Code / Cursor / Copilot / Codex / Gemini CLI **30+ 宿主**移植。

**代表案例**：Smithery、Glama、mcp.so、PulseMCP（MCP 目录）；Claude Code Skills 官方 + 第三方市场；中国区的 Coze/扣子插件市场、腾讯元器智能体商店、ModelScope（魔搭）/AgentScope。

**适用条件与边界**：成立的前提是**用户已经是 agent 用户**（Agora Layer 2 的人群漏斗），且能力是开发者能看懂的工具。**不成立**的时候：目录停留在"列表"——没有测试、权限校验、计费和运行归因，就会快速被官方 registry（MCP 官方 registry、AWS Agent Registry）和 Composio/Pipedream 这类执行层吃掉，沦为 SEO 站。

**失败/衰退案例**：纯 MCP directory 已显疲态——同质化严重、缺认证/收费，多个目录站靠 SEO 流量而非交易存活；这正是 Agora 判断"目录不是公司，只是入口"的依据。

**内容还是能力分发**：**能力分发**。与内容货架（App Store 截图即可决策）的关键差异：注册表只解决了链条的第一段（discovery + install），**权限、验证、结算、归因四段几乎都没解决**——这正是 66,500+ skill 零变现的根因（Agora 切口）。

---

### 做法 2：平台托管型 Agent/GPT Store（中心化 runtime + 平台代收）——"流量大但变现塌方"

**机制做法**：创作者在平台内（无代码）搭一个完整 agent，平台提供 runtime、discovery、分发流量和（理论上的）分成。分发单元是**完整 agent app**。触达完全靠平台算法和入口流量。

**适配场景**：非技术创作者；输入输出明确、不需要本地账号/本地执行的轻能力；平台想用海量供给丰富自己生态。

**取得效果（反面教材）**：
- ChatGPT GPT Store：累计创建 **300 万+ 自定义 GPT，但仅 15.9 万进入公开商店（95% 流失率）**。
- 承诺的 **revenue-sharing 计划本应 2024 Q1 上线，实际长期跳票**；少数能拿钱的也受制于"每周 25 次对话"门槛和不透明算法，估算**一个 5 万月活的头部 GPT 季度收入约 1,000 美元 ≈ 每用户每月 0.02 美元**。结果是聪明创作者全部绕开 Store 自建直销。

**代表案例**：OpenAI GPT Store、Poe、Coze/扣子、腾讯元器、百度文心智能体（均为平台内中心化分发）。

**适用条件与边界**：在"平台想丰富供给、创作者图曝光"时短期成立；一旦创作者要**真实收入 + 定价权**就崩——因为创作者既不能定价、又被平台锁定、还没有可验证交付来证明价值。

**失败/衰退案例**：GPT Store 本身就是标志性翻车——OpenAI 同时握有 distribution + billing + discovery + 品牌仍然失败，证明**"有流量 ≠ 能变现"**，缺的恰恰是 Agora 指出的 Layer 3（可验证交付）和创作者定价权。

**内容还是能力分发**：**能力分发**，但被包装成"内容货架"来分发——这正是它失败的原因：它假装能力像内容一样"看一眼就知道好坏"，于是只投入 discovery，没投入验证和归因。

---

### 做法 3：BYOC + 平台代收（注册表 + 计费）——Apify 模式，唯一被验证赚到钱的形态

**机制做法**：平台提供 registry + 托管 compute + 计费分账，但能力（Actor）由第三方开发者构建并发布，用户调用、平台代收、开发者分成。分发单元是**可独立运行、按用量计费的 Actor（actor = 打包好的自动化能力）**。触达靠 Store + 集成入口 + 被 agent 调用。

**适配场景**：web/data automation 这类**结果可量化、可按调用/按事件计费**的能力；开发者愿意为长尾 niche 持续供给。

**取得效果（正面标杆）**：
- Apify 主要靠 bootstrapped 达到 **$25M ARR、15,000+ 客户、40,000+ 活跃开发者**，Store 有 **6,000+ Actors**。
- 开发者通常分成 **80%**；社区创作者**月度 payout 已接近 50 万美元，同比 4x+**——这是少数能证明"第三方能力创作者真能赚到钱"的数据点。

**代表案例**：Apify（最像已成立的 agent actor marketplace）；按调用计费的模型/媒体层 Replicate、Modal、fal.ai（见做法 4）；中国区暂无直接对标。

**适用条件与边界**：成立的前提是**结果可量化 + 可托管 compute + 计费归因清晰**（爬虫/数据任务天然满足）。**不成立**于 identity-bound execution（必须用用户自己 xhs/淘宝账号、cookie 不能上云）——这正是 Apify 模式覆盖不到、Agora 想吃的本地执行 wedge。

**失败/衰退案例**：无明显翻车，但天花板在于绑死 web scraping 单一品类；扩到"通用 agent 能力包"时，验证和跨 runtime 安装都比抓数据难得多。

**内容还是能力分发**：**能力分发**，且是**目前把"能力链条五环节"补得最全的一种**——它同时解决了 install（托管 runtime）、计费、归因、分账。它之所以成功，恰因为 web automation 的"交付可验证"（抓到没抓到、几条数据，一目了然），间接印证了 Agora 的判断：**可验证交付是定价的上游**。

---

### 做法 4：按调用计费的能力 API（serverless / per-call inference）——"能力即水电"

**机制做法**：把模型/能力封装成 API，用户按调用量（per second / per call / per event）付费，平台托管 GPU 与执行。分发单元是**一次 API 调用**；触达靠开发者文档、模型 hub 和被 agent/应用集成。

**适配场景**：能力高度标准化、可即时验证输出（生成一张图、转一段音、跑一次推理）、对延迟和成本敏感的开发者场景。

**取得效果**：
- fal.ai（生成式媒体）**年化收入翻倍到 ~$400M（2025-10）**，2025-12 由红杉领投以 **$4.5B 估值**融 $140M，后续传洽谈 **$8B 估值**。
- Modal **ARR ~$50M（2026-02）**，洽谈 **$2.5B 估值**。
- Replicate 托管 **50,000+ 社区模型 / 9,000+ 公开模型**，2024 收入 $5.3M，**2025 年底被 Cloudflare 收购**（独立增长见顶、并入基础设施巨头）。

**代表案例**：fal.ai、Replicate、Modal、Runpod；中国区类似形态是各家 MaaS（火山方舟、百炼、硅基流动等按 token/调用计费的模型平台）。

**适用条件与边界**：成立于**能力可即时、客观验证**（图片质量、转录准确率、推理结果当场可见）——验证成本几乎为零，所以"先付费后验证"的信任问题不存在。**不成立**于"需要在用户私有上下文里跑、且结果好坏主观"的复杂 agent 工作流——那正是验证难、Agora 要攻的地方。

**失败/衰退案例**：Replicate 被收购可视为"对 model 打透、对 agent 能力未打透"的信号——纯算力/模型层正在 commodity 化、向 Cloudflare 这类基础设施聚合，价值正在往 discovery + trust + packaging 上游迁移（与 Agora 的判断一致）。

**内容还是能力分发**：**能力分发**，但属于**验证成本最低的那一端**（输出当场可见）。它恰好反衬出 Agora 难在哪：当能力的交付**不是一张图、而是"帮我把这套 xhs 账号运营好"**时，per-call 那套"调用即验证"完全失效。

---

### 做法 5：开放模型/制品 Hub（Hugging Face 模式）——"GitHub for ML + 可运行 demo"

**机制做法**：开放托管模型、数据集、可运行 demo（Spaces），社区上传、下载、clone、fork。分发单元是 **model / dataset / Space**。触达靠搜索 + trending + 社区引用；消费靠下载自托管或在 Spaces 里直接运行。

**适配场景**：研究者、ML 工程师、开源社区；需要 provenance、可复现、可 clone 的"制品分发"。是 artifact registry 的基础设施样板。

**取得效果**：到 2026 年 Hub 托管 **240 万+ 模型、73 万+ 数据集、约 100 万 Spaces**，2025 年用户达 **1,300 万**，**30%+ 财富 500 强**有认证账号；"第二个百万模型只用了约 335 天，第一个百万用了 1,000+ 天"，呈加速。

**代表案例**：Hugging Face（Hub + Spaces）；中国区 ModelScope（魔搭）。延伸到 Agent 产物分享层：Websim、YouWare、Promptarium、Claude Artifacts、v0/Lovable/Replit 各自的 template/remix gallery。

**适用条件与边界**：成立于"制品本身就是交付物、可复现、可 clone"。**不成立**于"跨 Agent/跨工具的 interactive artifact registry"——Agent 产物类型太杂（HTML/notebook/workflow/skill/视频）、运行安全（XSS/密钥泄露）、prompt-source-model provenance 复杂，至今没有出现"YouTube for Agent Artifacts"的默认平台（见 agent-output-sharing 报告）。

**失败/衰退案例**：不是衰退，而是**空白**——Spaces 解决了"可运行 demo + source + clone"，但没解决 agent 产物的 provenance + 安全 + 商业化，第一方平台（Claude/v0/Replit）各自锁定生态，跨工具 registry 冷启动最难。

**内容还是能力分发**：**两者之间**——模型/数据集偏"可复制的制品（内容）"，Spaces 偏"可运行的能力"。它说明：**当能力被降维成"可下载的静态制品"时，分发就退化回内容分发的逻辑**（下载量、star 即可决策）；而真正难的能力分发恰恰是"不能被降维成静态文件"的那部分。

### 做法 6：执行/认证/编排基础设施 + 企业治理注册表（Composio / AgentKit / AWS Agent Registry / A2A）——"补齐前 9 范式没有的新环节"

**机制做法**：这一层不直接卖能力，而是**为能力分发补上内容分发从未需要的基础设施**：managed auth（per-user OAuth）、tool router、connector registry、eval/trace、跨 agent 通信协议、企业内私有 catalog 与审批治理。分发单元是 **auth flow / connector / 治理记录 / 协议消息**。

**适配场景**：生产级、企业级 agent 部署；需要把"权限绑定 + 运行归因 + 合规治理"做成平台能力。这正是能力分发链条里**内容分发完全不存在的那五个新环节**的承包商。

**取得效果**：
- **OpenAI AgentKit（2025-10-06 DevDay 发布）**：Agent Builder + **Connector Registry**（统一管理数据源/第三方 MCP）+ ChatKit + 内建 Evals/Tracing + Apps SDK（Booking/Canva/Figma/Spotify 等在 ChatGPT 内渲染交互 UI）。
- **AWS Agent Registry（2026-04 preview）**：企业私有 catalog，覆盖 agents/tools/skills/MCP/custom resources，带**审批工作流**（只有过安全/合规/质量的记录才可被发现）+ 语义+关键词混合搜索 + 可作为 MCP server 被 IDE 调用。
- **A2A 协议（2025-06-23 入 Linux Foundation）**：一年内支持组织从 50+ 增至 **150+（含 AWS/Cisco/Google/IBM/微软/Salesforce/SAP/ServiceNow）**，核心仓库 **22,000+ GitHub stars**，SDK 扩到 5 种语言；配套 **AP2（Agent Payments Protocol）已有 60+ 支付/金融机构**。
- 执行/认证层融资：Composio（$29M，managed auth + 850+ integrations）、Arcade.dev（$12M，per-user secure auth）、Pipedream MCP（3,000+ API / 10,000+ tools）。

**代表案例**：Composio、Arcade.dev、Pipedream（执行/认证）；OpenAI AgentKit、AWS Bedrock AgentCore Agent Registry（平台/企业治理）；A2A / AP2 / Stripe ACP / x402 / Skyfire（通信与结算协议）。

**适用条件与边界**：成立于"大厂和企业必然要为 agent sprawl 做治理、为 identity-bound execution 做授权"。**边界**：这些大多是**平台内/组织内**的——OpenAI 希望能力留在 OpenAI，AWS 希望资源进 AgentCore，没人愿意做**跨 runtime 的 creator sovereignty**。

**失败/衰退案例**：暂无翻车，但隐含风险是大厂把 runtime/connector/治理全内化后，第三方只剩"中立跨 runtime 层"这一条缝——这恰是 Agora 的定位（publisher / installer / verifier / settlement for cross-runtime capability packages）。

**内容还是能力分发**：**纯能力分发的基础设施**——它存在的全部理由，就是内容分发从不需要的那五个新环节（install、auth、verify、attribution、settlement）。

### 对 Agora 的映射：这一簇相比前 9 个互联网范式，到底"新增"了什么

把六种做法对齐到能力分发链条，可以看清前 9 个内容范式与 Agent 能力分发的结构性差异：

| 链条环节 | 内容分发（前 9 范式）有没有 | Agent 能力分发新增 | 谁在做 | 仍空白 |
|---|---|---|---|---|
| Discovery | 有（门户/SEO/信息流/货架） | 注册表 + 语义检索 + 被 agent 调用 | Smithery、MCP registry、AWS Registry | 跨 runtime 中立目录 |
| Install / 跨 runtime | 无（内容打开即用） | **新增**：落到具体 runtime 才能跑 | 各宿主各自为政 | install doctor、兼容矩阵 |
| 权限绑定 | 无（内容不要你的账号） | **新增**：per-user OAuth、cookie、本地文件 scope | Composio、Arcade、AgentKit Connector Registry | 本地账号执行的信任模型 |
| **可验证交付** | 内容打开即知好坏 | **新增且是 binding constraint**：付钱前无法判断能力对自己有用 | 几乎无人系统做（AgentKit/LangChain 有 eval 但偏 builder 自测） | **canonical tests + 失败归因 = Agora 切口** |
| 运行归因 | 只需 PV/点击 | **新增**：哪个版本/哪一步失败 | 部分 observability（LangSmith、Composio） | 跨能力包的 event ledger |
| 结算分账 | 订阅/广告/电商成熟 | **新增**：按调用/按成功/分账/防盗版 | Apify（已验证）、Stripe ACP、x402、Skyfire | 多能力包分账 + 本地执行防盗版 |

**核心结论**：六种当下做法里，只有 **Apify（做法 3）和 per-call API（做法 4）真正赚到了钱**，而它们成功的共同前提都是**交付天然可验证**（抓了几条数据、生成了什么图，当场可见）。一旦能力的交付变成"帮我把这套账号运营好"这类**主观、滞后、依赖用户私有上下文**的 outcome，所有现成做法都失效——这正是 **Agora Problem Statement v2 锁定的 binding constraint（Layer 3 可验证交付）**：买家付钱前无法相信能力对自己有用 → 不敢付 → 创作者无法定价。

因此 Agora 不在"agent store / MCP marketplace"的红海里（那是 discovery，做法 1/2 已饱和且 GPT Store 已证伪），而在**所有现成做法都没补的那一环——把"未来会不会替你完成"的承诺，变成"被验证能跑、且持续有人负责"的可定价交付**。卖的单位是 capability contract（访问/更新/兼容/验证/支持/托管保护步骤/结算），不是文件——护城河是验证数据、runtime 兼容矩阵、更新渠道和 event ledger，这些"复制文件拿不到的东西"。

*数据来源：MCP/AAIF（Anthropic、Linux Foundation，2025-2026）；Smithery（6,000–7,300 servers，2026）；Apify（$25M ARR、80% 分成、月 payout ~$50 万，Cerebral Valley/Apify Docs 2025）；GPT Store（300 万 GPT/15.9 万公开、95% 流失，2024-2025）；fal.ai（$400M ARR、$4.5B→$8B 估值，TechCrunch/Sacra/Dealroom 2025-2026）；Modal（~$50M ARR、$2.5B，TechCrunch 2026-02）；Replicate（50,000+ 模型、被 Cloudflare 收购 2025）；Hugging Face（240 万模型/1,300 万用户，HF State of OS 2026）；OpenAI AgentKit（DevDay 2025-10-06）；AWS Agent Registry（2026-04 preview）；A2A（150+ 组织/22K stars，Linux Foundation 2025-2026）。*

> **数据校验注记**
> - [已修正] fal.ai 年化收入翻倍到 ~$400M（2025-10），2025-12 红杉领投 $4.5B 估值融 $140M → $4.5B 估值 + $140M 融资 + 红杉领投全部正确（2025-12-09，TechCrunch/Bloomberg/BusinessWire）。但时点错配：$400M 是 Sacra 估的 2026-02 年化数字，不是 2025-10；2025-10 时约为 $200M+，2025 年底约 $285M。建议把 '~$400M（2025-10）' 改为 '$200M+（2025-10）→ $400M 年化（2026-02，Sacra 估算）'。（来源：https://techcrunch.com/2025/12/09/fal-nabs-140m-in-fresh-funding-led-by-sequoia-tripling-valuation-to-4-5b/ ; https://sacra.com/c/fal-ai/）

# 四、横切规律

**规律 1：分发机制的选择由"四要素"联合决定 —— 边际复制成本 × 信任/验证门槛 × 消费频率 × 网络效应。**
内容（复制成本≈0、低信任门槛、高频）天然适配 Feed/推荐/病毒；能力（执行有成本、高信任门槛、低频决策）必须配市场+评审+结算。证据：高频轻量图文走抖音/小红书算法赛马，而高客单企业应用走 Salesforce AppExchange 的"安全评审+评分"（5141 款应用、每 1 美元带动生态 5.8 美元）。

**规律 2：内容可"先分发后信任"，能力必须"先信任后分发"。**
内容消费即验证（看了就知道好坏），所以能病毒扩散；能力调用前不可见、效果依赖买家自身上下文。证据：MCP/Skill registry 两年做到 10,000+ server，但"66,500+ skill 近乎零变现"——发现解决了，信任没解决。这是 Agora 的 binding constraint。

**规律 3：触达 ≠ 变现，"效果"是两层指标。**
几乎所有机制都能把触达做大，但变现只在信任+结算被解决时成立。证据：GPT Store 上线两月创建 300 万+ GPT，却"分成机制失败、多数创作者零收入"，头部 GPT 仅约 0.02 美元/用户/月——有流量不等于能变现。

**规律 4：viral / 裂变只在"低信任 + 高频 + 零摩擦即得"时成立，且红利会被治理回收。**
证据：Hotmail 靠隐性签名 18 个月获 1200 万用户、CAC<1 美元；但拼多多砍价裂变（微信贡献 61.9% 流量）后遭诉讼+消保委约谈+微信封杀；Clubhouse 邀请制几周冲千万、开放后半年掉 60%。高信任/低频的能力（企业软件、付费 agent）从来不靠 viral。

**规律 5：分发动力沿"策展 → 搜索 → 算法 → 协议/市场"单向演进，触发条件是供给规模超过上一机制的处理上限。**
证据：网站可穷举时用 Yahoo Directory 人工策展；内容爆炸后 DMOZ 关停（2017）、Google 查询量两年从 1 万/日涨到 300 万/日；协议层（SMTP/HTTP/RSS）撑起整个 Web 但治理/变现天然薄弱。能力分发正处在"从 registry（策展/搜索阶段）走向协议+市场（MCP/A2A+结算）"的拐点。

**规律 6：宿主寄生 vs 自建受众是一个永恒取舍 —— 借流量换增长，代价是单点依赖风险。**
证据：嵌入式 widget 让 GA 覆盖全网 55% 站点零成本分发；但平台可单方收回——X 2023 免费 API 仅留 1500 条/月、企业版传 4.2 万美元/月，Google Maps 2018 涨价超 1400%。自有受众（Substack email 列表、email ROI ~$36/$1）抗算法但冷启动慢。

**规律 7：平台抽成与创作者变现存在结构性张力，"代收+高分成+可验证"是唯一被验证的解。**
证据：开源四模式证明"可复制≠卖不掉"（Red Hat 340 亿被收购、MongoDB Atlas 占营收 70%）；Apify（BYOC + 平台代收、80% 分成、社区月 payout 近 50 万美元同比 4x）和 fal.ai（年化 ~$400M、估值冲 $8B）成功的共同点是**输出当场可验证 + 平台代收结算**。

**规律 8：协议化分发解决 N×M 集成爆炸，但协议本身不解决变现——治理/结算要靠协议之上的基础设施。**
证据：MCP/A2A 把 N×M 双边集成降为标准接口（A2A 一年 50→150+ 组织、22K stars、AP2 含 60+ 支付机构），但变现要靠 Composio/Arcade（auth/归因）、AWS Agent Registry（治理）这层补上。对照 SMTP/RSS：协议赢了互通、输了变现（RSS 因回源丢失广告失败、Google Reader 关停）。

**规律 9：分发位的稀缺性会被算法持续通胀回收，creator 自然触达单调下降。**
证据：Facebook 自然触达跌破 10%、大号常低于 1%；微信公众号打开率从 5% 跌破 3%、朋友圈发布量较 2021 峰值降 37%；订阅号打开率从 30%+ 跌至个位数。任何把分发权交给平台算法的形态，都要预期触达红利衰减。

**规律 10：能力分发比内容分发多出四个不可省略的环节 —— auth / 归因 / 验证 / 结算。**
内容分发天生不需要这四件事，能力分发缺一即无法变现。证据：簇10 的执行/治理基础设施（Composio、Arcade、A2A/AP2、AWS Agent Registry 2026-04 入治理 preview）正是在"补上能力分发独有、内容分发没有的新环节"。这是 Agora 产品形态的设计清单。

# 五、对 Agora 的映射

**Agora 定位**：供给侧的"能力分发"平台。**Problem Statement v2 的 binding constraint = 可验证交付**——买家付钱前无法相信能力对自己有用 → 不敢付 → 创作者无法定价。开源是反证：代码可无限复制，但 Red Hat / MongoDB 仍能卖出大钱，证明"可复制 ≠ 卖不掉"，真正的约束不是复制成本，而是**信任前置**。

### 哪些互联网做法可被 Agora 直接借用

- **包仓库的"一行 install + semver + 依赖解析"心智（簇6）**：npm/PyPI 已经训练了开发者"搜索→安装→复用"的肌肉记忆，MCP/Skill registry（Smithery 从 10 增到 6,000+）继承了它。Agora 应直接复用这套发现+安装 UX，**但不能停在这里**——registry 只解决发现，不解决变现。
- **BYOC + 平台代收的结算结构（Apify 模式，簇10）**：这是全部材料里**唯一被验证"创作者能赚钱"的形态**（$25M ARR、80% 分成、月 payout 近 50 万）。Agora 应直接采用"开发者自己跑能力（BYOC）+ 平台代收代付 + 高分成"。
- **按调用计费 + 输出当场可验证（fal.ai/Replicate 模式，簇10/7）**：成功因"输出当场可验证"。Agora 应把"可验证"做成产品内核，凡是能即时给出可检验产物的能力优先上架。
- **嵌入式登录/授权写进协议（OAuth/MCP，簇4/7）**：把权限与验证写进分发协议本身，而非事后补丁。

### 哪些不适用 / 要警惕

- **病毒裂变（簇2）不适用**：能力是高信任、低频决策，viral 只在低信任高频成立（规律 4）。Agora 不应押注砍价/邀请裂变。
- **纯算法推荐赛马（簇3）几乎不适用**：能力难像短视频靠完播率赛马（规律 5 的能力侧空白），强行算法分发会放大"有触达无变现"。
- **平台托管型 GPT Store 模式（簇5/10）是反面教材**：300 万 GPT、95% 流失、分成长期跳票、头部 GPT 仅 0.02 美元/用户/月。Agora 必须避开"平台流量分发 + 分成兑现失败"的陷阱。
- **纯宿主寄生（簇8）有单点风险**：依赖单一宿主会被收回 API/涨价（X、Google Maps）。Agora 若寄生 Claude Code/Cursor，需保留可迁移性。

### 能力分发多出来的四环节如何落到 Agora 产品形态

内容分发不需要、但能力分发必须补上的四件事（规律 10），逐一落地：

| 新环节 | 内容分发是否需要 | Agora 产品形态落点 |
|---|---|---|
| **验证 Verification** | 否（看即验证） | **沙箱试跑 / 用买家自己的输入预演 / 可验证产物预览**——直接攻 binding constraint，让买家付钱前就看到"对我有用" |
| **权限 Auth** | 否 | 把 OAuth/MCP 式授权写进上架协议，能力声明所需权限范围，买家可审 |
| **归因 Attribution** | 否（注意力即计量） | 按调用/事件计量，记录"是谁的能力解决了谁的问题"，作为分成依据 |
| **结算 Settlement** | 广告/CPS 已成熟 | BYOC + 平台代收代付 + 高分成（对标 Apify 80%），creator 不碰支付摩擦 |

### 3-5 条可操作结论

1. **把"可验证交付"做成产品内核，而非营销话术**：上架优先级 = 输出可即时验证程度。提供"用买家自己的上下文沙箱试跑"，让买家在付款前看到能力对自己的实际效果——这是直接解开 binding constraint 的唯一杠杆（参照 fal.ai/Apify 成功要素）。

2. **结算结构照抄 Apify，不照抄 GPT Store**：采用 BYOC（开发者自跑）+ 平台代收代付 + 高分成（≥80%），按调用/事件计量。避免"平台流量分发 + 分成跳票"的 GPT Store 死法。

3. **发现层复用 registry/包仓库心智，但不止步于此**：提供 npm 式"搜索→安装→调用"，同时在其上叠加 auth/归因/验证/结算这四个内容分发没有的环节——这正是从"注册表"到"可验证交付"的跃迁。

4. **押注协议（MCP/A2A）做互通，自建治理/结算做变现**：协议解决 N×M 集成（让能力可被任意 agent 消费），但变现要靠 Agora 自建的验证+结算层（参照 Composio/Arcade/AP2 把治理写进基础设施）。

5. **优先服务高信任、低频、高客单的能力，而非追求 viral 规模**：能力分发的钱在"先信任后分发"的形态里（AppExchange 每 1 美元带动 5.8 美元），不在病毒触达里。Agora 的北极星是"创作者首次能定价并收到钱"，不是 GPT Store 式的上架数量。
