# Agent 的 Shopify：产品化故事线 v0.1

> [!note] 状态说明（2026-07-17）
> “创作者是 merchant、Combo 提供商业后台”的类比仍可复用；面向所有 Agent Producer 的 Marketplace 口径属于历史叙事。当前公司定义见 [combo-current-story-2026-07](/output/reports/combo/narrative/combo-current-story-2026-07/)。

> Query: "结合之前调研的产品，构思我们的故事线；重点是做 Agent 的 Shopify，帮助生产方表达产品化和交易"  
> 日期: 2026-05-14  
> 用途: BP 叙事、官网 hero、融资邮件、内部产品定义

## 0. 最短版本

过去十年，Shopify 帮商品生产方从 "我会做货" 走到 "我能开店、收钱、履约、复购"。

未来十年，Agent 生产方也会遇到同一个问题：

> 我已经调出了一套能完成任务的 Agent workflow，但我不知道怎么把它变成产品、怎么让别人买、怎么证明有效、怎么持续收费。

我们要做的不是一个泛 Agent Store，而是 **Agent 生产方的产品化与交易系统**。

一句话：

> **Agora is Shopify for agent producers: it turns expert AI workflows into packaged, testable, sellable capabilities.**

中文：

> **Agora 是 Agent 生产方的 Shopify：把专家调出来的 AI 工作流，变成可包装、可验证、可交易、可持续更新的能力商品。**

---

## 1. 为什么要从 Shopify 讲

Shopify 不是 "商品 marketplace"。

它真正做的是把商家的后台能力产品化：

- 商品页
- 库存
- 支付
- 订单
- 履约
- 退款
- 客户关系
- 插件生态
- 数据分析

它让一个小商家不用先变成 Amazon，也能拥有一套商业操作系统。

Agent 经济里会出现同样的角色：**Agent Producer**。

这些人不一定是传统软件开发者。他们可能是：

- 会跑小红书/抖音账号工作流的运营者
- 会做 AI 短视频/漫剧/广告片的创作者
- 会维护高质量 LLM Wiki 的研究者
- 会把 Claude Code/Codex 用到极致的开发者
- 会搭销售、投研、招聘、客服 agent workflow 的行业专家

他们已经有 "货"：一套能反复完成任务的 AI workflow。

但他们还没有 "店"：没有商品定义、商品页、测试、权限、安装、定价、结算、退款、支持和更新渠道。

这就是 Agent 的 Shopify 的切入点。

## 2. 之前调研产品给出的拼图

市场不是完全空白。我们看过的产品已经分别证明了很多原语。

| 产品 | 已经证明了什么 | 还缺什么 |
|---|---|---|
| Claude Artifacts / Websim / YouWare / Promptarium | AI 产物可以展示、发布、remix、形成社区 | 展示 output，不等于交易 production method |
| Agent.ai | Agent listing 应该是 callable schema + metadata + executions + reviews；Agent Pack 可以拆成 `run_full` 和 `run_step_*` | 更偏平台内 builder/runtime，creator settlement 和 BYOC/local 授权不完整 |
| Poe | B 可以提供自托管 endpoint，A 在平台内使用，并按 message / dynamic cost 计费 | 更偏 chat/API bot，不解决复杂 workflow、权限、测试和本地资源绑定 |
| Apify | Automation/Actor 可以按 event、result、usage 计费，并有 payout、quality、run logs | 适合 cloud actor，不适合跨 Claude Code/Codex/Cursor/local worker 的能力包 |
| Relevance AI | Paid agent/tool listing 可以做 project entitlement、退款、clone restriction | 仍偏平台内运行，IP 保护和跨 runtime 能力有限 |
| Smithery | MCP server 可以被发现、连接、OAuth 授权 | connection 不是 transaction；缺定价、分账、失败归因和更新承诺 |
| OpenAI Workspace Agents / AWS Agent Registry | 组织内共享 agent 必须有 RBAC、审批、审计和 admin visibility | 解决企业治理，不解决开放 creator economy |
| Stripe ACP / Agentic Commerce | 商家仍应保留商户记录、客户关系、履约和退款责任 | 面向商品购买，不是 Agent 能力包的履约和归因 |

这些产品共同说明一件事：

> 市场不缺 Agent 分发入口，缺的是帮助生产方把能力表达成商品、把调用变成交易、把结果变成可结算事件的系统。

## 3. 核心洞察：can do != can sell

Agent 时代会出现很多 "会做" 的人。

他们会用 Claude Code 写代码，会用 ComfyUI / 即梦 / 可灵做视频，会用 MCP 抓网页，会用本地账号跑小红书，会用一堆 prompt 和脚本做投研。

但 "会做" 和 "能卖" 之间隔着一整套产品化工作：

```text
can do        -> can explain
can explain   -> can package
can package   -> can install
can install   -> can verify
can verify    -> can price
can price     -> can fulfill
can fulfill   -> can refund / support / update
```

今天大多数 Agent 产品停在前三步：

- 我能做一个 demo。
- 我能把 prompt 或 workflow 发给你。
- 我能给你一个 bot / MCP / repo / template。

真正的交易需要后四步：

- 买家能不能在自己的环境跑起来？
- 跑起来后是否通过 smoke test？
- 失败后是谁的问题？
- 使用了谁的账号和 API quota？
- 按什么事件计费？
- 版本升级会不会破坏旧 workflow？
- 生产方如何持续获得收入？

所以我们的故事不应该是 "我们做 Agent marketplace"。

更准确是：

> 我们做 Agent 能力的产品化后台。

---

## 4. 关键视角一：商品页不是介绍页，是运行合约

普通 marketplace 的 listing 是营销页面。

Agent capability 的 listing 必须是运行合约。

它不只是说 "这个 Agent 很强"，而是机器和人都能读懂：

```yaml
name: xhs-growth-scout
producer: creator_x
runtime:
  - claude-code
  - codex
  - cursor
  - local-browser-worker
inputs:
  - target_account
  - competitor_urls
  - brand_constraints
outputs:
  - research_report.md
  - topic_scores.csv
permissions:
  browser:
    domains: ["xiaohongshu.com"]
    credential_subject: buyer
tests:
  - login_detect_smoke_test
  - no_private_message_export
  - report_schema_validation
pricing:
  model: subscription + protected_step_usage
support:
  update_channel: monthly
  refund_window: 7d
```

这就是 Agent 商品页和普通软件商品页的区别。

它必须同时回答：

- 这个能力做什么？
- 需要什么输入？
- 输出长什么样？
- 在哪里运行？
- 要访问哪些资源？
- 用谁的凭据？
- 怎么验证？
- 怎么收费？
- 失败怎么处理？

所以 **listing = product contract + callable schema + trust surface**。

这点是 Agent.ai 给我们的最大启发：Agent listing 不应只是卡片，而应该是 function schema + metadata + executions + reviews。

---

## 5. 关键视角二：交易的不是 Agent，而是重复完成任务的概率

买家真正购买的不是 "一个 Agent"。

买家购买的是：

> 在我的环境里，以可接受成本，重复完成某类任务的概率。

这句话很重要。

它把 Agent 商品从 "智能体人格" 拉回商业对象：

- prompt 只是源码片段。
- MCP server 只是动作接口。
- workflow graph 只是执行路径。
- runtime 只是履约场所。
- tests 才是质量承诺。
- event ledger 才是交易凭证。

所以 Agent 的 Shopify 不能先做 "好看的 Agent 商店"。

它应该先做 "能力商品的履约系统"：

```text
Package
  -> Install
  -> Bind resources
  -> Run smoke test
  -> Execute task
  -> Record event
  -> Attribute success/failure
  -> Charge / refund / payout
  -> Update package
```

Apify 和 Relevance AI 的价值都在这里。Apify 证明 automation 可以按 event/result/usage 计费；Relevance 证明付费能力需要 project-scoped entitlement。我们要把这些机制迁移到跨 runtime 的 Agent 能力包里。

---

## 6. 关键视角三：产物社区解决展示，能力商店解决复用生产方式

Claude Artifacts、Websim、YouWare、Promptarium 都很重要。

它们证明了 AI output 会变成一种新的社交对象：

- 一个网页
- 一个小游戏
- 一个 dashboard
- 一个 app prototype
- 一个 artifact
- 一个可 remix 的创作结果

但 output sharing 只回答：

> 我做出了什么？

Agent 的 Shopify 要回答：

> 别人如何复用我做出它的方法？

这两个问题差别很大。

一个 Websim 作品可以被点赞、remix、传播；但如果一个买家想稳定复用背后的生产方式，他还需要：

- 生成流程
- prompt / skill
- 工具链
- 资源绑定
- 评测标准
- 版本更新
- 支持边界
- 商业授权

所以我们不应该把 Agora 做成 "Agent 产物 Instagram"。

更好的定位是：

> 从 artifact showcase 往上游走，交易可复现的 production method。

---

## 7. 关键视角四：MCP 解决连接，不解决交易

Smithery、Glama、MCP registry 这类产品很重要，因为 Agent 需要发现和连接工具。

但连接不是交易。

MCP server 被发现以后，生产方仍然要回答：

- 这个 server 的哪个能力可以收费？
- 谁能用？
- 每次调用多少钱？
- 出错算谁的？
- 版本升级如何兼容？
- 是否使用买方凭据还是卖方凭据？
- 怎么退款？
- 怎么证明某次调用产生了价值？

这就是 "tool protocol" 和 "commerce protocol" 的区别。

Shopify 不是 HTTP。

Agora 也不应该只是 MCP registry。

Agora 要做的是 MCP / runtime / local worker 之上的商业操作系统。

---

## 8. 关键视角五：生产方不是 developer，是 merchant

这可能是整个故事里最重要的视角。

很多 Agent 平台默认把供给方叫 developer / builder / creator。

但如果我们讲 Agent 的 Shopify，应该把他们看成 **merchant**。

因为 merchant 要面对的不是 "怎么构建功能"，而是 "怎么经营一个可持续售卖的商品"：

- 商品定位
- 包装
- 定价
- 试用
- 转化
- 履约
- 支持
- 退款
- 复购
- 评价
- 更新
- 分销

Agent producer 也一样。

他需要一个后台，不是一个上传按钮。

这个后台可以叫 **Producer Console**：

```text
Producer Console
  1. Workflow Compiler      把散落 workflow 编译成 package
  2. Storefront Builder     生成商品页 / callable schema
  3. Permission Designer    声明资源、凭据、审批点
  4. Test Lab               smoke tests / canonical tests / regression
  5. Pricing Studio         subscription / event / result / protected step
  6. Install Doctor         帮买家安装、绑定资源、诊断失败
  7. Event Ledger           记录调用、成本、结果、失败归因
  8. Payout / Support       分账、退款、更新、支持
```

这就是产品本身应该长成的样子。

---

## 9. 买方体验：不是浏览商店，而是安装一个可验证能力

买方路径也应该和传统 marketplace 不一样。

不是：

```text
search -> read description -> buy -> hope it works
```

而是：

```text
discover
  -> inspect permissions
  -> choose runtime
  -> bind resources
  -> run smoke test
  -> preview cost
  -> execute task
  -> receive receipt
  -> approve recurring use
```

买方每一步都应该知道：

- 它要访问什么？
- 用谁的账号？
- 会不会写入、发布、付款？
- 预计成本多少？
- 如果失败，能不能退款？
- 这个能力最近在哪些 runtime 里测试通过？

这会让 Agora 和普通 Agent Store 拉开差距。

普通 Agent Store 卖 "试试看"。

Agora 卖 "跑得通"。

## 10. 我们的独特产品切口

可以把产品切成三层。

### Layer 1: Productization

帮助生产方把隐性的 workflow 变成显性的商品：

```text
prompt / scripts / memory / tool config / examples
  -> capability package
  -> listing contract
  -> tests
  -> pricing
```

这是 "Agent Shopify" 最核心的一层。没有这层，供给方只是在上传一堆 prompt、MCP、repo 和 bot。

### Layer 2: Transaction

把一次能力调用变成可计费、可退款、可分账的事件：

```text
entitlement
  -> run token
  -> event ledger
  -> metering
  -> failure attribution
  -> payout / refund
```

Canteen Agora / Circle Arc 给我们的启发就是：Agent Economy 最后会落到 attribution 和 settlement，不是落到 "有多少 listing"。

### Layer 3: Fulfillment

不取代 runtime，但适配 runtime：

```text
Claude Code / Codex / Cursor / Agent-VM / MCP / local worker / hosted step
```

我们的机会不是重新造一个 Agent IDE，而是让同一个能力商品可以在多个 runtime 里被安装、绑定、测试和调用。

## 11. 这版故事如何讲给不同人

### 给投资人

AI Agent 的供给会爆炸，但供给方缺商业化后台。今天的 Agent Store 只解决展示和发现，没解决产品定义、权限、测试、安装、计费、结算和持续更新。

Agora 是 Agent 生产方的 Shopify：我们帮助 creator / expert / power user 把自己调出来的 Agent workflow 变成可安装、可验证、可交易的能力商品。长期看，Agent 经济需要的不只是 MCP 和 runtime，还需要 productization、entitlement、event ledger、settlement 和 reputation。

### 给生产方

你已经会用 Agent 做事了，但你还没有办法把这套能力卖给别人。

Agora 帮你把 workflow 拆成 package，生成商品页，声明输入输出和权限，跑测试，设置定价，支持安装，记录调用，处理退款和分账。你不只是把 prompt 发出去，而是开了一家自己的 Agent 能力店。

### 给买方

你不需要再从一堆 prompt、MCP server、GitHub repo 和模板里自己拼。

在 Agora 上，你购买的是一个经过测试的能力包：它告诉你需要什么权限，能在哪些 runtime 跑，怎么绑定你的资源，预计花多少钱，失败后谁负责。你先跑 smoke test，再决定是否正式使用。

### 给生态伙伴 / runtime

Agora 不和 Claude Code、Codex、Cursor、MCP registry、Agent-VM 竞争。

我们给它们补商业层：让第三方能力能在这些 runtime 中被发现、安装、验证、调用和结算。

## 12. 推荐的 BP 开场故事

可以这样开：

> AI 的第一阶段，让每个人都能生成。  
> AI 的第二阶段，会让一小批 power users 调出真正有生产力的 Agent workflows。  
> 但问题是，这些 workflow 今天没法像商品一样交易。  
> 
> 一个小红书运营者调出了一套选题 + 竞品分析 + 内容生成 workflow；一个研究者维护了高质量的 LLM Wiki；一个开发者沉淀了 repo onboarding 和 code review agent；一个创作者有完整的 AI 短视频 pipeline。  
> 
> 他们都 "会做"，但他们还不能 "开店"。  
> 没有商品页，没有安装流程，没有权限边界，没有测试，没有定价，没有调用记录，没有退款和分账。  
> 
> Shopify 把小商家的商品、支付、订单、履约和客户关系产品化。  
> Agora 要把 Agent 生产方的 workflow、权限、测试、runtime、计费和更新产品化。  
> 
> 我们不是另一个 Agent Store。  
> 我们是 Agent Producer 的商业后台。

## 14. 什么要避免

1. **避免只说 marketplace。** Marketplace 会让人以为你只是做发现和搜索。
2. **避免只说 Agent Store。** 这个词会把你拖进 GPT Store / Coze / Dify template 的比较。
3. **避免只说 capability package。** 这个词太技术，要接上 producer 的商业痛点。
4. **避免只说 Shopify 类比。** Shopify 类比必须落到 productization console、checkout、fulfillment、payout，否则会显空。
5. **避免只讲创作者。** 生产方可以是 creator、developer、operator、researcher、consultant。
6. **避免承诺本地 skill 加密。** 本地标准 runtime 下源码保护不成立，护城河应来自持续更新、测试、托管保护步骤、结算和网络信誉。

## 15. 下一步产品验证

用这版故事反推 MVP，不应该先做 marketplace 首页，而应该先做 **Producer Console v0**。

最小闭环：

1. 选 1 个生产方 workflow。
2. 手工编译成 capability package。
3. 生成 listing contract。
4. 绑定一个 runtime，例如 Agent-VM / Claude Code / Codex。
5. 写 2-3 个 smoke tests。
6. 设置一个 pricing model。
7. 让 3 个买方安装并跑通。
8. 记录 event receipt。
9. 手工处理一次失败/退款/更新。

目标不是上架 100 个 Agent。

目标是证明：

> 一个 Agent 生产方能从 "我会做" 走到 "我能卖"，并且买方能从 "我看懂" 走到 "我跑通"。
