# Pilot Protocol 与 Combo 的战略关系

> 生成时间：2026-07-29  
> 查询：Pilot Protocol 与 Combo 是什么关系，是竞品、基础设施、分发渠道还是合作方？

## 摘要

**按 Combo 当前边界，两者不是正面竞品。** Pilot 主要解决“一个 API / CLI 能力如何被 Agent 发现、安装和调用”；Combo 主要解决“一个人的方法如何被封装成消费者愿意付费、能够验收并在失败时获得补救的结果产品”。

最准确的关系是：

> **Pilot 是潜在的 Agent 能力分发与调用基础设施；Combo 是结果产品化、履约、交易和经营系统。Combo 可以成为 Pilot 上的一个 publisher，也可以把 Pilot App 当作履约工具，但现阶段不应该把 Pilot 变成 Combo 的核心技术依赖。**

两者真正重叠的是 Combo 旧 Agora 叙事中的“Agent Capability Package / Agent Marketplace / 能力分发平台”。Combo 当前已经主动把这一层降为后台机制，并把前台商品改成明确结果，因此战略上应避免重新滑回“做另一个 App/Skill directory”。

## 一、最关键的区别：两边卖的不是同一种东西

| 维度 | Pilot Protocol | Combo |
|---|---|---|
| 最小供给单元 | App / Adapter / method | 有明确输入、交付、价格、验收和补救的结果 SKU |
| 供给者提交 | HTTP API、CLI、methods、权限、版本 | 案例、方法、标准、边界、历史内容/服务轨迹 |
| 消费者动作 | Agent 安装 App，然后调用 method | 用户提交自己的 Context、付款并验收结果 |
| 直接消费者 | 用户自己的 Agent | 有具体问题的人 |
| 用户价值 | Agent 获得一个新工具或远程能力 | 用户获得一份可直接使用的成品或状态变化 |
| 运行闭环 | discover → install → call → response | contract → context → execution → verification → settlement / refund |
| 核心记录 | App、method、grant、call、node | Context、服务版本、Run、结果、Verdict、退款、复购 |
| 主要信任问题 | binary 是否可信、权限是否越界、网络与 publisher identity | 结果是否达标、谁负责、如何返工/退款、创作者如何持续纠正 |
| 当前商业方向 | 企业私网、SLA、未来 listing / call / payment | 结果交易抽成、履约和经营系统 |

一句话：

> **Pilot 把“能力”变成 Agent 可调用的方法；Combo 把“方法”变成用户可购买、平台可负责的结果。**

这也是为什么 Pilot 的 `App` 不能直接等同于 Combo 的“AI 产品”。前者只要 method 能正常返回，就基本完成技术履约；后者还必须回答范围、质量、时限、异常、返工、退款和收益分配。

## 二、两者在同一条技术栈上的位置

如果未来一个用户让自己的 Personal Agent 购买 Combo 服务，完整链路可以是：

```text
创作者的经验、案例和方法
          ↓
Combo 将其做成结果合约
          ↓
Combo Runtime 组织模型、工具和真人履约
          ↓
Combo HTTPS endpoint
          ↓
Pilot Adapter（可选）
          ↓
用户自己的 Agent
          ↓
用户提出目标、付款、验收结果
```

这里：

- **Combo 拥有商品定义和履约责任**；
- **Pilot 负责让用户 Agent 找到并调用 Combo**；
- Pilot Adapter 只是调用 Combo API 的薄翻译层；
- 用户最终买的依然是 Combo 的结果，不是 Pilot Adapter。

所以，如果类比：

| 现实系统 | 对应角色 |
|---|---|
| Shopify 商家 / 服务商 | Combo 上的创作者及结果产品 |
| 商品、订单、履约、退款 | Combo |
| App protocol / package installer / network | Pilot |
| 用户侧浏览器或 Personal Agent | Pilot-enabled Agent |

Pilot 更像“Agent 端的 App distribution + connectivity”，而 Combo 更像“专业服务商品化和交易履约系统”。

## 三、四种可能关系

### 1. Pilot 成为 Combo 的分发渠道

Combo 可以把一个已经验证的结果 SKU 暴露为 HTTPS API，再通过 Pilot 发布为 App。例如：

```text
combo.brand-audit.quote
combo.brand-audit.submit
combo.brand-audit.status
combo.brand-audit.deliver
```

用户自己的 Agent 发现并安装这个 App，提交材料、获取报价、创建订单并领取交付物。

这时 Pilot 类似一个新的 Agent-native channel，Combo 类似能力提供者和 merchant。

但当前 Pilot catalogue 只有约 23 个 active App，真实付费调用量也没有公开验证，因此它只能算一个低成本分发实验，不能成为 Combo 当前 GTM 假设。

### 2. Pilot App 成为 Combo 的履约工具

Combo Runtime 在完成一个结果时，可以调用 Pilot App：

- 搜索、数据查询、图片生成；
- 本地 CLI；
- 远程 specialist agent；
- 钱包或支付能力。

但如果同一能力已有稳定 HTTPS、MCP 或标准 SaaS API，Combo 没有必要为了调用它额外引入 Pilot daemon、overlay network 和本地 binary。只有出现以下条件时才值得采用：

- 工具运行在用户本地设备；
- 需要跨 NAT 主动调用；
- 必须利用 Pilot 独有的 specialist supply；
- Pilot 能提供明显更低的接入与交易成本。

### 3. Pilot 成为 Combo 的底层网络

这是最不应该现在做的关系。

Combo 当前首要任务是证明：

- 一个结果 SKU 是否有人付款；
- 是否明显优于裸通用模型；
- 真人分钟、退款和贡献毛利是否成立；
- 用户是否复购；
- 创作者是否持续发布。

这些问题用普通 HTTPS、队列、数据库、支付和 sandbox 就能验证。引入 Pilot 的 daemon、identity、overlay、catalogue、wallet 和 skill channel，不会提高这些核心假设的通过率，只会增加部署、安全和生态依赖。

因此，Pilot 不应成为 Combo MVP 的 architecture commitment。

### 4. 未来平台层发生竞争

如果两者都向横向平台扩张，才可能竞争：

- Pilot 从“App method marketplace”上升到按任务路由、支付、声誉和结果保证；
- Combo 从“垂直结果产品”下沉到通用 Agent App packaging、安装、网络和钱包。

这个重叠区正是 Combo 应避免过早进入的区域。Pilot 已经证明这里需要很重的 infra，但尚未证明 marketplace demand；Combo 若复制同一路径，会同时丢失当前的创作者分发优势和结果履约差异。

## 四、Pilot 对 Combo 最值得学习的东西

即使不采用 Pilot 网络，Combo 可以吸收它的五个设计：

### 1. 声明式能力描述

用 spec 描述：

- 能力名称；
- 输入参数；
- 输出；
- 时延类别；
- backend；
- auth；
- 权限。

Combo 可以在此基础上增加结果产品需要的：

- 价格；
- 时限；
- rubric；
- 适用与拒绝条件；
- 返工、升级真人和退款；
- 创作者收益规则。

### 2. Adapter 与 Backend 分离

Pilot 的 adapter 很薄，重能力留在原 API / CLI。Combo 也不应把每个创作者产品做成完全独立的 runtime；应让“结果 SKU 定义”与“可替换模型、工具、真人和 backend”分离。

### 3. Manifest 与权限显式化

每个 Combo 产品也需要自己的 manifest：

```text
输入与 Context 权限
+ 可调用工具
+ 可见数据范围
+ 输出边界
+ 真人升级规则
+ 费用上限
+ 版本与 provenance
```

这比一段 Prompt 更接近可经营、可审计的产品对象。

### 4. 首次调用体验

Pilot 为 App 提供 help method、product demo 和 next-steps graph。Combo 同样需要让消费者或其 Agent 清楚知道：

- 这个产品适合什么问题；
- 第一条输入怎么提交；
- 缺材料时下一步是什么；
- 失败、超预算或需要真人时怎么办。

### 5. Agent 作为新的需求入口

长期看，Combo 的消费者不一定亲自浏览货架；他的 Personal Agent 可以代表他选择、购买并跟踪专业服务。Pilot 提供了这一未来的一个具体接口形态。

但 Combo 的控制点仍应是结果合约、Context、订单、履约和 Verdict，而不是某一条网络协议。

## 五、Pilot 不能替 Combo 解决什么

Pilot 的 install/call/payment 不能自动补齐：

1. 用户究竟愿意为什么结果付钱；
2. 创作者方法是否优于通用模型；
3. 如何定义可验收的 result contract；
4. 失败由谁负责；
5. 何时返工、退款或升级真人；
6. 创作者如何授权、纠正和获得收益；
7. 什么 Context 可以被使用；
8. 一次结果如何形成复购、声誉和更好路由。

x402 或 wallet 只解决付款动作，不等同于 Combo 所需的订单、托管、分账、退款和争议系统。

同样，App call 成功只说明 API 技术返回，不说明用户认为交付物有价值。

## 六、当前战略建议

### 现在

- 不把 Pilot 视为直接竞品；
- 不把它作为 Combo 核心基础设施；
- 不复制其通用 App Store / Agent directory；
- 学习其 spec、manifest、permissions、adapter 和 first-call 设计；
- 保持 Combo 服务拥有标准 HTTPS API，使未来接入 Pilot、MCP 或其他 Agent channel 都很薄。

### 在一个结果 SKU 被真实验证之后

可以做一个最小 Pilot channel experiment：

1. 只发布一个低风险、可验收的 Combo 结果 SKU；
2. 用 HTTP adapter，不引入本地 CLI 与复杂权限；
3. 让 Agent 完成报价、下单、状态查询和领取结果；
4. Combo 继续掌握用户授权、订单、履约、退款和创作者分账；
5. 用付费结果而不是 install/call 数验收。

关键指标：

```text
Pilot 发现
→ 安装
→ 首次有效调用
→ 提交完整 Context
→ 付款
→ 完成交付
→ 验收 / 退款
→ 复购
```

只有出现来自 Pilot 的非补贴真实付款、合格交付和复购，它才从“技术兼容”升级为“有效渠道”。

## 最终判断

| 问题 | 判断 |
|---|---|
| 是直接竞品吗？ | 当前不是；只有双方都做横向 Agent marketplace 时才重叠 |
| 是 Combo 上游基础设施吗？ | 技术上可以，现阶段没有必要成为核心依赖 |
| 是潜在渠道吗？ | 是，未来可把 Combo 结果 SKU 发布成 Pilot App |
| 是潜在供给源吗？ | 是，Combo Runtime 可选择性调用 Pilot Apps |
| 最值得学习什么？ | spec、adapter、manifest、权限、first-call 与 Agent-native discovery |
| 最大误区是什么？ | 把 method 可调用误认为结果可交易，把 App 数量误认为市场需求 |

一句话收口：

> **Pilot 让能力进入 Agent；Combo 让能力进入交易和现实结果。当前最好的关系是兼容、学习、保留渠道期权，而不是基础设施绑定或重新把 Combo 做成 Agent App Store。**
