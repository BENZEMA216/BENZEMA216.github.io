## 结论先行

### 一句话

> **AI 会把大量专业服务从“出售人的时间”改造成“由人的方法、Agent 与少量人工共同运行的 Service Product”，并催生大规模的 AI-native Practices。Combo 从 Agent Miniapp 切入，让第一项服务出生；继而成为一门 AI 服务生意的 Practice OS；再让模型、工具、数据、人类专家、渠道和买方 Agent 围绕同一服务对象协作，最终成为 AI-native Service Commerce Network。**

### 未来终局的连续路径

```text
Agent Miniapp Launcher
→ AI-native Practice OS
→ Service Extension Economy
→ Outcome Demand Network / Service Commerce Infrastructure
→ General Agent 的 Specialist Procurement Rail
```

这条路径里，用户、商品和资产始终连续：同一个 Provider、同一个 Service Product、同一批客户与订单、同一段结果与经营历史。今天做的不是一张网页，而是未来平台的第一项结构化服务库存；每一笔订单，都可能成为一门 Practice 的经营状态；每一个独立 Partner 的接入，都可能把单边软件推进为扩展经济。

2035 年，一个用户可以告诉自己的 Agent：“下个月帮我完成日本众筹上线，预算两万元。”Agent 会通过 Combo 组合采购品牌诊断、本地化、众筹页和投放审核。另一端，一位专业者不再逐单出售时间，而是在 Combo 经营十几项由 Agent 主执行、由本人处理异常的服务。Combo 位于两者之间，组织 Service identity、Context、订单、履约、采用、补救和收益。

完整未来图景、五种平台形态、复利循环与融资 BP 表达见 [combo-platform-future-vision-and-evolution-2026-08-03](/output/reports/combo/narrative/combo-platform-future-vision-and-evolution-2026-08-03/)。下文保留的代码、经济和 Gate 研究，是对这幅未来的承销与反论，不再充当愿景本身。

### 当前事实距离这幅未来还有多远

创作者侧 Design Studio 已经不是普通 Landing Page Builder。它能把冻结的 Capability 契约变成一个任务型 Miniapp，创作者填写真实输入，主操作按生成契约通过 `combo:run` 调用 Combo Runtime；页面和 Run 也已有版本与事件记录。但“不得伪造结果”目前主要是 Prompt 契约，现有 validator 只能检查 bridge 形态及少数 timer / random 模式，不能提供语义上的反伪造保证。

但代码审计发现一个更早的断点：**这个 Miniapp 目前只在 Studio 中设计和试跑，还没有作为不可变发布资产绑定到 Capability Version 并进入普通消费者链路。** 当前消费者打开公开能力页后仍进入通用试用页，而不是已审核的 Studio Miniapp。Round 1 又发现，本地工作树新做了 KOL 主页冷启动与“体验发布”页面，但前者的样本校准不经过最终 Runtime，后者只保存到浏览器并生成本地预览。因此 Combo 现在不是一个已经完成发布闭环的 Agent 建站工具，而是五套相邻能力：

```text
素材 / Session → Capability Version → 发布与目录
公开主页 / 创作者回答 → authoring 样本校准 → Capability Version
Capability → 通用 Runtime → Run / Message / Artifact
Capability → Studio Miniapp → Revision / Test Run
Studio 退出 → 本地定价 / 命名 / “体验发布”预览
```

第二条链降低了供给冷启动成本，是有价值的创作者获取与校准增量；第五条链诚实标注为“尚未上线”，是 UX prototype。它们都没有把 Studio Surface 交给陌生消费者，也没有形成付款、授权或履约事实。最先要做的是把当前普通 Runtime HTML artifact 改成静态隔离，关闭已存在的消费者安全 P0；随后只建立能够支持真实实验的最小服务端 Publication 与可信宿主界面，不把完整交互 Miniapp 工程当作需求验证的前提。只有对照实验表明任务型 Miniapp 相对可信表单显著提高付款、明确采用或复购，才继续投资完整的 Surface binding、隔离与 typed action。

完成这道发布 Gate 后，系统记录的核心仍然只是：

```text
Capability
→ 自包含 HTML
→ prompt
→ Runtime Run
→ artifact / message
```

它还不是：

```text
Result Contract
→ 身份与授权
→ Order
→ Context
→ Run / 人工接管
→ Evidence
→ Verdict
→ 返工 / 退款
→ Settlement
→ 复购 / 路由改进
```

前一条链路最多证明“一个 Agent 可以拥有可设计、可试跑的产品界面”；后一条链路才可能让 Combo 成为 AI-native 专业服务的经营、交易与责任基础设施。

### 最重要的战略迁移

| 维度 | 当前容易形成的心智 | 应迁移到的心智 |
|---|---|---|
| 核心对象 | 一个 Agent 网站 / Miniapp | 一个可履约的 `Result Product` |
| 用户动作 | 创建、装修、分享页面 | 定义结果、经营订单、处理例外、持续改进 |
| 消费动作 | 打开页面、发出 Prompt | 提交 Context、授权、购买、验收、返工或复购 |
| 核心记录 | HTML、版本、调用量 | `Contract × Context × Run × Verdict × Economics` |
| 竞争基线 | 建站与 App Builder | 服务商 OS、结果公司、服务市场、交易基础设施 |
| 平台证据 | Agent 数、页面数、调用数 | 跨供给购买、平台新增需求、因果路由增益、第三方依赖 |

### 当前推荐

1. **先关闭当前消费者安全 P0，再建立最小真实发布**：普通 Runtime HTML 必须先 fail closed；首批需求用可信宿主表单 / declarative Surface 和服务端 Publication 验证。完整 `ExperienceSurfaceVersion`、交互隔离与 typed action 只有在 Surface 相对可信宿主 UI 对付款、采用或复购出现预注册 uplift 后才升级为主工程。结果正确性始终由 Result Contract 与 Verdict 证明。
2. **先修当前 Runtime HTML P0**：普通消费链的 Runtime `kind="html"` 产物现在默认进入可执行 renderer；在任何陌生消费者 pilot 前，必须先默认改为静态、网络隔离回显，不能等待未来 Surface Publication 一并解决。
3. **把原型状态和生产事实分开**：`authoring sample calibration`、本地“体验发布”和最终 Runtime / Publication 必须使用不同对象、事件与指标；未产生后端 Publication、精确 Surface hash 和真实 Run 的行为不得计入发布率或完成率。
4. **重写内部产品原子**：不再把 Agent Page 当终点，把它定义为 `Result Product` 的交互表面。
5. **先决定在验证哪一个市场**：专业团队内部反复生产、协作和审核的 `Workflow OS`，与粉丝为创作者方法生成的结果付费的 `Result Commerce OS`，是两套买家、触发、频率、GTM、留存与 P&L；现有访谈只支持前者，不能把工作流痛点自动桥接成粉丝购买。
6. **把专家 Result OS 降为待验证主干，而非既定商业概率**：先找到一个自然发生的 Buyer Job，验证独立买家是否相对免费通用模型愿意自付、采用和在自然周期内复购；再验证创作者能否在无创始人陪跑下持续处理订单、版本、返工、客户与收入。代码距离近不等于用户需求概率高。
7. **先选清资金链和收费对象**：创作者用自己的商户账户直收，只能把买家付款算作创作者 GMV；Combo 只有实际收到的 SaaS、usage 或服务费才是收入。若 Combo 收款再向创作者结算，则进入另一套 seller / merchant of record、退款、分账和责任经济。两种模式不得共用同一 `GMV - Creator Payout` 公式。
8. **不要预选唯一终局**：前 100–1,000 笔真实交易要判断用户忠于专家、结果、Combo 品牌、项目 Context，还是外部渠道；在此之前不得把 creator deep link 订单称为平台需求。
9. **只在垂直 system of record 成立后验证三条平台上行**：
   - 平台开始产生需求和跨供给购买，长成精选结果网络；
   - 外部内容、模型与 SaaS 持续把订单交给 Combo，长成嵌入式结果商业基础设施；
   - 外部 Agent 获得预算与权限后，长成机器采购、验收和结算接口。
   内容到行动只先作为获客机制；企业工作台是需要独立团队与 GTM 证据的战略分支，不与前三条同时投入。
10. **接受一个重要反直觉**：如果某一垂类高度集中，Combo 变成一家垂直结果公司，可能比急着成为中立平台更大、更快，也更真实。
11. **退出通用创建层的正面战争**：不要把下一阶段定义为更多模板、Agent 目录、连接器或任意 HTML；Google、Microsoft、OpenAI、腾讯、Wix、Canva 等已把 Builder、Runtime、Identity、Registry、Governance、UI 和分发做成平台能力。Combo 的当前 listing 只是已发布 Capability 的内部卡片投影，不是拥有需求、履约或结算的 Marketplace。
12. **把候选机会收窄为“垂直责任后台”**：前台可以存在于微信、ChatGPT、创作者主页或第三方 SaaS；Combo 若不能持续拥有 Result Contract、授权、Run / 人工接管、明确 Verdict、补救和责任经济，就不应称为平台。先成为一个垂类的 workflow / fulfillment system of record，再由第三方依赖决定能否升格。
13. **把渠道当租来的 Surface，而不是已获得的分发**：中国入口分别控制主体、类目、审核、域名、支付、订单同步、售后和结算。每个渠道都要有独立接入、事件和商业 Gate；“发布一次，到处运行”在当前官方规则下不是事实。

## 0. 证据口径

全文使用五类口径：

- **事实**：来自当前代码、真实产品行为、官方文档、监管文件或公司申报文件；
- **强推论**：由多个事实共同支持，但仍可能被新证据推翻；
- **待验证假设**：需要 Combo 自己的用户、订单、成本与 cohort 数据回答。
- **战略建议 / 实验 Gate**：建议投入顺序或预注册的通过 / 停止条件，不是事实；
- **实施 Gate**：必须由技术测试、安全审查、法律 / 治理决策或 Partner / 渠道协议关闭的问题，不能等同于“用户数据会回答”。

“建议”不是事实。所有数字 Gate 若没有真实基线，都应被视为实验预注册值，而不是行业规律。

为避免后文把路线裁决伪装成事实，统一采用以下解释规则：

- “结论先行”中的主干、优先级和分支属于**战略建议 / 待验证假设**；其中对当前代码状态的描述，以第 1 节的事实和内容快照为准；
- 第 1、3 节中明确列为“事实”且附真源的内容，才是已确认事实；
- 第 4–23 节的路线、公司形态和平台上限，除非另行标注，属于**待验证战略假设**；其中嵌入的代码、监管与渠道快照仍按“事实”处理，建议顺序按“战略建议 / 实验 Gate”处理，安全、法律、治理与渠道前置条件按“实施 Gate”处理；

### 1.1 创作者侧 Studio 已不是普通建站

**事实：**

- Design Studio 要求主交付物固定为 `artifactKey="main"`、`kind="html"` 的完整自包含 HTML；
- 页面主操作必须使用真实表单内容，通过 `window.parent.postMessage({ type: 'combo:run', version: 1, prompt }, '*')` 调用 Combo Runtime；

- 同一 `artifactKey` 会生成版本历史，Studio 另有成功 Revision 和真实 Test Run；
- Capability 已有冻结版本、输入字段、输出类型、风险级别和 red lines，Runtime 会校验 manifest hash。

## 2. 什么才叫平台级机会

“平台”不是更大的工具，也不是多一个 Marketplace 页面。一个产品至少要经过四层：

| 层级 | 第三方为什么用 | Combo 拥有什么 | 典型证据 |
|---|---|---|---|
| 工具 | 更快完成一次创建 | 编辑器、生成、Runtime | 首次成功率、生成时长 |
| Operating System | 持续经营离不开它 | 客户、订单、版本、履约、支付等 system of record | 周期性使用、D90 留存、迁移成本 |
| Network / Marketplace | 其他参与者的加入提高我的收益 | 需求、供给、匹配、信任和交易治理 | 跨供给购买、流动性、平台新增 GMV |
| Protocol / Infrastructure | 外部产品围绕其对象和状态运行 | 标准、身份、权限、事件、结算与责任接口 | 第三方集成、机器调用、跨渠道交易 |

### 2.1 本报告采用的平台判定

Combo 不能因为以下六项“多数通过”就被称为平台；那会把一个强 system of record、垂直结果公司或服务 OS 误判为平台。前两项是硬前提，后四项是支撑条件。

**两个硬前提必须同时成立：**

1. **独立第三方围绕标准对象构建或交易**：不是 Combo 自营团队在内部复用，而是独立供给者、渠道、开发者或 Agent 围绕同一个对象和接口持续创建、交易或执行，并形成真实依赖；
2. **跨参与者增益**：新增供给、需求、渠道或结果数据能够因果改善另一个独立参与者的体验或经济，而不是只让 Combo 自己规模化。

在两个硬前提成立后，还要观察系统记录、治理、经济捕获和可迁移前台等支撑条件：

3. **系统记录**：关键业务状态不是页面里展示，而是长期留在 Combo；
4. **治理权**：Combo 能定义身份、权限、质量、争议、退款或结算中的至少一项关键规则；
5. **经济捕获**：参与者增长能够提升平台收入或降低边际获客 / 履约成本；
6. **可迁移前台**：若某个外部入口完成主体、审核、身份、支付和事件回传验证，用户从该入口进入后，Combo 的关键记录和责任仍不消失。

因此，C 专家 OS 和 E 垂直结果公司可以是很大的公司，也可以拥有强记录、治理与毛利；只要没有独立第三方依赖和跨参与者增益，就仍不是本报告意义上的平台。

### 2.2 三种伪平台

- **供给伪平台**：Agent 很多，但每个 Agent 各自获客、各自使用，彼此没有增益；
- **流量伪平台**：页面和内容很多，但流量不能转成真实结果订单和复购；
- **数据伪平台**：积累大量 Prompt、对话和 Context，但没有可比较 Verdict，也没有证明它改善下一次结果。

## 3. 结构与历史类比：创建之后，哪些经营对象曾变成控制点

本节不是对 Wix、Shopify、ServiceTitan 或 Fiverr 做完整因果史，也不以今天的产品页反推当年的唯一动机。现有官方材料主要核对它们今天连接了哪些经营对象、收入或责任落在哪里、哪些关键状态被保留。下文每节先列**事实（官方当前快照）**，再列“结构模式”和“对 Combo 的含义”两类**强推论**。结构图中的箭头表示对象依赖与经营层叠加，不代表已经由纵向史料证明的唯一时间顺序。它们提供可反驳的类比，不证明 Combo 用户一定沿相同路径演化。

### 3.1 Wix：网站工作台连接 CRM、支付与 Partner 经营

**事实（官方当前快照）：**

Wix Studio 官方把网站之外的 CRM、支付、预约、订阅、发票、角色权限、客户交接和多站点管理放进一个工作台；Partner Program 再加入收入分成、线索、服务 Marketplace 与模板交易。[Wix Business Solutions](https://www.wix.com/studio/business-solutions)、[Wix Partner Program](https://www.wix.com/studio/partner-program)

**结构模式（强推论，不是纵向因果史）：**

```text
一次建站
→ 站点承接真实业务
→ CRM / 预约 / 支付 / 运营持续发生
→ 代理商管理多个客户
→ 平台获得经营频率和生态
```

**对 Combo 的含义（强推论）：**

Miniapp 只是一次创建。如果订单、审核、返工、版本、客户与收入不在 Combo 持续发生，Combo 会保留建站工具的低频结构。

### 3.2 Shopify：外部前台接入，commerce lifecycle 留在 Admin

**事实（官方当前快照）：**

Shopify 2025 年 76% 收入已来自 Merchant Solutions，主要与支付、金融、物流、POS、App Store 和买家获取相关；其 App Store 超过 21,000 个应用。[Shopify 2025 Form 10-K](https://www.sec.gov/Archives/edgar/data/1594805/000159480526000007/shop-20251231.htm)

2026 年，Shopify 允许商品在 ChatGPT、Copilot、Google AI Mode 和 Gemini 等外部 AI 入口被发现和购买，但订单仍回到 Shopify Admin，商家保留 merchant of record、客户关系和数据；Shopify 的表述是，它已经统一了商品、支付、欺诈、税、履约和订阅等完整 commerce lifecycle。[Shopify Agentic Storefronts](https://www.shopify.com/news/agentic-commerce-momentum)

**结构模式（强推论，不是纵向因果史）：**

```text
在线店铺 Builder
→ Catalog / Order / Payment 成为系统记录
→ Merchant Solutions 随 GMV 增长
→ 开放 App / Channel 生态
→ 新前台出现时，交易状态仍回到 Shopify
```

**对 Combo 的含义（强推论）：**

Combo 不一定要赢得所有消费者前台。只有当某个入口分别通过主体、审核、身份、支付和事件回传 Gate 后，Miniapp 才可能在该入口被发现、跳转或嵌入；而且只有 Result Contract、授权、Run、验收、退款和结算仍回到 Combo，这个入口才支持基础设施路线。

### 3.3 ServiceTitan：Core platform 连接支付与融资 usage revenue

**事实（官方当前快照）：**

ServiceTitan 的 Core platform 以订阅收费，同时通过平台内支付和融资获得 usage revenue；官方把自己定位为 trades 的 operating system。[ServiceTitan 2026 Form 10-K](https://investors.servicetitan.com/static-files/84e016f3-9a75-4199-ad42-b3babe1bb3dd)、[ServiceTitan Investor Relations](https://investors.servicetitan.com/)

**结构模式（强推论，不是纵向因果史）：**

```text
一个垂直工作流
→ 成为订单与运营 system of record
→ 支付、融资、营销等附着
→ Agent 接管更多已结构化工作
```

**对 Combo 的含义（强推论）：**

先成为一个垂直的结果经营 OS，不应因为它不是 Marketplace 就被预先判为“小机会”；它的规模上限仍必须由具体垂类 TAM、客单、频率、毛利和扩张成本验证。若这些指标成立，system of record 才可能成为未来第三方生态的底座。

### 3.4 Fiverr：投资履约层，同时面对活跃买家与收入下滑

**事实（官方当前快照）：**

Fiverr 2026 年正从交易 Marketplace 向 work platform 演化，重点建设 scope、progress、quality、端到端 fulfillment 和 outcome-based matching；早期测试称 mismatch 下降接近 10%。同期年活买家同比下降 17.8%，Marketplace revenue 同比下降 13.6%。[Fiverr Q1 2026](https://investors.fiverr.com/news-releases/news-release-details/fiverr-announces-first-quarter-2026-results)、[Fiverr Q1 2026 Shareholder Letter](https://investors.fiverr.com/static-files/78d482cc-b2ec-49d4-8c4a-7b17ef44ca5f)

**强推论：**

这组同期数据不能隔离因果，但足以否定“有目录、交易历史和 AI 匹配就必然健康增长”的说法。

**对 Combo 的含义（强推论）：**

Combo 不应从“上架更多 Agent”复制 Marketplace 的表面，而应从结果范围、过程、质量和补救这些成熟 Marketplace 仍在补的深层机制开始。

### 3.5 模型平台：Builder、Runtime、目录和 UI 已经是正面竞争区

**事实（官方当前快照）：**

OpenAI Apps SDK 仍处于 preview，但已允许开发者同时定义应用逻辑和界面、连接自己的后台；截至 2026-07-09，公开发现入口已由 App Directory 迁移到 Plugin Directory，App 继续作为 Plugin 内连接外部数据与行动的底层集成。Google Gemini Enterprise Agent Platform 已覆盖 Runtime、长任务、Memory、Identity、Registry、Gateway、Simulation、Evaluation、Observability 和 partner Agent Marketplace。[OpenAI Apps SDK 当前说明](https://help.openai.com/en/articles/12515353-build-with-the-apps-sdk)、[OpenAI Plugin Directory 说明](https://help.openai.com/en/articles/20001256-plugins-in-chatgpt-and-codex)、[Google Agent Platform](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)、[Google Agent Marketplace](https://cloud.google.com/blog/products/ai-machine-learning/partner-built-agents-available-in-gemini-enterprise)

Round 3 按官方发布状态进一步拆开：

| 平台 | 当前已公开的吸收面 | 状态与边界 |
|---|---|---|
| OpenAI | Codex、Agents SDK、Apps / Plugins，以及 ChatGPT Sites 的 prompt-to-site、托管、分享、登录、表单与第三方支付 | Apps SDK / Sites 等仍有 preview / beta 边界；旧 Agent Builder 与 Evals 已宣布在 2026-11-30 后停止可用，说明依赖单一上游产品层也有退场风险 |
| Anthropic | Claude Code、Artifacts 的公开链接 / 嵌入 / 托管 / 存储 / MCP、Managed Agents 的 sandbox、state / memory、permissions、schedule、webhook 与 observability | Managed Agents、部分 Artifacts 能力仍为 preview / beta；官方当前产品面未证明其原生承担第三方服务卖家的 MoR、履约与 payout |
| Google | ADK、Vertex AI Agent Engine、Interactions API、Gemini Managed Agents、Gemini Enterprise Agent Gallery / Marketplace，以及 UCP 的 checkout / order / adjustment 规范 | 不同能力分属 GA、Preview 与 rollout；UCP 明确 business / retailer 保持 MoR 和客户关系，不能把协议覆盖写成 Google 已承担履约 |
| Microsoft / GitHub | Copilot Studio 的多渠道发布、Agent Store、Agent 365 的 Entra identity / governed MCP / observability、Foundry Agent，以及 GitHub coding agent / CLI / automations | 企业身份、采购与治理很强；部分 hosted agent / Spark 能力仍为 preview，Marketplace 采购不等于消费服务结果担保 |
| Replit / Lovable / Vercel | prompt-to-full-stack、auth、DB、storage、deploy、logs / monitoring、browser test、安全修补和 Stripe / Paddle checkout | 商户仍连接自己的支付或 MoR provider；这些产品没有自动承担服务结果验收，但足以让 Runtime、hosting、auth 和支付接线商品化 |

**强推论：**

通用 `Agent Builder + Runtime + Plugin / App Directory` 是 Combo 最不应正面选择的战场。模型平台拥有模型、默认入口、账户、权限、分发和开发者生态；Combo 只有找到**模型平台当前未充分提供、用户又愿意付费的**垂直结果、真人授权、质量版本、补救和结算增量，才有差异化空间。本文不推测模型平台长期“愿不愿意”进入这些层。

### 3.6 Round 3：产业不是一片空白，而是五个控制面从四周合围

下面不是把不同公司强行归为同一“竞品类别”，而是回答一个更具体的问题：**当用户从提出意图走到结果被履约，谁已经控制了哪一段真实状态？**

| 控制面 | 已有官方产品事实 | 已经吸收的 Combo 薄层 | 尚未由这些事实证明被完整吸收的部分 |
|---|---|---|---|
| 意图与分发 | ChatGPT Apps / Plugins 可承载 UI、数据与行动；腾讯元器可把智能体发布到微信客服、公众号、服务号、企业微信和应用商店；Microsoft Agent Store、Google Agent Gallery 已提供组织或生态分发 | Agent 入口、目录、账户、权限提示、宿主 UI、基础调用 | 某一专业结果的责任合约、跨入口可迁移的验收与补救记录 |
| Builder、Runtime 与治理 | Google Gemini Enterprise 已把 Agent Studio / ADK、Runtime、Memory、Agent Identity、Registry、Gateway、Simulation、Evaluation、Observability 组合起来；Microsoft Agent 365 / Copilot、腾讯 WorkBuddy 也覆盖 Agent、Skill / MCP、身份、渠道和治理；部分 Marketplace 能力仍为 Preview / Pre-GA | 通用 Agent Builder、连接器、Runtime、Registry、Eval、Observability、企业治理 | 对具体结果质量与商业责任的垂类定义；不能因为平台原语完整就推定最终履约可靠 |
| 业务状态与经营后台 | Wix Headless 明确把自己定位为 AI-built sites / apps 的 business backend，提供 eCommerce、Bookings、Events、CMS 与 secure payments；Shopify 把 catalog、order、payment、fraud、tax、fulfillment 留在 Admin；Kajabi 已拥有专家内容、客户、营销、支付与 client experience | AI 前台连接 CRM / Catalog / Order / Payment、专家知识问答、创作者经营工作台 | 新垂类独有的 Result Contract、质量 rubric、人工例外和明确采用 Verdict |
| 服务供给与履约 | Gumroad Commission 已有 buyer instructions / files、50% deposit、deliverable、creator 标记完成和余额释放；Upwork 已有 milestone、escrow、accept / request changes / dispute；Fiverr 已有 requirements、delivery / draft、accept / revise、partial refund，并用 creator-trained model + seller edit / handoff 组织 AI 交付 | 水平服务发现、匹配、供给信誉、合同、里程碑、修改、争议和人工履约网络；`Result Contract` 字段与 human exception 本身也不是空白 | 某一垂类中可机器验证的结果本体、随真实 Verdict 改善的异常判例，以及由此产生的质量 / 成本优势 |
| 交易规则与责任 | 微信、小红书、抖音分别要求主体、类目、审核、域名 / 挂载、支付与订单 / 售后状态；抖音服务市场还存在用户确认实施、资金冻结、退款协商与结算规则 | 流量、商户准入、支付、订单、售后、结算和平台排序 | Combo 是否能经合同获得完整责任事件，以及跨渠道保留同一结果账本 |

**当前代码位置（Verified Fact）：**

- `marketplace_listings` 只保存 Capability、Version、slug、card、status 和搜索投影；Runtime 列表也只返回名称、tagline、类型和 byline。表名中的 Marketplace 不代表已有买家、订单、匹配、付款或履约市场；
- `capability_tiers.price_micros` 是定价字段，不是支付事实；收益页源码明确写明本期没有独立收益 / 结算端点，余额和收益为占位，提现为“本期未开放”；
- `skill_set` 仍是字符串数组；当前 Runtime API 契约记录 Session、Run、Message、Artifact、Revision 和 Test，没有外部渠道 connector、订单、退款、结算、seller / MoR 或服务责任对象。

因此，Combo 当前主要处于上述第二层的早期 Builder / Runtime / Listing 区域，同时尚未达到大厂在该层已经公开的身份、工具、治理、评测和分发完整度。Round 3 还推翻了“只要补上 Result Contract 和 human exception 就进入空白区”：Gumroad、Upwork、Fiverr 已经证明这些服务原语可以由既有市场补齐。Combo 真正可能保留的创业空间不能靠“比大厂更快做页面”或“字段更完整”解释，而必须由以下增量共同证明：

```text
一个窄垂类的 Result Contract
× 可取得的真实 Context 与授权
× AI / 人的可观测履约
× 比现有服务市场更准确、更低成本的 Adoption Verdict
× 可执行的返工、退款或人工接管
× 会随订单累积而改善的异常判例 / 信誉
× 正贡献的责任经济
```

### 3.7 Round 3：最强反例——强入口也没有必然吞掉 merchant lifecycle

OpenAI 的官方产品更新给“所有入口最终都会吞掉后台”提供了一个有价值的反例。早期 Instant Checkout 已让 ChatGPT 内的商品购买发生在对话中，但 Merchant 仍是 merchant of record，并负责订单、支付、履约和支持；2026 年 OpenAI 又公开说明，最初的 Instant Checkout 没有给 Merchant 足够灵活性，因此调整为让 Merchant 使用自己的 checkout，OpenAI 集中于商品发现。Walmart 的 ChatGPT App 也保留账户连接、会员关系和 Walmart 支付。[OpenAI Product Discovery](https://openai.com/index/powering-product-discovery-in-chatgpt/)、[OpenAI Instant Checkout](https://openai.com/index/buy-it-in-chatgpt/)

这并不证明 Combo 会成为“AI 服务的 Shopify”。它只支持一个较窄的**强推论**：

> 前台可以多元，掌握专业业务状态、责任和补救的后台仍可能独立存在；但后台必须已经是该业务的 system of record，不能只是一次 API 或页面调用。

对 Combo 的含义是两面的：

- **蓝方成立的部分**：不拥有全球意图入口，不等于没有平台机会；若 Combo 先在垂类拥有 contract、order、run、verdict、remedy 和 economics，它可以把多个入口当作需求 Surface；
- **红方成立的部分**：Shopify、Wix、Kajabi、Upwork 和 Fiverr 能保留后台，是因为它们已经拥有商户、客户、目录、订单或服务供给。Combo 当前没有这些先决资产，不能借它们的结构替自己证明地位。

### 3.8 Round 3 控制点裁决：平台路径必须改变起点

产业证据把候选路线从“横向补齐平台原语”改写为：

```text
先选一个自然发生、可验收且责任可控的垂类
→ 亲自形成 Result Contract 与人机履约闭环
→ 取得该垂类的 Context / Run / Verdict / Remedy system of record
→ 让一个外部入口持续交出完整责任事件
→ 再让第二个入口或第三方供给依赖同一对象
→ 只有此时才讨论跨渠道结果网络
```

这条路径的第一家公司形态更像 `Vertical Workflow / Fulfillment OS`，甚至是垂直结果公司，而不是中立 Agent 平台。只有当标准对象跨供给、跨入口复用，且第三方离开 Combo 会失去可量化经营收益时，才发生平台跃迁。

## 4. 演化不是一条线，而是一棵分叉树

```text
当前：Capability → Studio Miniapp / 通用 Runtime Run
                           │
              ┌────────────┴────────────┐
              │                         │
专业团队 Workflow OS             Result Commerce 假设
资产 / 版本 / 协作 / QA          Buyer Job → 付款 → 可采用结果
              │                         │
   B2B SaaS / seat / usage              ▼
                                  Result Contract → Order / Context
                                  → Run → Verdict / Remedy
                                            │
                   ┌────────────────────────┼──────────────────────┐
                   │                        │                      │
            创作者自带需求            Combo 自己拥有需求     企业 / 外部平台产生需求
                   │                        │                      │
       Creator Result OS / SaaS       垂直结果公司 / 市场       企业工作台 / 嵌入式设施
                   │                        │                      │
        方法授权 / Franchise         内容到行动 / 路由         Agent 采购与结算接口
```

Round 2 的关键修正是把最早的分叉前移：`Workflow OS` 与 `Result Commerce` 可以共享 Capability、版本、Runtime 和 QA 技术，但不是同一个市场。前者的买家是专业团队 / 创作者本人，现有四份访谈提供了工作流碎片化、资产管理、抽样效率和人工质量控制的质性证据；后者的买家是为创作者结果 SKU 付费的粉丝 / 客户，当前没有 Combo 一手现金订单、采用或复购证据。只有后者成立，才进入交易平台分叉。

真正决定分叉的不是功能，而是四个问题：

1. 谁产生并拥有需求？
2. 谁对结果做主要承诺？
3. 用户下一次回到哪里？
4. 什么状态必须留在 Combo 才能继续工作？

### 5.4 Round 2：`AI 用户` 不是市场，购买触发才是需求单位

AI 已越过大众接触门槛，但公开证据不能证明“大众高频购买 AI 结果”已经成立：

| 当前事实 | 能说明什么 | 不能说明什么 |
|---|---|---|
| CNNIC 第 57 次报告显示，截至 2025 年 12 月，中国生成式 AI 用户为 6.02 亿、普及率 42.8%；第 56 次报告中，80.9% 的用户把“回答问题”列为用途 | 自然语言问答已是大众行为，Combo 不必从零教育用户“可以问 AI” | 该口径不是 MAU、付款或结果采用，更不能证明会购买 KOL Agent |
| OpenAI Signals 2026 年 3 月样本中，68.9% 消息为非工作；Practical Guidance、Writing、Seeking Information 合计 74.5%。工作消息中 `Doing` 为 46.3%，明显高于非工作的 24.0% | 工作用户更接近“让 AI 做出东西”，消费侧主流仍是指导、信息与写作 | 消息占比不是用户占比；`Doing` 包括写作 / 计划 / 编码，不等于外部世界结果已验收 |
| Pew 2026 年美国调查中，49% 成年人用过 AI chatbot，24% 每天使用；未使用者中，83% 提到不感兴趣、79% 担忧个人信息、76% 不信任准确性、55% 不知道如何使用 | “用过”与“每日深用”仍有距离；扩散障碍包含用途、信任与隐私，不只是 Prompt 门槛 | 美国自报调查不能直接外推中国，也不能证明创作者品牌足以消除这些障碍 |
| PNC 真实账户数据中，2026 年初约 2% 的客户家庭出现生成式 AI 订阅支出 | 家庭真实自费远低于广义使用，`有付费访问权` 也不等于本人付款 | 单一银行客户会漏掉雇主付款、捆绑和其他渠道；不能外推 Combo 的愿付价格 |
| Anthropic 2026 年研究将 93% Claude 会话分类为产生 Artifact；在相同博客任务上，Chat / Cowork 中位需 13 轮，Claude Code 中位只需一次人类 Prompt，控制模型后 Surface 差异仍存在 | 同一模型上的工作流、Context 与交互 Surface 可以改变委托深度，产品层不是天然被模型吞掉 | Claude 的分类和单一任务不能证明任意 HTML Miniapp、KOL 分发、付款或留存有效 |

来源：[CNNIC 第 57 次报告](https://www.cnnic.net.cn/NMediaFile/2026/0304/MAIN1772588317069TUXN3827X8.pdf)、[CNNIC 第 56 次报告摘要](https://www.cnnic.cn/n4/2025/0721/c88-11328.html)、[OpenAI Signals consumer data](https://openai.com/signals/data/)、[OpenAI Signals 数据与方法](https://openai.com/signals/data-download/)、[Pew：Americans and AI 2026](https://www.pewresearch.org/internet/2026/06/17/americans-and-ai-2026-chatbots-smart-devices-and-views-on-impact/)、[Pew：非用户为何不用 chatbot](https://www.pewresearch.org/internet/2026/06/17/why-dont-people-use-chatbots/)、[PNC Consumer Health Check, April 2026](https://www.pnc.com/content/dam/pnc-com/pdf/aboutpnc/EconomicReports/consumer_health_check/PNC_Research_Consumer_Health_Check_April_2026.pdf)、[Anthropic Economic Index: Cadences](https://www.anthropic.com/research/economic-index-june-2026-report)。

因此，Combo 的最小需求单位不应是“一个 AI 用户”或“一位粉丝”，而应是：

```text
一个自然发生、能被追溯的 Buyer Job
× 明确触发、期限与赌注
× 用户愿意提交的 Context
× 相对免费通用模型仍存在的缺口
× 可直接采用的交付物与补救
× 真实自付
```

必须逐段验证的行为链是：

```text
创作者受众
→ 自然任务触发
→ 试过 / 考虑免费通用模型
→ 愿意提交 Context
→ 现金付款
→ 收到结果
→ 明确采用 / 修改 / 拒绝 / 退款
→ 在该 SKU 的自然周期内再次购买
```

当前 Combo 真源尚未提供这条链上任何可稳定回读的现金 cohort。AI 大盘只帮助筛选实验人群，不能替 Combo 填充需求漏斗。

### 5.5 Round 2：两套用户与三套留存不能混算

Vault 中现有的一手用户研究是四个专业漫剧 / 视觉制作团队。它们共同支持资产与工具碎片、抽样效率、协作和人工审美控制的痛点；其中有“愿为效率付费”的质性信号。它们没有证明团队会把方法授权给 Combo、向粉丝销售低客单结果、持续推广或接受交易抽成。见 [user-research-insights](/wiki/maps/user-research-insights/)、`raw/projects/user-interview/漫剧访谈 LSW - 总结.md` 与 `raw/projects/user-interview/漫剧访谈-福州畅读 - 总结.md`。

| 市场 | 谁付费 | 自然触发与频率 | 价值与收入 | 当前证据 | 进入下一层的 Gate |
|---|---|---|---|---|---|
| `Professional Workflow OS` | 专业团队 / 创作者本人 | 项目内高频的素材、版本、抽样、协作、审核 | 节省团队时间、提高吞吐与可控性；SaaS / seat / usage | **强推论**：四份实际访谈支持问题存在；没有 Combo 付费与留存数据 | 独立团队在无陪跑下反复使用，并以真实费用换取可测效率 / 质量增益 |
| `Creator Result Commerce OS` | 粉丝、消费者或企业客户 | 某个 Buyer Job 自然发生后购买可采用结果 | 创作者增量收入与买家结果；SaaS / usage / 交易费 / 托管服务 | **待验证假设**：没有 Combo 现金订单、采用、复购或完整成本 cohort | 相对免费通用模型显著提高采用，买家自付且自然复购，创作者与 Combo 都有正增量贡献 |

即使 Result Commerce 成立，也必须分开三套留存：

| 留存对象 | 要观察的返回行为 | 不得替代它的虚荣指标 |
|---|---|---|
| 买家 | 同 SKU 复购、同创作者跨 SKU、跨创作者购买；均按各自自然触发周期 | 通用 7 日 DAU、页面回访、KOL 再次群发 |
| 创作者 | 第二次自然发布、订单 / QA / 版本 / 退款工作台复用、D60 / D90 活跃 | Agent 仍上架、共创期间打开过后台 |
| 平台关系 | 没有原创作者再次触达仍产生的 Combo / Partner 需求、陌生供给成交、跨供给购买与路由 uplift | creator deep link GMV、上架数、总调用量 |

低频不天然等于坏生意，但它必须由更高客单、可控 CAC 和正贡献弥补；`低价格 + 低 take rate + 高触达人工` 不能同时作为默认模型。

## 6. 所有路线共同需要的平台原语

### 6.1 从当前代码到结果经济对象

| 原语 | 当前状态 | 最小新增 | 为什么必须 |
|---|---|---|---|
| Capability Version | 已有 | 保持模型无关、来源与授权血缘 | 知道用的是什么方法 |
| Immutable Surface Binding | 缺失；可物化为 `ExperienceSurfaceVersion` 或等价 Publication 子对象 | 原子绑定 Capability、Studio Revision、HTML hash、bridge 与 smoke-test Run | 让审核过的 Miniapp 真正进入发布和消费；不把 bridge 可用误称为结果正确 |
| Executable Surface Security | 当前 Runtime consumer 有 P0；未来 Surface 也缺失消费者级闭环 | Runtime 默认静态；交互层使用可信 renderer / declarative manifest，或真正无 egress 的隔离执行；再叠加 CSP / sandbox、发布扫描、signed entitlement、rate limit、audit、kill switch | 任意生成 HTML 是不可信可执行代码；版本一致不等于安全 |
| Miniapp Manifest | HTML + `combo:run(prompt)` 约定 | 消费者只接受 `action_id + typed payload schema + tool / data scope + host confirmation`；自由文本 Prompt bridge 仅限 Studio | nonce 只能认证请求，不能授权任意 payload；不能把所有任务压成一个 Prompt |
| Result Contract | 缺失 | input、deliverable、scope、deadline、acceptance、remedy | 能定价、验收和争议处理 |
| Identity & Authorization | 匿名 owner / creator 基础 | 买家、专家、方法、Context、用途、期限与撤回 | 知道谁允许什么 |
| Order | 缺失 | contract version、buyer、seller、price、status | 把 Run 放进经济关系 |
| Run Ledger | 部分已有 | contract/order/context/version/cost/human intervention | 把运行变成可审计履约 |
| Evidence & Verdict | 缺失 | accepted / revised / rejected / refunded + reason | 产生真实质量标签 |
| Remedy | 缺失 | retry、human escalation、replacement、refund | 平台开始承担责任 |
| Settlement | 缺失 | payment、refund、creator payout、platform fee | 形成商业与供给激励 |
| Attribution | 缺失或不足 | creator、content、platform、partner、agent source | 判断谁真正创造需求 |
| Unit Economics | 缺失 | model、tool、human、support、refund、channel cost | 防止用 GMV 掩盖服务成本 |

### 6.2 真正可能复利的数据对象

不是：

```text
Prompt 数量
聊天数量
页面数量
Agent 数量
```

而是：

```text
Result Contract Version
× Context Class
× Capability / Model / Human Version
× Actions and Evidence
× User Verdict
× Human Minutes
× Refund / Repurchase
× Full-cost Economics
```

只有当这组数据在 holdout 中提高首稿接受率、降低退款、减少人工分钟或改善匹配，它才是数据资产；否则只是日志。

### 6.3 建设顺序

```text
P-1 当前 Runtime HTML fail closed + 最小服务端 Publication
P0  Buyer Job 证据 + Result Contract ID + Order ID + Run ID + Verdict 最小账本
P1  身份 / 授权 / 人工升级 / 退款 / 全成本账本
```

### 6.4 从当前代码出发的 90 天架构 Gate

#### 第 0–15 天：关闭当前安全 P0，并建立可验证需求的最小发布

- **P0-A，先于任何消费者 pilot：**普通 Runtime artifact 统一走静态隔离路径；`kind="html"` 不能自动获得脚本、表单、弹窗、导航或网络能力。不能只依赖每个调用方记得传 `interactive={false}`：renderer API 应改为默认静态的显式 security profile，或拆成 `StaticArtifactRenderer` 与仅 Studio 可用的 `InteractiveStudioRenderer`，让漏传参数 fail closed；
- **P0-B，首批需求不用不可信交互代码：**使用可信宿主组件渲染 declarative schema；不加载创作者 / 模型生成脚本，不把完整 executable Miniapp 当作 Buyer Job 或付费验证前置条件；
- **P0-C，原型状态不得升级冒充生产状态：**当前 localStorage 定价 / 命名 / 体验预览继续保留为 prototype，但正式发布只能由服务端事务创建 Publication；只有后端回读同一 `capability_version_id + trusted_surface_schema_hash + security_profile + review_status` 后，前端才显示“已发布”。本地拼接结果永不写入成功率、Verdict 或质量数据；
- 最小 Run 必须绑定 Publication、actor 与 input snapshot，产生可追溯终态；早期允许人工发现、标记和补救失败，但不得把它表述为 durable reliable execution。

**最小发布 Gate：**陌生买家只在可信宿主中运行被审核的 declarative Surface；Capability Version、trusted Surface schema hash、Publication 与 Run 全链可追溯。这个 Gate 不加载 Studio 或模型生成的脚本。

#### P2：仅在 Surface uplift 通过后建设完整交互 Surface

只有 A/B 或交错对照证明任务型 Miniapp 相对可信宿主显著提高付款、明确采用或复购，才进入以下工程；它不是 Day 0–15 或首批 30 天需求验证的完成条件：

- 新建 `experience_surface_versions`，或在 Capability Publication 下实现满足同一不变量的不可变子对象；
- 绑定 `capability_version_id`、source Studio Revision、artifact hash / ref、bridge version、bridge smoke-test Run 与 security profile / scan result；
- Publish Gate 原子钉住 Capability Version 与 Surface Version；
- 把生成 HTML 一律视为 untrusted executable content：消费者 renderer 默认拒绝外部网络、表单提交、同 frame / 顶层导航、弹窗、meta refresh 和任意嵌套 frame；只有 declarative manifest 白名单能力可以进入可信宿主；
- 消费者桥不接受自由文本 `combo:run(prompt)`：发布前定义 `action_id`、typed payload schema、允许的 tool / data scope 和预算；每次会话签发短期 entitlement / 单次 action nonce，绑定 buyer、surface version、contract version、action、payload digest、scope、Run budget 与 expiry，并防重放；
- 不信任 iframe 自报的“用户点击”；所有计费、读敏感数据或改变外部状态的动作都必须由宿主 UI 展示规范化 action / payload 摘要，并由显式用户确认换取一次性授权；
- 对 creator、surface、IP / account 和 action 做限流、配额、滥用检测与审计；
- 每个 Surface Version 发布前运行恶意 HTML fixtures、bridge fuzz、权限越界和数据外传测试；
- 提供按 creator / capability / surface version 立即停用的 kill switch，以及已打开页面的撤销 / 失效策略；
- 消费端只有在上述安全 Gate 通过后，才按精确 Surface hash 加载并允许页面操作创建真实 Run。

标准依据：WHATWG HTML Standard 明确说明 `allow-scripts`、`allow-forms` 与 `allow-popups` 会重新开放对应能力；iframe sandbox 没有一个等价于“禁止所有网络”的默认开关。网络源、表单目标、frame 与 base 等限制需要由 CSP 或更强的隔离边界明确执行。[WHATWG HTML Standard](https://html.spec.whatwg.org/multipage/iframe-embed-object.html)、[W3C Content Security Policy Level 3](https://www.w3.org/TR/CSP/)

实施验收必须显式覆盖五个边界：

1. 外部导航请求本身必须在发出前被阻断；恶意 fixture 要覆盖 link、form、`window.location`、同 frame、top、popup、meta refresh 和嵌套 frame，不能只测试导航后旧 frame 的 nonce 失效；
2. 即使 entitlement 有效，未知 `action_id`、越界 tool / data scope、payload schema 不符、payload digest 被替换、自动触发、重放和没有宿主确认的 Run 仍被拒绝；
3. Runtime 新生成的 HTML 结果默认走静态、网络隔离的回显，不能因为 `kind="html"` 自动升级成 executable Surface；
4. 宿主页面禁止被第三方任意嵌套以避免 clickjacking / 假表单；高风险 SKU 必须经过专项人工审核，不能只通过通用扫描。
5. 清空浏览器存储、切换设备或直接伪造 localStorage 后，都不能改变后端 Publication、价格、域名、审核或可消费状态。

**完整 Surface 功能 Gate：**创作者发布 R3 后，陌生消费者加载的正是 R3 对应 Miniapp，Capability、Surface 和 Run 全链可追溯。

**安全 Gate：**一个恶意或被污染的 R3 不能发出外部网络 / 导航请求、外传数据、提交任意自由文本动作、绕过 typed scope 与宿主确认发起 Run、无限消耗预算、打开钓鱼弹窗 / 表单或在撤销后继续运行；所有拦截和放行均可按 Surface Version、action 和 payload digest 审计。未通过时只能在 Studio 内受控测试，不能向陌生消费者发布。

进入完整 Surface pilot 后，可用人工签发、可撤销的 pilot access grant 和固定 Run budget 完成这一 Gate；它不是完整 buyer identity、Entitlement 和交易系统的替代。

#### 第 16–35 天：统一 Runtime 与可靠执行

### 6.5 平台治理不能等规模出现后再补

平台化不仅增加抽佣，也增加记录、规则、消费者保护、个人信息和 AI 内容责任：

- 若 Combo 构成《电子商务法》所称电子商务平台经营者，第三十一条要求其记录、保存平台发布的商品 / 服务信息与交易信息；信息通常自交易完成之日起保存不少于三年。第六十二条另规定，电子商务争议处理中，电子商务经营者应提供原始合同和交易记录。两条的主体和情形不能混写。[国家市场监督管理总局：电子商务法](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2023/art_14453aa523094819aa8f1d4530ce3cc4.html)
- 2026 年《网络交易平台规则监督管理办法》要求平台通过规则承担服务质量、消费者权益、公平竞争、信用、个人信息与数据安全等责任。[国家市场监督管理总局](https://www.samr.gov.cn/zw/zfxxgk/fdzdgknr/fgs/art/2026/art_85b474fc5a08494bb60ca6a280b98d7d.html)
- 《个人信息保护法》要求自动化决策透明、公平，个人有拒绝纯自动化重大决定的权利；向其他处理者提供信息、处理敏感信息和自动化决策还涉及单独同意或影响评估等要求。[中国人大网：个人信息保护法](https://www.npc.gov.cn/npc/c2/c30834/202108/t20210820_313088.html)
- 《人工智能生成合成内容标识办法》自 2025 年 9 月起施行，适用于其第二条所列规则覆盖的网络信息服务提供者；显式标识义务取决于第四条所引特定情形，传播核验适用于网络信息内容传播服务。第九条的“不少于六个月”日志要求，仅对应用户申请获得不含显式标识内容的特定安排，不能泛化成所有生成内容服务的统一日志期限。[国家网信办](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)

**产品含义：**

若 Combo 的具体业务形态被认定适用相应规定，`Authorization Ledger`、`Contract Version`、`Result Provenance`、`AI Label Metadata`、`Dispute Evidence` 和 `Delete / Export` 就不能作为法务尾项。主体性质、SKU 类目和具体义务仍需在上线 / 收款前获得专业法律意见。

### 6.6 五个总证伪 Gate

在讨论任何平台路线之前，先做五项反事实检验：

1. **原子价值 Gate**  
   同一真实 SKU，用 Combo 与“通用模型原生 Agent + 建站 / 支付工具”对照。如果质量、上线效率、维护成本或成交没有显著增益，当前 Builder 是薄封装。

2. **全成本毛利 Gate**  
   逐单计入模型、Sandbox、专家审核、客服、返工、退款、支付、招募和运营工时。如果真人分钟不随累计订单下降，软件毛利只是服务成本尚未入账。

3. **供给复制 Gate**  
   同一 Result SKU 复制到多个独立创作者，由非创始团队上线和履约。如果每个人都要重做流程、产品或核心代码，Combo 是代运营。

4. **平台需求 Gate**  
   暂停 KOL 再次推广、补贴和人工召回后，用户是否仍由 Combo 或合作入口购买陌生供给。没有这件事，就只有很多独立店铺。

5. **数据因果 Gate**  
   用 prospective holdout 比较“历史 Context / 路由开启”与冻结基线。如果没有降低人工、退款和交付时间，或提高接受率与贡献毛利，数据只是合规成本。

前三项失败，应停止平台叙事；第四、第五项决定 Combo 最终是工具 / OS、垂直结果公司，还是严格意义的平台。

### 6.8 冷启动和防脱媒机制

平台冷启动不应从“同时招供需双方”开始，而应按以下顺序：

```text
1 位有真实私域需求的专家
→ 1 个标准 Result SKU
→ 10–30 笔真实付费与 Verdict
→ 3–5 位独立供给者复制同一 SKU 族
→ 用户在平台保障下购买陌生供给
→ Combo / 合作入口开始产生新增需求
```

Combo 留住交易不能靠封闭链接，而要让留在平台内的净收益更高：

- 精确绑定的方法、Surface 和 Result Contract 版本；
- 自动复用但可撤回的客户 Context；
- 支付、发票、分账、退款和争议证据；
- 失败后的备用供给与平台补救；
- 创作者可见的版本质量、人工分钟、复购和真实净收入；
- 用户可见的进度、证据、历史结果和责任出口。

**脱媒实验：**首单后允许双方获得可直接联系的路径，不以产品限制掩盖问题；比较有 / 无平台保障、Context 复用和自动复购时的 D30 / D90 站内复购。若保障不能抵消抽成和摩擦，Combo 应按 SaaS / OS 定价，不应宣称交易网络。

### 6.9 三类必须持续寻找的反例

1. **OS 很强、网络始终不出现**  
   供给者高频使用客户、订单、QA 和结算，但每个供给者仍自带需求，买家也不跨供给。此时可以是高价值经营软件，却不是 Marketplace；不得用 SaaS 留存替代平台需求 Gate。

2. **供给很多、Marketplace 经济恶化**  
   Listing 增长、价格竞争和选择增加，但活跃买家、质量、贡献毛利和保障成本变差。Fiverr 2026 年一季度活跃买家与 Marketplace revenue 同比下降，提示“已有供需市场”仍需持续解决匹配、范围和履约，不是供给规模自动复利。

3. **调用量很大、嵌入式控制权很弱**  
   外部渠道带来大量 API 请求，却不提供订单、退款、授权与用户关系；渠道随后压价、自建或切换供应商。此时 Combo 是可替换 Runtime，不是结果商业基础设施。

每轮定时研究必须主动寻找能使主路线失败的现实样本，而不是只累计正面对标。

### 6.10 Round 2：先拆资金链，再谈单位经济

现有材料同时出现了两种不兼容的现金流：

- 主报告的保守 pilot：创作者 / 实际服务提供者使用自己的合规商户账户直接向买家收款；
- 现有单位经济公式：`Net Revenue = Realized GMV - Creator Payout`，隐含 Combo 先取得买家现金、再形成创作者应付。

两者不得共用一张 P&L：

| 资金链 | 买家付款属于谁 | Combo 收入 | 额外责任 | 本轮能验证什么 |
|---|---|---|---|---|
| `Creator seller / MoR`：创作者直收 | 创作者 GMV | Combo 实际收到的 SaaS、usage、上线或订单服务费；若免费则为 0 | 创作者承担合同、开票与退款；Combo 仍承担自身数据、产品和承诺责任 | 买家需求、结果履约、创作者增量收入；只有实际收取 Combo 费用才能验证 Combo monetization |
| `Combo seller / MoR`：Combo 收款并欠创作者结算 | Combo 可确认的交易现金与收入，再形成供给成本 / 应付 | 依合同和会计口径确认，不能只用页面 GMV | seller / MoR、支付、税务、退款、拒付、消费者保护、分账和结果责任 | 完整交易经济，但必须先关闭法律、资金与产品 Gate |

订单级管理账应按实际资金链记录，而不是先假定 15% 抽成：

```text
G_i =
  买家现金实收
  - 退款本金
  - 拒付本金
  - 非收入性代收

若 Combo 是销售方：
  ComboRevenue_i = 依法可确认的 G_i - 供给者实际结算

若创作者是销售方：
  ComboRevenue_i = Combo 实际收到的 SaaS / usage / 服务费
  创作者 GMV ≠ Combo revenue

VariableCost_i =
  模型 + 工具 + Sandbox + 全部重试
  + Combo 人工审核 / 补交付
  + 客服 / 争议
  + Combo 承担的支付费
  + 渠道激励 + 保障损失

OrderCM_i = ComboRevenue_i - VariableCost_i
```

创作者还需要独立的净增量账，不能把创作者到账当创作者价值：

```text
CreatorIncrementalProfit =
  创作者实际保留现金
  - Combo 费用
  - 创作者承担的支付 / 退款 / 渠道成本
  - 发布、审核、客服、真人接管工时 × 机会成本
  - 被低价 AI 产品蚕食的原人工服务毛利
  - 可识别的声誉损失
```

现有录音分析曾把 `¥3 / ¥9.9 / ¥19.9` 作为实验价格，将 15% 作为抽成假设。即使暂不计任何成本，每单 Combo 收入上限也只有：

| 买家价格 | 15% 的每单上限 | 100 单收入上限 | 尚未扣除 |
|---:|---:|---:|---|
| ¥3 | ¥0.45 | ¥45 | 模型、重试、支付、客服、退款、创作者获取与共创 |
| ¥9.9 | ¥1.485 | ¥148.50 | 同上 |
| ¥19.9 | ¥2.985 | ¥298.50 | 同上 |

因此，`高触达共创 + 低价格 + 15% take rate` 在数学上不能同时被当作默认可行。若没有极大规模和接近零的变动成本，Founder 必须在下列生意之间选择并分别验证：

1. 更高价值、可验收的 Result SKU；
2. 面向创作者的 SaaS / onboarding / usage 费；
3. 成本 pass-through + 明确服务费；
4. 低价 SKU 只是高价值真人服务的 lead-gen；
5. Combo 承担更多需求与责任，并收取更高交易费 / 项目毛利。

它们的付费者、价值承诺、CAC、责任与毛利不同，不是同一条价格梯度。

另一个指标必须立即纠正：当前验证计划把“退款窗结束且未全额退款”定义为 `Accepted`。对低客单产品，沉默和嫌退款麻烦都可能产生“无退款”。事件应拆为：

```text
delivered
→ usable_without_revision / needs_revision / rejected
→ explicit_adoption_evidence
→ refund_state
→ actual_repeat
```

`no refund` 只能说明退款状态，不能证明结果被接受、采用或形成留存。

### 蓝方

当前已有 Capability 契约、发布、市场 listing、Runtime、HTML artifact、版本、Revision 和 Test。继续增加 SDK、组件、连接器、托管、计费和目录，可以成为 Agent App 的开发与运行平台。

### 红方

- Combo 没有比模型入口更强的消费者分发，也没有企业 IT 治理优势；
- 开发者会把 Combo 视为又一个 Runtime，而不是必须依赖的平台。

### 裁判

**不作为公司主线。** Round 3 已把它从“拥挤但仍可补齐”进一步下调为“控制面劣势明确”：Combo 当前拥有的 Builder / Runtime / Listing 不仅缺失平台硬门槛，而且正与模型、云、办公和微信入口的默认能力重叠。保留 Runtime 和 Miniapp 作为垂直结果产品的内部基础设施，不再以连接器数量、Listing 数或发布渠道数作为独立平台进展。

| 项目 | 判断 |
|---|---|
| 用户新动作 | 开发并发布一个可运行 Agent App |
| 提交物 | Capability、UI、connectors、code |
| 消费结果 | 一个通用 App |
| system of record | App 版本、运行、权限 |
| 网络效应 | 开发者—用户—连接器生态 |
| 关键支撑 | SDK、sandbox、auth、storage、billing、distribution、governance |
| 最大对手 | OpenAI、Google、Microsoft、Replit、Wix |
| 最小证伪实验 | 让 10 位非团队开发者在无陪跑下发布并获得真实外部复访 |
| 停止条件 | 使用只来自团队 / 熟人；用户更愿直接在模型平台发布；无独立分发 |

## 9. 路线 C：专家结果经营与履约 OS

### 产品画面

专家每天打开 Combo，不是为了改页面，而是为了：

- 看新订单和待审核；
- 处理低置信度与高风险例外；
- 比较服务版本的接受率、退款与人工分钟；
- 更新方法、边界和价格；
- 查看客户 Context、复购与结算；
- 发布第二、第三个结果 SKU。

Round 2 必须把这里的“专家 OS”拆成两件事：

| 形态 | 直接买家 | 核心循环 | 主要收入 | 当前证据等级 |
|---|---|---|---|---|
| `Professional Workflow OS` | 专业创作者 / 制作团队 | 导入资产与任务 → 多模型 / 人协作 → 版本与审核 → 项目交付 → 下次复用 | SaaS、seat、usage | **强推论**：四份实际工作流访谈支持问题；付费与留存仍未验证 |
| `Creator Result Commerce OS` | 粉丝 / 消费者 / 企业客户；创作者同时是供给与首个渠道 | 自然任务触发 → 买家付款 → AI / 人履约 → 明确采用 / 补救 → 自然复购 | SaaS、usage、交易费或项目毛利 | **待验证假设**：当前无 Combo 现金订单、采用、复购或单位经济 cohort |

两者可以共享 Capability、Runtime、版本、QA 和人机协同，但前者成立不推出后者成立。只有 `Result Commerce` 的买方行为成立，订单、退款、结算和跨供给才可能成为平台路径的经营状态。

### 蓝方

专业创作者的工作流、资产、版本和人工审核痛点已有一手质性证据；这是从当前能力提取、Miniapp、Runtime 和版本体系最自然的延伸。若另外找到一个反复发生的 Buyer Job，创作者自带首批需求可以减少早期双边冷启动变量；一旦独立买家付款并采用结果，且订单、客户、版本、退款和真实净收入都留在 Combo，才可能形成 Result Commerce 的 system of record。

Wix 当前把网站、客户、支付、预约、CRM 与多站点管理放在同一工作台；ServiceTitan 当前把垂直工作流、支付和融资放在同一经营系统。它们只提供“创建 / 工作流表面与经营状态可以共存”的结构类比，不提供纵向因果史，也不能证明 Combo 的目标创作者会产生同样频率。

Round 3 还发现，专家 OS 的相邻区域已经有更直接的占位者：

| 相邻产品 | 官方当前已做 | 对 Combo 的直接压力 | 仍可检验的窄缺口 |
|---|---|---|---|
| Kajabi Expert Agents | 宣传中的 Sales Agent、Teaching Assistant、Universal Inbox 和人工接管利用创作者已有内容；Kajabi 本体已有产品、营销、支付和 client experience。当前 Pricing 仍标 `Coming Soon`，不能写成普及 GA | “专家内容 → Agent → 客户经营”并不是独特叙事；Kajabi 先天拥有内容与客户状态 | 官方 V1 说明尚不在聊天中处理付款、主动发起、跨 Surface memory 或替代专家判断；某一垂类的正式结果合约与补救仍可检验 |
| 腾讯 WorkBuddy / 元器 | Expert = 人设 + 方法论 + 工具链，Expert Team 可多 Agent 交付；元器可把公众号内容生成知识 Agent 并发布到微信渠道，微信支付 MCP 已能创建订单和查询支付状态 | “博主分身 + 方法 + 微信分发 + 付费门”薄层已被默认入口直接吸收 | 当前公开支付工具与文档没有证明通用服务的退款、验收、创作者结算、责任分配与跨渠道账本 |
| Wix Headless | 把任意 AI-built site / app 接到 eCommerce、Bookings、Events、CMS 与 secure payments，且明确标注 AI-tool agnostic | “AI 生成前台 + 业务后台”也不是 Combo 独占的演化方向 | Wix 的通用业务对象不自动定义特定专业结果的质量、人工例外和责任 |
| Gumroad Commission | Buyer 提交 instructions / files 并支付 50% deposit；Creator 上传 deliverable 并标记完成，平台再收剩余款并计入余额；Gumroad 作为 MoR | 最小的 intake、deposit、deliverable、completion、payout 已可被既有创作者平台快速补齐 | Seller 自报完成不是独立 buyer Verdict；机器验收、revision / exception routing 和可学习的责任证据仍需验证 |
| Upwork / Fiverr | Upwork 从 ChatGPT 需求进入人才发现与 job draft，固定价 milestone 具有 escrow、accept / changes、退款与 dispute；Fiverr 已有 requirements、delivery / draft、accept / revise、partial refund，Fiverr Go 又加入 creator-trained model 和 seller edit / handoff | 水平供给、信誉、合同、验收、争议、人工交付与 AI-first exception 已有强网络控制者 | 一个新而可标准化、可机器验收、无需既有人才市场的垂类结果品类仍可能从垂直处长出 |

### 红方

- 大多数创作者可能低频售卖，不会每周经营；
- 他们可能只要一次建站和支付链接，后续仍在微信处理；
- 每位专家的服务都不同，Combo 会退化成代运营；
- KOL 可能不愿把客户、支付和品牌关系交给 Combo；
- 既有知识商业、建站、电商、私域交易和模型平台已经补齐相邻能力；Combo 不能靠“别人尚未做 Agent”作为窗口，只能逐项证明自己的结果合约、验收、补救、经济与跨渠道记录有不可替代增量；
- AI 初稿后的审核、客服和退款可能让它成为隐形服务公司。

### 裁判

**当前只是第一个可证伪主干，不是已证实的最高概率路线。** 专业 `Workflow OS` 与 `Creator Result Commerce OS` 应先作为两个市场分别验证；在买家现金、采用、自然复购和双边净增量成立前，不得把前者的访谈证据迁移给后者。

| 项目 | 判断 |
|---|---|
| 买家 | Workflow OS：专家、创作者、专业团队；Result Commerce：粉丝、消费者或企业客户 |
| 频率 | Workflow：项目内高频；Commerce：按具体 SKU 的自然 Buyer Job 周期，当前未知 |
| 提交物 | 方法、Result Contract、案例、QA rubric、授权 |
| 消费结果 | 可持续经营的 AI 服务产品 |
| system of record | 客户、订单、Run、版本、人工、退款、支付 |
| 商业模式 | Workflow：SaaS / seat / usage；Commerce：按 seller / MoR 与需求来源选择 SaaS、usage、交易费或项目毛利 |
| 网络效应 | 初期没有；先是规模经济和 switching cost |
| 关键支撑 | 自助发布、订单台、QA、HITL、支付分账、客户 Context、成本账本 |
| 最大对手 | 创作者 SaaS、原生内容平台、支付 / 小店、模型原生 Agent |

### Gate

建议以同一结果 SKU 族中的 3–5 位独立供给者验证：

1. 每位创作者先提供过去自然发生的重复咨询或付费需求证据；不能以画像、粉丝量或共创意愿代替 Buyer Job；
2. 非团队人员能按同一 SOP 上线；
3. 不依赖持续陪跑也能完成独立买家的真实现金订单；
4. Combo 相对免费通用模型达到预注册的质量 / 采用增益；
5. 至少多位供给者自然更新版本、完成第二次发布或发布第二个 SKU；
6. 在 SKU 的自然再次触发窗口中仍有未补贴复购；未进入窗口者标记为 right-censored，不用通用 D7 冒充失败；
7. 人工分钟、退款与贡献毛利不随订单线性恶化；
8. 创作者净增量收入为正，并愿意把订单、交付和相应收费继续留在 Combo。

### 杀死指标

- 每位新创作者都要求重写产品和核心代码；
- 创始人 / 运营人力随订单或供给线性增长；
- 第二次自然推广普遍消失；
- 订单和售后长期回到微信，Combo 只剩页面；
- 创作者净收入扣除审核时间、蚕食和声誉风险后不增长；
- 通用模型或原生平台以更低成本达到同等结果。

## 10. 路线 D：专家方法授权 / AI Franchise

### 蓝方

如果知名专家的方法能够脱离本人时间持续产生明显质量溢价，Combo 可以把方法版本、品牌授权、执行者认证、质量抽查和版税分账组织成网络。专家从亲自服务变成更新方法和处理例外。

### 红方

Prompt 与方法难以形成稳固产权；用户可能只信专家本人；不同执行者导致质量漂移；授权网络容易变成品牌联营和人工运营。

### 裁判

**是专家 OS 的供给扩张机制，不应先作为独立平台。**

| 项目 | 判断 |
|---|---|
| 用户新动作 | 授权他人 / Agent 按某专家官方方法交付 |
| 提交物 | 方法版本、品牌权、rubric、许可边界 |
| 消费结果 | 获认证的结果交付 |
| system of record | 授权、版本、质量、版税、撤销 |
| 网络效应 | 更多合格运营者扩大专家供给，更多结果改善认证 |
| 关键支撑 | 法律授权、版本、认证、审计、撤销、分账 |
| Gate | 隐去专家本人、由不同执行者交付时仍有稳定质量与愿付溢价 |
| 停止条件 | 价值仅来自专家亲自背书；方法无法脱离本人；质量漂移不可控 |

## 11. 路线 E：单一垂类结果公司 / 服务总包商

### 产品画面

用户不选择 Agent 或专家，只告诉 Combo：

> “今晚前完成一套新品发布素材。”

Combo 在后台组合模型、能力、人和工具，自己对价格、期限、质量和补救负责。

### 蓝方

- 回避双边市场冷启动；
- 能强制标准化 Result Contract、流程与质量；
- 可以用一个品牌积累需求和信任；
- 一个高频 / 高客单垂类可能比横向平台更快形成大收入；
- 如果用户只关心结果，创作者品牌反而是多余摩擦。

### 红方

- 本质可能是 AI-enabled service，而非软件或平台；
- 销售、项目管理、客服、人工返工吞掉毛利；
- 单垂类集中，市场上限和周期风险更高；
- Combo 同时做自营和中立平台会产生推荐与利益冲突；
- 每扩一个垂类都可能重新创业。

### 裁判

**这是合法的大公司路径，但不是平台本身。** 如果真实订单显示用户只认 Combo 的结果承诺、一个垂类占据大部分高质量需求，应果断选择它，不要为了“平台”牺牲 PMF。

| 项目 | 判断 |
|---|---|
| 买家 | 有明确结果需求的消费者或中小企业 |
| 频率 | 同一业务周期中的重复 / 相邻任务 |
| 提交物 | 目标、材料、预算、期限 |
| 消费结果 | 一个由 Combo 负责的完整成品 |
| system of record | 项目、流程、QA、供应链、客户 |
| 商业模式 | 结果定价、订阅、项目毛利 |
| 网络效应 | 通常弱；主要是品牌、数据、流程与规模经济 |
| 关键支撑 | 垂直 QA、供应链、人工运营、SLA、责任与品牌 |
| 最大对手 | 垂直 SaaS、服务公司、模型原生工作流 |

### Gate

- 一个结果品类贡献大部分自然订单和复购；
- 用户不在意具体专家身份；
- Combo 品牌承诺提高转化；
- AI 持续减少人工分钟且质量不降；
- 全成本后贡献毛利为正；
- 相邻服务复用同一 Context、分发与 QA。

### 停止条件

- 每单都变成定制项目；
- 项目经理和专家工时随收入线性增长；
- 结果不可验收、争议率高；
- 用户只为创作者身份购买；
- 相邻服务无法复用同一资产。

### E2. AI-native 服务总包商

这不是简单扩大垂类 SKU，而是让客户只提交一个复合目标，由 Combo 拆解任务、组合多个人 / Agent / 工具，并承担单一责任出口。

| 项目 | 判断 |
|---|---|
| 买家 | 有复合目标、预算和单一责任需求的消费者 / SMB / 企业部门 |
| 频率 | 同一项目内多阶段高频；跨项目复购取决于垂类业务周期 |
| 供给 / 需求 | Combo 组合签约专家、Agent 与工具；需求先由 Combo 或合作渠道获得 |
| 用户新动作 | 提交完整目标、预算、期限与审批边界 |
| 提交物 | Goal Contract、企业 / 个人 Context、阶段验收 |
| 消费结果 | 一套复合交付物，而非多个独立 Agent 输出 |
| system of record | task graph、依赖、供给贡献、审批、成本、责任 |
| 商业模式 | 项目毛利、Retainer、供应商价差 |
| 可能复利 | 项目数据改善任务拆解、报价和供给选择 |
| 网络效应 | 通常没有；先是供应链规模经济。只有独立供需参与者互相增益后才可能网络化 |
| 关键支撑 | task graph、阶段验收、预算控制、多供给分账、项目管理 |
| 最大对手 | 传统代理 / 咨询公司、垂直服务商、托管式平台服务；具体对象需逐项验证 |

**蓝方：**同一客户的复杂目标天然需要多个相邻结果；Combo 可以把分散采购和协调压缩成一个价格、一个进度、一个责任人。

**红方：**组合任务会重新引入 scope creep、项目管理和人工协调；“动态 Agent 团队”在后台很酷，但前台仍可能是一家传统 Agency。

**Gate：**固定一个复合结果套餐，与逐项购买对照；组合后的客单、周期、复购和毛利更好，而且协调人工不随复杂度线性增长。

**停止条件：**每单都重新定义范围；创始人亲自拆解；协调工时吞掉 AI 节省；客户最终购买的是定制人力。

## 12. 路线 F：精选结果 Marketplace

### 蓝方

当多个供给者销售可比较的同类 Result Contract，Combo 可以用 Context、历史结果和平台保障帮助用户选择；更多供给提高覆盖，更多订单改善匹配和质量，形成真正跨边网络效应。

### 红方

- 以 Fiverr 为代表的横向服务市场已有供给、需求、交易历史和争议处理能力；其他具体竞争者需逐项核验；
- 模型平台拥有默认意图入口；
- 专业服务不标准，比较和验收比商品难；
- 用户可能只跟随原创作者，不愿购买陌生供给；
- 首单后买卖双方可转到微信脱媒；
- 平台为了质量必须重运营，毛利可能不成立。

### 裁判

**不能从开放上架开始，只能从真实交易“长出来”。**

| 项目 | 判断 |
|---|---|
| 用户新动作 | 按结果选择并购买陌生供给 |
| 提交物 | Result Contract、案例、价格、SLA、授权 |
| 消费结果 | 经平台保障的可验收结果 |
| system of record | 供给、需求、匹配、订单、质量、争议 |
| 商业模式 | 抽佣、支付、保障、推广 |
| 网络效应 | 供需流动性 + 结果数据改善路由 |
| 关键支撑 | 标准 SKU、搜索 / 匹配、托管、QA、退款、声誉、备用供给 |
| 最大对手 | 横向服务市场、超级 App 的本地服务 / 支付入口、模型入口；具体对象及其能力需逐项核验 |

### 解锁 Gate

以下三项必须同时发生：

1. 用户在没有原创作者再次触达时，购买第二位供给者；
2. Combo 自有或合作入口带来的未补贴订单持续出现；
3. 路由实验相对用户自选 / 轮询，显著提高接受率或降低退款和人工，并保持正贡献。

### 杀死指标

- 90% 以上长期需求仍由各创作者私域独立产生；
- 用户只买熟悉创作者；
- 路由不优于用户自己选择；
- 供给替换会破坏 SLA；
- 保障、退款、客服和备用供给使贡献转负；
- 首单后持续脱媒。

## 13. 路线 G：内容到行动 / 持续目标网络

这里包含两种不同需求结构，不能混为一个 Feed：

### G1. 内容到行动

用户先看到真实 Before / After 或案例，才意识到自己的问题，然后点击“应用到我”。

### G2. 持续目标

用户已经知道目标，但目标持续数周或数月；Combo 保存项目 Context，持续触发相邻任务和服务。

### 蓝方

真实 Run 可以在授权和脱敏后生成案例；案例不只是内容，而是带有可执行入口的需求证明。持续目标又能把一次性低频任务组织成项目关系。

### 红方

- AI 内容极易变成 slop；
- 隐私与专业结果不一定适合公开；
- 抖音、小红书、微信拥有注意力和社交关系；
- 浏览时长与结果订单可能负相关；
- 给低频任务强行加订阅会制造虚假留存；
- Feed 团队、内容治理和交易履约是两种组织能力。

### 裁判

**先把内容视为订单分发机制，把持续目标视为复购结构；两者有真实行为后再称网络。**

| 项目 | 内容到行动 | 持续目标 |
|---|---|---|
| 用户新动作 | 看案例并应用到自己 | 把一段目标持续交给 Combo |
| 提交物 | 授权案例、自己的 Context | 目标、约束、预算、进展 |
| 消费结果 | 个性化同类结果 | 连续任务和阶段结果 |
| system of record | 案例—需求—订单关系 | 长期 Context—计划—Run—Verdict |
| 商业模式 | 交易抽佣、效果分发 | 会员、Retainer、服务抽佣 |
| 网络效应候选 | 更多真实案例改善需求识别和同类结果转化 | 更多阶段 Verdict 改善下一任务与相邻供给选择 |
| 关键支撑 | 案例授权、脱敏、归因、内容质量、订单闭环 | versioned Context、授权、计划、提醒、相邻任务编排、成本上限 |
| 最大对手 | 小红书、抖音、微信及创作者自有内容渠道 | 通用助手、项目 / 目标管理产品、垂直会员服务 |
| Gate | 自然浏览产生正贡献订单 | 订阅优于一次购买且成本可控 |

### 停止条件

- 内容只有浏览，没有付款；
- 分享需要补贴或违反隐私；
- 用户不会无任务回访；
- 项目会员的使用成本随频率失控；
- 相邻任务之间不能复用 Context。

## 14. 路线 H：嵌入式结果商业基础设施

### 产品画面

若分别完成主体、审核、身份、支付、跳转 / 嵌入和事件回传 Gate，用户才可能在小红书、微信、ChatGPT、第三方 SaaS 或创作者主页完成发现与输入；Combo 能否在后台负责以下链路，必须由逐渠道合同和端到端测试证明：

```text
Result Contract
→ intake / authorization
→ execution
→ evidence / verdict
→ refund / settlement
```

### 蓝方

这条路线接受注意力长期属于大平台。Shopify 2026 年的策略和 OpenAI 从 Instant Checkout 转向 Merchant checkout 的变化共同提供了一个反例：前台可以进入 AI 对话，而 catalog、订单、归因和 merchant lifecycle 仍回到专业系统；它们不证明 Combo 必然能保有同样的状态。Combo 只有先在一个垂类拥有完整责任事件，再由外部渠道合法、持续地把这些事件交回，才可能成为嵌入式结果后台。

### 红方

- 外部平台可能逐步内生支付、Agent、订单和售后；
- Combo 不拥有消费者品牌和直接关系；
- API 容易被压价或替换；
- 渠道可以封锁外链、数据和支付；
- 若只提供 Runtime 调用，就是通用基础设施红海；
- 合作方可能只把低质量、低毛利需求交给 Combo。
- 腾讯元器已把“公众号知识 → 智能体 → 微信支付门”做成官方能力；扣子已吸收通用 Agent 建站与部署，抖音又拥有内容锚点、支付、退款、分账和复访。Combo 若只做博主分身、页面或支付接线，会退化成可替换 ISV；
- 渠道不是中性前台：它同时控制主体、类目、审核、身份、订单、退款、数据与结算，且规则可变。跨渠道不是“多写几个 adapter”，而是 Partner、SRE、法律和单位经济问题。

### 裁判

**Round 3 将它从“当前第二自然的平台期权”降级为 `Partner-conditioned option`。** 第一阶段只能是一种垂直结果 SKU 的渠道专用履约后台；只有同一 SKU 在两个独立渠道产生正贡献订单，且 Combo 合法保有身份映射、授权、订单、退款、Verdict 与归因事件，才能升级为嵌入式基础设施。

### 渠道现实：不能把“可发现”直接写成“可嵌入、可交易、事件可回传”

以下是 2026-07-31 的官方文档快照；渠道规则可能变化，接入前必须重验：

| 入口 | 可承载方式 | 身份 / 支付 / 审核现实 | Combo 能否获得订单与责任事件 | 当前裁决 |
|---|---|---|---|---|
| 微信 | 企业主体小程序可用 `web-view` 承载已配置业务域名的网页；个人类型小程序不支持；H5 与小程序消息只在特定时机送达，`web-view` JSSDK 不能直接等同原生支付 shell | URL Link / Scheme 也仅向非个人主体开放；需要主体、类目、域名、发布审核和商户 / 服务商进件 | 只有控制商户后端，或作为获授权服务商，才能获得支付回调、查单、退款、对账与分账事件；普通 H5 外链只得到点击 | 最适合创作者私域需求验证，但不是独立分发；先做薄原生 shell 和一笔端到端订单，不得把 `web-view` 当跨渠道 Runtime |
| 腾讯元器 / 微信生态 | 可把零代码 Agent、RAG、Workflow、Multi-Agent、插件 / MCP 发布到元器、微信公众号 / 服务号、微信客服、企业微信等 | 微信支付 MCP 已可创建 Native 订单并查单，但仍为公测 / 白名单；元器小程序支付标为“敬请期待” | 当前公开工具未见通用服务退款、创作者 payout、分账、明确验收或跨渠道责任账本 | 已直接吞掉“博主知识分身 + 微信付费门”薄层；Combo 只有在正式结果合约、验收 / 补救和责任经济上证明增量 |
| 小红书 | 官方小程序可进入商家主页、笔记、POI、私信 / 群聊和侧边栏；`web-view` 只能打开逐一配置的业务域名 | 需要企业资质专业号、类目 / 备案 / 上线审核；服务商申请仍是定向 / 存量合作，目标小程序必须回读实际 `trade_ability` 与 `support_trade` | 开发者保存自己的订单，同时必须同步商品、订单、支付、售后和结算状态；结算 API 的技术服务费计算不代表实际资金流 | `Partner-dependent` 候选渠道；文档对直连 / 担保能力存在版本差异，不能用一条总览替代目标账号实测 |
| 抖音 | 原生小程序可经搜索、分享、短视频 / 直播锚点、主页和侧边栏复访；`web-view` 受业务域名与运营规范约束 | 企业主体、类目、审核、保证金、支付进件与服务商授权分别成立；收费小程序须接担保交易 | 原生交易覆盖预下单、支付、预约 / 核销、退款、分账、CPS 和 D+N 结算；平台与开发者共同持有订单事件，服务商须经商家授权 | “内容 → 交易”能力最完整，吸收风险也最高；若 Combo 只做页面、推理和支付接入，会被压成 ISV |
| ChatGPT / Plugin | Apps SDK 可把自有逻辑、UI 和 backend 带入 ChatGPT，公开发现已迁移到 Plugin Directory；ChatGPT Sites 又覆盖托管站点、登录、表单和第三方支付 | Apps / Sites 各有 preview / beta 边界；OpenAI 已从初版 Instant Checkout 转向 Merchant checkout，不能假定专业服务存在统一内联结算 | Combo 可控制自己的 backend；OpenAI 当前变化反而说明真正 MoR、履约、客服与退款仍需专业后台承担 | 先验证发现、身份和任务回传；在真实订单事件与商业条款明确前，不计入 H 的交易 Gate |
| 其他 SaaS / 内容平台 | API、SDK、Webhook、白标、Deep Link 都可能 | 完全取决于合作方账户、支付、审核和数据条款 | 只有签约获得 order / authorization / refund / attribution 事件，才算基础设施渠道；只有 click / call 不算 | 每个 Partner 单独做 event contract 与集中度压力测试 |

**Round 3 的渠道结论：**“发布一次、到处运行”在当前官方规则下为假。真正可移植的只能是 Combo 自己定义的 contract / authorization / run / verdict / remedy 数据模型；每个 Surface 仍需要独立的主体、类目、审核、身份映射、原生 shell、支付、退款、事件、结算和数据留存合同。若没有这些，所谓多渠道只是同一个 H5 链接被多处点击。

| 项目 | 判断 |
|---|---|
| 买家 | 创作者平台、内容平台、SaaS、模型应用 |
| 频率 | 每次外部需求触发一个结果订单 |
| 提交物 | machine-readable contract、Context、授权、预算 |
| 消费结果 | 可追踪、可补救、可结算的交付 |
| system of record | contract、order、run、verdict、settlement、attribution |
| 商业模式 | API usage、交易费、保障费、白标 SaaS |
| 网络效应 | 更多渠道带需求，更多供给提高覆盖，更多结果改善 SLA |
| 关键支撑 | SDK/API、webhook、OAuth、portable identity、multi-channel attribution、billing |
| 最大对手 | 支付平台、内容平台、模型 Apps 平台、垂直 SaaS |

### Gate

- 同一结果 SKU 在至少两个独立外部入口产生正贡献订单；
- 合作方无需 Combo 人工陪跑即可持续扩容；
- 即使前台不出现 Combo，订单、退款、授权和质量事件仍可审计；
- 每个计入 Gate 的渠道都完成可嵌入 / 跳转、主体资质、身份、支付、审核、外链、订单 / 退款事件与客户数据归属核验；
- 渠道带来的需求不是负向选择；
- 替换某一模型或某一入口不破坏核心记录。

### 停止条件

- Combo 拿不到订单 / 退款 / 授权事件；
- 只剩低价推理与页面托管；
- 单一渠道决定大部分生存能力；
- 渠道抽成后无法覆盖履约责任；
- API 量增长但贡献毛利和质量下降。

## 15. 路线 I：企业结果工作台

### 蓝方

企业有更高任务频率、明确预算、正式权限、审批和审计需求。当前 Capability 版本、Run 事件、Revision 与 Test 更容易迁移到企业中的批准能力、任务执行和质量记录。

### 红方

- 需要完全不同的销售、实施、安全与采购能力；
- Microsoft、Google、飞书等拥有账户、组织 Context 和正式工作入口；Microsoft Copilot Studio 与飞书 Aily 还直接提供企业 Agent 构建、连接和治理。[Microsoft Copilot Studio](https://www.microsoft.com/en-us/microsoft-copilot/microsoft-copilot-studio)、[飞书 Aily](https://www.feishu.cn/content/3d5z9ttt)
- 每家企业集成不同，容易变成项目制；
- 创作者 GTM 与企业 GTM 会分散团队；
- 通用 Agent 平台已经覆盖 Runtime、Identity、Registry、Evaluation 和治理。

### 裁判

**这是独立战略分支，不是创作者路线自然多加几个功能。** 只有出现真实企业任务和预算后再启动。

| 项目 | 判断 |
|---|---|
| 买家 | 品牌、营销、运营、法务、销售等团队 |
| 频率 | 反复出现的部门结果任务 |
| 提交物 | 目标、企业 Context、权限、预算、审批 |
| 消费结果 | 经审计的复合交付 |
| system of record | task、policy、approval、run、evidence、vendor |
| 商业模式 | 年费、usage、项目费、服务支出抽佣 |
| 网络效应 | 经批准的内部 / 外部能力生态 |
| 关键支撑 | tenant、RBAC、SSO、audit、DLP、integration、SLA、procurement |
| 最大对手 | Microsoft、Google、飞书及已拥有部门 Context 的垂直 SaaS |

### Gate

- 一个部门反复采购同类结果；
- 能量化节省工时、周期或提高结果；
- 从一个团队扩展到第二个团队；
- 企业把 Combo 写进正式流程；
- 定制实施不随客户线性增长。

### 停止条件

- 只有一次性 PoC，没有预算续约；
- 每个客户都要重做集成、权限和流程；
- 销售、实施与安全成本在合理周期内无法回收；
- 无法从一个团队扩至第二团队；
- Microsoft、Google、飞书或垂直 Suite 以现有账户和 Context 直接内生同等能力。

## 16. 路线 J：Agent 采购、验收与结算网络

### 产品画面

一个外部 Agent 发现自己无法完成某项高责任任务，于是：

```text
查询 Result Contract
→ 选择供给 / 请求报价
→ 提交最小 Context
→ 按预算与权限付款
→ 接收结构化结果和证据
→ 自动或人工验收
→ 争议、退款或结算
```

### 蓝方

当个人和企业 Agent 获得预算与行动权，它们需要的不只是 Tool call，而是具有 SLA、责任、质量和补救的人类 / Agent 混合服务。Combo 的 Result Contract 和履约账本可以成为机器可采购的专业结果协议。

### 红方

- 外部 Agent 真实拥有预算和独立采购权限的证据仍少；
- 模型与支付平台可能直接定义协议和入口；
- 机器很难验收主观专业结果；
- 法律责任仍会回到人和企业；
- 交易量可能先集中在高度标准化 API，而不是人的专业服务；
- 没有密集的人类订单，先造协议只会成为空目录。

### 裁判

**保留 API-ready 架构，不提前造 Agent Marketplace。**

| 项目 | 判断 |
|---|---|
| 预算与责任主体 | 个人或企业委托方 |
| 交易 actor | 获明确授权的外部 Agent、企业 Agent 或 SaaS workflow |
| 频率 | 重复的外购专业任务 |
| 提交物 | contract query、Context、budget、policy |
| 消费结果 | machine-readable result + evidence + status |
| system of record | machine identity、authorization、order、SLA、verdict、settlement |
| 商业模式 | API、交易费、托管、保障 |
| 网络效应 | Agent 需求 × 专业供给 × 结果质量数据 |
| 关键支撑 | principal-agent binding、可撤回 delegated budget / authorization、policy engine、责任追溯、webhook、dispute、insurance |
| 最大对手 | OpenAI / Google / 支付平台 / 企业采购平台 |

### Gate

- 外部 Agent 发起真实、重复、付费交易；
- 交易不是团队演示或补贴；
- 结果存在机器可读或人机结合的验收；
- 外购持续优于模型自己完成；
- Combo 的保障和供给不会被入口平台直接内生。

### 停止条件

- 找不到承担预算与责任的真实委托主体；
- 只有团队 Demo 或单一入口补贴，没有跨入口重复付费；
- 结果无法由机器或人机结合验收；
- 委托授权不可撤回、不可追溯或超出责任边界；
- 模型、支付或采购入口直接内生同等供给、验收与争议能力。

## 17. 路线之间真正互斥的选择

### 17.1 专家品牌 vs Combo 品牌

- 专家品牌主导：C、D、G1；
- Combo 品牌主导：E、G2；
- 中立选择主导：F。

三者可以共享底层，但不能长期用同一前台承诺含糊处理。

### 17.2 开放平台 vs 自营履约

开放平台让供给者定义产品并承担主要承诺；自营结果公司由 Combo 定义价格、质量和补救。若同时做，必须明确：

- 自营供给是否参与平台排序；
- 平台如何披露利益冲突；
- 退款和保障由谁承担；
- 数据是否被自营团队不公平使用。

### 17.3 消费者目的地 vs 嵌入式基础设施

目的地需要用户记住 Combo；基础设施需要合作平台相信 Combo 不会抢走用户。二者在品牌、数据和渠道契约上可能冲突。

### 17.4 Creator GTM vs Enterprise GTM

一个依赖内容、私域和低摩擦自助；一个依赖安全、采购、集成和销售。中局阶段不应由同一小团队同时做深。

### 17.5 中立推荐 vs 主动管家

如果 Combo 的长期 Agent 替用户主动选服务，就必须解释排序、佣金和自营供给冲突；否则“更懂用户”会变成不透明销售。

### 17.6 分支触发后的停止投入规则

| 观察到的主信号 | 选择 | 同期停止或冻结 |
|---|---|---|
| 需求长期由专家私域产生，用户不跨供给，但专家高频经营 | C 专家 OS；按需加 D | 冻结开放 Marketplace、消费者 Feed 和平台补贴 |
| 用户只认 Combo 的结果承诺，单垂类需求与毛利集中 | E 垂直结果公司 | 冻结“中立平台”叙事；自营供给不参与伪中立排序 |
| 陌生供给购买、平台新增需求、路由增益同时成立 | F 精选 Marketplace | 冻结无品类边界的开放上架；先守一个密集 SKU 族 |
| 两个以上外部入口持续带来正贡献订单 | H 嵌入式基础设施 | 冻结与核心渠道争夺用户的消费者目的地；明确数据与客户归属 |
| 一个企业部门复购并扩至第二团队 | I 企业工作台 | 独立预算与 Roadmap；不让 Enterprise 定制吞噬 Creator 自助产品 |
| 外部 Agent 在无补贴下重复付费采购 | J Agent 采购网络 | 在此之前只保持 contract API-ready，不建设空 Registry |
| 上述信号均不成立，但单个 Result SKU 有利润 | 保持 Result Product / 垂直服务 | 停止平台融资叙事，优先 PMF 与现金流 |

**资源纪律：**同一季度只能有一条公司终局分支获得主要新增人力。B、D、G 只能作为主分支的效率 / 分发机制，不得各自长成独立 Roadmap。

## 18. 推荐的条件式主干

```text
Phase 0A  Studio-only Agent Miniapp
  证明界面与 bridge smoke test 可用，不代表可向消费者发布
        ↓
Phase 0B  Safe Experiment Publication
  Runtime HTML fail closed + 服务端 Publication + 可信宿主界面
        ↓
先用一手证据选择市场，不把两种用户混成一步
        ├─ Phase 1A  Professional Workflow OS
        │    专业团队的资产、版本、协作、QA；验证 SaaS / usage 与项目内留存
        │
        └─ Phase 1B  Creator Result Product
             一个自然 Buyer Job、一个结果、一个价格、一个边界、一个验收与补救
                      ↓
           Phase 2  Creator Result Commerce OS
             独立买家现金、采用、订单、QA、人工、退款、收费、客户与自然复购
        ↓
用真实交易选择分支
        ├─ 用户忠于专家 → 专家 OS + 方法授权
        ├─ 用户忠于 Combo 结果 → 垂直结果公司
        ├─ 用户跨供给购买 → 精选 Marketplace
        ├─ 案例产生需求 → 内容到行动网络
        ├─ 外部渠道持续带单 → 嵌入式基础设施
        ├─ 企业反复采购 → 企业结果工作台
        └─ 外部 Agent 真采购 → Agent 采购与结算网络
```

### 为什么结果交易路线通常要先经过经营与责任层

Marketplace 需要真实供给、质量和交易；内容网络需要真实案例；嵌入式基础设施需要稳定 contract 与 SLA；Agent 采购需要机器可读履约。它们共同依赖的不是更多 HTML，而是一个已经运行的结果经营与责任系统。但这不证明所有公司路线都必须先做多租户 Creator OS：专业 Workflow OS 可以成为独立的 B2B 软件而不进入交易；垂直结果公司可以把责任层内化为自营流程；企业工作台可以由单一企业承担买卖双方关系；模板 / 开发工具路线也可能根本不进入结果交易。Creator Result Commerce OS 只是与当前代码和叙事连续性较高、但买方需求、自然频率、资金链和双边毛利都待证的第一个假设。

### 一种内部一致、但尚未达到投资证据门槛的平台终局

如果后续第三方依赖、跨参与者增益、真实订单和责任事件证据成立，一种内部一致的终局不是“Agent 网站平台”，而是：

> **AI-native 专业结果的 operating and settlement layer：让人的方法、Agent 和工具在任何入口被发现，但由 Combo 把它们组织成有合约、有证据、有验收、有补救和有结算的结果。**

这更像：

```text
Shopify 的 lifecycle ownership
+ ServiceTitan 的垂直 system of record
+ Fiverr 正在补的 fulfillment / quality layer
+ 面向 Agent 的 machine-readable contract
```

它不是上述公司的功能拼装，而是一种控制权结构：**前台可租，模型可换，支付轨道可接；结果合约、授权、履约、Verdict 与责任账本必须属于 Combo。**

## 19. 30 / 90 / 365 天行动路线

以下日期是**实验顺序，不是既定交付承诺**。资源假设是：一支能同时覆盖 Product、Runtime、Web / Data 的核心研发小队，加一名持续负责真实订单 / QA / 创作者成功的人，并能按需获得支付与隐私法务支持。若缺少这一配置，必须顺序降级：

```text
先做 Runtime HTML fail closed、最小真实发布与可追溯 / 人工可补救 Run
→ 再做一套 Result / Verdict 人工可运营闭环，并在合规资金路径上验证真实付款
→ 在多供给复制前把 Run 升级为 durable reliable execution
→ 真实订单成立后才工程化完整 Surface、支付、结算与发现
```

不得为了凑 90 天范围，同时做开放 Marketplace、复杂推荐、企业集成和 Agent 协议。

### 未来 30 天：先验证真实结果，再决定完整 Miniapp 是否值得建设

目标不是增加模板，也不是“证明平台”，而是先关闭发布断点，并回答第一性问题：真实市场究竟是专业团队的 Workflow OS，还是买家为创作者结果付费的 Result Commerce；若选择后者，再跑通一个可核验的最小经济闭环。

1. 立即把当前 Runtime HTML artifact 默认改为静态隔离；第一批付费需求先用可信宿主表单 / declarative Surface、人工履约和服务端 Publication 验证，不把任意生成 HTML 的安全发布设施作为需求验证前置大工程。只有 A/B 证据证明任务型 Miniapp 相对可信宿主 UI 显著提高完成、接受或复购，才继续建设不可变 Surface Binding、无 egress 隔离、typed action、宿主确认、发布扫描、短期 entitlement、限流、滥用审计和 kill switch；
2. 先做 `Gate U0`：在获得同意并去标识后，收集连续、自然发生的重复咨询 / 付费服务样本，记录触发、期限、赌注、用户原有替代、希望采用的交付物与再次发生周期；画像、粉丝量、公开资料抓取与创作者“觉得可以卖”不得代替实际 Buyer Job；
3. Founder 明确二选一：若样本主要是专业团队内部反复生产 / 审核，先验证 Workflow OS 的付费与项目内留存；只有出现独立买家反复需要的可范围化结果，才选定一个 Result SKU 族进入以下交易实验；
4. 为其定义 `Result Contract v0`：
   - 输入；
   - 交付物；
   - 不做什么；
   - 期限；
   - 验收；
   - 返工 / 退款；
5. 给每次 Run 增加：
   - `contract_id / version`；
   - `order_id`；
   - `buyer / provider`；
   - `source_attribution`；
   - `human_minutes`；
   - `verdict`；
   - `refund`；
   - `direct_cost`；
6. 使用 3 位独立创作者做同一 SKU 族，不做 3 个完全不同的 Agent；每位按相同条款完成两次自然发布，熟人、团队代购、折扣、保底与补贴各自独立成 cohort；
7. 对同一真实输入运行三方盲测：免费通用模型 shadow baseline、Combo 结果产品、专家本人；预注册最小质量 / 采用增益，不用事后挑最好案例；
8. 可信宿主 UI 与任务型 Miniapp 做随机或交错对照，检验 Surface 是否提高 `intake completion → cash payment → explicit adoption`，而不是只提高点击；
9. 逐单记录触达、启动、Context、现金付款与付款主体、全部 Run / 重试、交付、`usable_without_revision / needs_revision / rejected`、采用证据、退款、站外投诉、各方人工分钟和双方贡献；
10. 预先写明该 SKU 的自然复购窗口、最低贡献和 Creator 净增量阈值；没有真实基线时阈值是 Founder Choice，不抄行业平均数，30 天内尚未进入自然窗口的用户标记为 right-censored。

**首笔付款前的法律 / 资金 Gate：**必须先确定服务销售方与合同相对方、merchant of record、收款账户、发票与税务、退款 / 拒付责任、是否构成平台经营，以及资金是否涉及托管、归集和向创作者分账；支付服务商的存在不会自动解决这些问题。支付机构自身还受客户身份、协议、交易真实性 / 可追溯性和退款原路返回等规则约束，但 Combo 的具体义务取决于资金与合同结构，必须由专业意见确认。[中国人民银行：非银行支付机构网络支付业务管理办法](https://www.pbc.gov.cn/zhifujiesuansi/128525/128527/541ae120fc6d4840836b4d089a82d94d/2015122817313737874.pdf)

30 天最保守的付费 pilot 是：由创作者 / 实际服务提供者使用自己的合规商户账户直接向买家收款，并承担合同、开票和退款责任；Combo 不归集、不保管、不代结算创作者资金，只凭可核验付款证明签发可撤销 pilot access grant，并在获得必要授权后记录订单状态和全成本。该模式下，买家现金属于创作者 GMV；如果 Combo 没有按真实合同收到 SaaS、usage 或服务费，这个 pilot 只能验证买方需求与履约，不能验证 Combo 的 take rate、收入或贡献毛利。若改由 Combo 收款或形成创作者应付，必须在首笔付款前完成对应法律审查、支付 / 分账产品能力和合同安排，不能用人工应收 ledger 代替。

第 56–75 天才在已确认的资金路径上，把 buyer identity、Webhook、Entitlement、order / payment / refund / settlement 产品化。早期 pilot 只是业务验证，不得表述为 Combo 已有内建交易基础设施。

**30 天裁决问题：**

> 陌生买家是否在安全、可追溯的可信界面中，为一个明确结果真实付费并明确采用；Combo 是否相对“直接问通用模型”或“可信表单 + 人工”带来可测增益？只有 Surface 对付款、采用或复购另有因果 uplift 时，“发布完整 Miniapp”才成为下一阶段必要条件。

还必须同时回答：

> 这个买方任务是否会在可观察的自然周期再次发生；结果是否被明确采用而不只是“没有退款”；创作者和 Combo 分别获得了什么真实净增量？若这些问题没有答案，30 天结果只能叫兴趣 / 供给 / 履约实验。

### 未来 90 天：证明“经营系统”而不是“共创项目”

1. 把 Run 改为可恢复、可审计的可靠执行，而不是只由 API 进程内存状态维持；
2. 上线最小订单 / QA / 人工升级 / 退款 / 分账工作台；
3. 让非创始团队按 SOP 上线新供给；
4. 跟踪第二次自然发布、第二 SKU、D60 / D90 供给活跃；买方分别跟踪同 SKU、同创作者跨 SKU、跨创作者，并按自然触发周期而非统一 DAU 判断；
5. 做 Context 开关实验；
6. 做 Combo 售后 vs 创作者自行售后实验；
7. 区分 creator deep link、平台入口、Partner 入口与投放 cohort；
8. 为跨供给推荐保留结构，但不开放泛 Marketplace。
9. 用同一 SKU 分别做 Combo 与一个成熟 Builder / Commerce 组合的对照（如 Replit / Lovable / Wix + 支付 Provider）；记录上线时间、缺陷、support cost、交付与采用。若 Combo 没有预注册的数量级改进，Builder 不再作为 wedge；
10. 对照“通用表单 + 人工 review”与“Result Contract + machine / human Verdict”；预注册付费完成、明确采用、返工、退款与 support minutes 的胜负标准。合同字段增加但行为没有改善时，停止把 Result Contract 本体写成差异；
11. 让目标创作者实际试用 Gumroad Commission、Fiverr 或 Upwork 的相邻流程；若他们无法指出可重复的验收、异常、版本或跨渠道痛点，Creator Result OS 假设应被杀死，而不是继续补功能；
12. 对机器 Verdict 做 blind expert 对照，记录一致率、可解释分歧和 exception rate；具体阈值属于预注册 Founder Choice，但必须证明它会随 rubric / version / cohort 改善，而不是固定制造人工队列；
13. 至少积累 30–50 笔未补贴真实付费单再判断 outcome data；若到约 100 单后版本 / rubric 没有改善 exception、refund、adoption 或人工分钟，所谓 outcome graph 只是归档，不是复利资产；
14. 渠道验证先做一个真实授权主体的一笔完整订单事件样本；只有该垂类后台已正贡献，再进入第二渠道。微信、小红书、抖音分别回读身份、支付、退款、结算、数据导出和服务商权限，不把测试支付或 H5 点击计为接入完成。

**90 天裁决问题：**

> 专家是否因为 Combo 的订单、履约和经营价值持续回来；每多一笔订单，Combo 是否更难被替代？

在 Round 2 修正后，还要先问：

> 被留存的到底是谁：专业团队因为 Workflow OS 回来，创作者因为经营与净增收回来，买家因为结果回来，还是只有 KOL 再次发链接？只有最后一种时，Combo 仍没有自己的需求关系。

### 未来 365 天：由数据选择一种公司

#### 分支 1：专家 OS

条件：专家品牌强，客户与经营留在 Combo，第二 SKU 和 D90 供给留存成立。

#### 分支 2：垂直结果公司

条件：用户不在意供给身份，一个垂类高度集中，Combo 品牌与流程更重要。

#### 分支 3：精选结果网络

条件：平台自产需求、跨供给购买与因果路由增益同时成立。

#### 分支 4：嵌入式基础设施

条件：两个以上第三方入口可重复地产生正贡献订单，且 Combo 保有关键履约记录。

#### 分支 5：企业工作台

条件：企业预算、频率与正式流程明显优于消费者路径，且愿意承担独立 GTM。

#### 分支 6：Agent 采购与结算协议

条件：外部 Agent 由明确个人 / 企业主体授权，在无补贴下跨入口重复发起真实付费采购，结果可由机器或人机结合验收，且入口平台没有直接内生同等供给、保障与争议能力。若 365 天内没有该信号，J 只保留 schema / API-ready 兼容，不投入独立 Registry 或 Marketplace。

**365 天裁决问题：**

> 哪一侧开始主动依赖 Combo：专家经营、消费者需求、企业流程、外部渠道，还是外部 Agent？

## 21. 红蓝总辩论

### 蓝方总论

AI 已形成大众问答与 Artifact 消费，公开研究又表明同一模型在不同 Surface 上能产生不同委托深度；四份真实创作者访谈则证明专业生产中的资产、版本、抽样、协作与人工质控有问题。Combo 的本地代码拥有从方法 / Session 提取 Capability、生成任务型 Miniapp、运行通用 Runtime 并保留部分版本记录的技术起点。OpenAI 和 Google 的 commerce 设计又明确把 MoR、客户关系与履约责任留给 Merchant，OpenAI 甚至从灵活性不足的原生 Instant Checkout 转向 Merchant checkout；这证明强入口与专业后台可以分离。若 Combo 在一个窄垂类中以结构化 intake、Context、可核验结果本体、机器 / 人 Verdict、异常补救和责任经济显著提高采用与净收入，它可以先成为专业 Workflow / Fulfillment system of record；如果后续再出现独立买家现金、平台新增需求、跨供给增益和两个渠道交出的完整责任事件，需求、供给、结果数据和外部入口才可能围绕同一标准对象连接。

### 红方总论

AI 使用不等于购买结果，专业创作者的内部工作流痛点也不等于其粉丝愿意购买 AI 结果；当前 Combo 真源没有可回读的现金订单、采用、退款、复购、创作者到账或每单人工分钟。创作者可能低频、不愿交客户，买家可能直接问免费模型或首单后回微信。低价、15% take 与高触达人工在数学上相互挤压；Fiverr 的当前经营披露还显示，AI 正在吸收高频低价值服务，平台本身转向更高价值、可信履约。创作者直收不能验证 Combo 交易收入。与此同时，OpenAI、Anthropic、Google、Microsoft、腾讯、Replit、Lovable、Wix 与 Canva 已商品化创建、Runtime、身份、连接器、托管、测试、治理、分发或支付接线；Kajabi / 元器已进入专家 Agent；Gumroad、Upwork、Fiverr 已拥有 Result Contract、里程碑、验收、修改、争议或 human exception 的多个组成部分；微信、小红书、抖音控制主体、审核、支付、订单和售后。所谓“责任层空白”也可能只是责任重、毛利低、资金和人工成本高，而不是无人发现。只要 Combo 没有真实订单、可学习的验收判例和正贡献责任账本，所有“平台”仍只是把现有功能画大。

### 裁判总论

蓝方证明了**方向上的可能性**，红方否定了**线性升级的必然性**。

最终裁决是：

> **Combo 存在一个尚未达到投资证据门槛的平台假设，但平台不是当前产品的放大版。只有真实行为证明用户围绕 Result Contract 交易、围绕经营动作留存、用 Verdict 改善下一单，并让独立第三方依赖 Combo 的履约与责任规则，这个假设才开始成立。**

Round 2 进一步裁决：

- `Verified Fact`：当前审计真源没有 Combo 稳定现金订单与成熟 cohort；实际访谈只直接支持专业创作者 Workflow 问题；
- `Strong Inference`：结构化任务 Surface 与 Workflow OS 可能有独立价值；KOL 私域是减少首轮实验变量的合理方式，但不是平台渠道或护城河；
- `Hypothesis`：创作者品牌、Result Contract、Context、QA 与补救足以把免费问答转成买家自付、明确采用、自然复购和正贡献；
- `Founder Choice`：先做专业 Workflow OS 还是 Creator Result Commerce；谁是 seller / MoR、向谁收费、选择何种自然频率与贡献阈值，不能由报告替团队决定。

Round 3 进一步裁决：

- `Verified Fact`：Combo 当前 `marketplace_listings` 是已发布 Capability 的内部卡片投影，收益 / 结算为占位，Runtime API 没有渠道、订单、退款或结算对象；外部平台已覆盖绝大多数横向 Builder / Runtime / Identity / Registry / Governance / Checkout 原语，既有服务市场也已有合同、交付、验收、修改与争议机制；中国渠道要求各自的主体、类目、审核、支付、订单和服务商 Gate；
- `Strong Inference`：Runtime HTML、连接器、托管、支付接入和 Result Contract 字段都不足以形成壁垒；若有机会，只能迁移到某一垂类的任务本体、可验证 Verdict、异常判例、责任经济和供需信誉。外部前台可以多元，但专业后台必须先成为真实 system of record；
- `Hypothesis`：Combo 能在一个高价值、自然复购的垂类中，比通用 Builder + 既有服务平台显著提高明确采用、降低返工 / 人工分钟，并让 accepted-outcome / repair 数据形成跨供给与跨模型复利；
- `Founder Choice`：首个垂类与 SKU、seller / MoR、验收与赔付边界、人工兜底深度、首个渠道、是否成为服务商 / 隐身后台，以及何时从垂直运营转为中立平台，必须主动选择。

## 22. 什么会让我们改变主意

### 会让我们更乐观

- 同一 SKU 族跨独立创作者复制，无创始人陪跑；
- 用户愿意为 Combo 相对通用模型的结果增益付费；
- 人工分钟随版本和数据持续下降；
- 创作者把订单、支付、返工和客户留在 Combo；
- 用户无原创作者触达仍复购或跨供给购买；
- Context / routing 在随机或准实验中改善结果；
- 第三方渠道持续嵌入并交出关键订单事件；
- 外部 Agent 发起真实采购。

### 会让我们转向垂直结果公司

- 一个垂类占据绝大部分高质量订单；
- 用户不关心供给身份；
- Combo 品牌承诺和自营流程显著提高转化；
- 横向 Context 与跨供给复用很弱。

### 会让我们停止平台叙事

- 创作者私域长期贡献几乎全部订单；
- 用户不跨供给；
- Context 和结果数据不改善下一单；
- 所有订单都需要线性人工；
- 页面 / Agent 数增长但付费与复购不增长；
- 原生模型平台能用更低成本完成同样结果与售后；
- Combo 无法获得订单、授权、退款和结算记录。
- 目标创作者用 Gumroad / Fiverr / Upwork 或 Wix / Kajabi + 通用模型即可完成相同结果，且说不出持续的验收、异常或版本痛点；
- 机器 Verdict 与专家判断不一致、exception 不随 rubric / cohort 下降，人工分钟长期线性；
- 首个渠道无法取得真实商户 / 服务商授权和完整事件，或第二渠道的接入与履约成本重新线性增长；
- 约 100 笔订单后，Outcome / Repair 数据仍未改善 adoption、refund、rework、人工分钟或贡献毛利。

## 23. 当前未决问题

1. **用户 / 交易研究：**第一类真正可售卖的 Result Contract 是什么？
2. **用户研究：**当前目标创作者是否把“持续经营”视为真实工作，还是只想要一次性链接？
3. **用户 / 交易研究：**用户购买的是专家身份、结果质量、Combo 保障，还是低价格？
4. **技术实施 Gate：**未来完整交互 Surface 面向陌生消费者时，typed action 是发布前置条件；仍需决定各 SKU 的 `action_id`、payload schema、tool / data scope 和宿主确认粒度。自由文本 `prompt` bridge 只限 Studio。可信宿主 pilot 不加载生成脚本，按最小 Publication、pilot access 与 Run traceability Gate 执行。
5. **安全 / 隐私 / 法律 Gate：**哪些 Context 必须由用户逐项授权，哪些可以跨订单复用？
6. **交易 / 经济研究：**首稿接受、退款和人工分钟的真实基线是什么？
7. **支付 / Partner / 渠道 Gate：**Combo 能否获得支付、退款和结算真事件，而不是只接一个外部支付链接？
8. **运营 / 经济研究：**哪一种失败最常见，返工、换供给还是退款最经济？
9. **产品 / 隐私实验：**一个真实结果能否安全地产生下一个需求或案例？
10. **治理 / 法律决策：**平台是否应允许自营供给，如何处理排序冲突？
11. **Partner / 渠道 Gate：**外部内容 / 模型平台愿意交给 Combo 哪一层状态？
12. **质量 holdout：**专家方法是否带来可盲测的质量增益，还是只带来转化信任？
13. **Founder Choice：**先验证专业团队 Workflow OS，还是粉丝侧 Creator Result Commerce；什么一手证据会触发改道？
14. **需求研究：**首个 Buyer Job 的自然发生率、期限、现有替代和自然复购窗口分别是什么？
15. **经济 / 法律决策：**首个 pilot 中谁是 seller / MoR，Combo 实际向谁收什么费用，退款、拒付、发票与结果责任由谁承担？
16. **行为研究：**买家收到结果后是明确采用、修改、拒绝、退款，还是沉默；第二次需求回 Combo、回创作者微信，还是回通用模型？
17. **竞争对照：**同一 SKU 相对 Replit / Lovable / Wix + 支付 Provider，以及 Gumroad / Fiverr / Upwork，究竟减少了什么可测成本或增加了什么可测采用？
18. **质量研究：**机器 Verdict 与 blind expert 的一致率、可解释分歧、exception rate 与学习曲线是什么？
19. **渠道 / Partner Gate：**首个 SKU 在微信、小红书、抖音分别属于什么类目，Combo 或合作方能否取得商户 / 服务商资格、退款权、数据导出权与可接受的结算周期？
20. **渠道经济：**扣除平台佣金、保证金 / 账期、支付费、退款、人工和服务商成本后，哪个入口仍有正贡献？
21. **平台依赖：**若 OpenAI / 腾讯 / 渠道关闭某一 Builder、目录或支付能力，Combo 哪个核心记录与客户关系仍可独立迁移？

## 24. 四轮综合裁决：先成为垂直结果经营者，再争取平台资格

这一节是四轮复审共同形成的最终增量。它不是再增加一条宏大路线，而是把当前身份、必要顺序、最强正反论和 90 天停止条件压成一个可执行裁决。

### 24.1 当前公司到底是什么

**今天的技术产品：**

> `Capability-to-Miniapp Compiler + Runtime Studio` 的早期组合。

**今天应验证的公司：**

> 只服务一个垂类、只验证一个 Result SKU 族的 AI-native 结果履约产品公司。

**今天不是什么：**

- 不是已经完成消费者发布闭环的 Agent 建站工具；
- 不是 Agent Marketplace；
- 不是专家分身平台；
- 不是 Creator Commerce OS；
- 不是跨渠道结果基础设施；
- 不是“AI 服务的 Shopify”；
- 不是平台。

“OS”至少要求多位独立经营者在自然周期内、无需创始人陪跑地反复使用同一套订单、版本、Verdict、补救与经济状态，并产生全成本正贡献。“平台”则还必须同时满足：

1. 独立第三方持续围绕同一标准对象构建、履约或交易；
2. 新增供给、需求、渠道或结果数据，能因果改善另一个独立参与者的体验或经济。

在本次审计范围内，Combo 对两项平台硬前提均为 `0 / 2`。因此当前只有**运行平台实验的资格**，没有**宣称平台已沿确定路径长出的资格**。

### 24.2 四轮各自改变了什么

| 轮次 | 原先容易相信的故事 | 本轮加入的事实 | 最终修正 |
|---|---|---|---|
| Round 1：代码与产品真相 | Combo 已经把 Agent 做成可发布 Miniapp | 当前实际是五条相邻链；Studio Surface 未绑定消费者 Publication；普通 Runtime HTML 默认可执行；没有真实授权、订单、退款、结算和可靠执行闭环 | “建站工具”也未闭环；先关闭 Runtime HTML P0，用可信宿主与最小 Publication 做实验，不把 Roadmap 当现状 |
| Round 2：用户与经济真相 | AI 用户很多，创作者有粉丝，因此结果交易自然成立 | 当前没有可回读的 Combo 现金、采用、复购、退款、创作者到账或逐单人工；访谈只直接支持专业生产 Workflow 痛点 | `AI 使用`、`创作者愿意做`、`买家购买结果`、`Combo 获得收入` 是四件事；必须从自然 Buyer Job 与三方全成本开始 |
| Round 3：竞争与产业真相 | 补上 Runtime、Listing、支付、Result Contract 与 human handoff 就进入平台空白 | 模型平台、AI Builder、Agent 平台与 Wix 等正在吸收横向创建 / Runtime；Gumroad、Upwork、Fiverr 已有多种服务合同、验收与争议原语；中国渠道各自控制主体、审核、支付、订单和售后 | 字段与接线不是壁垒；唯一仍可验证的是一个垂类的 `任务本体 × Verdict × 异常学习 × 责任经济 × 供需信誉` |
| Round 4：综合裁决 | 可以沿相邻能力逐层升级为平台 | 三轮没有提供需求连续性、经济连续性或网络连续性；责任空白可能是低毛利、高人工、高法律责任的负选择区 | 先验证一个结果原子，再验证无创始人复制、垂直 system of record 与学习曲线；第三方依赖和跨参与者增益出现后才升格平台 |

### 24.3 蓝方：最强仍可成立的平台论

蓝方最强命题不是“更多人建 Agent”，而是：

> 模型负责生成，渠道负责发现，专业者处理例外；Combo 在一个垂类中连续拥有 `Result Contract → Context / Authorization → Run → Evidence → Verdict → Remedy → Economics`。当多个独立供给者和入口围绕同一责任对象运行，且新增订单与异常判例会改善他人的质量、成本或匹配时，这套垂直后台才可能跃迁成平台。

证据链是：

```text
AI 降低第一稿与软件生成成本
→ “能生成”日益丰裕
→ 可信完成、失败处理与责任仍稀缺
→ 垂类 Contract + Verdict 把模糊服务变成可经营对象
→ 连续订单沉淀 accepted / repaired / rejected 与全成本
→ 异常判例降低下一单的返工、人工或退款
→ 同一对象跨独立供给复用，形成备用履约与可比较质量
→ 同一责任账本跨入口复用，降低渠道切换成本
→ 第三方因为共同记录获得净增益
→ 平台成立
```

支持这条命题的**已验证事实**只有：

- Combo 已有 Capability、Version、Studio、Run、Artifact、Revision 与 Test 等技术骨架；
- 这些对象已经覆盖方法 / 契约、任务界面、执行与版本记录的部分链路；
- 强入口并不必然接管专业后台。OpenAI 2026 年把 commerce 重心转回 product discovery，允许商家使用自己的 checkout；Walmart 仍保有账户、会员和支付关系。[OpenAI Product Discovery](https://openai.com/index/powering-product-discovery-in-chatgpt/)
- Wix 已把自己公开定位为 AI-built site / app 可复用的 business backend，说明横向建造层正在商品化，同时业务状态后台可以与任意前台分离。[Wix Headless](https://www.wix.com/blog/wix-headless)

由此可以形成的**强推论**是：这条技术连续性可能减少迁移到垂类结果账本的重建成本，使 Combo 比从纯 Landing Page、聊天或支付工具起步更快验证一个结果责任后台。

不能形成的结论是：Combo 已拥有独有分发、专有业务数据、供给网络、品牌、交易关系或结果责任能力。现有技术连续性只是 execution continuity，不是 right-to-win。

### 24.4 红方：最强反论不是大厂，而是“责任层可能没有好生意”

红方最致命的反论是：

> 低风险、易标准化的结果会被免费通用模型和成熟 Builder 压价；高风险、有明确责任的结果又需要专家审核、客服、返工、退款、争议和赔付。所谓责任层空白，可能是一个低毛利、高人工、高法律责任的负选择区，而不是尚未被发现的基础设施机会。

Combo 因而面临一个两难：

- 不承担结果责任，只是一个可被模型、创作者、渠道和既有服务市场绕开的工具；
- 承担结果责任，就必须证明人工、客服、争议和赔付不会随收入线性增长，否则它只是一家尚未完整入账的服务公司。

当前证据中，以下因果链每一箭头都仍未成立：

```text
能提取 Capability、生成 Miniapp
≠ 有自然 Buyer Job
≠ 买家愿意相对免费模型付费
≠ 交付被明确采用
≠ 买家在自然周期复购
≠ 多位供给者能复制同一 SKU
≠ Verdict 数据会改善下一单
≠ 买家愿意购买陌生供给
≠ 渠道愿意交回完整责任事件
≠ 独立第三方形成平台依赖
```

腾讯元器的微信支付 MCP 当前只公开“创建支付”和“查询订单”两个工具，Miniapp 支付仍标注“敬请期待”，正式版还受白名单 / 公测限制。这是“支付能力存在”不等于“平台资金、订单、退款、结算闭环存在”的直接例子。[腾讯元器微信支付 MCP](https://yuanqi.tencent.com/guide/wechat-pay-mcp-plugin)

### 24.5 裁判：什么被推翻，什么被保留

**被推翻：**

- 技术相邻会自然导向平台；
- 无人完整占据责任层，就等于存在高质量生意；
- 创作者私域天然解决需求冷启动；
- `Result Contract`、HITL、支付接线或更多字段天然形成壁垒；
- 日志累积天然形成数据飞轮；
- 一次发布、跨渠道运行在当前规则下已经成立；
- 完整可执行 Miniapp 是验证 Buyer Job 的前提。

**被保留：**

- 通用 Builder / Agent 建站不应成为 Combo 的主战场；
- 一个窄垂类 Result Product 仍值得严谨实验；
- Professional Workflow SaaS、Creator Fulfillment OS、垂直结果公司都可能是独立、真实而且足够大的公司形态；
- Combo 现有技术骨架能缩短实验路径；
- 只有垂直 system of record、独立第三方依赖与跨参与者因果增益同时出现，平台期权才重新打开。

**最终裁决：**

> Combo 的平台论在结构上可能成立，在证据上尚未成立。未来 90 天的任务不是建设平台，而是用一个垂类、一个 SKU 和一套不可篡改的结果经济账本，决定这家公司究竟应该成为 Workflow SaaS、Creator Fulfillment OS、垂直结果公司，还是停止该市场。

### 24.6 “为什么是 Combo、为什么是现在、为什么不会被吞掉”

#### 为什么是 Combo

当前成立的答案只有：

- Capability、Studio、Runtime、Version、Artifact、Revision、Test 提供了一条可以继续演化的技术脊柱；
- 团队已经在“方法 → 任务界面 → 运行记录”上有实现连续性，可以比从零起步更快完成垂类实验。

当前不成立的答案包括独有分发、独家供给、专有结果数据、平台流动性、交易信誉与渠道控制权。因此更诚实的表述是：

> **Combo 有资格比别人更快运行这项实验，但尚无证据证明只有 Combo 能赢。**

#### 为什么是现在

“现在”来自三种结构变化同时发生：

1. 模型让第一稿、解释、代码和页面生成的边际成本快速下降；
2. Builder、Runtime、托管、支付接线与入口能力正在被模型公司、云和 Site Builder 商品化；
3. 专业结果的 Context、授权、验收、异常补救和责任仍分散在模型、专家、渠道与买家之间。

这给垂类 system of record 留出一个短验证窗口，但不是天然护城河。模型进步同时会继续降低结果价格、提升大厂吸收速度；如果 Combo 继续停在 Builder / Runtime / Listing，它更容易被吞掉。

#### 为什么不会被模型或大厂吞掉

今天没有诚实的肯定答案。只有以下条件逐步成立，Combo 才可能不被替换：

1. 模型可换：换模型不带走订单、授权、结果历史与责任记录；
2. 前台可租：微信、ChatGPT、创作者主页等带来需求，但权威 Contract、Run、Verdict 与 Remedy 回到 Combo；
3. 状态难迁移：离开 Combo 会失去版本化 rubric、历史 Context、异常处置、备用履约与责任证据，而不只是换一个 API；
4. 数据真学习：新订单能在 prospective holdout 中降低下一单的返工、人工、周期或退款；
5. 第三方真获益：买家、供给者与渠道各自因 Combo 获得可量化净增益，并在自然周期重复。

“模型无关”只是韧性，不是壁垒；“渠道很多”只是依赖分散，不是需求所有权；“字段完整”只是 schema，不是制度。

### 24.7 必要演化顺序与关键支撑

```text
Phase 0  安全可试验
Runtime HTML fail closed；可信宿主；服务端 Publication；可追溯、人工可补救的最小 Run
        ↓
Phase 1  单一付费结果成立
一个 Buyer Job、一个 SKU 族、一个 seller / MoR、一个责任边界
        ↓
Gate 1.5  durable execution
在进入无创始人、多供给复制前完成 queue / lease / recovery 与可补救终态
        ↓
Phase 2  无创始人复制履约
3–5 位独立供给者复用 Contract、QA、Verdict、Remedy 与经济账
        ↓
Phase 3  垂直 system of record
订单、版本、结果、例外、客户与经济在自然周期持续留在 Combo
        ↓
Phase 4  正贡献与结果学习
异常、退款、人工与周期随 cohort 改善；三方净增量为正
        ↓
Phase 5  平台资格
独立第三方依赖 + 跨参与者因果增益 + 真实规则治理
        ↓
Phase 6  第二渠道 / 外部 Agent 协议
只在同一责任对象可复用、且新入口正贡献时展开
```

每次跃迁需要的关键支撑：

| 支撑 | 进入下一阶段前必须拥有 | 当前边界 |
|---|---|---|
| 产品 | 自然 Buyer Job、明确 Result Contract、显式采用与补救 | 没有真实 Buyer Job / 采用 cohort |
| 技术 / 实验 | HTML fail closed、可信 Publication、可追溯且人工可补救的最小 Run | 当前仍缺消费者安全与最小真实发布闭环 |
| 技术 / 复制 | 在进入 Phase 2 前完成 durable queue / lease / recovery、可补救终态与不可篡改事件账 | 当前仍缺可靠执行闭环 |
| 数据 | 逐单 Context / Run / Verdict / exception / human minutes / economics | 当前没有真实订单数据 |
| 运营 | 盲测 QA、SOP、人工升级、退款 / 争议和无创始人供给复制 | 尚未形成可审计履约体系 |
| 经济 | 买家、供给者和 Combo 三方的全成本正增量 | 当前没有 Combo 现金与单位经济 |
| 法律 / 治理 | seller / MoR、合同、税务、隐私授权、退款、责任与渠道资质 | 首笔付款前仍需明确 |
| GTM | 独立买家自然触发；区分创作者私域、平台、Partner 与投放 cohort | 当前没有自有需求证据 |
| 资本纪律 | 一个季度只验证一个市场、一个 SKU、一个主要分支 | 不能并行建设 Marketplace、多渠道、Enterprise 与 Agent 协议 |

### 24.8 四级 Kill Criteria

下列数量是为形成可审计 cohort 建议的**预注册 Founder Choice**，不是行业成功率。

#### Level 1：结果原子

停止该 SKU，若：

- 前 10–30 个自然任务样本中找不到可重复、可范围化、可验收且责任可限定的 Buyer Job；
- 真实独立买家相对免费通用模型、可信表单 + 人工或成熟服务平台不愿付费，或结果没有明确采用；
- Combo 在付款、采用、返工、人工分钟或全成本上没有预注册增益；
- seller / MoR、资金、退款和结果责任在首笔付款前无法合法明确。

#### Level 2：复制履约

停止 Creator OS / 软件规模化叙事，若：

- 3 位独立供给者仍需分别重写流程、核心代码或由创始人陪跑；
- 累计 30–50 笔未补贴真实订单后，创始人 / 人工分钟仍随订单近似线性增长；
- 连续两个真实 cohort 的单单贡献不能为正，或创作者扣除全部人工与机会成本后没有净增量；
- 首单后买卖双方普遍回微信，Context、保障、补救与自动续购不足以抵消站内摩擦。

#### Level 3：system of record 与数据学习

停止 outcome graph / 垂直 OS 叙事，若：

- 订单、客户、版本、Verdict 与补救不在自然周期留在 Combo；
- 约 100 笔真实订单后，冻结基线对照下的 exception、refund、rework、adoption 或 human minutes 没有改善；
- 机器 Verdict 与 blind expert 的可解释一致性不改善，只持续制造人工队列；
- 需求仍全部依赖原创作者再次发链接，没有未召回的自然再次触发。

#### Level 4：平台增益

将公司重新分类为 Workflow SaaS、Creator OS 或垂直结果公司，并停止平台叙事，若：

- 没有平台新增需求、陌生供给购买或因果路由 uplift；
- 没有独立第三方围绕同一对象持续经营；
- 一个真实渠道不能交回合法主体、订单、退款、结算与责任事件；
- 第二渠道必须重建整套履约，而不是复用同一责任账本；
- 外部 Agent 没有在无补贴下重复发起真实采购。

另有三条不可用商业指标绕过的实施红线：

- Runtime HTML 未 fail closed，或最小服务端 Publication、pilot access 与 Run traceability 未过 Gate，不得开始可信宿主的陌生买家 pilot；
- 完整交互 Surface 的 typed action、entitlement、宿主确认、撤销与审计未过 Gate，不得让陌生消费者加载或执行创作者 / 模型生成代码；
- seller / MoR 与资金责任未明确，不得收款；绕过上述安全或资金红线得到的订单不得计作平台证据。

### 24.9 唯一 90 天执行主线

| 时间 | 唯一决策 | 必须记录 | 通过后才做 | 本阶段禁止 |
|---|---|---|---|---|
| Day 0–10 | 选择一个市场、一个垂类、一个 SKU、一个 seller / MoR | 10–30 个自然任务的触发、期限、现有替代、历史支出、采用证据与再次发生周期 | 进入真实结果实验 | 第二垂类、第二渠道、Marketplace、Enterprise GTM |
| Day 0–15 | 让实验可安全发生 | Runtime HTML fail closed、可信宿主、服务端 Publication、可追溯且人工可补救的最小 Run；资金与责任边界 | 陌生买家 pilot | 任意可执行 HTML、开放目录、自动分账 |

| 真实信号 | 公司形态 |

### 24.10 证据分级与最终公式

**Verified Fact**

- 当前没有安全消费者 Publication、真实订单 / 资金 / 退款 / 结算、稳定 cohort 与全成本单位经济；
- 当前代码主要占据 Builder / Runtime / Listing，外部横向平台与服务市场正在覆盖其相邻原语；
- 中国渠道对身份、审核、支付、订单、售后与数据回读有各自 Gate。

**Strong Inference**

- 横向创建层不值得继续正面投入；
- 若有独立空间，只可能先在一个垂类形成 `Contract × Run × Verdict × Remedy × Economics` system of record；
- 可信宿主足以先验证结果价值；完整 Surface 只有在 uplift 成立后才值得建设。

**Hypothesis**

- 某个中间 SKU 同时具备自然重复、明确验收、相对通用模型的质量溢价、可控责任和正贡献；
- 机器 Verdict、专家 rubric 与异常判例能降低返工与人工；
- 买家、供给者和渠道会因为 Context、保障与补救持续留在 Combo。

**Founder Choice**

- 首个市场、垂类、Buyer Job、SKU、价格与自然周期；
- Workflow 还是 Commerce；
- seller / MoR、收费对象、责任与赔付边界；
- 专家品牌还是 Combo 品牌；
- 所有尚无真实基线的通过阈值。

最终公式：

```text
平台不是一张 Roadmap

平台资格
= 一个垂类结果原子成立
× 无创始人复制
× 全成本正贡献
× 结果数据因果改善
× 独立第三方依赖
× 跨参与者因果增益
```

其中任一项为零，都不能用更多页面、Agent、连接器、渠道或 GMV 补成平台。

## 26. 迭代日志

### 2026-07-31 · v1.0 · Four-round review — Round 4 / Final synthesis

**本轮问题：**

1. 前三轮证据共同授权 Combo 成为什么公司，又不授权它叫什么？
2. 从当前产品到平台有哪些不可跳过的必要条件和顺序？
3. 最强平台论与“责任层可能是负选择区”的最强反论，哪一部分分别成立？
4. 为什么是 Combo、为什么是现在、为什么不会被模型或大厂吞掉，能否诚实回答？
5. 未来 90 天应当用什么可证伪动作决定公司形态，而不是继续补平台功能？

**独立蓝方：**

- Combo 现有 Capability、Version、Studio、Run、Artifact、Revision 与 Test 是向垂类结果责任后台迁移的技术脊柱；
- 如果 Combo 在一个垂类连续拥有 `Contract → Context / Authorization → Run → Evidence → Verdict → Remedy → Economics`，并让多位独立供给者和入口因同一责任账本获得净增益，平台结构可能成立；
- 强入口没有必然吞掉 merchant lifecycle，横向底座商品化也让团队能够把资源集中到垂类 Context、验收、异常和责任。

**独立红方：**

- 当前没有现金、采用、复购、全成本、供给复制、学习曲线或第三方依赖，技术连续性不能替代需求连续性；
- 责任层可能是低毛利、高人工、高赔付的负选择区：不担责会退化为工具，担责又可能退化为线性服务；
- Builder、支付、Result Contract、HITL、Webhook 与更多字段均可被大厂或既有市场吸收，不能单独构成壁垒。

**裁判：**

- `Verified Fact`：当前仍是未闭环的 Builder / Runtime / Listing 邻接组合，不是 OS 或平台；
- `Strong Inference`：唯一值得继续的条件式空间，是先验证一个垂类结果履约产品，再争取成为 system of record；
- `Hypothesis`：Result SKU、Verdict、异常判例和三方责任经济能形成学习曲线与第三方依赖；
- `Founder Choice`：首个市场、SKU、自然周期、seller / MoR、责任边界、品牌与所有无基线阈值。

**最终变化：**

- 当前事实身份统一为未闭环的 `Capability / Miniapp authoring + Runtime / Listing` 邻接组合；下一阶段唯一允许验证的公司假设收窄为“单一垂类、单一 Result SKU 的 AI-native 结果履约产品”；
- 解决了“先完整发布 Miniapp”与“先验证结果”的冲突：Runtime HTML 立即 fail closed，首批实验用可信宿主和最小服务端 Publication；完整 Surface 只在因果 uplift 成立后建设；
- 演化顺序收敛为“结果原子 → 无创始人复制 → 垂直 system of record → 正贡献与学习 → 第三方依赖与跨参与者增益 → 平台”；
- Kill criteria 收敛为结果原子、复制履约、system of record、平台增益四级；
- 90 天只允许一个市场、一个垂类、一个 SKU、一条资金链与一条主要分支；开放 Marketplace、多渠道、Enterprise 与 Agent 协议全部冻结；
- 明确“为什么是 Combo”目前只是实验执行连续性，“为什么是现在”只是短验证窗口，“为什么不会被吞掉”尚无成立答案。

**仍缺的决定性证据：**

- 自然 Buyer Job、独立买家现金与明确采用；
- 自然再次触发与防脱媒；
- 完整全成本和买家 / 供给者 / Combo 三方净增量；
- 机器 Verdict 盲测与约 100 单后的学习曲线；
- 3–5 位供给者无创始人复制；
- 一个渠道的完整责任事件与第二入口的真实复用成本。

### 2026-07-31 · v0.9 · Four-round review — Round 3 / Competition and industry truth

**本轮问题：**

1. 模型平台、AI coding / site builder、Agent 平台已经吸收了 Combo 当前价值链的哪些层？
2. 创作者 OS、commerce backend 与服务 Marketplace 是否已经拥有 Result Contract、HITL、验收、退款和履约？

4. 在四周合围之后，什么空间仍未被官方事实证明已由单一公司完整占据；它是机会，还是低毛利责任区？

**新增代码事实：**

- `db/migrations/0005_publish_tables.sql` 中的 `marketplace_listings` 只包含 Capability / Version、slug、card、status 和搜索投影；`apps/runtime/src/modules/capability/list.ts` 返回的也只是名称、tagline、类型和 byline。它是已发布 Capability 的内部目录投影，不是买卖双方、订单、付款、匹配或履约市场；
- `capability_tiers.price_micros` 只是发布价格字段；`apps/web/src/pages/revenue/RevenuePage.tsx` 明确注明本期没有独立收益 / 结算端点，金额均为占位，提现为“本期未开放”；
- `packages/shared/src/domains/structure.ts` 的 `skill_set` 是字符串数组；`packages/shared/src/domains/runtime-api.ts` 记录 Session、Run、Message、Artifact、Revision 和 Test，没有渠道 Connector、Order、Refund、Settlement、seller / MoR 或服务责任契约；
- 因此 Combo 当前主要位于最容易被横向平台吸收的 Builder / Runtime / Listing 层，尚未占据渠道、业务状态、服务供给或责任结算控制面。

**新增产业事实：**

- OpenAI、Anthropic、Google、Microsoft / GitHub、腾讯及 Replit / Lovable / Vercel 已在不同 GA / Preview 状态下覆盖 Builder、Runtime、hosting、auth、sandbox、memory、MCP / connector、identity、registry、evaluation、observability、目录、企业治理或 checkout；OpenAI 的旧 Agent Builder / Evals 又已宣布退场时间，说明依赖上游产品层同时存在吸收与退场风险；
- Wix Headless 已公开定位为 AI-built sites / apps 的 business backend；Shopify 把 catalog、order、payment、fraud、tax、fulfillment 留在 Admin；Kajabi 的 Expert Agents 虽仍为 announced / rolling / coming soon，但“专家内容 grounding + AI 客服 + Universal Inbox human takeover”已不是独特叙事；
- Gumroad Commission 已有 instructions / files、deposit、deliverable、completion 和 payout；Upwork 已有 milestone、escrow、accept / changes、refund / dispute；Fiverr 已有 delivery / revision / partial refund，并用 creator-trained model + seller edit / handoff 组织 AI-first 服务。Result Contract 字段和 human exception 本身不是空白；
- OpenAI 的 commerce 路径提供了反例：Merchant 一直保有 MoR 与履约责任，2026 年又因初版 Instant Checkout 灵活性不足转向 Merchant checkout；Google UCP 同样明确 retailer 保有 MoR。强入口不必吞掉专业后台，但后台必须已经拥有真实业务状态；
- 腾讯元器已把公众号知识 Agent、微信渠道发布和支付 MCP 放在一起；当前 MCP 可创建订单和查单，但仍为公测 / 白名单，公开文档未证明通用服务的退款、分账、创作者 payout、明确验收与跨渠道责任账本；
- 微信、小红书、抖音都分别控制主体、类目、审核、域名 / 挂载、身份、支付、订单、退款 / 售后和结算。小红书交易文档存在直连 / 担保能力版本差异，必须以目标授权小程序实际 `trade_ability` 为准；其结算 API 的服务费计算不代表真实资金流。抖音担保交易的原生状态最完整，也最可能把 Combo 压成 ISV。

**蓝方：**

- OpenAI / Google 明确把 merchant relationship、MoR 和履约责任留给专业后台，说明 intelligence、Builder 和入口平台化后，业务 system of record 仍可能独立；
- 中国渠道允许合法开发者 / 获授权服务商保留自己的用户映射和订单后台，但各渠道记录隔离，官方文档未证明任何一个入口拥有跨渠道 `contract × authorization × run × evidence × verdict × remedy` 统一账本；
- 通用 Builder 与支付接线越商品化，Combo 越可以少造底座，把有限资源放在一个高价值垂类的任务本体、机器 / 人验收、异常处置和结果信誉；
- 若同一 Result SKU 在多个供给者、模型与入口间复用，并且 accepted-outcome / repair 数据持续降低异常和人工成本，Combo 可能成为可嵌入的垂直责任后台。

**红方：**

- 横向技术原语几乎都已有更强供给；腾讯元器直接吸收“公众号知识 → 博主分身 → 微信付费门”，Wix / Shopify / Kajabi 控制经营状态，Gumroad / Upwork / Fiverr 控制服务合同、供给和争议；
- Fiverr 的当前经营披露表明 AI 正在吸收 simple / high-volume work；“低价高频结果”不是默认甜蜜点，可能正是最先被免费模型压缩的区域；
- Result Contract、buyer instructions、milestone、验收、revision、partial refund、human edit / handoff 均可被既有平台快速补齐，字段和流程图不能形成 moat；
- 渠道并非中性流量：主体、保证金、平台费、账期、支付、退款、数据与服务商授权会压低毛利并增加固定运营；统一 webhook 不构成防御；
- 若 Combo 不承担 MoR、履约、退款、客服和争议，就只是可替换工具；若承担，KYC、资金、人工、赔付和责任成本会陡增。所谓“空白”可能是坏经济而不是创业机会。

**裁判：**

| 类型 | 本轮裁决 |
|---|---|
| `Verified Fact` | Combo 当前只有内部 listing、价格字段和 Runtime / Artifact 记录，没有渠道、订单、退款或结算闭环；外部平台已覆盖绝大多数横向技术层和多个服务履约原语；中国渠道有独立主体、审核、支付、事件和服务商 Gate |
| `Strong Inference` | 通用 Agent Builder、Runtime HTML、连接器、hosting、checkout 以及 Result Contract 字段都不能独立构成平台壁垒；机会若存在，将向垂类任务本体、可验证 Verdict、异常判例、责任经济与供需信誉迁移 |
| `Hypothesis` | Creator rubric + machine Verdict + human exception 能显著提高明确采用、降低返工 / support，并让跨供给、跨模型的失败—修复数据形成复利 |
| `Founder Choice` | 首个高价值垂类、seller / MoR、验收和赔付边界、人工兜底深度、首个渠道、服务商身份、消费者品牌 vs 隐身后台，以及何时才开放平台 |

**本轮推翻：**

1. “大平台目前只会聊天 / 写代码，通用 Agent Builder 仍是创业空白”；
2. “Runtime HTML、连接器、hosting、auth 或支付接入可以成为 Combo moat”；
3. “补齐 Result Contract 与 human exception 就进入无人占据的责任层”；
4. “博主知识 Agent + 微信付费门仍是独占巧思”；
5. “中国内容平台只是可以租用的流量前台，发布一次即可到处运行”；
6. “嵌入式基础设施是当前第二自然平台期权”——现下只能是 `Partner-conditioned option`；
7. “低价高频服务天然适合 AI 平台化”。

**本轮保留：**

1. 通用 Agent App 平台仍不应作为公司主线；
2. 前台可以多元，专业业务后台仍可能独立，但 Combo 必须先成为一个垂类的真实 system of record；
3. `Result Product` 仍是实验原子，但壁垒不在字段，而在垂类任务本体、Verdict 准确度、异常学习和责任经济；
4. 跨模型、跨渠道可迁移性仍有价值，但当前代码没有实现，且每个渠道必须单独过 Gate；
5. 垂直 Workflow / Fulfillment OS 或垂直结果公司应先于中立平台；只有跨供给、跨入口的第三方依赖出现后才发生平台跃迁。

**主报告变化：**

- 新增五个产业控制面、当前代码位置、强入口保留专业后台的反例与路径改写；
- 扩充模型 / coding 平台、专家 OS、服务市场与中国渠道的官方竞争事实，并严格区分 GA、Preview、Coming Soon 与未证明能力；
- 将路线 H 降级为 `Partner-conditioned option`，明确“发布一次、到处运行”为假；
- 加入同 SKU 的 Builder / Commerce / Service Marketplace 对照、机器 Verdict 对照、真实渠道事件和 outcome learning curve 等 90 天证伪 Gate；
- 更新红蓝总论、停止条件、结论审计与未决问题。

**遗留证据缺口：**

- 各 Agent / Plugin / Channel 目录的真实 referral、付费、留存与商户条款；
- 首个 SKU 在微信、小红书、抖音的类目开放、服务商资格、保证金、费率、账期、退款权和数据导出权；
- 创作者是否愿意交出 MoR、客服与客户关系，以及可接受的 take rate；
- 机器 Verdict vs blind expert 的一致率、exception rate 和 cohort 学习曲线；
- QA、退款、争议、人工兜底与资金成本后的真实单位经济；
- Result Contract / task ontology 能否跨创作者、模型和渠道复用；
- 责任层无人完整占据究竟因为尚待整合，还是因为低毛利、高责任。

### 2026-07-31 · v0.8 · Four-round review — Round 2 / User and economic truth

**本轮问题：**

1. 当前 AI 用户实际在消费什么，广义使用如何转化成 Combo 的购买需求？
2. 谁是 Combo 当前真实用户，现有一手研究究竟支持 Workflow OS 还是 Result Commerce？
3. 买家、创作者、渠道与 Combo 的频率、留存和单位经济如何分别核算？
4. 什么事实会推翻 `Result Product → Creator Result OS → Platform` 的线性叙事？

**新增事实：**

- 当前审计真源没有可稳定回读的 Combo 现金订单、退款、复购、创作者到账、Creator CAC 或每单各方人工分钟；现有单位经济和垂类验证表仍是 `[待填]` 的计划，不是执行数据；
- Vault 中真正的一手用户研究是四个专业漫剧 / 视觉制作团队；它们支持工作流碎片化、资产管理、抽样、协作和人工审美控制问题，没有证明方法授权、粉丝侧低客单购买、持续推广或 take-rate 接受；
- CNNIC、OpenAI、Pew、PNC 与 Anthropic 的当前数据共同表明：AI 已大众化，主流消费仍集中于问答、指导、信息、写作和 Artifact；工作用户更偏 `Doing`，Surface 会影响委托深度，但真实家庭自费远低于广义使用。它们不能替 Combo 证明付费结果需求；
- 主报告的创作者直收 pilot 与现有 `GMV - Creator Payout` 公式属于两种资金链；前者没有 Combo 实际收费时，只验证买家需求和履约，不验证 Combo monetization；
- 录音中的 `¥3 / ¥9.9 / ¥19.9` 与 15% 抽成假设，在不计任何成本时每单收入上限仅为 ¥0.45 / ¥1.485 / ¥2.985；高触达共创、低价格和低 take 不能同时作为默认；
- 当前把“退款窗结束且未全额退款”定义为 `Accepted` 会把沉默流失误报为采用，必须拆开明确采用、修改、拒绝、退款和复购。

**蓝方：**

- 自然语言问答和 Artifact 生产已形成大众习惯，Combo 不必重新教育“可以向 AI 表达需求”；
- 同一模型在不同 Surface 上形成不同委托深度，说明 intake、Context、结果契约、工具编排、证据和补救可能构成模型之外的产品增量；
- 四份实际访谈支持专业创作者 Workflow OS 的问题存在；Result Contract + AI 第一层 + 人类例外也符合真实创作流程中的 HITL；
- KOL 私域可把首轮试验缩小为“一位创作者 × 一个 SKU × 一类受众”，减少同时解决公开双边市场的变量。

**红方：**

- `AI 使用 → 高频聊天 → 愿意购买 KOL Agent → 接受结果 → 自然复购` 包含多次未经证明的因果跳跃；
- 专业创作者需要内部效率工具，不等于其粉丝会购买创作者 AI 结果；当前桥接证据为零；
- 创作者自带需求也拥有客户关系，Combo 没有独立需求时，首单后回微信是结构性风险；
- 低风险高频任务容易被免费通用模型吸收，高赌注任务更愿付费却需要验证、真人和责任；当前没有找到同时满足重复、差异、可验收、低人工和可复购的“中间 SKU”；
- 创作者直收、无 Combo fee 的 pilot 不能验证 take rate；`no refund` 不能验证采用；没有完整 Run ledger 就无法验证毛利；
- `Professional Workflow OS`、`Creator Result Commerce OS`、`Marketplace` 和 `Vertical Result Company` 是不同需求与经济引擎，不会因为功能增加自然连续。

**裁判：**

| 类型 | 本轮裁决 |
|---|---|
| `Verified Fact` | 当前材料没有 Combo 稳定现金订单与成熟 cohort；四份实际访谈只直接支持专业工作流问题；两种资金链不能共用一套收入公式 |
| `Strong Inference` | 结构化任务 Surface 与 Professional Workflow OS 可能有独立价值；KOL 私域是合理实验 wedge，但不是平台渠道或护城河；`no refund` 不能当采用 |
| `Hypothesis` | 创作者品牌 + Result Contract + Context + QA / 补救能让独立买家相对免费模型愿意自付、采用、自然复购，并让双方获得正增量贡献 |
| `Founder Choice` | 首个市场、Buyer Job、SKU、自然复购窗口、seller / MoR、收费对象、最低质量与贡献阈值，以及优先做 OS 还是垂直结果公司 |

**本轮推翻：**

1. “专业创作者存在工作流痛点，所以粉丝侧 Creator Result OS 是当前最高概率主干”；
2. “AI 用户规模或聊天频率可以作为 Combo 的市场需求证据”；
3. “创作者直收的 pilot 可以直接验证 Combo 的 15% 抽成经济”；
4. “未退款可以作为 Accepted / 结果采用”；
5. “一个统一的留存指标可以同时代表买家、创作者和平台关系”。

**本轮保留：**

1. `Result Product` 仍是值得验证的交易原子，但必须从自然 Buyer Job 而非 AI 用户画像出发；
2. `Professional Workflow OS` 有一手问题证据，可以作为独立 B2B 分支；
3. `Creator Result Commerce OS` 可保留为第一个可证伪平台上行假设，但不再称为已证实最高概率；
4. KOL 私域仍可用于缩小首轮实验变量，但 creator deep link GMV 不得冒充平台需求；
5. 真正的平台 Gate 仍是独立第三方依赖、平台新增需求、跨供给增益、完整责任事件与正贡献。

**遗留证据缺口：**

- 连续自然 Buyer Job 样本、现有替代、真实愿付与自然再次触发周期；
- 独立买家从触达到现金、采用、退款和复购的完整 cohort；
- Workflow OS 与 Result Commerce 两个市场的独立付费、留存和 CAC；
- seller / MoR、实际 Combo cash receipt、双方全成本、Creator 净增量利润；
- 通用模型 vs Combo 的盲测采用增益、可信宿主 UI vs Miniapp 的因果 uplift；
- 第二次自然发布、站内 / 站外复购、多归属、脱媒与平台自产需求。

### 2026-07-31 · v0.7 · Four-round review — Round 1 / Product and code truth

**蓝方：**

- 未提交 worktree 已形成一条更短的供给冷启动链：公开主页 / 创作者粘贴 → 方向生成 → Context 校准 → 创作者认可 → Capability / Version → Studio；
- crawler 已考虑私网、DNS rebinding、redirect、响应体和登录墙等边界，owner、幂等和限流也有本地实现；
- 正式旧 publish transaction 已能冻结 Capability Manifest、tier、visibility 与 listing；Runtime 显式 Run、SSE event 和 Artifact 版本记录也提供了继续演化的技术骨架；
- 76 个相关单元 / 前端测试通过：authoring 49、web 18、runtime-web 9。

**红方：**

- 57 个 modified 和 127 个 untracked 文件都未证明已部署；KOL 与 publishing 新链尤其不属于当前 HEAD；
- KOL “真实试跑”只是 authoring 直接 LLM 示例，甚至可能返回未标记 fallback；它不运行最终 Capability / Runtime / tool 配置；
- 定价、命名、确认和预览只写浏览器存储，预览结果由前端拼接；测试通过恰好证明这是无 fetch 的 prototype，而非正式发布；
- Studio HTML 不进入 Capability Manifest 或 Publication。消费者打开公开 Capability 后创建新 consume session，再由 Agent 生成 Artifact；当前发布的是 Agent 契约，不是已设计 Miniapp；
- 普通 Runtime HTML 仍默认执行脚本、表单和 popup，无交互 CSP；`runGrant` 未消费、匿名 cookie 未签名、无消费者预算 / 并发 / 速率硬闸，旧 `/runtime/agui` 还能绕过显式 Run 账本；
- 当前 Agent 只有内部 Artifact tool；input 最终压成 Prompt，尚无 Connector、secret broker、typed action 与外部行动授权；
- API 进程内 Run + 2 replicas + 内存 AbortController 不构成可靠分布式履约。

**裁判：**

> 新代码改善的是供给发现、创作者校准和发布流程表达，不是消费者发布、付款、履约或平台控制权。当前最准确的定义是 `Capability-conditioned Artifact Agent + Runtime Studio + supply onboarding / publishing UX prototypes`。

本轮推翻三项说法：

1. “KOL 用户已完成真实 Agent 试跑” → 降为 `authoring_llm_sample`；
2. “定价和体验发布已形成发布闭环” → 降为 `prototype_preview`；
3. “专家 OS 是商业概率最高的必经层” → 降为与当前代码连续性较高、但需求 / 频率 / 毛利待证的首个主干假设。

本轮保留三项判断：

1. Runtime HTML 静态 fail-closed 是立即 P0；
2. 如果任务型 Miniapp 相对可信宿主 UI 确有可测增益，精确 Surface binding 与消费者安全才值得继续投资；
3. 真正的平台 Gate 仍是独立第三方依赖、跨参与者增益和不可绕开的经营 / 责任事件，而不是 Agent、页面或测试数量。
