MPAI · Message Relationship Model

每条消息到底和谁有关系？

把“多人 Agent 通信”拆开看，MPAI 实际管理的是：谁把哪条输入，送进哪一个 Host 已有的原生 Agent session，并如何把这一轮的流事件、完成状态与审计记录串起来。

!
MPAI 不是 Agent ↔ Agent；它是 Human → Host-owned Agent Session。

多人可以进入同一会话，也可以切换不同会话；但 Codex session 和 Claude session 之间没有消息转发关系。

没有跨 Agent message bus / reply graph

Lifecycle

一条消息怎样被串成“一轮”

关键不是为每条聊天消息建 replyTo，而是用不同层级的 ID 把远程提交、provider turn 和内部事件对齐。

Data Model

关系不是一张 chat graph，而是一串嵌套 ID

最实用的理解方式：task 决定“在哪条会话”，request 决定“哪次远程提交”，turn 决定“provider 的哪轮执行”，item 决定“Codex 轮内的哪个动作”。

taskId → requestId → turnId → itemId / event stream
requestId / turnId  ↛  transcript message.id（MPAI 没有保存可精确 join 的外键）
taskId归属哪一个 native session
requestId远程提交、幂等与 audit 关联
turnIdprovider 本轮执行
itemIdCodex 轮内 command / diff 等动作
message.idtranscript 刷新去重，不表达 reply 关系

Actor

name 进入 prompt 文本前缀和 audit。它告诉人“谁发起”，但不是每个 tool call 的强 provenance。

Remote Request

requestId 是 MPAI 层的幂等键，把 received / completed / failed 与这次提交对应起来。

Provider Turn

turnId 来自 Codex；Claude 的规范化结果以 sessionId/nativeId 充当完成关联锚点。

Native Transcript

可见消息最终被压平成 {id, role, author, text, at} 数组，由原生 session 持久化；没有 parent / reply，也没有 requestId 外键。

MPAI audit.jsonl

保存 prompt.received / completed / failed；received 事件包含 prompt 原文。它是审计，不是第二份完整 transcript。

Ephemeral State

presence 和 active remote prompt lock 在内存中；服务重启后不构成消息历史。

源码中没有的关系

没有 replyToId、parentMessageId、跨 Agent route、共享 message bus、全局 causal graph、CRDT 或公共长期 memory。UI 展示的是每个 task 的线性可见 transcript。

Persistence

哪一份是事实源？

对话内容以 provider native transcript 为主；MPAI 每 2 秒读取并投影可见消息。

Attribution

作者怎么显示？

匹配 [Multiplayer teammate: NAME] 就显示 NAME；没有前缀的人类输入回退为 Host。

Concurrency

会不会交错？

远程锁不覆盖 Host 原生 UI，且设置锁前存在 await 窗口；所以它不是严格的全局串行系统。

一句话防误解：一个 task 对应一个 Codex 或 Claude session；不同 session 彼此独立，MPAI 当前没有实现 Agent A 与 Agent B 的消息路由。
